# پلن 29.1.0 — انتقال ComponentInputAcl به ساختار جدید

> **وضعیت:** پیاده‌سازی‌شده؛ قرارداد درخواست سرور نیازمند تأیید مصرف‌کننده  
> **نسخه پلن:** 29.1.0  
> **منبع Legacy:** last/Older/ComponentInputAcl.js  
> **راهنما:** documents/guides/component-create.md  
> **مقصد:** src/framework/module_ui/module_components/lists/componentInputAcl/  
> **API هدف:** UiCategory.UI.Inputs.InputAcl(config, methods, identity)؛ نام نهایی پس از بررسی قراردادهای نام‌گذاری و نبود تداخل ثبت شود.

## 1. هدف و محدوده

انتقال انتخاب‌گر دسترسی از ComponentBase و render رشته‌ای Legacy به ساختار ComponentManager، با حفظ انتخاب چندگانه، جست‌وجوی صفحه‌بندی‌شده، انتخاب موقت، تأیید/لغو، پاک‌کردن مقدار، نمایش خلاصه و تنظیمات نمایشی.

ComponentInputAcl یک input ساده نیست: پنل انتخاب آن داده را از prop_requestUrl می‌گیرد و انتخاب‌های موقت را تا زمان Accept از مقدار تأییدشده جدا نگه می‌دارد. پیاده‌سازی باید state را در Observableها نگه دارد و برای ردیف‌ها، آیکون‌ها و دکمه‌ها از اجزای جدید استفاده کند؛ تولید HTML با innerHTML و اتصال رویداد inline از Legacy منتقل نشود.

پیش از پیاده‌سازی، مصرف‌کنندگان و قرارداد endpoint با rg بررسی شوند. در حال حاضر شواهد قطعی سرور یا نمونهٔ response خارج از همین فایل Legacy یافت نشده است؛ تغییر قرارداد شبکه یا فرض دربارهٔ شناسه‌ها خارج از این پلن است.

## تطابق معماری Legacy با ساختار فعلی

این فایل از نسل قدیمی‌تر Componentهای Legacy است؛ بنابراین کار فقط تبدیل JavaScript به TypeScript یا جایگزینی چند tag نیست. مدل ثبت Component، تعریف prop/schema، رندر، مدیریت رویداد و state باید به قرارداد فعلی ComponentManager منتقل شود. تطبیق زیر، مرجع تصمیم پیاده‌سازی است:

| الگوی Legacy در ComponentInputAcl | معادل ساختار فعلی | قاعدهٔ انتقال |
|---|---|---|
| ComponentInputAclBase extends ComponentBase و کلاس window.ComponentInputAcl | فایل‌های ComponentInputAclBase.ts و ComponentInputAcl.ts در پوشهٔ componentInputAcl؛ کلاس نهایی extends Base و constructor با config, methods, identity | از CoreComponents.App و createInputAclStep استفاده شود؛ component به window یا global ثبت نشود. |

ComponentElementPosition فقط برای positioning منفرد است و جای منوی باز/بسته‌شونده نیست. |
| درخواست از tools_submit.fetcth و دسترسی به DOM برای Loading | سرویس درخواست فعلی پروژه و loading state / ComponentLoading در صورت تطبیق قرارداد | قبل از انتخاب transport، abstraction شبکهٔ فعال را پیدا کنید؛ هیچ endpoint یا فرمت پاسخ جدیدی حدس زده نشود. |
| CSS داخل template، مقادیر اندازه از tools_css و directionRtl محلی | style/styleBind، UtilStyle و CoreConfig.Settings.SizeName/DirectionRtl | استایل‌های قابل سفارشی‌سازی حفظ شوند؛ اندازه‌های عمومی از config سیستم و util بیایند. |
| prop_langs fa/en و prop_langSelected مشتق از RTL | ترجمهٔ CoreLanguage و Keys | متن Accept/Cancel از زبان سیستم بیاید؛ نگه‌داشتن props قدیمی فقط در صورت اثبات وابستگی مصرف‌کننده انجام شود. |
| ورودی مخفی JSON که در DOM تولید می‌شود | prop_name/prop_value reactive و در صورت نیاز فرم، hidden input reactive داخل schema | ابتدا مصرف فرم HTML بررسی شود؛ اگر لازم است، همان serialization آرایه حفظ شود، اما state از input مخفی خوانده نشود. |
| کلاس و فایل registration قدیمی listComponent | Definition/Step/index جدید، ثبت ComponentManager و Category | مطابق guide، public API از Category callable ساخته شود و Category به Component وابسته شود، نه برعکس. |

الگوی ساخت و lifecycle از ComponentInput و الگوی منوی شناور از ComponentInputListSelector گرفته شود. ACL نباید با ComponentInputListSelector شبیه‌سازی کامل شود: آن component برای انتخاب/مرتب‌سازی ستون‌های محلی طراحی شده، در حالی که ACL نتایج remote و paging دارد. فقط primitives مشترک آن، به‌ویژه ComponentPositionMenu و ComponentListSelectedScroller، پس از بررسی API reuse شوند.

## 2. رفتار Legacy مشاهده‌شده

### مقدار و انتخاب

- prop_value مقدار پیش‌فرض [] دارد و دادهٔ انتخاب‌شده به‌شکل آرایه‌ای از {id, name} نمایش داده می‌شود.
- Header نام‌های انتخاب‌شده را با جداکنندهٔ , نمایش می‌دهد.
- Legacy یک input مخفی با prop_name و JSON مقدار می‌سازد؛ حفظ سازگاری ارسال فرم باید بررسی و در صورت استفاده نگه‌داری شود.
- انتخاب/حذف ردیف‌ها ابتدا فقط فهرست موقت را تغییر می‌دهد. Accept آن را به prop_value منتقل می‌کند؛ Cancel باید انتخاب موقت را کنار بگذارد و مقدار پذیرفته‌شده را دست‌نخورده بگذارد.
- Clear مقدار پذیرفته‌شده را خالی می‌کند.
- Select All روی موارد دریافت‌شدهٔ فعلی اعمال می‌شود؛ Clear All موارد انتخاب‌شدهٔ موقت را به فهرست انتخاب‌نشده برمی‌گرداند.

### درخواست شبکه و جست‌وجو

- با بازشدن پنل، state صفحه و فهرست دریافت‌شده از نو آغاز و درخواست ارسال می‌شود.
- prop_requestUrl همراه JSON شامل count, search, page به helper قدیمی tools_submit.fetcth داده می‌شود.
- prop_requestCount پیش‌فرض 100 است؛ درخواست بعدی هنگام نزدیک‌شدن scroll فهرست به انتها (حدود 50px) ارسال می‌شود.
- response به‌صورت آرایه‌ای از آیتم‌های دارای id و name مصرف می‌شود. ساختار response در سرور از شواهد repository تأیید نشده است.
- جست‌وجو بعد از timeout با مقدار پیش‌فرض prop_requestTimout: 400، فهرست و صفحه را تازه‌سازی می‌کند.
- وضعیت‌های loading، پایان صفحات، صفحهٔ جاری، عبارت جست‌وجو و قفل درخواست در فیلدهای داخلی Legacy نگه‌داری می‌شوند.

### نمایش و پیکربندی

- پنل انتخاب با باز/بسته‌شدن از Header و آیکون اصلی کنترل می‌شود؛ Clear آیکون جدا دارد و در حالت disabled نمایش داده نمی‌شود.
- پنل Legacy ارتفاع prop_bodyHeight (پیش‌فرض تعریف‌شده 300px؛ در برخی fallbackهای render مقدار 200px) و offset بالایی prop_bodyTop دارد.
- چیدمان پنل شامل Search، دو فهرست انتخاب‌نشده/انتخاب‌شده، کنترل Select All و Clear All و دکمه‌های Cancel و Accept است.
- جهت آیکون انتقال ردیف بر اساس RTL/LTR عوض می‌شود.
- props رنگ جداگانه برای ردیف‌های انتخاب‌نشده/انتخاب‌شده و hover، رنگ/پس‌زمینهٔ header و footer، رنگ border دو فهرست و رنگ آیکون/دکمه وجود دارند.
- زبان دکمه‌ها از prop_langs با کلیدهای fa/en و prop_langSelected انتخاب می‌شود. پیش‌فرض زبان از directionRtl گرفته شده است.
- var_itemsSelected در الگوی props اعلام شده ولی در پیاده‌سازی مشاهده‌شده برای state استفاده نمی‌شود؛ state جدید باید خصوصی و reactive باشد، مگر مصرف‌کننده‌ای برای این متغیر پیدا شود.

## 3. Props و قرارداد مهاجرت

Props زیر از Legacy استخراج شده‌اند. نام‌های عمومی را بدون شواهد مصرف‌کننده تغییر ندهید؛ prop_size مانند اجزای جدید دیگر منتقل نشود و ابعاد استاندارد از CoreConfig.Settings.SizeName بیایند.

| Prop | تصمیم پلن |
|---|---|
| prop_name, prop_value, prop_title, prop_isDisable | حفظ شوند؛ prop_value آرایهٔ {id, name} باشد و Observable را پشتیبانی کند. عنوان باید با ComponentLabelTrait/عنوان Header به‌شکل مستند و بدون ادغام فرضی نگاشت شود. |
| prop_labelTitle, prop_labelTooltipDescription, prop_labelShow و سایر props رسمی LabelTrait | برای ComponentLabelTrait از props استاندارد trait استفاده شوند. prop_title قدیمی جدا بماند و فقط برای عنوان validation/header طبق شواهد مصرف‌کننده به کار رود. |
| prop_hasRules, prop_isAbsoluteRule, prop_listRules, prop_msgRules | props استاندارد validation با defaultهای سازگار با ComponentInput اضافه شوند؛ مقدار validator باید از prop_value تأییدشده خوانده شود و در نبود rule، ComponentValidate نمایش داده نشود. |
| prop_inputClass, prop_inputStyles, prop_colorIcon | استایل Header/آیکون ورودی را حفظ کنند؛ به APIهای معادل جدید نگاشت شوند. |
| prop_bodyHeight, prop_bodyTop | ارتفاع و offset پنل را حفظ کنند؛ fallbackهای متناقض 300/200/5/0 در implementation با شواهد مصرف‌کننده تعیین و یکسان شوند. مقدار حدس زده نشود. |
| prop_backgroundColorHeaderList, prop_backgroundColorBodyHeader, prop_backgroundColorBodyFoter, prop_borderColorSelector, prop_btnColor | استایل‌های مربوط حفظ شوند؛ املای Legacy (Foter) برای سازگاری API تغییر نکند مگر alias مستند اضافه شود. |
| prop_itemAclColorUnSelected, prop_itemAclIconColorUnSelected, prop_itemAclBorderColorUnSelected, prop_itemAclBackgroundColorUnSelected, prop_itemAclColorUnSelectedHover, prop_itemAclBackgroundColorUnSelectedHover | ظاهر و hover موارد قابل انتخاب را حفظ کنند. |
| prop_itemAclColorSelected, prop_itemAclIconColorSelected, prop_itemAclBorderColorSelected, prop_itemAclBackgroundColorSelected, prop_itemAclColorSelectedHover, prop_itemAclBackgroundColorSelectedHover | ظاهر و hover موارد انتخاب‌شده را حفظ کنند. |
| prop_requestTimout, prop_requestCount, prop_requestUrl | نام Legacy حفظ شود؛ timeout، تعداد صفحه و URL درخواست را کنترل کنند. typo در نام timeout فقط با alias سازگار و مستند قابل اصلاح است. |
| prop_langs, prop_langSelected | در مصرف‌کنندگان بررسی شوند. ترجیح معماری جدید استفاده از ترجمهٔ سیستم برای Accept/Cancel و حذف انتخاب دستی زبان است؛ حذف props فقط پس از تأیید نبود مصرف وابسته انجام شود. |
| var_itemsSelected | prop عمومی نسازید/منتقل نکنید مگر مصرف‌کنندهٔ واقعی یافت شود؛ برای staging از state داخلی استفاده شود. |

## 4. ساختار درختی پیشنهادی در معماری فعلی

ساختار درختی باید با قرارداد COMPONENT/STRUCTURE و composition فعلی هماهنگ باشد. ریشه با ComponentStructureTrait ساخته می‌شود؛ Label و PositionMenu از الگوی ComponentInputListSelector پیروی می‌کنند. PositionMenu برای selector/body و دکمه‌های footer طراحی شده و برای این پنل مناسب‌تر از ComponentElementPosition است.

    component-input-acl
    └── component-structure
        ├── ComponentLabelTrait (عنوان/tooltip، در صورت نمایش)
        ├── part-input-acl-main
        │   ├── ComponentBorder (ظرف کنترل)
        │   │   ├── part-input-acl-header (selector منو و خلاصهٔ مقدار)
        │   │   ├── ComponentIcon (بازکردن پنل، در selector)
        │   │   └── ComponentIcon (پاک‌کردن مقدار)
        │   └── ComponentPositionMenu
        │       ├── menuSelector: header کنترل
        │       └── menuBody
        │           ├── ComponentInputSimple (جست‌وجو)
        │           ├── فهرست remote با renderer reactive / ComponentRecyclerView
        │           ├── ComponentIcon یا ComponentButton (انتقال RTL/LTR هر ردیف)
        │           ├── کنترل‌های Select All و Clear All
        │           ├── ComponentListSelectedScroller (فهرست staging، در صورت تطبیق داده و interaction)
        │           └── footer Accept/Reject مدیریت‌شده توسط ComponentPositionMenu
        ├── ComponentValidate (قواعد و پیام‌های اعتبارسنجی انتخاب ACL)
        └── hidden input reactive فقط در صورت اثبات نیاز ارسال فرم HTML

Legacy یک component-validate خالی می‌سازد و در props موجود rule یا validation قابل تنظیمی ندارد. ساختار جدید باید با این حال schema و child واقعی ComponentValidate داشته باشد؛ props استاندارد hasRules, isAbsoluteRule, listRules, msgRules افزوده شوند و validator به مقدار ACL تأییدشده وصل شود. برای جلوگیری از فرض دربارهٔ semantics قواعد، مثال و قواعد پیش‌فرض فقط پس از تعیین قرارداد validation تعریف شوند؛ در حالت بدون rule، validator نمایش داده نشود.

ComponentLabelTrait باید به Schemas و Props اضافه شود. prop_labelTitle و prop_labelTooltipDescription از API استاندارد trait استفاده کنند؛ prop_title قدیمی جداگانه حفظ شود تا نقش آن با عنوان Label یکی فرض نشود. کلیک روی Label باید منوی انتخاب را از مسیر event/method ساختار جدید باز کند، بدون DOM query.

در renderContentComponent ترتیب root به این شکل باشد: LABEL، MAIN، VALIDATE. renderManagerComponent برای Label از مسیر trait و برای MAIN/VALIDATE از متدهای اختصاصی استفاده کند. برای رندر فهرست remote، ComponentRecyclerView تنها در صورتی استفاده شود که API آن با ساخت آیتم‌های observable و جایگاه loading سازگار باشد؛ در غیر این صورت child list با CoreReactive و state محلی ساخته شود، نه با innerHTML.

### فهرست schemaهای پیشنهادی

| Schema | Part | نقش و props اصلی |
|---|---|---|
| COMPONENT / STRUCTURE | از ComponentStructureTrait | wrapperهای پایهٔ ComponentManager |
| LABEL | از ComponentLabelTrait | propهای LabelTrait؛ بالای فرم |
| MAIN | part-input-acl-main | مقدار، disabled، name و props نمایشی کنترل |
| MENU | part-input-acl-menu | ساخت ComponentPositionMenu و اتصال selector/body |
| MENU_SELECTOR | part-input-acl-menu-selector | Header، خلاصهٔ انتخاب‌شده، آیکون بازکردن و Clear |
| MENU_BODY | part-input-acl-menu-body | body منو شامل search، دو فهرست و کنترل‌ها |
| SEARCH | part-input-acl-search | ComponentInputSimple و prop_requestTimout |
| AVAILABLE_LIST | part-input-acl-available-list | نتایج remote، loading و scroll pagination |
| AVAILABLE_ITEM | part-input-acl-available-item | یک آیتم {id, name} و event انتخاب |
| ACTIONS | part-input-acl-actions | Select All و Clear All برای مجموعهٔ نتایج جاری/staging |
| SELECTED_LIST | part-input-acl-selected-list | آیتم‌های staging و حذف آیتم |
| VALIDATE | part-input-acl-validate | prop_title, prop_hasRules, prop_isAbsoluteRule, prop_listRules, prop_msgRules, prop_value؛ ساخت ComponentValidate با مقدار تأییدشده |

Schemaها فقط prop/part را اعلام می‌کنند. ساخت ComponentPositionMenu، ComponentInputSimple، فهرست‌ها و ComponentValidate در متدهای render خود ComponentInputAcl انجام می‌شود؛ منطق اجرایی داخل Schemas یا Props قرار نمی‌گیرد.

## 5. State، رویدادها و چرخهٔ عمر

- مقدار تأییدشده و فهرست staging جدا باشند؛ تغییر آیتم‌ها در staging نباید تا Accept مقدار عمومی را تغییر دهد.
- state reactive برای پنل باز/بسته، عبارت جست‌وجو، فهرست دریافت‌شده، staging selection، صفحه، loading، پایان صفحات و debounce ساخته شود.
- دریافت هر صفحه موارد تکراری یا موارد حاضر در staging را دوباره به فهرست انتخاب‌نشده اضافه نکند.
- درخواست هم‌زمان تکراری جلوگیری شود؛ با تغییر search، پاسخ stale نباید نتایج جست‌وجوی جدید را بازنویسی کند. برای این کار از شناسه/نسخهٔ درخواست یا لغو درخواست در صورت پشتیبانی runtime استفاده شود.
- بازکردن پنل از ابتدا صفحه و search را reset کند و مقدار تأییدشده را به staging منتقل کند.
- Accept مقدار staging را یک بار منتشر کند، پنل را ببندد و callback با مقدار نهایی اجرا کند.
- Cancel بدون تغییر prop_value staging را دور بریزد و پنل را ببندد.
- Clear مقدار تأییدشده را خالی و callback را با مقدار خالی اجرا کند؛ staging و ظاهر Header نیز همگام شوند.
- dispose باید timer، subscription، child components و درخواست‌های قابل لغو را آزاد کند.
- نام و payload callback Legacy در repository/مصرف‌ها تعیین شود. در این فایل fn_callback(event, prop_value) دیده می‌شود؛ ترتیب فعلی Accept ابتدا callback و سپس set(prop_value, ...) دارد و مقدار callback در helper از config خوانده می‌شود. این ترتیب احتمالاً مقدار قدیمی می‌دهد و پیش از تثبیت API باید مصرف واقعی بررسی شود؛ در قرارداد جدید callback باید مقدار صریح همان عملیات را دریافت کند.

## 6. ابهام‌ها و مواردی که پیش از implementation باید تأیید شوند

1. فرمت شناسهٔ id: بعضی مسیرهای Legacy با parseInt می‌خوانند، در حالی که نوع واقعی سرور دیده نشده است. تا بررسی endpoint، ID را در مدل جدید به عدد محدود نکنید.
2. قرارداد request helper و خطاها: نمونهٔ response، وضعیت HTTP، شکل خطا، لغو درخواست و مجوز endpoint از فایل Legacy قابل تعیین نیست. قرارداد مصرف‌کننده/backend را پیدا کنید؛ endpoint یا Laravel تغییر نکند.
3. callback: بررسی شود مصرف‌کنندگان مقدار قبلی را دریافت می‌کردند یا انتظار مقدار نهایی را دارند. هدف مهاجرت رفع silent bug با تغییر بی‌خبر API نیست.
4. عنوان: prop_title تعریف شده اما در قسمت‌های قابل مشاهده نقش آن در label قطعی نیست؛ کاربردش را در مصرف‌ها/قواعد Legacy مشخص کنید.
5. لغو درخواست و جست‌وجوی سریع: سیاست برخورد با پاسخ قدیمی و خطای شبکه در Legacy کامل نیست؛ رفتار جدید باید مستند و در محدودهٔ UI باشد.
6. prop_bodyHeight و prop_bodyTop: مقدارهای پیش‌فرض pattern و render یکسان نیستند؛ مصرف‌کننده یا نمونهٔ بصری را مرجع قرار دهید.
7. زبان: وجود تنها fa/en در prop سفارشی شاهد نیاز به تغییر ترجمهٔ runtime نیست؛ ابتدا قرارداد فعلی پروژه برای زبان سیستم را رعایت و سازگاری را بررسی کنید.

## 8. معیارهای پذیرش

1. ورودی در ComponentManager و Category با API سه‌آرگومانی جدید در دسترس باشد.
2. Header نام‌های مقدار تأییدشده را نشان دهد و باز/بسته‌شدن، Clear و disabled با state هماهنگ باشند.
3. بازشدن پنل staging را از prop_value مقداردهی و اولین درخواست را با پارامترهای count/search/page ارسال کند.
4. جست‌وجو debounce شود؛ pagination با scroll انتهایی کار کند و درخواست موازی/نتیجهٔ stale باعث تکرار یا برگشت نتایج قبلی نشود.
5. انتخاب، حذف از staging، Select All موارد بارگذاری‌شده و Clear All قابل پیش‌بینی باشند.
6. Cancel مقدار تأییدشده را تغییر ندهد؛ Accept فقط یک بار آرایهٔ {id, name} را منتشر کند؛ Clear مقدار را خالی کند.
7. LabelTrait بالای فرم رندر شود؛ اگر عنوان/tooltip نمایش داده می‌شود، کلیک Label منوی انتخاب را باز کند.
8. ComponentValidate به prop_value تأییدشده متصل باشد، قواعد خالی/غیرخالی را از prop_listRules اجرا کند و با تغییر مقدار دوباره validate کند.
9. هر دو فهرست در RTL/LTR، disabled و hover درست نمایش داده شوند و آیکون‌های جهت‌دار مطابق جهت باشند.
10. اگر hidden input برای ارسال فرم لازم است، name و JSON آن با prop_value reactive بمانند.
11. سبک‌ها و ابعاد از utilهای پروژه و CoreConfig.Settings.SizeName بیایند؛ prop_size جدید اضافه نشود.
12. dispose timer، subscription و children را آزاد کند.
13. مثال‌ها، typecheck مرتبط، build موجود و git diff --check اجرا شوند؛ خطاهای پایهٔ ازقبل‌موجود جدا گزارش شوند.

## 9. خارج از محدوده

- تغییر API یا پیاده‌سازی Laravel/backend و endpointهای مصرف‌کننده.
- مهاجرت مصرف‌کنندگان قدیمی یا تغییر ساختار response شبکه بدون قرارداد مستند.
- بازطراحی UX انتخاب‌گر فراتر از حفظ رفتار و هم‌راستایی با اجزای UI جدید.
- افزودن validation جدید بدون props/rules یا مصرف واقعی مستند.
- اصلاح رفتارهای نامرتبط Legacy؛ هر اصلاح با اثر قراردادی باید جداگانه و مستند بررسی شود.

## 10. گزارش پیاده‌سازی

- API جدید با نام `UiCategory.UI.Inputs.InputAcl(config, methods, identity)` ثبت شد.
- Label و Validate، پنل `ComponentPositionMenu`، ورودی جست‌وجو، فهرست remote و `ComponentListSelectedScroller` برای موارد انتخاب‌شده ترکیب شدند.
- انتخاب موقت از مقدار تأییدشده جداست؛ Accept مقدار را منتشر می‌کند، Cancel staging را برمی‌گرداند و Clear مقدار تأییدشده را خالی می‌کند.
- transport فعلی از `fetch` با POST JSON شامل `count`, `search`, `page` استفاده می‌کند. helper قدیمی و قرارداد endpoint در سورس جدید موجود نبودند؛ این payload باید با مصرف‌کنندهٔ واقعی تأیید شود، و این پیاده‌سازی به‌تنهایی سازگاری Laravel را ثابت نمی‌کند.
- typecheck کامل پروژه از قبل خطاهایی در `last/categories/ui/inputs/index.ts` و `module_components/lists/index.ts` دارد؛ در خروجی فیلترشده خطایی از فایل‌های ComponentInputAcl دیده نشد. اجرای Vite build با `spawn EPERM` در محیط فعلی متوقف شد.
