# 12.3 — Real-World Performance Validation

> **هدف:** پاسخ به سوال اصلی: آیا overhead کتابخانه قابل‌قبول است؟
> آیا ارزش استفاده از کتابخانه (reactive, typed API, accessibility, consistency)
> هزینه performance آن را توجیه می‌کند؟

> **انگیزه:** 12.2.4 نشان داد cloneNode optimization در jsdom بن‌بست است.
> ولی jsdom ≠ browser. قبل از هر optimization دیگری، باید بدانیم:
> 1. آیا مشکل در browser واقعی هم وجود دارد؟
> 2. overhead کتابخانه نسبت به raw implementation چقدر است؟
> 3. در چه workloadهایی overhead قابل‌قبول است و در کجا نیست؟

| # | سوال | چگونه پاسخ می‌دهیم |
|---|------|-------------------|

## ۲. استراتژی benchmark

### ۲.۱. سه implementation رقیب

#### A. Library (فعلی)
```ts
UiIcons.CreateIcon(def, { primaryColor: obs })
```

#### B. Raw DOM (معادل دستی)
```ts
function rawCreateIcon(def): SVGSVGElement {
    const svg = document.createElementNS("http://www.w3.org/2000/svg", "svg");
    svg.setAttribute("xmlns", "...");
    svg.setAttribute("viewBox", `0 0 ${def.viewBoxX} ${def.viewBoxY}`);
    svg.setAttribute("role", "img");
    svg.setAttribute("fill", "none");
    svg.setAttribute("aria-label", "...");
    svg.setAttribute("width", "24");
    svg.setAttribute("height", "24");
    for (const child of def.render(ctx)) {
        svg.appendChild(child.element);  // یا دستی createElementNS
    }
    return svg;
}
```

#### C. Raw SVG Template (innerHTML)
```ts
function rawSvgTemplate(def): SVGSVGElement {
    const html = `<svg xmlns="..." viewBox="..." role="img" fill="none" ...>
        ${def.render(ctx).map(el => el.element.outerHTML).join("")}
    </svg>`;
    const container = document.createElement("div");
    container.innerHTML = html;
    return container.querySelector("svg");
}
```

> **نکته:** B و C نباید reactive باشند. هدف نشان دادن baseline بدون abstraction است.

### ۲.۲. workload scenarios

| Scenario | count | ترکیب | هدف |
|----------|-------|-------|------|
| Small UI | 5 | mixed icons | typical widget |
| Typical page | 20 | mixed icons | normal page |
| Dense table | 50 | mixed icons | data-heavy UI |
| Stress | 100 | mixed icons | extreme case |
| Extreme | 500 | mixed icons | pathological |

> **mixed icons:** ترکیبی از سبک (score=1-3)، متوسط (score=5-10)، سنگین (score=20-30)
> نه فقط heaviest. این واقعی‌تر از diagnostic فعلی است.

### ۲.۳. lifecycle phases

برای هر scenario، 5 phase را benchmark کن:

| Phase | عملیات | metric |
|-------|--------|--------|
| **create** | ساخت N آیکون | time (ms) |
| **mount** | append به DOM | time (ms) |
| **update** | تغییر primaryColor روی همه | time (ms) |
| **event** | dispatch click روی همه | time (ms) |
| **destroy** | remove + cleanup | time (ms) + retained nodes |

> **نکته مهم:** update فقط برای Library معنا دارد (reactive).
> برای B/C باید دستی loop کنی و setAttribute کنی — این هم بخشی از overhead است.

## ۳. محیط benchmark

### ۳.۱. jsdom (فعلی — baseline مقایسه‌ای)

- سریع برای development
- نویز بالا ولی قابل اعتماد برای نسبت‌ها
- **هدف:** مقایسه relative (Library/Raw ratio)

### ۳.۲. browser واقعی (جدید — production truth)

- Chrome با DevTools
- `performance.now()` با دقت بالا
- **هدف:** مقایسه absolute (آیا واقعاً محسوس است؟)

> **implementation:** یک HTML page با script که benchmark را اجرا می‌کند
> و نتایج را console.log می‌کند. یا Vitest با browser environment.

## ۴. معیار موفقیت

### ۴.۱. معیار منطقی (نه "سریع‌تر از raw")

| workload | overhead قابل‌قبول | توجیه |
|----------|---------------------|-------|
| 5 icons | < 2ms | کاربر نمی‌سنجد |
| 20 icons | < 5ms | acceptable برای typical page |
| 50 icons | < 15ms | acceptable برای dense table |
| 100 icons | < 40ms | acceptable برای stress |
| 500 icons | < 200ms | acceptable برای extreme (نادر) |

> **منطق:** اگه overhead < 1 frame (16ms) در typical workload باشه، کاربر نمی‌سنجد.

### ۴.۲. معیار شکست

| شرط | معنی |
|------|------|
| Library > 3× Raw DOM در 20 icons | abstraction گران‌تر از ارزشش است |
| update > 50ms در 20 icons | reactive بسیار کند است |
| retained nodes > 0 بعد از destroy | memory leak |

### ۴.۳. value proposition (چرا کتابخانه؟)

کتابخانه باید این‌ها را فراهم کند که raw implementation باید **دستی** پیاده‌سازی کند:

| قابلیت | Library | Raw DOM | Raw SVG |
|--------|---------|---------|---------|
| typed API | ✓ | ✗ | ✗ |
| reactive props | ✓ | ✗ (دستی) | ✗ (دستی) |
| accessibility (aria/role) | ✓ auto | ✗ (دستی) | ✗ (دستی) |
| event handling | ✓ | ✗ (دستی) | ✗ (دستی) |
| lifecycle management | ✓ | ✗ (دستی) | ✗ (دستی) |
| template caching | ✓ | ✗ (دستی) | ✗ (دستی) |
| consistent behavior | ✓ | ✗ (ad-hoc) | ✗ (ad-hoc) |

> **نتیجه‌گیری هدف:** "Library overhead = Xms، ولی N قابلیت را فراهم می‌کند
> که raw implementation باید M خط کد دستی بنویسد."
