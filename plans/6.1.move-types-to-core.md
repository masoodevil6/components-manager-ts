# Plan 6.1 — انتقال Types و ComponentManager از module_ui به module_core

## هدف

Types و ComponentManager که در `module_ui/module_components/basic` تعریف شده‌اند، باید به `module_core/module_components` منتقل شوند.

**دلیل:** `module_core/module_components` برای تعریف زیرساخت مشترک Componentها طراحی شده. این Types قراردادهای پایه Component هستند و به UI وابسته نیستند — پس باید در Core باشند.

## مشکلات وضعیت فعلی

### ۱. تکرار TComponentDefinition

`TComponentDefinition` هم در Core و هم در UI تعریف شده — دقیقاً یکسان.

### ۲. Types پایه در UI

`TComponentPropEntry`, `TComponentProps`, `TComponentSchemaEntry`, `TComponentSchemas`, `TComponentIdentity` — همه در UI هستند ولی به Core وابسته‌اند (به `CoreEvent`, `UtilBrands`). هیچ وابستگی به UI ندارند.

### ۳. ComponentManager در UI

`ComponentManager` به `CoreComponents` و `CoreEvent` وابسته است — به UI وابسته نیست. پس باید در Core باشد.

### ۴. Re-export اضافی

`TComponentExampleDefinition.ts` در UI فقط re-export از Core است — حذف شود.

## نکات مهم

### چرا این Types باید در Core باشند؟

۱. **وابستگی:** این Types به `CoreEvent`, `UtilBrands` وابسته‌اند — نه به UI.
۲. **مصرف‌کننده:** `ClComponentBase` (در Core) به این Types نیاز دارد.
۳. **اصل معماری:** Core نباید به UI وابسته باشد. اگر Type در UI باشد و Core به آن نیاز داشته باشد، وابستگی معکوس ایجاد می‌شود.

### چرا ComponentManager باید در Core باشد؟

۱. **وابستگی:** ComponentManager به `CoreComponents` و `CoreEvent` وابسته است — نه به UI.
۲. **مصرف‌کننده:** Component Manager باید بتواند همه Componentها (Core و UI) را مدیریت کند.
۳. **اصل معماری:** اگر ComponentManager در UI باشد، Core نمی‌تواند از آن استفاده کند.

### Backward Compatibility

برای حفظ backward compatibility، `module_ui/.../basic/index.ts` می‌تواند re-export از Core داشته باشد. این اجازه می‌دهد کدهای موجود که از `UiComponents.Basic.Types.*` استفاده می‌کنند بدون تغییر کار کنند.
