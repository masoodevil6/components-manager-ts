# Component Architecture Evolution Plan

## هدف اصلی

تثبیت معماری `ComponentStructure` به‌عنوان **Base Runtime مشترک تمام UI Componentها** و ایجاد یک معماری تمیز برای:

* Runtime
* Configuration
* Schema
* Schema Behavior
* Component Metadata
* Component State
* Lifecycle
* Examples
* Graphical Component Manager

معماری نهایی باید به شکلی باشد که Componentهایی مانند:

* `ComponentButton`
* `ComponentCollapse`
* `ComponentInput`
* `ComponentSelect`

بدون ایجاد coupling غیرضروری با Core ساخته شوند.

---

# 1. معماری مفهومی نهایی

هر Component از چند لایه مستقل تشکیل می‌شود:

```text
                    Component
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       Metadata        Runtime        Examples
          │              │              │
     Definition    ComponentStructure  ExampleDefinition
          │              │              │
          │       ┌──────┼──────┐       │
          │       │      │      │       │
          │     Props  Schema Methods   │
          │              │              │
          │        SchemaHandlers       │
          │                             │
          └──────────── Component Manager
```

اصل مهم:

> **Metadata نباید مسئول Runtime باشد و Runtime نباید وابسته به Tooling باشد.**

---

# 2. ComponentStructure

`ComponentStructure` همچنان باید **Class** باقی بماند.

دلیل:

این کلاس صرفاً یک container برای config نیست.

در آینده مسئول قابلیت‌های Runtime مانند:

* State
* Lifecycle
* Instance Identity
* Runtime APIs
* Component-level utilities

خواهد بود.

بنابراین حذف Class و تبدیل آن به configuration object تصمیم مناسبی نیست.

---

# 3. مسئولیت فعلی ComponentStructure

در وضعیت فعلی:

```text
ComponentStructure
│
├── Definition
├── Props
├── Schemas
├── SchemaHandlers
└── Methods
```

کلاس فقط زیرساخت Runtime را فراهم می‌کند.

---

# 4. Definition

`Definition` باید باقی بماند.

مثلاً:

```ts
export const Definition: UiComponents.Basic.Types.ComponentDefinition = {

    id: "component_structure",

    name: "componentStructure",

    version: "v1.0.0",

};
```

مسئولیت:

```text
Definition
│
├── id
├── name
├── version
├── metadata
├── category
├── capabilities
└── future graphical-manager information
```

### نکته مهم

`Definition` شناسنامه Component است، نه Runtime configuration.

بنابراین:

```ts
_COMPONENT_DEFINITION
```

در `ComponentStructure` منطقی است.

اما در آینده بهتر است Type آن به شکلی توسعه‌پذیر باشد:

```ts
interface ComponentDefinition {

    id: string;

    name: string;

    version: string;

    category?: string;

    description?: string;

    capabilities?: string[];

}
```

---

# 5. Props

Props باید کاملاً declarative باقی بمانند.

```text
Props.ts
```

مثلاً:

```ts
export const Props = {

    selector: {
        prop: "selector",
        default: null,
        name: ...,
        description: ...
    },

    append: {
        prop: "append",
        default: false,
        name: ...,
        description: ...
    },

};
```

وظیفه:

```text
Prop Definition
      │
      ├── name
      ├── default
      ├── description
      └── metadata
```

Props نباید شامل rendering logic باشند.

---

# 6. Schemas

Schema نیز باید declarative باقی بماند.

نمونه:

```ts
export const Schemas = {

    COMPONENT: {

        part: "part-component",

        props: [
            Props.classList,
            Props.styles
        ],

        name: ...,

        description: ...
    },

    STRUCTURE: {

        part: "part-component-structure",

        props: [
            Props.prop_show,
            Props.prop_structureClass,
            Props.prop_structureStyles
        ],

        name: ...,

        description: ...
    }

};
```

Schema فقط مشخص می‌کند:

> این Part چیست و چه configurationای دارد؟

نه اینکه چگونه render شود.

---

# 7. SchemaHandlers

رفتار Schema باید از Schema جدا باشد.

ساختار فعلی:

```text
Schemas.ts
     │
     │ definition
     ▼
SchemaHandlers.ts
     │
     │ behavior
     ▼
Runtime Renderer
```

مثلاً:

```ts
SchemaHandlers.COMPONENT.render(context)
```

این معماری باید حفظ شود.

---

# 8. Schema Interface

برای جلوگیری از محدود شدن Component به `render()`، Handler نباید صرفاً یک object با یک متد فرض شود.

به جای این:

```ts
interface ComponentSchemaHandler {

    render(context): CoreReactive.App;

}
```

بهتر است معماری به سمت چیزی شبیه این حرکت کند:

```ts
interface ComponentSchemaHandler<TContext = any> {

    render(
        context: TContext
    ): CoreReactive.App;

}
```

اما این interface باید قابلیت توسعه داشته باشد.

در آینده ممکن است Handler نیاز داشته باشد:

```ts
interface ComponentSchemaHandler<TContext = any> {

    render(context: TContext): CoreReactive.App;

    beforeRender?(
        context: TContext
    ): void;

    afterRender?(
        context: TContext,
        element: CoreReactive.App
    ): void;

}
```

این بخش فعلاً **طراحی معماری** است و نباید بدون نیاز واقعی وارد Core شود.

اصل:

> Schema declarative است، Handler behavioral است.

---

# 9. Methods

Methods برای رفتارهای Component هستند، نه rendering Schema.

مثلاً Button:

```ts
Methods = {

    CLICK: {
        ...
    }

}
```

و Runtime:

```ts
this.executeMethod(
    "fn_onClickButton",
    event,
    params
);
```

این separation باید حفظ شود:

```text
SchemaHandler
    ↓
Rendering behavior

Component Method
    ↓
Component behavior / events
```

---

# 10. ComponentStructure فعلی

در وضعیت فعلی ساختار پیشنهادی:

```ts
export class ComponentStructure<
    TProp extends Record<string, any> = PropsType,
    TSchemas = SchemasType,
    TMethods extends Record<string, any> = MethodsType
> extends CoreComponents.App<
    TProp,
    TSchemas,
    any,
    TMethods
> {

    constructor(
        componentName: string = "structure",
        elId: string | null = null,
    ) {
        super(componentName, elId);
    }

    protected _COMPONENT_DEFINITION = Definition;

    protected _COMPONENT_PATTERN =
        CoreComponents.DefineProp<TProp>({
            ...Props,
        } as any);

    protected _COMPONENT_SCHEMA =
        CoreComponents.DefineSchema<TSchemas, TProp>({
            COMPONENT: {
                part: Schemas.COMPONENT.part,
                props: Schemas.COMPONENT.props ?? [],
                handler: SchemaHandlers.COMPONENT,
            },

            STRUCTURE: {
                part: Schemas.STRUCTURE.part,
                props: Schemas.STRUCTURE.props ?? [],
                handler: SchemaHandlers.STRUCTURE,
            },

        } as any);

    protected _COMPONENT_METHODS =
        CoreComponents.DefineMethod<TMethods, TProp>({
            ...Methods,
        } as any);
}
```

این ساختار در حال حاضر **قابل قبول و تثبیت‌شده** است.

---

# 11. آیا این چهار Property باید داخل ComponentStructure باشند؟

## بله، فعلاً

```text
_COMPONENT_DEFINITION
_COMPONENT_PATTERN
_COMPONENT_SCHEMA
_COMPONENT_METHODS
```

چون این‌ها configuration اجرایی Base Runtime هستند.

اما باید از بیرون `protected` باشند.

یعنی:

```ts
protected _COMPONENT_PATTERN
protected _COMPONENT_SCHEMA
protected _COMPONENT_METHODS
protected _COMPONENT_DEFINITION
```

تا Component فرزند بتواند آنها را override/extend کند ولی API عمومی Component آلوده نشود.

# 20. State

State برای Componentهایی مانند Collapse ضروری است.

مثلاً:

```ts
class ComponentCollapse extends ComponentStructure {

    protected _STATE = {

        opened: false,

    };

}
```

یا در معماری Reactive آینده:

```ts
protected _STATE = {

    opened: new CoreObservable.App(false),

};
```

اما این بخش **فعلاً نباید پیاده‌سازی شود**.

دلیل:

State API متعلق به Core Runtime است و باید قبل از استفاده گسترده طراحی شود.

---

# 21. Lifecycle

Lifecycle نیز باید در Core طراحی شود.

هدف آینده:

```text
constructor
    ↓
initialize
    ↓
render
    ↓
mounted
    ↓
updated
    ↓
destroy
```

اما ComponentStructure فعلی نباید lifecycle مصنوعی دریافت کند.

Lifecycle زمانی اضافه شود که Core API آن مشخص شده باشد.

# 22. Identity

پارامترهای:

```ts

emit
elId
```

باید در آینده بخشی از Identity/Instance Runtime محسوب شوند.

اما این موضوع نیز نیازمند طراحی Core است.

فعلاً:

```ts

    componentName,
    elId

```

تغییر داده نشود مگر اینکه Core جدید آماده باشد.

# 26. اصل معماری نهایی

چهار مفهوم نباید با هم قاطی شوند:

```text
Definition
    ↓
Identity / Metadata

Props + Schemas
    ↓
Configuration

SchemaHandlers + Methods
    ↓
Behavior

Examples
    ↓
Tooling / Documentation / Preview
```

و در مرکز همه آنها:

```text
ComponentStructure
        ↓
Runtime
```

بنابراین `ComponentStructure` نه باید حذف شود، نه تبدیل به یک object ساده شود.

نقش آن باید به‌تدریج از یک کلاس صرفاً config-holder به یک **Runtime Base واقعی برای Componentها** تبدیل شود.

اما قابلیت‌های سنگین‌تر مانند State، Lifecycle و Identity فقط زمانی وارد آن شوند که Core API آنها واقعاً طراحی شده باشد.

---

# 27. اولین قدم اجرایی پیشنهادی

در وضعیت فعلی، قبل از رفتن سراغ State و Lifecycle:

```text
1. تثبیت ComponentStructure
        ↓
2. تثبیت Definition
        ↓
3. تثبیت Schema + SchemaHandler
        ↓
4. طراحی ComponentExampleDefinition
        ↓
5. طراحی ExampleRenderer
        ↓
6. ساخت ComponentButton
        ↓
7. تست Example System روی Button
        ↓
8. ساخت Collapse
        ↓
9. استخراج نیاز واقعی State
        ↓
10. طراحی State API در Core
```

این ترتیب مهم است.

**State، Lifecycle و Identity فعلاً پروژه‌های Core هستند، نه کارهای فوری `ComponentStructure`.**

در مقابل، `Definition` و `ExampleDefinition` همین حالا ارزش معماری دارند، چون مستقیماً به Component Manager آینده وصل می‌شوند.
