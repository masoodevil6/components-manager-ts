# Plan 8.2.10 — Component Wrapper Layer در Trait

> **پیش‌نیاز:** Plan 8.1.2 (ComponentStructureTrait), Plan 8.2.8 (Per-Message Event Scope)
> **هدف:** بازگرداندن لایه `<component-{name}>` در معماری Composition — بدون ارث از ComponentStructure

---

## ۱. مسئله

### ۱.۱ وضعیت فعلی

در معماری قدیمی (legacy)، هر Component یک ساختار دو لایه‌ای داشت:

```text
<component-message>          ← لایه خارجی (نام کامپوننت + RTL + classList + styles)
  <section>                  ← لایه structure (show/hide + structureClass + structureStyles)
    <div>...</div>           ← content اختصاصی
  </section>
</component-message>
```

این ساختار در `GOG_ComponentBasicConfigs_Component_render` ساخته می‌شد:
```typescript
ReactiveElement.component(this._COMPONENT_NAME, {
    classBind: [classList],
    stylesBind: { direction: rtl, styles },
    children: [executeSchemaPart("part-component-structure")]
})
```

در معماری فعلی (Composition با Trait)، `ComponentMessages` از `ComponentStructureTrait.renderContent` استفاده می‌کند که `ComponentStructure.create()` صدا می‌زند. ولی:

```typescript
// ComponentStructure.create() در ComponentStructure.ts:
const instance = new ComponentStructure("structure", null, identity);  // ← نام هاردکدشده!
```

**نام کامپوننت `"structure"` است — نه `"messages"`.**

در نتیجه خروجی فعلی:

```text
<component-structure>        ← ❌ نام غلط — باید component-messages باشد
  <section>
    <div>...</div>
  </section>
</component-structure>
```

### ۱.۲ مشکل

1. **DOM identity از دست رفته** — در DevTools همه کامپوننت‌ها `component-structure` نمایش داده می‌شوند — تمایز `component-messages` از `component-icon` ناممکن است.
2. **CSS targeting ناممکن** — اگر استایلی مخصوص `component-messages` بخواهیم، نمی‌توانیم با selector هدف‌گیری کنیم.
3. **debugging سخت** — در DevTools tree نمی‌توان فهمید کدام Component کجاست.
4. **semantic inconsistency** — Component اسم دارد ولی در DOM با اسم دیگری ظاهر می‌شود.

### ۱.۳ ریشه مشکل

`ComponentStructureTrait.renderContent` یک `ComponentStructure.create()` می‌سازد با نام هاردکدشده `"structure"`. Trait به نام کامپوننت مصرف‌کننده دسترسی ندارد.

```typescript
// Trait.ts — وضعیت فعلی:
renderContent(component, content) {
    return ComponentStructure.create({
        classList, styles, prop_show, prop_structureClass, prop_structureStyles,
        content,
    });
    // ↑ نام = "structure" (هاردکدشده در ComponentStructure.create)
}
```

## ۲. هدف معماری

### ۲.۱ ساختار مطلوب

```text
<component-messages>         ← لایه خارجی (نام کامپوننت مصرف‌کننده)
  <section>                  ← لایه structure
    <div>...</div>           ← content اختصاصی
  </section>
</component-messages>
```

برای `ComponentIcon`:

```text
<component-icon>
  <section>
    <svg>...</svg>
  </section>
</component-icon>
```

### ۲.۲ اصل

> **نام کامپوننت در DOM باید با `_COMPONENT_NAME` کامپوننت مصرف‌کننده مطابقت داشته باشد.**

## ۳. راه‌حل

### ۳.۱ پاس دادن نام کامپوننت به Trait

`renderContent` باید نام کامپوننت مصرف‌کننده را بپذیرد و به `ComponentStructure.create()` پاس دهد.

```typescript
// Trait.ts — وضعیت مطلوب:
renderContent(component, content) {
    const componentName = component._COMPONENT_NAME;  // ← از component خوانده شود
    return ComponentStructure.create(componentName, {  // ← پاس داده شود
        classList, styles, prop_show, prop_structureClass, prop_structureStyles,
        content,
    });
}
```

### ۳.۲ تغییر `ComponentStructure.create()`

`create()` باید نام کامپوننت را به‌عنوان پارامتر اول بپذیرد:

```typescript
// ComponentStructure.ts — وضعیت مطلوب:
static create(
    componentName: string,  // ← پارامتر جدید
    config: Record<string, any> & { content?: () => CoreReactive.App },
    methods: Record<string, any> = {},
    identity: { unique?: any; emit?: any; events?: Record<string, any> } = {},
): CoreReactive.App {

    const { content, ...props } = config;

    const instance = new ComponentStructure(
        componentName,  // ← به‌جای "structure"
        null,
        identity as any,
    );
    // ...
}
```

### ۳.۳ تغییر `ComponentStructureTrait.renderContent()`

Trait باید نام کامپوننت را از `component._COMPONENT_NAME` بخواند:

```typescript
// Trait.ts — وضعیت مطلوب:
renderContent(component, content) {
    // ... validation ...

    const componentName = component._COMPONENT_NAME;

    return ComponentStructure.create(
        componentName,  // ← نام کامپوننت مصرف‌کننده
        {
            classList, styles, prop_show, prop_structureClass, prop_structureStyles,
            content,
        }
    );
}
```

> **شرط دسترسی به `_COMPONENT_NAME`:**
> اگر `_COMPONENT_NAME` بخشی از Contract داخلی Traitهاست → استفاده مستقیم قابل قبول است.
> اگر صرفاً implementation detail است → قبل از اجرا accessor رسمی (`getComponentName()`) بررسی شود.
> برای این Plan: صرفاً برای زیبایی API جدید نسازیم.

### ۳.۴ API Design — تفکیک identity از configuration

```typescript
ComponentStructure.create(
    componentName,   // ← identity (نام کامپوننت)
    {                // ← configuration (propها و content)
        classList, styles, prop_show, ...
        content,
    }
)
```

این تفکیک بعدها برای APIهای دیگر هم الگوی خوبی است:
- `componentName` جزء **identity** است
- `classList`, `styles`, `prop_show`, `content` جزء **configuration** هستند

### ۳.۵ backward compatibility — رد شد

**راه‌حل B (default "structure") رد شد** — چون دقیقاً همان bug معماری را زنده نگه می‌دارد.

**راه‌حل A (breaking change) تأیید شد** — چون:
- فقط یک مصرف‌کننده مستقیم وجود دارد (Trait)
- breaking change عمدی است تا مصرف‌کنندگان قدیمی پیدا شوند
- نام کامپوننت یک مفهوم اساسی است — نباید optional باشد

## ۶. نکات مهم

### ۶.۱ چرا نه `componentName` در config؟

اگر `componentName` در config باشد، ممکن است فراموش شود و default `"structure"` استفاده شود — همان مشکل فعلی. به‌عنوان پارامتر اول، اجباری است و فراموششدن آن خطای compile می‌دهد.

### ۶.۲ Invariant — تفکیک Identityها (مهم بعد از 8.2.8)

این Plan فقط **DOM Identity** را تغییر می‌دهد. سه Identity دیگر نباید تغییر کنند:

```text
DOM Identity          ← تغییر می‌کند (component-structure → component-messages)
    ≠
Event Identity        ← نباید تغییر کند (Step.unique, Step.identity)
    ≠
Event Scope           ← نباید تغییر کند (SubEvent tree, Message Scopes)
    ≠
Business Identity     ← نباید تغییر کند (message.id)
```

**Invariantهای رسمی:**
- ✅ DOM component name تغییر می‌کند
- ✅ Event identity نباید تغییر کند
- ✅ Event Scope نباید تغییر کند
- ✅ Business identity نباید تغییر کند

این تفکیک بعد از Plan 8.2.8 حیاتی است — چون Per-Message Event Scopeها بر اساس Step.identity کار می‌کنند، نه بر اساس DOM tag name.

### ۶.۳ تأثیر روی Inspector

`Framework.Core.Event.inspect()` بر اساس `Step.unique` کار می‌کند — نه بر اساس DOM tag name. تغییر DOM name از `component-structure` به `component-messages` **نباید** باعث تغییر Event identity شود.

اگر بعد از اجرا `inspect()` نشان داد که `unique` تغییر کرده، یعنی یک coupling ناخواسته بین DOM و Event وجود دارد که باید بررسی شود.

### ۶.۴ تأثیر روی CSS

اگر استایل‌هایی روی `component-structure` نوشته شده باشند، شکسته می‌شوند. ولی چون این نام هاردکدشده و اشتباه بود، بعید است استایل معتبری روی آن وجود داشته باشد. بررسی شود.
