## ۰. اصل بنیادین — حاکم بر کل پلن

> ### این مأموریت یک Rollback معماری نیست.

اهداف این مأموریت:

1. بازگرداندن **فایل‌ها و قابلیت‌هایی** که در اجرای 6.1 به‌صورت ناخواسته حذف یا تخریب شده‌اند.
2. تثبیت `ComponentBase` به‌عنوان **تنها Base Component رسمی**.
3. هماهنگ‌سازی Componentهای موجود با **قرارداد جدید ComponentBase**.
4. جلوگیری از **بازگشت معماری Legacy**.

بنابراین:

> **Restore فایل‌ها مجاز است.**
>
> **Restore معماری Runtime قدیمی مجاز نیست.**

### معماری هدف (Target):

```
                ComponentBase
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
ComponentStructure  Button      Collapse
        │             │             │
        │       (State/Render/Methods در هر کلاس)
        │
        └──── Runtime Logic ────┘
```

### معماری ممنوع (Forbidden):

```
ComponentBase
    │
    └── Old Base (Legacy)
          │
          └── Old Component Logic (SchemaHandler/renderComponent/...)
```

خواسته اصلی مأموریت 6.1 فقط این بود:

## ۲. قید مهم — منابع بازگردانی

آخرین کامیت (`create-module-event`) **قبل از** کارهای 5.x است؛ یعنی git نسخه «قبل از مأموریت 6.1» را ندارد. منابع مجاز بازگردانی:

| منبع | کاربرد |
|------|--------|
| **گفتگوی مأموریت‌ها** | محتوای فایل‌ها قبل از تغییر در مأموریت‌های 5.11 و 6.1 خوانده و ثبت شده — مرجع اول بازگردانی |
| **git HEAD** | فقط فایل‌های `D` (حذف‌شده از HEAD) مثل `lists/basic/**` |
| **بازسازی مهندسی** | فقط وقتی دو منبع بالا ناقص باشند — با کمترین تغییر نسبت به الگوی قبلی |

⚠️ استفاده از `git checkout` برای فایل‌های `M` **ممنوع** است — نسخه HEAD قدیمی‌تر از همه کارهای 5.x است و rollback به آن، کل مهاجرت Component را نابود می‌کند.

### ۲.۱ قانون استفاده از منابع قدیمی

منابع قدیمی فقط برای استخراج این موارد استفاده می‌شوند:

- **Behavior** مورد انتظار
- **API مورد انتظار** (کلیدها، امضاها)
- **Metadata** (Definition/Props/Schemas/Methods)
- **Example** و **Registry**
- **Test cases**

و **نه** برای Copy کورکورانه Runtime. هر قطعه کد قدیمی ابتدا از نظر سازگاری با `ComponentBase` جدید بررسی می‌شود.

## ۳. تفکیک Behavior از Implementation

این تفاوت ظاهراً کوچک، خط مرزی این پلن است:

| مفهوم | تعریف | مثال (Collapse) | تصمیم |
|-------|-------|-----------------|-------|
| **Behavior** | چیزی که Component باید انجام دهد | نمایش/مخفی‌سازی محتوا، `toggle()`، reactive state، event handling | **حفظ می‌شود** |
| **Implementation** | نحوه‌ای که Behavior پیاده شده | `ClComponentBase`، `renderComponent()`، `SchemaHandler`، `_COMPONENT_PROPS_BIND` | **بازنویسی با قرارداد جدید** |

### قانون طلایی Restore

| عملیات | وضعیت |
|--------|--------|
| Restore Metadata (Definition/Props/Schemas/Methods) | ✅ مجاز |
| Restore Example | ✅ مجاز |
| Restore Registry | ✅ مجاز |
| Restore Test Behavior | ✅ مجاز |
| Restore Expected UX | ✅ مجاز |
| Restore Legacy Runtime (`renderComponent` و مسیر Schema) | ❌ ممنوع |
| Restore Legacy API (امضای دوآرگومانی، `super("button", null, ...)`) | ❌ ممنوع |
| Restore Legacy Base (کلاس پایه میانی در UI) | ❌ ممنوع |
| Restore SchemaHandlers | ❌ ممنوع — باید حذف‌شده باقی بماند |

## ۴. قراردادهای معماری الزامی (حاکم بر بازسازی Runtime)

### ۴.۱ — تنها Base رسمی

در معماری جدید فقط یک Base Component رسمی وجود دارد:

```ts
src/framework/module_core/module_components/basic/class/ComponentBase.ts
```

تمام Componentهای UI باید **مستقیماً** از آن ارث ببرند:

```ts
export class ComponentStructure extends ComponentBase<Props, Schema, Methods> {}
export class ComponentButton    extends ComponentBase<Props, Schema, Methods> {}
export class ComponentCollapse  extends ComponentBase<Props, Schema, Methods> {}
```

**ممنوع** — ساخت Baseهای میانی در `module_ui/module_components`:

```ts
class ComponentStructureBase extends ComponentBase {}  // ❌
class ComponentButtonBase    extends ComponentBase {}  // ❌
class ComponentCollapseBase  extends ComponentBase {}  // ❌
class MyComponentBase        extends ComponentBase {}  // ❌
```

مگر اینکه در پلن مستقل آینده صراحتاً تصویب شود.

### ۴.۲ — مسئولیت Runtime

هر Component مسئول پنج چیز است — همه در کلاس Component:

```ts
export class ComponentCollapse extends ComponentBase<Props, Schema, Methods> {

    protected readonly state = {
        show: new CoreObservable.App(true),   // State
    };

    toggle(): void {                          // Method / Behavior
        this.state.show.set(!this.state.show.get());
    }

    protected render(): CoreReactive.App {    // Rendering
        // ...
    }
}
```

این مسئولیت‌ها **نباید** به Schema، Props، Example یا Handler منتقل شوند.

### ۴.۳ — Schema فقط Metadata است

Schema مسئول توصیف ساختار Component است:

```ts
export const Schemas = {
    CONTENT: {
        part: "part-collapse-content",
        name: "...",
        description: "...",
    },
};
```

**ممنوع:**

```ts
Schema → CoreReactive.App       // ❌ Rendering
Schema → State                  // ❌
Schema → Event handler          // ❌
Schema → Component instance     // ❌
Schema → Rendering logic        // ❌
Schema → SchemaHandler          // ❌
```

### ۴.۴ — State در Component است

```ts
protected readonly state = {
    show: new CoreObservable.App(true),   // ✅ داخل کلاس
};
```

**تفکیک Props از State:**

| مفهوم | تعریف | مثال |
|-------|-------|------|
| Props | ورودی‌های Component از بیرون | `selector`, `classList`, `content` |
| State | وضعیت Runtime داخلی | `this.state.show` |

**ممنوع:** تعریف State در Schema / Props / Example / Handler.

### ۴.۵ — Rendering در Component است (و Lazy)

```ts
protected render(): CoreReactive.App {
    return CoreReactive.App.part("section", { /* ... */ });
}
```

Schema فقط می‌گوید یک Part وجود دارد؛ نمی‌گوید چگونه رندر شود.

**Lazy Render الزامی است** (کرش‌فیکس تثبیت‌شده):

```ts
// ❌ ممنوع — فیلدهای فرزند هنوز مقداردهی نشده‌اند
constructor(props, methods, identity) {
    super(props, methods, identity);
    this.getElement();
}

// ✅ صحیح
new Component(...) → getElement() → render()
```

### ۴.۶ — Methods عمومی در کلاس Component

```ts
toggle(): void {
    const current = this.state.show.get();
    this.state.show.set(!current);
}
```

Methods نباید برای انتقال منطق Rendering به Schema استفاده شوند.

### ۴.۷ — Composition

اگر Component محتوای قابل تزریق دارد، از طریق API مشخص:

```ts
const component = new ComponentStructure({
    selector: null,
    append: false,
    classList: ["p-2", "border"],
    styles: {},
    prop_show: true,
    prop_structureClass: ["bg-light", "rounded"],
    prop_structureStyles: {},
    content: () => {
        return ReactiveApp.button({
            className: ["btn"],
            children: ["Toggle"],
        });
    },
});
```

**نکته:** `content` فقط **نقطه Composition** است — محل تعریف State یا Business Logic نیست.

**Anti-Pattern ممنوع:**

```ts
// ❌ prop مصنوعی برای حل Rendering
const config = {
    prop_content: () => { /* ... */ },
};
```

Composition باید با نام و مفهوم مشخص `content` تعریف شود.

### ۴.۸ — Constructor سه‌آرگومانی

قرارداد رسمی:

```ts
constructor(
    props: TProp,
    methods: TMethod,
    identity?: Partial<ComponentIdentity>,
)
```

مثال مصرف:

```ts
const button = new ComponentButton(
    { label: "Save" },                    // آرگومان ۱: props
    { onClick: () => {} },                // آرگومان ۲: methods (کال‌بک‌ها)
    { events: { click: handler } },       // آرگومان ۳: identity (unique/emit/events)
);
```

Constructor محل اجرای Rendering نیست (بخش ۴.۵).

### ۴.۹ — Example فقط Data است

```ts
// ✅ صحیح
export const DefaultExample = {
    id: "button_default",
    name: "Default Button",
    description: "Basic button",
    config: { label: "Save" },
    methods: {},
};

// ❌ غلط
export const DefaultExample = {
    render() {
        return new ComponentButton(/* ... */);
    },
};
```

Example فقط مشخص می‌کند: **چه Componentی، با چه Configuration، و چه Methodهایی** نمایش داده شود.

### ۴.۱۰ — ExampleRenderer و جهت وابستگی

```
Example → ExampleRenderer → Component → getElement() → Render
```

- `ExampleRenderer → Component` ✅ مجاز
- `Component → ExampleRenderer` ❌ ممنوع

### ۴.۱۱ — ComponentManager فقط Registry

مسئولیت: `Register` / `Get` / `Has` / `List` / `GetExamples`

**ممنوع:** Render، مدیریت State، رفتار Component، مدیریت Schema.

### ۴.۱۲ — API Legacy در Componentهای جدید ممنوع

```ts
super("button", null, identity, Step);     // ❌
this.renderComponent(config, methods, events);  // ❌
_COMPONENT_PROPS_BIND;                     // ❌
SchemaHandlers;                            // ❌
LegacySchemaComponent;                     // ❌
```

مگر در بخش Legacy پروژه که صرفاً برای سازگاری تاریخی نگهداری می‌شود.

### ۵.۴ تصمیم‌های معماری

**D1 — فرزندان با امضای سه‌آرگومانی و ارث مستقیم از ComponentBase می‌مانند:**
توافق کاربر constructor سه‌آرگومانی را مشخص کرده است. بازگردانی فرزندان به دوآرگومانی قدیمی، ComponentBase در Core را بی‌استفاده می‌کند. پس: **قرارداد می‌ماند؛ محتوای درونی (State/render/logic) بازسازی می‌شود تا Behavior قبلی را با قرارداد جدید تولید کند.**

**D2 — کلیدهای Props: فرزندِ بازسازی‌شده مرجع است:**
Definition/Props/Schemas بازگردانی‌شده باید با کلیدهایی که فرزندان می‌خوانند (`this.prop("...")`) هم‌خوان شوند — نه عکس. هر کلید متفاوت در فاز ۴ هماهنگ می‌شود.

**D3 — راهنمای `component-create.md`:**
بازگردانی کامل به نسخه قبلی. به‌روزرسانی راهنما برای قرارداد جدید **خارج از scope این پلن** است و در پلن مستقلی انجام می‌شود.

**D4 — Legacy (`ClComponentBase`) کاملاً دست‌نخورده:**
هیچ تغییر نام، JSDoc یا انتقالی. تمرکز این پلن فقط بازگردانی است.

## ۶. فازهای اجرا

### فاز ۱ — بازگردانی Metadata های componentStructure
1. بازآفرینی `Definition.ts` (name/description/component)
2. بازآفرینی `Props.ts` و `Schemas.ts` و `Methods.ts` (الگوی Registry — فقط Metadata)
3. بازگردانی `Example.ts` به محتوای قبلی (فقط Data — بخش ۴.۹)
4. بازگردانی `index.ts` با export کامل قبلی

### فاز ۲ — بازسازی Runtime فرزندان (Behavior قبلی + Implementation جدید)
1. `ComponentStructure` / `ComponentButton` / `ComponentCollapse`:
   **بازیابی رفتار مورد انتظار نسخه 5.11، با پیاده‌سازی مطابق قرارداد جدید ComponentBase**
   - State در کلاس (بخش ۴.۴)
   - render در کلاس (بخش ۴.۵)
   - Methods عمومی در کلاس (بخش ۴.۶)
   - Behavior قبلی: Structure (لایه ساختاری + visibility + class/style binding + content)، Button (label/state/event)، Collapse (show state + toggle + reactive rendering + content)
2. حفظ: امضای constructor سه‌آرگومانی + `extends ComponentBase` از `@/core_components` + Lazy Render
3. بازگردانی `lists/index.ts`

### فاز ۳ — بازگردانی صفحات و Legacy
1. `ClTestsPage.ts` — ساختار قبلی + هماهنگی فقط فراخوانی‌های `new`
2. `lists/ui/basic/Definition.ts` (category)
3. حذف JSDoc از `ClComponentBase.ts`
4. بازگردانی `component-create.md`

### فاز ۴ — هماهنگ‌سازی کلیدها (طبق D2)
1. تطبیق کلیدهای `Props.ts` با `this.prop()` های فرزندان
2. تطبیق کلیدهای `Methods.ts` با `this.method()` ها

### فاز ۵ — بررسی موارد ۵.۳
1. ارجاع‌یابی `lists/basic/**` → تصمیم بازگردانی از HEAD یا ماندن حذف
2. تکلیف `index copy.ts`

### فاز ۶ — تأیید
1. کامپایل TypeScript — بدون خطای جدید نسبت به وضعیت قبل از 6.1
2. تست دستی صفحه Tests — رندر Structure/Button/Collapse + رفتار toggle
3. بررسی Registry/Example در صفحه نمایش Component
4. مرور Acceptance Criteria بخش ۸ — تک‌تک موارد

## ۱۱. قاعده نهایی — اولویت در تعارض

> **اگر بین Restore نسخه قدیمی و قرارداد جدید ComponentBase تعارضی وجود داشت، قرارداد جدید ComponentBase اولویت دارد.**
>
> Do not restore the old Component architecture.
>
> Restore the old Component **behavior** and **metadata**,
> then implement that behavior using the **new ComponentBase contract**.

```
ComponentBase → Concrete Component → State + Behavior + Methods + Composition + Rendering

Schema       → Metadata only
Example      → Data only
ExampleRenderer → Instantiates and renders Example
ComponentManager → Registry only
```
