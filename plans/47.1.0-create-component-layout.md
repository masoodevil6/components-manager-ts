# پلن 47.1.0 — انتقال `ComponentLayout` به ساختار جدید

> **وضعیت:** اجرا شد؛ build تولیدی موفق بود<br>
> **دستهٔ ثبت:** `UI.Basic` با شناسهٔ موجود `basic` و عنوان فعلی `Basic Components`<br>
> **API عمومی پیشنهادی:** `UiCategory.UI.Basic.Layout(config, methods, identity)`<br>
> **سورس Legacy:** `last/Older/components.js`، تعریف `ComponentLayout` (حدود خطوط 32093 تا 32265)<br>
> **راهنمای مبنا:** `documents/guides/component-create.md`

## ۱. هدف و محدوده

`ComponentLayout` قدیمی به ساختار فعلی Componentها منتقل شود. این کامپوننت یک wrapper محتوایی عمومی است که کلاس و استایل بخش layout را می‌پذیرد و محتوای ورودی یا محتوای فرزند/slot را نمایش می‌دهد.

رفتار اصلی قدیمی حفظ شود: `prop_layoutContent` در صورت داشتن مقدار بر محتوای body اولویت دارد؛ اگر `null` باشد، محتوای ورودی فرزند نمایش داده شود. تنظیمات ساختار از `ComponentStructureTrait` به ارث برسند و تنظیمات ظاهری اختصاصی روی part خود layout اعمال شوند.

کامپوننت در دستهٔ موجود `UI.Basic` با عنوان `Basic Components` ثبت شود؛ دستهٔ تازه‌ای برای آن ساخته نشود.

## ۲. شواهد Legacy و تصمیم‌های مهاجرت

- در `last/Older/components.js`، `ComponentLayoutBase` سه prop اختصاصی دارد: `prop_layoutClass`، `prop_layoutStyles` و `prop_layoutContent`. دو prop ساختار (`prop_structureClass` و `prop_structureStyles`) با قرارداد پایهٔ جدید جایگزین شوند.
- Schema قدیمی `part_structure → part_layout` است. بخش layout یک `<section data-part-name="part_layout">` می‌سازد و کلاس‌ها و styleهای اختصاصی را روی همان بخش می‌گذارد.
- اگر `prop_layoutContent` مقدار غیر `null` داشته باشد، همان محتوا نمایش داده می‌شود؛ در غیر این صورت، محتوای body اول به‌عنوان fallback استفاده می‌شود.
- در نمونه‌های `last/Older/render.html` از `prop_layoutClass` برای ظاهر wrapper استفاده شده و در بعضی نمونه‌ها `classList` برای ساختار ریشه آمده است. این دو سطح در API جدید جدا بمانند: propهای ساختار از Trait و propهای layout از `ComponentLayout`.
- `call_addElement(html, tagId, typeDirection)` فقط در کد Legacy، از جمله `last/Older/Stepper.js`، دیده می‌شود. این متد با `document.querySelector` سراسری و `innerHTML` محتوا را جایگزین یا اضافه می‌کند؛ در سورس جدید مصرف‌کننده‌ای برای آن پیدا نشد. آن را به‌عنوان API اصلی جدید بازتولید نکنید؛ محتوای پویا از طریق `prop_layoutContent` واکنشی یا فرزندهای کامپوننت مدیریت شود.
- `fn_callback` در کلاس Legacy تعریف شده، اما خود `ComponentLayout` آن را به هیچ رویدادی متصل یا فراخوانی نمی‌کند. برای آن event یا Method ساختگی اضافه نشود.
- دستهٔ موجود `basic` عنوان `Basic Components` دارد و `ComponentStructure` را در خود ثبت می‌کند؛ `Layout` نیز به‌عنوان کامپوننت پایه در همین دسته قرار بگیرد.

## ۳. ساختار رندر

```text
COMPONENT                         از ComponentStructureTrait
└── STRUCTURE                     از ComponentStructureTrait
    └── LAYOUT: part-layout      wrapper اختصاصی ComponentLayout
        └── prop_layoutContent یا محتوای body/فرزند
```

- `COMPONENT` و `STRUCTURE` از `ComponentStructureTrait.schemas` استفاده کنند.
- Schema اختصاصی `LAYOUT` با `part: "part-layout"` تعریف شود تا نام Part قدیمی حفظ شود.
- Part ریشهٔ layout یک `<section>` بسازد. `prop_layoutClass` و `prop_layoutStyles` فقط روی همین section اعمال شوند؛ کلاس‌ها و styleهای ریشه از props پایهٔ Structure بیایند.
- `renderContentComponent` از `executeSchemaPart(Schemas.LAYOUT.part, {})` استفاده کند و `renderManagerComponent` مسیر دو Schema پایه را به Trait و Part اختصاصی را به renderer کلاس هدایت کند.
- Schema صرفاً declarative بماند و هیچ markup، handler یا rendering logic در `Schemas.ts` قرار نگیرد.

## ۴. قرارداد Props و محتوای پذیرفته‌شده

Props با `Define_ComponentProp<T>` و ترجمه‌های `Keys` تعریف شوند. `PropsType` و `PropsConfigType` از helperهای `TypeHelpers` استخراج شوند.

| Prop | نوع و مقدار پیش‌فرض | کاربرد |
|---|---|---|
| `prop_layoutClass` | `string[]` / `[]` | کلاس‌های بخش `part-layout` |
| `prop_layoutStyles` | `Record<string, string>` / `{}` | styleهای سفارشی بخش `part-layout` |
| `prop_layoutContent` | `unknown` / `null` | محتوای صریح؛ در صورت `null` محتوای body/فرزند جایگزین آن شود |

Props پایهٔ Structure، از جمله `classList`، `styles`، `prop_show`، `prop_structureClass` و `prop_structureStyles` از `ComponentStructureTrait` به ارث برسند و دوباره تعریف نشوند.

محتوای فرزند به‌صورت `content?: () => CoreReactive.App` در config سازنده دریافت شود؛ این callback prop نیست و فقط وقتی `prop_layoutContent` برابر `null` باشد به‌عنوان fallback اجرا می‌شود.

محتوا با الگوی normalization فعلی `ComponentWidget` رندر شود:

- `null` و `false` هیچ childی تولید نکنند؛ آرایه‌ها بازگشتی normalize شوند.
- `string` و `number` به متن تبدیل شوند، نه markup خام HTML.
- `HTMLElement`، `CoreReactive.App`، کامپوننت دارای `getReactiveElement()` یا `getElement()` و Observableهای پشتیبانی‌شده قابل نمایش باشند.
- اگر `prop_layoutContent` برابر `null` باشد، محتوای ثبت‌شده از body/فرزندهای ورودی به‌عنوان fallback نمایش داده شود. مقدار صریحی مثل رشتهٔ خالی fallback را فعال نکند.
- تغییر Observable مربوط به محتوا باید بدون ساخت مجدد Component در DOM منعکس شود.

از `innerHTML`، selector سراسری یا تزریق markup رشته‌ای در رندر جدید استفاده نشود. برای محتوای HTML، مصرف‌کننده باید DOM یا عنصر reactive بسازد و به‌عنوان content بدهد.

## ۵. Runtime، Methods و چرخهٔ عمر

- `ComponentLayoutBase` از `CoreComponents.App` ارث‌بری کند و چهار فیلد `_COMPONENT_DEFINITION`، `_COMPONENT_PATTERN`، `_COMPONENT_SCHEMA` و `_COMPONENT_METHODS` را تعریف کند؛ props و schemaهای Trait در فیلدهای مربوطه spread شوند و `disposeStep()` پیاده‌سازی شود.
- کلاس نهایی از Base ارث ببرد، constructor سازگار با `(config, methods, identity?)` داشته باشد، `createLayoutStep()` را در constructor بسازد، با `super("layout", null, identity, step)` عنصر `<component-layout>` را ایجاد کند و `renderComponent(config, methods, identity?.events ?? null)` را فراخوانی کند.
- چون این wrapper رفتار تعاملی یا رویداد Legacy ندارد، Method یا Step event غیرواقعی اضافه نشود. برای انطباق با ساختار جاری، `Methods.ts` خالی با typeهای استاندارد و factory مربوط به Step با `CoreEvent.Step({children: {}})` تعریف شود.
- Renderer از `_COMPONENT_PROPS_BIND` و `data` استفاده کند تا مقادیر خام و Observableهای prop درست خوانده شوند. computedها به Scope همین Component متصل باشند.
- `dispose()`، `disposeStep()` را صدا بزند؛ چرخهٔ عمر Scope طبق قرارداد `CoreComponents.App` باقی بماند. در صورت normalize کردن فرزندهای Component، همان قرارداد مالکیت و dispose کامپوننت‌های مشابه موجود رعایت شود.
- API قدیمی `call_addElement` و callback بی‌مصرف `fn_callback` در سطح عمومی جدید قرار نگیرند. تغییر محتوای پویا با تنظیم `prop_layoutContent` انجام شود.

ثبت‌های لازم:

1. Definition با `id: "component_layout"`، `name: "componentLayout"` و `version: "v1.0.0"` ساخته شود.
2. Component، Definition، Props، Schemas، Methods، Examples و constructor در `module_components/lists/index.ts` ثبت و از barrelهای عمومی مربوطه export شوند.
3. callable عمومی `UiCategory.UI.Basic.Layout` با `CreateCategoryComponent` ساخته شود؛ آن را به `components` در `ui/basic/Definition.ts` و exportهای `ui/basic/index.ts` اضافه کنید. barrel بالادستی `ui/index.ts` از قبل `Basic` را export می‌کند.
4. کلیدهای نام، توضیح، props، schema و example در `module_categories/languages/Keys.ts` و متن فارسی و انگلیسی آن‌ها در `Fa.ts` و `En.ts` اضافه شوند.
5. Exampleها در ComponentManager ثبت شوند تا در صفحهٔ TestsPage قابل کشف باشند.

## ۷. مثال‌ها

- **Default:** wrapper با `prop_layoutClass` و `prop_layoutStyles`، به‌همراه متن یا عنصر ساده در `prop_layoutContent`.
- **SlottedContent:** `prop_layoutContent: null` و محتوای فرزند/slot؛ همچنین تغییر محتوای Observable برای بررسی رندر واکنشی.
- Exampleها از callable عمومی `UiCategory.UI.Basic.Layout(...)` استفاده کنند و `render(): () => HTMLElement` مطابق قرارداد `ComponentExample` داشته باشند.

## ۸. معیارهای پذیرش و بررسی

- `UiCategory.UI.Basic.Layout` از Category resolve شود و Component در فهرست `Basic Components` دیده شود.
- DOM جدید ساختار `component-layout > section[data-part-name="part-layout"]` را مطابق Schemaها بسازد.
- کلاس و style مربوط به Structure روی ریشه و `prop_layoutClass`/`prop_layoutStyles` روی layout section اعمال شوند.
- `prop_layoutContent` در صورت مقداردهی بر slot مقدم باشد؛ `null` محتوای فرزند را نشان دهد و رشتهٔ خالی به‌عنوان مقدار صریح حفظ شود.
- رشته و عدد به‌صورت متن نمایش داده شوند؛ DOM، عنصر reactive، Component و Observable طبق normalization تعریف‌شده کار کنند.
- تغییر propهای محتوایی و ظاهری پس از render به‌صورت واکنشی دیده شود.
- `prop_show` و propهای پایهٔ Structure مطابق قرارداد `ComponentStructureTrait` عمل کنند.
- runtime جدید از `innerHTML` و `document.querySelector` سراسری برای دستکاری محتوا استفاده نکند؛ هیچ `[object Object]` در DOM ظاهر نشود.
- build بدون خطای جدید انجام شود و `git diff --check` موفق باشد.

## ۹. خارج از محدوده

- بازنویسی `ComponentMouseScroller`، `ComponentBorder` یا `ComponentWidget`.
- انتقال یا نگه‌داری API قدیمی `call_addElement(html, tagId, typeDirection)` و استفادهٔ Legacy آن در `last/Older/Stepper.js`؛ آن مصرف‌کننده در چارچوب جدید باید با content واکنشی یا فرزندهای Component بازطراحی شود.
- افزودن callback یا event عمومی برای `fn_callback`، چون در پیاده‌سازی Legacy به هیچ eventی متصل نیست.
- تغییر محتوای رشته‌ای از متن به HTML خام یا افزودن API ویژهٔ تزریق HTML.
- اضافه‌کردن style/layout پیش‌فرض جدیدی که در Legacy وجود نداشته است؛ wrapper باید پیش‌فرض خنثی داشته باشد.
