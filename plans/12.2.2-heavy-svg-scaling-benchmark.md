## ۰. اصول این Plan

### ۰.۱ سؤال واقعی investigation

سؤال اصلی این Plan نیست:

> «۱۰۰ تا SVG چند میلی‌ثانیه طول می‌کشد؟»

سؤال اصلی این است:

> ۱. **هزینه‌ی اضافه‌شدن هر SVG چقدر است؟**
> ۲. **آیا این هزینه خطی است یا غیرخطی؟**
> ۳. **آیا unique بودن definition باعث افزایش معنی‌دار هزینه می‌شود؟**

اگر خروجی Plan بتواند این سه را جواب بدهد، می‌توان با اطمینان تصمیم گرفت که مشکل از SVG creation است، از reactive/component setup است، یا از DOM/rendering. این داده برای 12.2.3 باارزش‌تر از صرفاً یک `max@100` است.

### ۰.۲ max مهم است، اما «کاربر با max تعریف می‌شود» بیش از حد مطلق است

`max` شدیداً مستعد outlier است:

```
20 iterations:
  8.2, 8.5, 8.4, 8.3, 8.5, 8.4, ..., 8.6, 47.3  ← GC / scheduler / OS

max    = 47.3ms
median = 8.4ms
p95    ≈ 9ms
```

اگر chart را فقط بر اساس max بسازیم، ممکن است تصور کنیم workload ذاتاً ۵ برابر کند شده، در حالی که یک GC pause اتفاق افتاده.

**قاعده این Plan:**

```
p95    = metric اصلی scalability (tail latency — مقاوم به outlier)
max    = worst-case diagnostic (worst observed iteration)
median = central tendency (context)
```

در chart:

- **p95** خط اصلی scalability (برجسته)
- **max** به‌عنوان worst-case diagnostic (رنگ متمایز، ولی نه primary)
- **median** به‌عنوان context

**توضیح صریح:** `max` برای تشخیص worst observed execution است، نه تخمین latency معمول کاربر. `p95` مقاوم‌تر در برابر outlier است و به‌عنوان metric اصلی scalability استفاده می‌شود.

### ۰.۳ Scaling ≠ Single-Target Benchmark

بنچمارک فعلی (`benchmark`) یک target با N iteration می‌سنجد و یک `BenchmarkResult` می‌دهد. Scaling چندین target با تعداد متغیر را می‌سنجد و یک **سری** `BenchmarkResult` می‌دهد:

```
Single-Target Benchmark:
  target="IconPage", iterations=30  →  یک BenchmarkResult

Scaling Benchmark:
  counts=[0,10,20,...,100]
  هر count → یک BenchmarkResult
  خروجی → یک ScalingReport (آرایه‌ای از {count, benchmark})
```

این دو نباید با هم قاطی شوند. Scaling یک لایه بالاتر است: N بار single-target benchmark با پارامتر متغیر.

### ۰.۴ Heavy SVG باید بر اساس primitiveهای واقعی SVG تعریف شود، نه `result.length`

«سنگین» نباید نظر شخصی یا شمارش سطحی باشد. `heavyScore` باید بر اساس **primitiveهای واقعی SVG** محاسبه شود.

خروجی `definition.render()` یک آرایه از `CoreReactive.App` (یعنی `ClReactiveElement`) است. هر کدام یک `tagName` دارد. primitiveهای SVG که در `CoreReactive.App` موجودند:

```
svgPath, svgLine, svgCircle, svgEllipse, svgRect, svgPolygon,
svgText, svgG, svgFragment, svgDefs, svgFilter, svgFeGaussianBlur,
svgFeMerge, svgFeMergeNode, svgAnimate, svgAnimateTransform, svgAnimateMotion
```

`heavyScore` باید `tagName` هر element خروجی را بررسی کند و primitiveهای شکل‌ساز را بشمارد:

```ts
const SVG_PRIMITIVE_TAGS = new Set([
    "path", "line", "circle", "ellipse", "rect", "polygon",
    "polyline", "text", "g",  // شکل‌ساز/گروه‌بندی
]);

function heavyScore(definition: IIconDefinition): number {
    const result = definition.render({...} as any);
    if (!Array.isArray(result)) return 0;
    return result.reduce((sum, el) => {
        const tag = (el as any)?.tagName ?? "";
        return sum + (SVG_PRIMITIVE_TAGS.has(tag) ? 1 : 0);
    }, 0);
}
```

**نکته:** `svg` wrapper خودش جزو primitiveها حساب نمی‌شود — wrapper در `MtCreateIcon` اضافه می‌شود، نه در `definition.render()`. فقط محتوای داخلی SVG شمرده می‌شود.

اگر بعداً primitiveهای دیگری (مثل `svgUse` برای sprite) اضافه شوند، باید به `SVG_PRIMITIVE_TAGS` اضافه شوند. این یک لیست صریح و قابل‌تغییر است، نه یک فرض پنهان.

### ۰.۵ Selection باید deterministic باشد — sort پایدار با tie-breaker

اگر دو icon score یکسان داشته باشند و sort پایدار نباشد، selection می‌تواند بین environmentها (Node versions، test runs) تغییر کند.

```ts
const sorted = scored.sort((a, b) =>
    b.score - a.score ||
    (a.def.title as string).localeCompare(b.def.title as string)
);
```

`title` به‌عنوان tie-breaker استفاده می‌شود چون یک identifier پایدار روی definition است.

### ۰.۶ Workload باید صریحاً مشخص کند چه می‌سنجد

`benchmark()` فقط synchronous function execution را timing می‌کند. اگر بنویسیم:

```ts
benchmark(..., () => {
    CreateIcon(...);
    App.div({children});
});
```

این **creation cost** را می‌سنجد (ساخت `ClReactiveElement`، reactive setup، ساخت DOM element از طریق `document.createElement`). نه mount به صفحه، نه layout/paint.

**نام‌گذاری صریح:** در گزارش و chart، metric نام‌گذاری شود:

```
Heavy SVG Creation Scaling
```

نه «Render Scaling». چون `render()` در این context به `definition.render()` (تولید path descriptions) اشاره دارد، نه به render/mount صفحه. ambiguity خطرناک است.

اگر بعداً mount cost خواسته شد، Challenge جدا (با `appendChild` به document.body).

### ۰.۷ ۰ SVG به‌عنوان baseline/control

اگر فقط `10..100` را بگیریم، نمی‌دانیم هزینه ثابت (container creation، array allocation، framework overhead) چقدر است.

```
0 SVG   → 2ms   (baseline: container + framework overhead)
10 SVG  → 6ms
20 SVG  → 10ms
...
100 SVG → 42ms
```

آن‌وقت:

```
incremental cost ≈ (time - baseline) / count
```

خیلی معنادارتر از `time / count` می‌شود. این به سؤال اصلی کمک می‌کند: **آیا مشکل هزینه ثابت component است یا هزینه هر SVG؟**

`count=0` در `counts` array گنجانده شود. در workload، اگر `count=0` باشد، فقط container ساخته شود:

```ts
function heavySvgRenderFactory(heavy: IIconDefinition[]) {
    return (count: number) => () => {
        const children: any[] = [];
        for (let i = 0; i < count; i++) {
            children.push(UiIcons.CreateIcon(heavy[i % heavy.length]));
        }
        CoreReactive.App.div({ className: ["row"], children });
    };
}
```

`count=0` → `children=[]` → فقط `App.div` ساخته می‌شود. این baseline overhead را می‌سنجد.

### ۰.۸ دو workload: Unique و Repeated

این داده برای تصمیم بعدی بسیار ارزشمندتر از یک chart تنهاست:

```
سناریو A — Unique Heavy:
  هر SVG یک definition متفاوت دارد
  → اندازه‌گیری creation cost بدون cache benefit

سناریو B — Repeated Heavy:
  همه SVGها یک definition دارند
  → اگر سریع‌تر از A باشد، caching/definition reuse نقش دارد
```

تفسیر:

```
A: 100 → 100ms
B: 100 → 45ms
→ caching / definition reuse احتمالاً نقش بزرگی دارد

A: 100 → 100ms
B: 100 → 98ms
→ هزینه بیشتر در creation/render instance است، نه definition
```

این همان الگوی `scaling.test.ts` فعلی است (که فقط console.log می‌کند). Plan این را به chart می‌آورد.

### ۰.۹ Slope با linear regression + R²، نه دو نقطه

`slope = Δmax / Δcount` برای دو نقطه خوب است، ولی وقتی `0,10,20,...,100` داریم، بهتر است slope با linear regression محاسبه شود:

```
maxTime = a * count + b
slope = a (ms / SVG)
R² = goodness of fit
```

این خیلی اطلاعات بیشتری می‌دهد:

```
Linear (O(n)):
  10 → 4ms, 50 → 20ms, 100 → 42ms
  slope = 0.42 ms/SVG, R² = 0.97

Superlinear:
  10 → 4ms, 50 → 30ms, 100 → 95ms
  slope (linear fit) = 0.91 ms/SVG, R² = 0.89  ← R² پایین نشان‌دهنده non-linearity
```

R² پایین سیگنال قوی برای non-linear bottleneck است (GC pressure، scope accumulation، ...).

### Step ۱ — ScalingBenchmark (Module capability)

**هدف:** یک تابع reusable که benchmark را در چندین count اجرا می‌کند + slope/R² محاسبه می‌کند.

#### ۱.۱ ScalingReport type

در `core/types.ts` اضافه شود:

```ts
export interface ScalingPoint {
    count:     number;
    benchmark: BenchmarkResult;
}

export interface ScalingSlope {
    metric:  "median" | "p95" | "max";   // کدام آمار برای regression استفاده شد
    slope:   number;                      // ms per unit (ms/SVG)
    intercept: number;                    // baseline overhead (ms)
    rSquared: number;                     // goodness of fit [0,1]
}

export interface ScalingReport {
    target: string;
    series: ScalingPoint[];
    slopes: ScalingSlope[];   // برای median, p95, max
}
```

#### ۱.۲ benchmarkScaling

در `benchmarks/ScalingBenchmark.ts`:

```ts
export function benchmarkScaling(
    target:           string,
    counts:           number[],
    renderFnFactory:  (count: number) => () => void,
    config:           BenchmarkConfig = DEFAULT_CONFIG,
): ScalingReport {
    // Validation
    if (counts.length === 0) {
        throw new Error(`benchmarkScaling: counts must be non-empty`);
    }
    if (counts.some(c => c < 0)) {
        throw new Error(`benchmarkScaling: counts must be >= 0 (got negative)`);
    }
    for (let i = 1; i < counts.length; i++) {
        if (counts[i] <= counts[i-1]) {
            throw new Error(`benchmarkScaling: counts must be strictly increasing`);
        }
    }

    const series: ScalingPoint[] = [];
    for (const count of counts) {
        const fn = renderFnFactory(count);
        const result = benchmark(`${target}-${count}`, fn, config);
        series.push({ count, benchmark: result });
    }

    const slopes: ScalingSlope[] = [
        computeSlope(series, "median"),
        computeSlope(series, "p95"),
        computeSlope(series, "max"),
    ];

    return { target, series, slopes };
}
```

#### ۱.۳ computeSlope — linear regression

```ts
function computeSlope(
    series: ScalingPoint[],
    metric: "median" | "p95" | "max",
): ScalingSlope {
    const xs = series.map(p => p.count);
    const ys = series.map(p => p.benchmark[metric]);

    const n = xs.length;
    const sumX = xs.reduce((a, b) => a + b, 0);
    const sumY = ys.reduce((a, b) => a + b, 0);
    const sumXY = xs.reduce((s, x, i) => s + x * ys[i], 0);
    const sumX2 = xs.reduce((s, x) => s + x * x, 0);
    const sumY2 = ys.reduce((s, y) => s + y * y, 0);

    const denom = n * sumX2 - sumX * sumX;
    if (denom === 0) {
        return { metric, slope: 0, intercept: sumY / n, rSquared: 0 };
    }

    const slope = (n * sumXY - sumX * sumY) / denom;
    const intercept = (sumY - slope * sumX) / n;

    // R²
    const meanY = sumY / n;
    const ssTot = ys.reduce((s, y) => s + (y - meanY) ** 2, 0);
    const ssRes = ys.reduce((s, y, i) => {
        const pred = slope * xs[i] + intercept;
        return s + (y - pred) ** 2;
    }, 0);
    const rSquared = ssTot === 0 ? 1 : 1 - ssRes / ssTot;

    return { metric, slope, intercept, rSquared };
}
```

**Invariant:**
- ترتیب `series` با ترتیب `counts` یکسان باشد
- هر point یک `BenchmarkResult` کامل (median/p95/min/max) داشته باشد
- `slopes` همیشه ۳ مقدار (median, p95, max) داشته باشد
- `benchmarkScaling` در Registry ثبت نکند — فقط `ScalingReport` برمی‌گرداند. ثبت مسئولیت consumer است (همان الگوی `benchmark`)

#### ۱.۴ Ordering invariant در خود benchmark() — نه consumer

این invariant متعلق به `BenchmarkResult` است، نه SVG. باید در تست خود `BenchmarkEngine` باشد:

```
tests/perf/benchmark-engine.test.ts (یا تست موجود benchmark):
  for any benchmark result:
    expect(min).toBeLessThanOrEqual(median)
    expect(median).toBeLessThanOrEqual(p95)
    expect(p95).toBeLessThanOrEqual(max)
```

### Step ۳ — Scaling Chart در SvgReporter

#### ۳.۱ داده ورودی — target-specific chunks

```ts
// reportCollector.ts
export function saveScalingChunk(report: ScalingReport): void {
    try {
        if (!fs.existsSync(CHUNK_DIR)) fs.mkdirSync(CHUNK_DIR, { recursive: true });
        // target-specific filename: scaling-<target>.json
        const filePath = path.join(CHUNK_DIR, `scaling-${report.target}.json`);
        fs.writeFileSync(filePath, JSON.stringify(report), "utf-8");
    } catch (e) { /* ignore */ }
}

export function generateCombinedSvg(): void {
    const allReports: PerfReport[] = [];
    const scalingReports: ScalingReport[] = [];

    for (const name of ["pages", "stress", "components"]) {
        const filePath = path.join(CHUNK_DIR, `${name}.json`);
        if (fs.existsSync(filePath)) {
            const data = JSON.parse(fs.readFileSync(filePath, "utf-8")) as PerfReport[];
            allReports.push(...data);
        }
    }

    // خواندن همه scaling chunks (target-specific)
    if (fs.existsSync(CHUNK_DIR)) {
        for (const f of fs.readdirSync(CHUNK_DIR)) {
            if (f.startsWith("scaling-") && f.endsWith(".json")) {
                const filePath = path.join(CHUNK_DIR, f);
                const report = JSON.parse(fs.readFileSync(filePath, "utf-8")) as ScalingReport;
                scalingReports.push(report);
            }
        }
    }

    // ... clear chunks

    PerformanceRegistry.clear();
    for (const r of allReports) PerformanceRegistry.register(r);
    reportToSvg(undefined, scalingReports);
}
```

این API را single-target نکن — اگر فردا `component-scaling` یا `dom-scaling` اضافه شد، روی هم overwrite نمی‌شوند.


```
y-scale: time → y (معکوس، چون y به پایین)
  y(t) = chartTop + CHART_H - (t / maxTime) * CHART_H
```
