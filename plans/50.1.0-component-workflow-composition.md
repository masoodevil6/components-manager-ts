# پلن 50.1.0 — ترکیب Workflow کامپوننت‌های تو‌در‌تو

> **وضعیت:** پیشنهادی؛ آمادهٔ بررسی و اجرا  
> **دامنه:** اتصال workflow فرزند به workflow کامپوننت والد  
> **راهنمای مرجع:** `documents/guides/Basic/01-systems/AI_GUIDE_WORKFLOW.md`، `AI_GUIDE_EVENT.md` و `AI_GUIDE_SCOPE.md`  
> **پیش‌نیاز معماری:** workflow عمومی کامپوننت‌ها در `module_core/module_components/tools/workflow` و API اتصال Stepها در `module_core/module_event`

## ۱. مسئله و هدف

هر نمونهٔ کامپوننت workflow مستقل خودش را دارد و از `getComponentWorkflow()` قابل دریافت است. وقتی یک کامپوننت داخل محتوای کامپوننت دیگری ساخته می‌شود، Stepهای آن در حال حاضر به‌طور خودکار زیر workflow والد قرار نمی‌گیرند. در نتیجه درخت workflow ساختار واقعی UI را نشان نمی‌دهد؛ هرچند خود Stepهای فرزند ممکن است جداگانه در CoreEvent ثبت شده باشند.

هدف این پلن، ایجاد قرارداد عمومی و type-safe برای ترکیب workflowهاست تا:

- workflow فرزند با همان هویت Stepهای runtime به درخت والد متصل شود؛
- سلسله‌مراتب چندسطحی والد ← فرزند ← نوه قابل پیمایش و نمایش باشد؛
- هر نمونهٔ فرزند یک جایگاه پایدار در workflow والد داشته باشد؛
- اضافه‌شدن، تعویض، حذف و dispose شدن فرزند، رابطه و registry را سالم نگه دارد؛
- درخواست‌ها همچنان با همان `TStepRef`های قبلی کار کنند.

این پلن فعلاً هیچ تغییری در سورس اعمال نمی‌کند و رفتار eventهای فعلی را تغییر نمی‌دهد.

## ۲. وضعیت فعلی و محدودیت‌ها

- `ClComponentBase` workflow هر نمونه را در `_COMPONENT_WORKFLOW` نگه می‌دارد و `getComponentWorkflow()` ارائه می‌کند.
- هر کامپوننت Stepهای خودش را با `DefineWorkflow` می‌سازد.
- `CoreEvent.SubEvent(parent, key, child)` با `addChild`، Step موجود را به والد وصل می‌کند و همان هویت Step را حفظ می‌کند.
- `ClStep` یک والد دارد، اما `SubEvent` فعلی پیش از اتصال، رابطهٔ قبلی فرزند را بررسی یا جدا نمی‌کند.
- `CoreEvent.dispose(parent)` همهٔ نوادگان را بازگشتی dispose می‌کند؛ در حالی که خود کامپوننت فرزند نیز ممکن است در dispose خودش همان workflow را dispose کند.
- محل‌های ترکیب کامپوننت‌ها عموماً فرزند را مستقیماً می‌سازند و عنصرش را در DOM قرار می‌دهند. این نقطهٔ ترکیب باید workflow را هم ثبت کند.

بنابراین اتصال مستقیم `SubEvent` در هر renderer به‌تنهایی قرارداد کاملی نیست: باید namespace، کلید پایدار، مالکیت، جایگزینی و پاک‌سازی نیز استاندارد شوند.

## ۳. قرارداد پیشنهادی درخت

هر workflow والد شاخه‌ای رزروشده با نام `components` خواهد داشت. این شاخه فقط برای workflow کامپوننت‌های رندرشده درون آن والد است و با Stepهای محلی کامپوننت مخلوط نمی‌شود:

```text
parent workflow
├── click                         # رویداد محلی والد
└── components                    # شاخهٔ رزروشدهٔ composition
    ├── header.menu               # slot پایدار فرزند
    │   ├── select                # Stepهای محلی فرزند
    │   └── components            # composition داخلی همان فرزند
    │       └── item.delete
    └── form.email
        ├── inputChange
        └── inputBlur
```

کلید slot نام قابل‌خواندن و پایدار برای همان جایگاه در UI است؛ مانند `form.email` یا `header.menu`. برای فهرست‌های تکرارشونده از شناسهٔ پایدار آیتم استفاده شود و اگر شناسه‌ای وجود ندارد، index فقط به‌عنوان fallback پذیرفته شود. شناسهٔ تصادفی Component یا `identity.unique` به‌عنوان کلید نمایش استفاده نشود.

`components` کلید رزروشدهٔ workflow است. اگر Step محلی از قبل همین کلید را گرفته باشد، اتصال باید با خطای روشن متوقف شود؛ overwrite خاموش مجاز نیست.

## ۴. راه‌حل و API پیشنهادی

در `module_core/module_components/tools/workflow` یک API عمومی برای اتصال و جداکردن workflow ساخته شود. پیشنهاد نام‌ها:

```typescript
Attach_ComponentWorkflow(parentComponent, slotKey, childComponent);
Detach_ComponentWorkflow(parentComponent, slotKey);
```

همچنین یک helper در `ClComponentBase` فراهم شود تا rendererهای والد به‌جای اتصال دستی Step و سپس افزودن عنصر، از یک نقطهٔ واحد استفاده کنند:

```typescript
const emailInput = new ComponentInput(config, methods);
const emailInputElement = this.renderChildComponent("form.email", emailInput);
```

`renderChildComponent` باید workflow فرزند را زیر شاخهٔ `components` متصل کند و عنصر reactive فرزند را برای قرارگیری در خروجی والد برگرداند. helper عمومی امکان استفادهٔ مستقیم خارج از rendererهای داخلی را نیز فراهم کند.

### رفتار اتصال

1. والد از `getComponentWorkflow()` گرفته می‌شود.
2. شاخهٔ رزروشدهٔ `components` در صورت نیاز یک‌بار ساخته و با `CoreEvent.SubEvent` به workflow والد متصل می‌شود.
3. workflow فرزند با `slotKey` به این شاخه وصل می‌شود؛ هویت فرزند clone یا بازسازی نمی‌شود.
4. اتصال دوبارهٔ همان فرزند به همان slot باید idempotent باشد.
5. slot اشغال‌شده توسط workflow متفاوت نباید بی‌صدا جایگزین شود. جایگزینی باید ابتدا detach/dispose مشخص داشته باشد.
6. چرخهٔ والد↔فرزند و اتصال یک workflow به دو والد هم‌زمان باید رد شود یا با API صریح reparent انجام شود؛ اتصال ضمنی و مبهم مجاز نیست.

### نمونهٔ استفاده و حفظ هویت event

```typescript
const child = new ComponentInput(config, methods);
const childWorkflow = child.getComponentWorkflow();

this.renderChildComponent("form.email", child);

// درخواست همچنان از همان Step فرزند استفاده می‌کند:
CoreEvent.App.request(
    CoreEvent.requestMap([[childWorkflow.inputChange, payload]]),
    this.getComponentWorkflow(),
);
```

نام property در مثال با workflow واقعی همان کامپوننت جایگزین می‌شود. اتصال فقط parent-child graph را کامل می‌کند و مسیر request، dispatch یا response را تغییر نمی‌دهد.

## ۵. مالکیت، render مجدد و dispose

### مالکیت

- هر نمونهٔ کامپوننت در composition فقط یک والد workflow دارد.
- اتصال workflow، هویت Stepهای فرزند را حفظ می‌کند و child instance را clone نمی‌کند.
- رابطهٔ workflow نشان‌دهندهٔ مالکیت subtree در درخت CoreEvent است؛ چرخهٔ عمر DOM و منابع UI همچنان باید توسط renderer/والد مدیریت شود.
- قرار دادن یک instance در چند جایگاه یا چند والد هم‌زمان ممنوع است؛ برای چند نمایش باید چند instance ساخته شود.

### render مجدد و حذف فرزند

- اتصال‌ها با slot key نگه‌داری شوند تا render مجدد، فرزند موجود را دوباره با کلید تازه اضافه نکند.
- cleanup اتصال به Scope render والد وصل شود؛ در render مجدد، لینک قدیمی پیش از اتصال جدید جدا شود.
- حذف یک فرزند باید آن را از شاخهٔ `components` جدا کند و سپس مطابق قرارداد مالکیت، instance و workflow فرزند را dispose کند.
- جایگزینی در یک slot باید ترتیب مشخص `detach → dispose old → attach new` داشته باشد.
- جداکردن فرزند نباید Stepهای workflow والد یا slotهای دیگر را تغییر دهد.

### dispose دوباره

`CoreEvent.dispose(parent)` در حال حاضر subtree را بازگشتی dispose می‌کند. چون خود component child نیز مسیر dispose مستقل دارد، CoreEvent باید در این پلن disposal را idempotent کند یا `ClComponentBase` همهٔ disposalها را از یک مسیر idempotent عبور دهد. فراخوانی مجدد روی Step حذف‌شده نباید registry را دوباره تغییر دهد، خطا بسازد یا شمارندهٔ lifecycle را نادرست افزایش دهد.

## ۶. تغییرات برنامه‌ریزی‌شده

### ۶.۱. CoreEvent

- بررسی و تکمیل قرارداد `SubEvent` برای اتصال idempotent و جلوگیری از orphan شدن فرزند.
- افزودن API detach امن و بدون dispose برای re-render و جایگزینی.
- افزودن محافظت در برابر cycle، self-attachment، collision و attach هم‌زمان به چند parent.
- idempotent کردن `CoreEvent.dispose` و حفظ قرارداد فعلی disposal بازگشتی.
- حفظ هویت واقعی Stepها، registry، emit handlerها و قرارداد `requestMap`.

### ۶.۲. ابزار workflow کامپوننت

- افزودن helperهای public attach/detach در پوشهٔ `tools/workflow` و export از barrelها.
- افزودن نوع نمایندهٔ کامپوننت workflow-aware برای ورودی helperها.
- افزودن `renderChildComponent(slotKey, child)` به base عمومی کامپوننت یا ابزار composition مشترک.
- ثبت اتصال‌ها به Scope والد و جلوگیری از detach شدن اشتباه attachment جدید توسط cleanup قدیمی.
- توسعهٔ typeهای workflow برای دسترسی type-safe به شاخهٔ رزروشده، بدون از دست دادن generic workflow اختصاصی کامپوننت.

### ۶.۳. مهاجرت محل‌های composition

ابتدا یک inventory از محل‌هایی تهیه شود که child component را می‌سازند و `getElement()` یا `getReactiveElement()` را مستقیماً در محتوای والد می‌گذارند. سپس همهٔ محل‌های داخلی به helper مشترک مهاجرت کنند. اولویت مهاجرت:

1. کامپوننت‌های سادهٔ دارای child مثل `ComponentInput` و `ComponentCollapse`؛
2. compositeهای چندفرزندی مثل `ComponentInputGroup` و `ComponentLayout`؛
3. سازنده‌ها و containerها مثل `ComponentElementCreator`، `ComponentLayoutCreator` و `ComponentPage`؛
4. سایر rendererهای داخلی و مثال‌هایی که انتظار درخت composition دارند.

کامپوننتی که به‌صورت `HTMLElement` خام یا `CoreReactive.App` داده شده و نمونهٔ Component آن در دسترس نیست، workflow قابل اتصال ندارد؛ این حالت باید مستند و از قرارداد auto-attach مستثنا شود.

### ۶.۴. نمایش درخت

- serializer workflow باید شاخهٔ `components` و slotهای آن را بدون flatten کردن حفظ کند.
- `ComponentJsonTree` باید نام slot و ساختار workflow فرزندان را نشان دهد.
- درخت فعلی صفحهٔ جزئیات کامپوننت پس از تکمیل composition، به‌عنوان نمایش نهایی زنجیرهٔ تو‌در‌تو بررسی شود.

## ۷. گزینه‌های بررسی‌شده

### اتصال ضمنی با context سراسری

رد می‌شود. renderهای reactive، callbackها و ساخت child در زمان‌های مختلف باعث می‌شوند مالک والد از context موقت به‌طور قابل‌اعتماد تشخیص داده نشود.

### کپی‌کردن children فرزند به والد

رد می‌شود. کپی یا بازسازی Stepها هویت `TStepRef`های مورد استفاده در `requestMap` و emitها را می‌شکند.

### `SubEvent` دستی در هر component renderer

به‌تنهایی رد می‌شود. باعث تکرار منطق namespace، slot key، collision، re-render و cleanup در هر کامپوننت می‌شود. `SubEvent` می‌تواند پیاده‌سازی داخلی helper مشترک باقی بماند.

## ۸. اعتبارسنجی و آزمون‌های پذیرش

### آزمون‌های CoreEvent و helper

- اتصال یک فرزند، شاخهٔ `components` و slot مورد انتظار را ایجاد کند.
- اتصال مجدد همان فرزند به همان slot، گره تکراری نسازد.
- اتصال یک فرزند به دو parent یا ایجاد cycle، به‌صورت کنترل‌شده رد شود.
- collision در نام `components` یا slot، workflow موجود را overwrite نکند.
- detach فقط slot درخواست‌شده را حذف کند و Stepهای child را در صورت انتخاب detach-only زنده نگه دارد.
- dispose والد، تمام نوادگان را پاک کند؛ dispose فرزند قبل یا بعد از والد نتیجهٔ یکسان و بدون شمارش تکراری داشته باشد.
- درخواست با Step فرزند پس از اتصال همچنان به همان identity و emit handler برسد.
- دو instance از یک کلاس، درخت‌ها و Stepهای مستقل داشته باشند.

### آزمون‌های integration

- `ComponentInputGroup` درختی شامل workflow خودش و workflow هر input فرزند بسازد.
- `ComponentCollapse`، workflow اجزای داخلی خودش را زیر slotهای مجزا نشان دهد.
- حذف/جایگزینی child در render پویا، Step یا emit قدیمی در registry باقی نگذارد.
- مثال‌های `ComponentLayout` و `ComponentPage` ساختار تو‌در‌توی workflow را در `ComponentJsonTree` نشان دهند.
- تعامل‌های فعلی componentها، request/response و eventهای header/form بدون تغییر باقی بمانند.

## ۹. معیار پایان

پلن زمانی کامل است که هر composition داخلی با helper استاندارد ثبت شود، درخت CoreEvent همان ساختار والد/فرزند UI را با Step identity اصلی منعکس کند، و dispose/re-render هیچ orphan، duplicate یا Step stale در registry باقی نگذارد. استفاده از Category API و constructor فعلی باید backward-compatible بماند؛ اتصال workflow فقط برای compositionهایی الزامی شود که قصد دارند workflow فرزند را در workflow والد قابل مشاهده کنند.

## ۱۰. خارج از محدوده

- تغییر شکل payloadهای request/response یا ترتیب dispatchها؛
- بازطراحی همهٔ factoryهای Step یا حذف workflow مستقل کامپوننت؛
- اتصال خودکار workflow برای DOM خام یا ReactiveElementهایی که Component instance در دسترس ندارند؛
- تغییر UI یا رفتار `ComponentJsonTree` فراتر از نمایش شاخه‌های تو‌در‌تو.
