# پلن 39.1.0 — انتقال `ComponentWidget` به ساختار جدید

> **وضعیت:** پیاده‌سازی شد؛ تزریق HTML پاسخ و سازگاری محتوای پویا خارج از محدوده است
> **نسخه پلن:** 39.1.0
> **منبع Legacy:** `last/Older/components.js`، بخش `ComponentWidgetBase` و `ComponentWidget`
> **راهنما:** `documents/guides/component-create.md`
> **مقصد:** `src/framework/module_ui/module_components/lists/componentWidget/`
> **دسته‌بندی هدف:** `fetch → widget`
> **API هدف:** `UiCategory.UI.Fetch.Widget(config, methods, identity)`

## 1. هدف و محدوده

انتقال `ComponentWidget` به معماری ComponentManager و ساختار declarative فعلی. `ComponentBorder` ریشه‌ی بصری Widget است و تمام محتوای آن، شامل محتوای اولیه/slot، پیام‌ها، loading، خطا و آیکون بیشتر، در محتوای همین Border قرار می‌گیرد؛ هیچ‌کدام sibling بیرونی Border نیستند. تنظیمات `ComponentBorder` از Props خود Widget قابل کنترل و به Border منتقل می‌شوند. Widget در صورت داشتن URL از `UtilTools.Fetch.Request` استفاده می‌کند و پاسخ 404 را با `ComponentWebCode` و امکان retry نمایش می‌دهد.

این پلن فقط خود `ComponentWidget`، ثبت Component و Category آن، ترجمه‌ها و مثال‌هایش را پوشش می‌دهد. انتقال `ComponentLayout`، `Stepper`، Reportها یا پروژه‌های مصرف‌کننده در این نسخه انجام نمی‌شود.

## 2. شواهد و رفتار Legacy

سورس اصلی در `last/Older/components.js`، حدود خطوط 4852 تا 5154 قرار دارد.

- `prop_layoutContent` محتوای اولیه‌ی امن است؛ معماری جدید slot `body` ندارد و در نبود این prop محتوای اولیه خالی است.
- محتوای Widget داخل `ComponentBorder` قرار می‌گیرد. بخش داخلی شامل پیام‌ها، `ComponentLayout`، `Component404` و `ComponentLoading` است.
- `prop_widgetClass` و `prop_widgetStyles` در Legacy به `prop_structureClass` و `prop_structureStyles` مربوط به ComponentBorder داده می‌شوند؛ `prop_widgetMinHeight` نیز `min-height` را در styleهای structure آن override می‌کند. در API جدید، تنظیمات اختصاصی ComponentBorder نیز از ComponentWidget دریافت و به همان ComponentBorder فرستاده می‌شوند.
- `prop_fetch.url` و `prop_fetch.data` به helper قدیمی `tools_submit.fetcth` داده می‌شوند. اگر URL خالی باشد، callback پاسخ با مقدار `<!--empty-component-->` فراخوانی می‌شود.
- پیش از درخواست، `fn_onGetNewToken` در صورت وجود فراخوانی می‌شود.
- پس از پاسخ، `response.html` داخل `ComponentLayout` قرار می‌گیرد و `fn_onGetResponse(response, requestData)` فراخوانی می‌شود.
- پاسخ می‌تواند `script` یا `script_src` داشته باشد؛ نسخه قدیمی آن‌ها را با `eval` اجرا می‌کند و `__params` و `__request` را در اختیار کد قرار می‌دهد.
- `prop_btnMore_icon`, `prop_btnMore_show` و `prop_btnMore_link` به ComponentBorder قدیمی داده می‌شوند؛ آیکون در گوشه Border نمایش داده می‌شود و لینک را در تب جدید باز می‌کند.
- `prop_error404` و `prop_minHeight` در `call_fetchWidget` خوانده می‌شوند، ولی در `_COMPONENT_PATTERN` تعریف نشده‌اند؛ در نتیجه قرارداد declarative قابل اتکایی برای آن‌ها در Legacy وجود ندارد.
- مقادیر پیش‌فرض `prop_widgetClass` و `prop_widgetStyles` در Pattern با fallbackهای render یکسان نیستند. پیاده‌سازی جدید باید برای هرکدام فقط یک مقدار پیش‌فرض مستند داشته باشد.

### مصرف‌کنندگان Legacy مشاهده‌شده

- `last/Older/Stepper.js` برای افزودن Widget فرزند، `call_getComponentLayout().call_addElement(...)` را استفاده می‌کند.
- بخش گزارش در `last/Older/components.js`، `ComponentWidget` را با `prop_layoutContent` و `prop_fetch` می‌سازد و از `fn_onGetResponse` برای پردازش داده پاسخ استفاده می‌کند.
- `last/Older/index.html` نمونه‌های Widget ثابت و fetchدار دارد.

## 3. قرارداد API پیشنهادی

### Props

| Prop | نوع پیشنهادی | پیش‌فرض | رفتار |
|---|---|---|---|
| `prop_layoutContent` | `CoreReactive.App \| HTMLElement \| component instance \| string \| null` | `null` | محتوای typed آغازین؛ رشته به‌صورت متن امن نمایش داده شود، نه HTML اجرایی. در معماری جدید slot `body` وجود ندارد؛ در نبود مقدار، بخش محتوا خالی می‌ماند. |
| `prop_widgetClass` | `string[]` | `[]` | alias سازگاری Legacy برای کلاس‌های structure مربوط به ComponentBorder داخلی. |
| `prop_widgetStyles` | `Record<string, string>` | `{"min-height":"80px"}` | alias سازگاری Legacy برای styleهای structure مربوط به ComponentBorder داخلی؛ بدون mutate کردن شیء ورودی. |
| `prop_widgetMinHeight` | `string \| null` | `null` | alias Legacy؛ در صورت مقدار داشتن، `min-height` را پس از ادغام styleهای structure Border override کند. مقدار باید CSS length معتبر باشد. |
| `prop_fetch` | `{url: string; data?: TFetchRequestData \| unknown}` | `{url: "", data: null}` | درخواست اولیه؛ URL خالی یعنی fetch خودکار انجام نشود. |
| `prop_btnMore_icon` | `IIconDefinition \| null` | `null` | آیکون اختیاری لینک بیشتر. |
| `prop_btnMore_show` | `boolean` | `false` | نمایش یا پنهان‌کردن آیکون بیشتر. |
| `prop_btnMore_link` | `string \| null` | `null` | در صورت مقدار داشتن، لینک با رفتار Legacy در تب جدید باز شود. |

Props باید با `Define_ComponentProp<T>` و metadata ترجمه‌شده تعریف شوند. Propهای پایه از `ComponentStructureTrait` حفظ شوند.

### تنظیمات ComponentBorder در API مربوط به Widget

ComponentWidget باید تنظیمات ComponentBorder داخلی را با namespace `prop_componentBorder*` در API خود در دسترس قرار دهد و آن‌ها را بدون تغییر معنایی به همان Border منتقل کند؛ این الگو با `ComponentForm` هماهنگ است و با Props پایه‌ی ساختار ComponentWidget تداخل ندارد. از metadata و typeهای ComponentBorder استفاده شود تا defaultها و قرارداد دو کامپوننت از هم واگرا نشوند.

- Props پایه‌ی میزبان Border: `prop_componentBorderSelector`, `prop_componentBorderAppend`, `prop_componentBorderClassList`, `prop_componentBorderElementStyles`, `prop_componentBorderShow`, `prop_componentBorderStructureClass`, `prop_componentBorderStructureStyles`.
- محتوای Border: `prop_componentBorderContentSize`, `prop_componentBorderContentColor`, `prop_componentBorderContentColorHover`, `prop_componentBorderContentBackgroundColor`, `prop_componentBorderContentBackgroundColorHover`.
- ظاهر Border: `prop_componentBorderColor`, `prop_componentBorderColorHover`, `prop_componentBorderClass`, `prop_componentBorderStyles`, `prop_componentBorderType`, `prop_componentBorderOpacity`, `prop_componentBorderWidth`, `prop_componentBorderMinWidth`.
- فلش Border: `prop_componentBorderArrowType`, `prop_componentBorderArrowWidth`, `prop_componentBorderArrowPosition`.
- کنترل گوشه‌ها و ضلع‌ها: `prop_componentBorderTopLeftRadiusHas`, `prop_componentBorderTopRightRadiusHas`, `prop_componentBorderBottomLeftRadiusHas`, `prop_componentBorderBottomRightRadiusHas`, `prop_componentBorderTopHas`, `prop_componentBorderRightHas`, `prop_componentBorderBottomHas`, `prop_componentBorderLeftHas`.
- `ComponentBorder.prop_content` نقطه‌ی اتصال داخلی Widget است: Widget محتوای ترکیبی خود را در آن قرار می‌دهد؛ محتوای قابل‌تأمین توسط مصرف‌کننده از `prop_layoutContent` می‌آید.

Props پایه‌ی `prop_structureClass` و `prop_structureStyles` فقط لایه‌ی بیرونی خود ComponentWidget را تنظیم می‌کنند. تنظیمات Border از `prop_componentBorder*` می‌آیند. اگر `prop_componentBorderStructureClass`/`prop_componentBorderStructureStyles` با alias قدیمی `prop_widgetClass`/`prop_widgetStyles` هم‌زمان تعیین شوند، propهای جدید اولویت دارند؛ `prop_widgetMinHeight` همچنان override نهایی `min-height` روی structure داخلی Border است.

### Methods و fetch lifecycle

- `BEFORE_FETCH`: پیش از درخواست فراخوانی شود؛ جایگزین امن و تایپ‌شده‌ی `fn_onGetNewToken` باشد.
- `GET_RESPONSE`: هنگام شروع درخواست، Promise درخواست را در اختیار مصرف‌کننده بگذارد.
- `RESPONSE`: پس از پاسخ موفق، `RESULT_EXP`، پاسخ parseشده و داده‌ی درخواست را به‌صورت payload مشخص ارائه کند.
- `RETRY_CLICK`: با کلیک retry اجرا شود و همان مسیر fetch را با مقادیر جاری Props دوباره آغاز کند.

در قرارداد جدید ترتیب آرگومان‌ها به شکل نام‌دار و از طریق `Methods.ts` مشخص شود. برای مهاجرت مصرف‌کننده‌های Legacy، تفاوت با ترتیب positional تابع `fn_onGetResponse(response, requestData)` مستند شود.

درخواست فقط با متد کمکی `UtilTools.Fetch.Request` از ماژول `util.tools.fetch` انجام شود (پیاده‌سازی فعلی: `src/framework/module_util/module_tools/methods/fetch/MTFetchRequest.ts`). ComponentWidget با import از `@/util_tools` این متد را فراخوانی کند و lifecycle آن را از callbackهای `onLoading`, `onNotFound`, `onMessages`, `onResponse` و `onError` به state و child componentهای خودش وصل کند. `prop_fetch.data` به ورودی typed helper نگاشت شود تا ساختارهای `{type, data}` و `{formData, data}` قابل انتقال باشند؛ Widget نباید helper fetch جداگانه یا `fetch` مستقیم بسازد.

## 4. تصمیم‌های رفتاری نهایی‌شده

### پاسخ HTML و اجرای Script

ساختار فعلی پروژه محتوای `HTMLElement`, `CoreReactive.App` و component instance را می‌پذیرد، اما `ComponentLayout` جدید یا API امن تبدیل رشته‌ی HTML به component در مخزن موجود نیست. Legacy پاسخ `response.html` را با `innerHTML` تزریق می‌کند و `response.script`/`response.script_src` را با `eval` اجرا می‌کند.

تصمیم اجرایی:

1. پاسخ خام از `RESPONSE` به مصرف‌کننده برسد؛ `response.html` خودکار به DOM تزریق نشود.
2. string در `prop_layoutContent` به‌صورت متن نمایش داده شود؛ محتوای UI از نوع `HTMLElement`, `CoreReactive.App` یا component instance باشد.
3. `script` و `script_src` در Widget اجرا نشوند. هیچ `eval`, تزریق script یا `innerHTML` در پیاده‌سازی جدید اضافه نشود.
4. در صورت نیاز به محتوای HTML مورد اعتماد، قرارداد امن و جداگانه‌ای برای TrustedHTML/ساختار پویا تعریف شود؛ این پلن آن قرارداد را اختراع نمی‌کند.

این مرز در پیاده‌سازی 39.1.0 اعمال شده است؛ پشتیبانی از HTML مورد اعتماد یا محتوای پویای پاسخ به قرارداد و پلن جداگانه نیاز دارد.

### افزودن محتوای Widget در زمان اجرا

`ComponentLayout` در ساختار جدید پیدا نشد. `Stepper` قدیمی به `call_getComponentLayout().call_addElement()` وابسته است، اما این پلن `Stepper` را تغییر نمی‌دهد و ComponentWidget جدید نباید API قدیمی global-style را بی‌مدرک بازسازی کند.

برای سازگاری کامل با Stepper لازم است در پلن جداگانه یکی از این دو مسیر طراحی شود:

- انتقال `ComponentLayout` به ساختار جدید و تعریف API مدیریت محتوای فرزند؛ یا
- مهاجرت Stepper به state/Observable محتوای Widget و حذف فراخوانی imperative قدیمی.

تا آن زمان، پلن حاضر فقط محتوای اولیه و callback پاسخ را پوشش می‌دهد.

## 5. ساختار Schema

تمام Schemaهای پایه از `ComponentStructureTrait` بیایند و در ابتدای تعریف قرار گیرند.

```text
COMPONENT
STRUCTURE
ROOT: part-widget
└── BORDER: part-widget-border                         (ComponentBorder؛ ریشه‌ی بصری)
    └── CONTENT: part-widget-body                      (محتوای prop_content خود Border)
        ├── MESSAGES: part-widget-messages             (ComponentMessages)
        ├── LAYOUT: part-widget-content                (محتوای prop_layoutContent)
        ├── ERROR: part-widget-error                   (ComponentWebCode)
        ├── LOADING: part-widget-loading               (ComponentLoading)
        └── MORE: part-widget-more                     (ComponentIcon اختیاری)
```

- `part-border` اصلی با `position: relative` رندر شود؛ مانند `ComponentForm`، این مقدار در styleهای `ComponentBorder` پس از ادغام styleهای سفارشی تثبیت شود تا containing block overlayها باشد.
- Props ساختار و ظاهر ComponentBorder از ComponentWidget کنترل و به نمونه‌ی داخلی Border پاس داده شوند؛ برای Props موجود ComponentBorder default موازی تعریف نشود.
- محتوای initial، پیام‌ها، لایه‌های loading و 404 و آیکون بیشتر همگی داخل Border بمانند.
- `ComponentLoading` و `ComponentWebCode` مثل `ComponentForm` با `position: absolute; left: 0; top: 0; width: 100%; height: 100%` روی Border قرار گیرند. WebCode در صورت نیاز `overflow: hidden` داشته باشد تا محتوای overlay از Border بیرون نزند.
- خود لایه‌ی full-size جابه‌جا نشود؛ اگر محتوای دیداری Loading/WebCode به مرکز نیاز دارد، مرکزکردن با `left: 50%; top: 50%; transform: translate(-50%, -50%)` روی محتوای داخلی انجام شود، نه روی لایه‌ای که باید کل Border را بپوشاند.
- آیکون بیشتر با `ComponentIcon` ساخته شود، فقط وقتی `prop_btnMore_show` true است رندر شود و در نبود لینک غیرفعال یا بدون handler باشد.
- Schema فقط part و props را تعریف کند؛ composition و rendering در متدهای کلاس Component بماند.

## 6. Workflow و lifecycle

در `Step.ts` یک Step مستقل برای fetch، retry و پاسخ تعریف شود. Step پیش از render در constructor ساخته و به identity والد متصل شود.

1. محتوای اولیه از `prop_layoutContent` خوانده شود؛ در نبود آن بخش محتوای آغازین خالی بماند.
2. اگر `prop_fetch.url` خالی است، درخواست شبکه انجام نشود و محتوای اولیه حفظ شود.
3. اگر URL موجود است، `BEFORE_FETCH` اجرا، پیام خطای قبلی پاک و `ComponentLoading` فعال شود.
   لایه‌ی Loading باید داخل `ComponentBorder` و به‌صورت absolute با مختصات صفر و اندازه‌ی 100٪ نمایش داده شود؛ محتوای آن در مرکز overlay قرار گیرد.
4. `UtilTools.Fetch.Request` درخواست را انجام دهد؛ 404 باعث خاموش‌شدن loading و نمایش `ComponentWebCode` شود.
   WebCode نیز داخل همان Border با مختصات صفر و اندازه‌ی 100٪ overlay شود و محتوای داخلی آن در مرکز قرار بگیرد.
5. retry، WebCode را ببندد و fetch را از نو آغاز کند.
6. پاسخ موفق و request data از طریق `RESPONSE` منتشر شود؛ محتوای UI خودکار از HTML/string پاسخ ساخته نشود.
7. خطاهای شبکه و پاسخ ناموفق از مسیر callbackهای Fetch به `ComponentMessages` بروند و loading در همه مسیرها خاموش شود.
8. `dispose()` تمام child componentها، Step، Observableها و scopeهای متعلق به Widget را آزاد کند.

1. ComponentWidget در `src/framework/module_ui/module_components/lists/index.ts` ثبت شود.

3. callable `Widget` با `CreateCategoryComponent` در `fetch/widget/index.ts` صادر شود.
4. Category Widget به children دسته‌ی Fetch افزوده و از `fetch/index.ts` و مسیر عمومی `ui/index.ts` در دسترس باشد.
5. کلیدهای category، component، props، schemas، methods و examples در `Keys.ts` و ترجمه‌های `En.ts`/`Fa.ts` ثبت شوند.

- `ComponentBorder`
- `ComponentMessages`
- `ComponentWebCode`

## 8. Examples

- **Default:** محتوای ثابت به‌صورت component/HTMLElement و تنظیم class/style/minHeight.
- **Fetch:** پیکربندی درخواست و callback پاسخ با URL خالی؛ مثال هیچ درخواست شبکه‌ای ارسال نمی‌کند.
- مثال‌ها باید نحوه‌ی استفاده از `prop_btnMore_show` و `prop_btnMore_link` را نشان دهند، اگر آیکون لینک بیشتر در API نگه داشته شود.
- name و description تمام مثال‌ها از `Keys` ترجمه شوند.

## 9. معیارهای پذیرش و بررسی

- `ComponentManager` و مسیر `UiCategory.UI.Fetch.Widget` کامپوننت را کشف کنند.
- ComponentBorder ریشه‌ی بصری باشد و همه‌ی بخش‌های محتوا داخل آن رندر شوند؛ هیچ پیام، loading، خطا یا آیکونی بیرون Border قرار نگیرد.
- `part-border` دارای `position: relative` باشد و overlayهای Loading/WebCode داخل آن با position absolute، `left/top: 0` و width/height صددرصد قرار گیرند؛ جابه‌جایی مرکز با transform روی محتوای داخلی باشد.
- تنظیمات ساختار، رنگ، کلاس، اندازه، فلش و ضلع/گوشه‌های ComponentBorder از Props مربوط به ComponentWidget قابل کنترل و به Border داخلی منتقل شوند.
- `prop_layoutContent` به‌صورت typed/متن امن رندر شود؛ slot قدیمی در معماری جدید در دسترس نیست.
- URL خالی باعث درخواست خودکار نشود؛ URL معتبر فقط از `UtilTools.Fetch.Request` در `util.tools.fetch` استفاده کند و callbackهای helper وضعیت loading، 404، message و response را مدیریت کنند.
- شروع درخواست، 404، retry، پاسخ موفق، خطای شبکه و dispose به‌درستی loading/message/error را هماهنگ کنند.
- یک Widget نتواند Observable، Step یا child component Widget دیگری را پس از dispose فعال نگه دارد.
- هیچ پاسخ HTML یا Script از شبکه با `innerHTML`/`eval` خودکار اجرا نشود.
- `npm run build:app` موفق باشد؛ مثال Fetch برای نمایش پیکربندی از URL خالی استفاده کند و درخواست بیرونی نداشته باشد.

## 10. خارج از محدوده

- انتقال `ComponentLayout` و تغییر `Stepper` یا Reportهای قدیمی.
- اجرای `script` یا دریافت و اجرای `script_src` از پاسخ شبکه.
- تزریق خودکار رشته‌ی `response.html` به DOM.
- تغییر `tools_submit.fetcth` قدیمی، Laravel یا backendها.
- تبدیل فراخوانی‌های `window.ComponentWidget` و اصلاح مصرف‌کنندگان Legacy.

## 11. جمع‌بندی قرارداد

ComponentWidget جدید یک container مبتنی بر ComponentBorder است که محتوای typed را نمایش می‌دهد و چرخه‌ی fetch، loading، messages، 404 و retry را با ابزارهای فعلی پروژه مدیریت می‌کند. API پاسخ به شکل typed Methods ارائه می‌شود. اجرای کد سرور و تفسیر خودکار HTML خام حفظ نمی‌شود. سازگاری Stepper با `call_getComponentLayout().call_addElement()` نیازمند تصمیم و پلن مستقل برای مدیریت محتوای پویا است.
