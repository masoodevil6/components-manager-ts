# 12.2.4 — رفع bottleneck باقی‌مانده: cloneNode

> **هدف:** کاهش هزینه `cloneNode(true)` که در measurement فعلی هزینه قابل‌توجه CreateIcon است.
> بعد از 12.2.3 + fast-path، D1 ≈ D7 (49.86 vs 49.89ms/100) — یعنی اختلاف overhead غیر-cloneNode در حد خطای اندازه‌گیری است.

---

## ۱. وضعیت فعلی

### داده‌های diagnostic بعد از 12.2.3 + fast-path

| Test | median | توضیح |
|------|--------|-------|
| **D1** (CreateIcon heaviest ×100) | 49.86ms | کل CreateIcon |
| **D7** (raw cloneNode ×100) | 49.89ms | cloneNode تنها |
| **D1-D7** (overhead) | **~0ms** | کل overhead حذف شد ✅ |
| D2 (median ×100) | 5.32ms | آیکون سبک |
| D8 (wrapper ×100) | 1.92ms | ClReactiveElement constructor |

**نتیجه:** در measurement فعلی، هزینه قابل‌توجه CreateIcon در حد خطای اندازه‌گیری با `cloneNode(true)` برابر است. اختلاف D1 و D7 حدود 0.03ms است که در benchmarkهای jsdom با نویز GC قابل صرف‌نظر است. این به معنی اثبات ریاضی «۱۰۰٪» نیست، اما نشان می‌دهد overhead غیر-cloneNode عملاً ناچیز شده است.

### bottleneck

`cloneNode(true)` روی SVG با 30 primitive = **0.50ms/icon** در jsdom.
هزینه خطی با تعداد primitive است: هر primitive ≈ 0.016ms.

---

## ۲. استراتژی‌ها

### Strategy D: innerHTML serialization cache

**ایده:** به‌جای `cloneNode(true)`، innerHTML عنصر cache شده را یک‌بار serialize کن و برای هر clone، `<svg>` جدید بساز و `innerHTML` را set کن.

```
build cache:
  1. buildStaticSvg → svgElement
  2. cachedInnerHTML = svgElement.innerHTML    ← یک‌بار serialize

per clone:
  1. svg = createElementNS("svg")              ← ساخت فقط root element
  2. svg.innerHTML = cachedInnerHTML            ← parse کل children در یک عملیات
  3. set attrs (xmlns, role, fill, aria-label, viewBox, width, height)
  4. CoreReactive.App.svg({ existingElement: svg })
```

**فرضیه:** در jsdom، `innerHTML` parse ممکن است سریع‌تر از `cloneNode(true)` باشد چون:
- cloneNode به‌صورت بازگشتی هر node را clone می‌کند (30 بار)
- innerHTML یک‌بار string را parse می‌کند

**ریسک:** تست قبلی (12.2.3) نشان داد innerHTML 1.6× کندتر بود. اما آن تست قبل از fast-path بود و شرایط متفاوتی داشت. باید دوباره سنجیده شود.

**مزیت:** اگر سریع‌تر باشد، به complexity وابسته نیست — حتی برای آیکون‌های سبک هم بهبود دارد.

**معیار موفقیت:** D1 < 40ms (یعنی >20% بهبود نسبت به 49.86ms)

### Strategy E: Shallow clone + innerHTML

**ایده:** ترکیب cloneNode(shallow) + innerHTML:

```
per clone:
  1. cloned = cached.svgElement.cloneNode(false)   ← shallow: فقط <svg> با attrs، بدون children
  2. cloned.innerHTML = cachedInnerHTML             ← children را از string set کن
  3. CoreReactive.App.svg({ existingElement: cloned })
```

**فرضیه:** `cloneNode(false)` بسیار ارزان است (فقط یک node) و attrs را کپی می‌کند. `innerHTML` هم children را در یک عملیات set می‌کند. ممکن است از هر دو روش (cloneNode(true) و innerHTML-only) سریع‌تر باشد.

**مزیت:** attrs به‌صورت خودکار کپی می‌شوند — نیازی به set کردن دستی نیست.

### Strategy F: Lazy observables (رد شده — فعلاً)

D1-D7 ≈ 0ms است. یعنی constructor overhead (3 CoreObservable + 6 addEventListener) عملاً ناچیز است. lazy کردن آن بازدهی ندارد.

### Strategy G: کاهش complexity آیکون‌های سنگین (scope جدا — 12.2.4-B)

> **توجه:** این استراتژی optimization موتور ساخت آیکون نیست، بلکه تغییر complexity داده ورودی است.
> اگر آیکون از 30 primitive به 14 تبدیل شود، طبیعی است که benchmark بهتر شود.
> این باید از بهینه‌سازی CreateIcon تفکیک شود تا attribution نتایج روشن بماند.

**ایده:** آیکون‌های با score بالا (PaymentTransaction=30, PaymentDeposit=29) را بازطراحی کنیم تا با تعداد primitive کمتر همان شکل را تولید کنند.

مثال: چند `<path>` ساده → یک `<path>` با `d` پیچیده.

| آیکون | score فعلی | هدف | روش |
|--------|-----------|------|-----|
| PaymentTransaction | 30 | <15 | ترکیب pathها |
| PaymentDeposit | 29 | <15 | ترکیب pathها |
| PaymentWithDrawal | 29 | <15 | ترکیب pathها |

**مزیت:** cloneNode هزینه خطی با primitive count دارد. کاهش از 30 به 15 = 50% بهبود.

**ریسک:** نیاز به بازطراحی بصری آیکون — ممکن است ظاهر تغییر کند. نیاز به تایید طراحی.

**معیار موفقیت:** heaviest score < 15 → D1 < 25ms

**تفکیک scope:**
- **12.2.4-A:** آیا روش ساخت/کپی DOM سریع‌تر می‌شود؟ (Strategy D/E)
- **12.2.4-B:** اگر نه، آیا complexity آیکون‌های واقعی غیرضروری است؟ (Strategy G)

### Strategy H: Pre-clone pool (رد شده)

Pre-clone N کپی در idle time و serve از pool. پیچیدگی lifecycle management بالا و در jsdom بازده ندارد چون cloneNode همان عملیات است.

> **شرط بازگشت به 12.2.4-B:** فقط اگر profiler واقعی (browser) نشان دهد SVG complexity
