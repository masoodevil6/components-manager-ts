# Plan 8.2.7 — SubEvent: قرارداد سلسله‌مراتبی Events در CoreEvent

> **پیش‌نیاز:** Plan 8.2.5 (Reactive Element Getters)
> **هدف:** تعریف رابطه رسمی **SubEvent** بین Parent Step و Child Step — جدا کردن Contract معماری از Implementation

---

## ۱. انگیزه و مشکل

### ۱.۱ مشکل فعلی

`MessagesStep` یک **ثابت module-level** است:

```typescript
// Step.ts — ایستا، بین همه instanceها مشترک
export const MessagesStep = CoreEvent.Step({
    children: {
        message: CoreEvent.Step({ ... }),
        icon:    CoreEvent.Step({ ... }),
    }
});
```

پیامدها:

1. **همه instanceها همان `identity` (symbol) را به اشتراک می‌گذارند** — `registerEmit` آخرین handler را overwrite می‌کند.
2. **Step داخلی از جریان اصلی ایزوله است** — والد نمی‌تواند `parentStep → messages → message` را target کند.
3. **هیچ مالکیت صریحی وجود ندارد** — وقتی Component حذف می‌شود، Stepها در رجیستری باقی می‌مانند (memory leak).

### ۱.۲ چرا راه‌حل‌های قبلی کافی نیستند

- **Multi-Handler Emit (8.2.6 — رد شد):** O(n) روی هر Request، شکستن مفهوم یکتایی Step، memory leak در dispose.
- **emit روی parent div با arrow function:** از نظر data flow درست است، ولی هنوز Step داخلی از جریان اصلی ایزوله است و چند instance تداخل دارند.

### ۱.۳ هدف واقعی

> مرز **CoreEvent → SubEvent → Component** را قفل کنیم.
> اگر این مرز درست باشد، بخش بزرگی از معماری Event بعدی خودش سر جای خود می‌نشیند.

---

## ۲. قرارداد معماری (Contract)

### ۲.۱ مفهوم SubEvent

**SubEvent** رابطه رسمی بین یک **Parent Step** و یک **Child Step** است.

```
Parent Step
    │
    └── SubEvent
          │
          └── Child Step
```

- **Parent Step** متعلق به لایه بیرونی است (والد Component).
- **Child Step** متعلق به Component Instance است.
- **SubEvent** خود یک Step نیست — یک **رابط** (binding) است که دو Step را سلسله‌مراتبی متصل می‌کند.

### ۲.۲ Event Identity Contract

قوانین غیرقابل مذاکره:

- **Step identity متعلق به Component Instance است.** هر Instance Step خودش را دارد — نه ثابت مشترک.
- **Step نباید در Render Cycle ساخته شود.** Step در constructor Component ساخته می‌شود — قبل از هر render.
- **هر Component Instance حداکثر یک SubEvent Scope اصلی دارد.** چند SubEvent تو در تو مجاز است، ولی یک Scope ریشه‌ای واحد.
- **SubEvent باید lifecycle کامپوننت را دنبال کند.** وقتی Component ساخته می‌شود، SubEvent ثبت می‌شود؛ وقتی Component حذف می‌شود، SubEvent dispose می‌شود.
- **حذف Component باید باعث dispose شدن subtree مربوط به آن شود.** همه Stepهای زیر آن SubEvent از رجیستری پاک شوند.
- **Parent فقط از API عمومی Step/SubEvent برای دسترسی به Child استفاده می‌کند.**
- **دسترسی مستقیم به ساختار داخلی `children` ممنوع است.** هیچ Component یا لایه بالاتر نباید `step.children[key] = ...` را mutate کند.

### ۲.۳ Ownership، Registration و Disposal

| مسئولیت | مالک | توضیح |
|:---|:---|:---|
| **ساخت Child Step** | Component Instance | در constructor — قبل از render |
| **ساخت SubEvent binding** | Component Instance | بعد از ساخت Child Step |
| **ثبت در رجیستری** | `CoreEvent.App` | `registerAll` بازگشتی — خودکار در factory |
| **دسترسی Parent → Child** | `CoreEvent.App` API | `App.getChild(parent, "messages")` یا `parent.messages` (read-only Proxy) |
| **Disposal** | Component Instance | متد `dispose()` در Component — کل subtree پاک می‌شود |

## ۳. API عمومی

### ۳.۱ گزینه A — `CoreEvent.SubEvent` مستقل

```typescript
// ساخت Child Step (مستقل)
const messagesStep = CoreEvent.Step({
    children: {
        message: CoreEvent.Step({ ... }),
        icon:    CoreEvent.Step({ ... }),
    }
});

// اتصال به Parent — رابط رسمی
CoreEvent.SubEvent(
    parentStep,    // ← Parent Step
    "messages",    // ← key (نام child در parent)
    messagesStep   // ← Child Step
);
```

### ۳.۲ گزینه B — `CoreEvent.Step` با option `parent`

```typescript
const messagesStep = CoreEvent.Step(
    {
        children: {
            message: CoreEvent.Step({ ... }),
            icon:    CoreEvent.Step({ ... }),
        }
    },
    {
        parent: parentStep,   // ← Parent Step
        key:    "messages",   // ← نام child در parent
    }
);
```

### ۳.۳ تصمیم

**گزینه A** — `CoreEvent.SubEvent` مستقل — چون:

1. **تفکیک مسئولیت:** ساخت Step (identity) و اتصال آن (relationship) دو عملیات مجزا هستند.
2. **قابلیت ترکیب:** می‌توان Step را اول ساخت، بعد (در شرایط متفاوت) به Parentهای متفاوت متصل کرد.
3. **خوانایی:** `CoreEvent.SubEvent(parent, key, child)` صریح‌تر از option پنهان در factory است.

### ۳.۴ API نهایی

```typescript
// CoreEvent/index.ts

/** ساخت Step — بدون اتصال به Parent */
export const Step = <TDef extends TStepDefinition>(definition: TDef): TStepInstance<TDef> => { ... };

/** اتصال Child Step به Parent Step — رابط رسمی SubEvent */
export const SubEvent = (
    parent: TStepRef,
    key:    string,
    child:  TStepRef
): void => { ... };

/** دسترسی Parent به Child — read-only */
export const getChild = (parent: TStepRef, key: string): TStepRef | null => { ... };

/** Disposal بازگشتی — کل subtree */
export const dispose = (step: TStepRef): void => { ... };
```

### ۳.۵ چه چیزی در API نیست

- ❌ `step.children[key] = ...` — mutate مستقیم ممنوع
- ❌ `step.children` به‌عنوان public API — ساختار داخلی، فقط از طریق `getChild` قابل دسترسی
- ❌ `App.emits` — فقط `App.request` و `App.registerEmit`

## ۴. مثال Dynamic — MessageList

این مثال نشان می‌دهد **dynamic بودن تعداد Stepها یک ویژگی سیستم است، نه نشانه بد بودن Component.**

### ۴.۱ سناریو

یک `MessageList` با N پیام. هر پیام یک `ComponentMessages` نیست — هر پیام یک **SubEvent Scope** مستقل دارد با ساختار یکسان:

```
MessageList (Parent Step)
│
├── Message#1
│    └── SubEvent#1
│         ├── message
│         └── icon.close
│
├── Message#2
│    └── SubEvent#2
│         ├── message
│         └── icon.close
│
└── Message#N
     └── SubEvent#N
          ├── message
          └── icon.close
```

### ۴.۲ جریان

1. `MessageList` ساخته می‌شود با `ParentStep` (جریان اصلی).
2. برای هر پیام (در constructor — نه در render cycle):
   - یک `ChildStep` با ساختار `{ message, icon.close }` ساخته می‌شود.
   - `CoreEvent.SubEvent(parentStep, "message_1", childStep)` ثبت می‌شود.
   - `identity` هر ChildStep یکتاست — تداخلی نیست.
3. وقتی کاربر روی `icon.close` پیام #۲ کلیک می‌کند:
   - Request به `childStep_2.message` ارسال می‌شود — فقط handler همان instance اجرا می‌شود.
   - پیام #۲ از `prop_messages` حذف می‌شود.
   - `dispose(childStep_2)` صدا زده می‌شود — کل subtree از رجیستری پاک می‌شود.
4. وقتی کل `MessageList` حذف می‌شود:
   - `dispose(parentStep)` بازگشتی — همه SubEventها و ChildStepها پاک می‌شوند.

### ۴.۳ نکته کلیدی

> تعداد Stepها در زمان اجرا dynamic است. این **قابلیت سیستم** است — هر پیام identity خودش را دارد، هر SubEvent lifecycle مستقل دارد، و disposal بازگشتی memory leak نمی‌گذارد.

## ۵. Implementation — قرارداد، نه جزئیات

این بخش **قرارداد implementation** را مشخص می‌کند — نه کد نهایی. جزئیات دقیق در زمان اجرا تصمیم گرفته می‌شوند، ولی باید این مرزها رعایت شوند.

### ۵.۱ `ClStep` — کپسوله‌سازی ساختار داخلی

- `children` باید **private** (یا protected) شود — دسترسی مستقیم از بیرون ممنوع.
- متد **public** `addChild(key, child)` برای اتصال رسمی — این تنها راه mutate `children` است.
- متد **public** `getChild(key)` برای دسترسی read-only.
- متد **public** `removeChild(key)` برای قطع اتصال.
- متد **public** `dispose()` برای disposal بازگشتی — کل subtree.

### ۵.۲ `CoreEvent.SubEvent` — رابط رسمی

```typescript
export const SubEvent = (parent: TStepRef, key: string, child: TStepRef): void => {
    // استفاده از API عمومی ClStep — نه mutate مستقیم
    (parent as ClStep).addChild(key, child as ClStep);
};
```

### ۵.۳ `CoreEvent.getChild` — دسترسی read-only

```typescript
export const getChild = (parent: TStepRef, key: string): TStepRef | null => {
    return (parent as ClStep).getChild(key) ?? null;
};
```

### ۵.۴ `CoreEvent.dispose` — disposal بازگشتی

```typescript
export const dispose = (step: TStepRef): void => {
    // ۱. disposal بازگشتی همه children
    // ۲. حذف از App.registry
    // ۳. حذف از App.emits
    // ۴. قطع اتصال از parent (اگر دارد)
};
```

### ۵.۵ `Step.ts` — از ثابت به factory

```typescript
// قبل — ثابت مشترک
export const MessagesStep = CoreEvent.Step({ ... });

// بعد — factory که در constructor صدا زده می‌شود
export const createMessagesStep = (): TStepInstance<...> =>
    CoreEvent.Step({
        children: {
            message: CoreEvent.Step({ ... }),
            icon:    CoreEvent.Step({ ... }),
        }
    });
```

### ۵.۶ `ComponentMessagesBase` — SubEvent در constructor

```typescript
constructor(componentName, elId, identity, step) {
    super(componentName, elId);

    this._COMPONENT_UNIQUE = identity?.unique ?? null;
    this._COMPONENT_EMIT   = identity?.emit ?? null;
    this._COMPONENT_STEP   = step ?? null;

    // SubEvent: اگر Parent Step و Child Step هر دو هستن، اتصال رسمی
    if (step && identity?.unique) {
        CoreEvent.SubEvent(identity.unique, componentName, step);
    }
}

/** Disposal — وقتی Component از DOM حذف می‌شود */
dispose(): void {
    if (this._COMPONENT_STEP) {
        CoreEvent.dispose(this._COMPONENT_STEP);
    }
    super.dispose?.();
}
```

### ۵.۷ `ComponentMessages` — Step dynamic در constructor

```typescript
constructor(config?, methods?, identity?) {
    // Step داخلی در constructor ساخته می‌شود — نه در render cycle
    const step = createMessagesStep();

    super("messages", null, identity, step);

    // نرمال‌سازی prop_messages و render...
}
```

## ۶. مراحل اجرا

- [ ] `children` → private/protected

- [ ] متد `removeChild(key)` — قطع اتصال
- [ ] متد `dispose()` — disposal بازگشتی

### Phase ۲ — CoreEvent API عمومی

- [ ] `CoreEvent.SubEvent(parent, key, child)` — رابط رسمی

- [ ] `CoreEvent.dispose(step)` — disposal بازگشتی (registry + emits + parent link)
- [ ] `CoreEvent.Step` factory — `registerAll` بازگشتی برای children

## ۷. مرزهای قفل‌شده

این مرزها بعد از این Plan غیرقابل تغییر هستند:

```
┌─────────────────────────────────────────────────────────┐
│  Parent Layer (Component والد)                          │
│                                                         │
│  CoreEvent.Step(definition)         → ساخت Parent Step  │
│  CoreEvent.getChild(parent, key)    → دسترسی read-only   │
│  CoreEvent.App.request([...])       → ارسال Request      │
│                                                         │
├─────────────────────────────────────────────────────────┤
│  Component Layer (ComponentMessages)                    │
│                                                         │
│  createMessagesStep()               → ساخت Child Step   │
│  CoreEvent.SubEvent(parent, key, child) → اتصال رسمی    │
│  CoreEvent.dispose(childStep)       → disposal           │
│                                                         │
├─────────────────────────────────────────────────────────┤
│  CoreEvent Internal (ClStep / ClEventDispatcher)        │
│                                                         │
│  ClStep.addChild / getChild / removeChild / dispose     │
│  → کپسوله‌سازی ساختار داخلی — API عمومی فقط              │
│  → هیچ لایه بالاتر مستقیماً children را mutate نمی‌کند   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```
