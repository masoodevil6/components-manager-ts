# PLAN: بازطراحی ComponentStructure و ایجاد Definition به‌عنوان شناسنامه Component

## هدف

ساختار `ComponentStructure` باید به سه مفهوم مشخص تفکیک شود:

```text
Definition
    ↓
Component Identity / Metadata / Selection

ComponentStructure
    ↓
Runtime Base Component

Schemas / Props / Methods
    ↓
Component Configuration & Rendering
```

هدف این Phase فقط refactor نیست؛ باید پایه‌ای ایجاد شود که بعداً بتوان از آن برای:

* Component Manager
* انتخاب Component در محیط گرافیکی
* نمایش نام و توضیحات
* دسته‌بندی Componentها
* تشخیص نوع Component
* ساخت Component به‌صورت دستی
* Workflow / Step integration

استفاده کرد.

---

# 1. معماری هدف

ساختار نهایی:

```text
componentStructure/
│
├── Definition.ts
├── Props.ts
├── Schemas.ts
├── Methods.ts
├── ComponentStructure.ts
└── index.ts
```

مسئولیت هر فایل:

```text
Definition.ts
    │
    ├── Identity
    ├── name
    ├── description
    ├── category
    ├── component type
    └── اطلاعات لازم برای Component Manager
             │
             ▼
ComponentStructure.ts
    │
    ├── Runtime Component
    ├── Constructor
    └── Definitionهای اجرایی
             │
             ├── Props
             ├── Schemas
             └── Methods
```

---

# 2. Definition نباید Renderer باشد

اصل مهم:

```text
Definition ≠ Runtime
```

`Definition.ts` نباید شامل:

```text
❌ DOM
❌ CoreReactive.App
❌ Observable
❌ render
❌ executeSchemaPart
❌ renderContentComponent
```

باشد.

Definition فقط باید اطلاعاتی داشته باشد که یک سیستم خارجی بتواند بدون instantiate کردن Component از آن استفاده کند.

مثلاً:

```ts
export const Definition = {
    type: "structure",
    name: ...,
    description: ...,
    category: ...,
};
```

ساختار دقیق Definition باید بر اساس قرارداد موجود پروژه تعیین شود و در این Phase نباید اطلاعاتی به‌صورت حدسی اضافه شود.

---

# 3. Definition باید قابل استفاده توسط Component Manager باشد

Component Manager در آینده باید بتواند تقریباً چنین کاری انجام دهد:

```text
Component Registry
        │
        ├── ComponentButton
        │      └── Definition
        │
        ├── ComponentInput
        │      └── Definition
        │
        └── ComponentTable
               └── Definition
```

و بدون ساختن Instance بتواند:

```text
Component
├── Name
├── Description
├── Category
├── Type
└── قابلیت‌های قابل نمایش
```

را تشخیص دهد.

بنابراین Definition باید مستقل از lifecycle مربوط به Runtime باشد.

# 5. انتقال Definitionهای Runtime

سه بخش فعلی:

```text
_COMPONENT_PATTERN
_COMPONENT_SCHEMA
_COMPONENT_METHODS
```

به `ComponentStructure` منتقل شوند.

اما این‌ها با `Definition.ts` اشتباه نشوند.

این سه مورد:

```text

```

هستند، در حالی که:

```text
Definition.ts
```

شناسنامه Component است.

# 6. Schemas همچنان مسئول Rendering باشند

معماری فعلی:

```text

    ↓
Schema.method
    ↓
executeSchemaPart()
```

حفظ شود.

بنابراین:

```text
Schema
├── part
├── props
├── method
├── name
└── description
```

همچنان قرارداد Schema باقی می‌ماند.

`renderManagerComponent` در `ComponentStructure` استفاده نشود.

# 7. renderManagerComponent فقط fallback باقی بماند

در این Phase:

```text
ClComponentBase.renderManagerComponent
```

حذف نشود.

همچنان به‌عنوان مسیر legacy/fallback باقی بماند.

اما:

```text
ComponentStructure.renderManagerComponent
```

وجود نداشته باشد.

مسیر اصلی:

```text
executeSchemaPart()
        │
        ├── Schema.method
        │       ↓
        │    Renderer
        │
        └── no method
                ↓
        renderManagerComponent()
                ↓
             legacy
```

باشد.

# 8. Definition و Schema Metadata از هم تفکیک شوند

نباید هر دو سیستم یک مفهوم را دوباره تعریف کنند.

مثلاً:

```text
Definition
    → Component چیست؟

Schema
    → Component از چه Parts تشکیل شده؟

Props
    → چه ورودی‌هایی دارد؟

Methods
    → چه رفتارهایی expose می‌کند؟

Renderer
    → چگونه روی DOM اجرا می‌شود؟
```

این تفکیک باید در Guideهای پروژه نیز به‌عنوان یک قانون معماری ثبت شود.

---

# 9. Component Manager آینده

ساختار باید برای Registry آینده مناسب باشد:

```text
ComponentRegistry
        │
        ▼
Component Definition
        │
        ├── identity
        ├── metadata
        ├── category
        └── factory/reference
```

Component Manager نباید مجبور شود برای نمایش لیست Componentها، Component را instantiate کند.

به بیان ساده:

```text
Manager
    ↓
Definition
    ↓
انتخاب Component
    ↓
Factory / Constructor
    ↓
Runtime Instance
```

نه:

```text
Manager
    ↓
new Component()
    ↓
حدس زدن اینکه این چیست
```

---

# 10. وابستگی Definition

`Definition.ts` تا حد امکان dependency بسیار کمی داشته باشد.

به‌خصوص:

```text
Definition
    ❌ نباید به ComponentStructure وابسته باشد
    ❌ نباید به Renderer وابسته باشد
    ❌ نباید DOM بسازد
```

ترجیحاً dependency graph:

```text
Definition
    ↑
ComponentStructure
    ↑
ComponentButton
```

باشد، نه:

```text
Definition
    ↔
ComponentStructure
```

هدف جلوگیری از circular dependency است.

# 12. Definition برای Componentهای فرزند قابل توسعه باشد


نباید برای آینده abstraction پیچیده ساخته شود.

# 15. عدم ورود Unique و Workflow در این Phase

`unique`، Workflow و Step architecture در این Phase طراحی یا پیاده‌سازی نشوند.

اما Definition باید به شکلی طراحی شود که در آینده بتواند Component را به‌عنوان یک عنصر قابل انتخاب/شناسه‌دار در Component Manager معرفی کند.

## اصل معماری این Phase

چهار مفهوم نباید با یکدیگر مخلوط شوند:

```text
Definition
    = Component چیست؟

Props
    = Component چه ورودی‌هایی دارد؟

Schema
    = Component از چه بخش‌هایی تشکیل شده؟

Runtime
    = Component چگونه اجرا و Render می‌شود؟
```

این Phase باید این مرزبندی را تثبیت کند تا Component Manager آینده روی یک قرارداد پایدار ساخته شود.
