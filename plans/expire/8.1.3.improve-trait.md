# Plan 8.1.3 — حذف Wrapper اضافی و تثبیت خروجی Reactive ComponentStructure

## ۰. هدف

حذف `<section>` اضافی ایجادشده توسط `ComponentStructureTrait` بدون ایجاد coupling جدید و بدون تغییر غیرضروری در APIهای موجود.

هدف نهایی:

```text
Component
   ↓
ComponentStructureTrait
   ↓
ComponentStructure
   ↓
Reactive Component
```

و نه:

```text
Component
   ↓
Trait
   ↓
HTMLElement
   ↓
section wrapper
   ↓
Reactive Component
```

---

## ۱. اصل معماری

این پلن نباید صرفاً برای حذف یک wrapper، قرارداد عمومی `ComponentStructure.create()` را تغییر دهد.

ابتدا باید مشخص شود:

> `ComponentStructure.create()` در معماری جدید دقیقاً چه چیزی را باید برگرداند؟

قرارداد مطلوب:

```ts
ComponentStructure.create(...)
    → CoreReactive.App
```

اما این تغییر فقط در صورتی مجاز است که با قرارداد عمومی Component و تمام مصرف‌کنندگان سازگار باشد.

بنابراین تغییر return type یک **تصمیم معماری** است، نه صرفاً یک refactor محلی.

**قانون مهم:** `ComponentStructure.create()` باید در نهایت بر اساس قرارداد Component جدید خروجی بدهد، نه بر اساس implementation داخلی `ClComponentBase`.

اگر `create()` برای تولید `CoreReactive.App` مجبور شود از `ClComponentBase.getReactiveElement()` استفاده کند، عملاً Trait را از Legacy جدا نکرده‌ایم، فقط Legacy را پشت یک متد پنهان کرده‌ایم.

---

## ۲. بررسی API فعلی

قبل از هر تغییر، تمام مصرف‌کنندگان واقعی:

```ts
ComponentStructure.create(...)
```

باید جستجو شوند.

همچنین این موارد بررسی شوند:

```text
ComponentStructure.Component.create
UiCategory.UI.Basic.ComponentStructure
CreateCategoryComponent
getElement()
getReactiveElement()
```

هدف این بررسی:

- مشخص شدن تمام call siteها
- مشخص شدن نوع خروجی مورد انتظار هر call site
- مشخص شدن اینکه آیا `create()` بخشی از API عمومی محسوب می‌شود
- مشخص شدن تفاوت بین:
  - Component instance
  - HTMLElement
  - CoreReactive.App

### ۲.۱ تفکیک `create()` و `new ComponentStructure()`

باید مشخص شود `create()` واقعاً factory مربوط به چه abstractionی است:

```text
create()
  ↓
آیا قرار است CoreReactive.App برگرداند؟
  ↓
آیا قرار است HTMLElement برگرداند؟
  ↓
آیا قرار است Component instance برگرداند؟
```

`create()` و `new ComponentStructure()` دو مسیر متفاوت هستند و نباید بدون دلیل خروجی یکسان داشته باشند.

### ۲.۲ بررسی خود `ComponentStructure` قبل از تغییر `create()`

قبل از تغییر `create()` باید خود `ComponentStructure` را ببینیم.

چون از همین متن هنوز نمی‌شود با قطعیت گفت `getReactiveElement()` واقعاً abstraction درست برای این کار است یا فقط یک bridge قدیمی.

بنابراین Phase 1 باید شامل بررسی کامل `ComponentStructure` باشد:

- [ ] constructor signature
- [ ] `_COMPONENT_CONTENT` چیست و چه نوعی دارد
- [ ] `getReactiveElement()` آیا API رسمی است یا Legacy bridge
- [ ] `getElement()` آیا API رسمی است یا Legacy bridge
- [ ] رابطه بین `create()` و constructor

## ۳. قرارداد خروجی

### ۳.۱ خروجی مطلوب

اگر بررسی API نشان دهد که `create()` صرفاً برای ساخت representation قابل Render استفاده می‌شود، قرارداد جدید می‌تواند:

```ts
static create(...): CoreReactive.App
```

باشد.

اما اگر مصرف‌کننده‌ای واقعاً به:

```ts
HTMLElement
```

وابسته باشد، تغییر مستقیم `create()` مجاز نیست.

در این حالت باید APIهای زیر از هم تفکیک شوند:

```text
ComponentStructure.create()
ComponentStructure.createElement()
ComponentStructure.createReactive()
```

نام‌گذاری نهایی بر اساس API موجود پروژه انتخاب شود.

### ۳.۲ قانون جدایی از Legacy

اگر `create()` برای تولید `CoreReactive.App` مجبور شود از `ClComponentBase.getReactiveElement()` استفاده کند، این یعنی:

```text
create()
  ↓
ClComponentBase internals
  ↓
_COMPONENT_CONTENT
  ↓
getReactiveElement()
```

این همان دور زدن abstraction است که در بخش ۴ ممنوع شده.

پس قبل از تغییر `create()`، باید مشخص شود آیا API رسمی Component (نه ClComponentBase) خروجی Reactive ارائه می‌دهد یا خیر.

اگر نه، مسیر B (API جداگانه) باید انتخاب شود تا `create()` موجود شکسته نشود.

---

## ۴. قانون مهم: Trait نباید API را دور بزند

Trait نباید برای رسیدن به خروجی Reactive مستقیماً وارد internals شود.

ترتیب صحیح:

```text
Trait
  ↓
Public Component API
  ↓
ComponentStructure
  ↓
Reactive representation
```

نه:

```text
Trait
  ↓
ClComponentBase internals
  ↓
_COMPONENT_CONTENT
  ↓
getReactiveElement()
```

بنابراین این الگو باید بررسی شود:

```ts
instance.getReactiveElement()
```

اگر `getReactiveElement()` متعلق به Legacy/Base implementation باشد، استفاده مستقیم از آن در Trait مجاز نیست.

Trait باید به API رسمی Component جدید متکی باشد.

---

## ۵. حذف Wrapper

پس از تثبیت قرارداد خروجی، Trait باید از:

```ts
return CoreReactive.App.part("section", {
    children: [structEl],
});
```

به:

```ts
return structEl;
```

تغییر کند.

یعنی:

```ts
renderContent(
    component,
    content,
): CoreReactive.App {

    // ... Error Contract validation ...

    return ComponentStructure.create({
        classList:            classList.get(),
        styles:               styles.get(),
        prop_show:            prop_show.get(),
        prop_structureClass:  prop_structureClass.get(),
        prop_structureStyles: prop_structureStyles.get(),
        content,
    });
}
```

### ۵.۱ قانون مهم: Trait مجاز نیست خودش wrap کند

`return structEl` فقط زمانی مجاز است که `structEl` طبق Output Contract نهایی، یک `CoreReactive.App` باشد.

اگر `ComponentStructure.create()` همچنان `HTMLElement` بدهد (مسیر B انتخاب شود و API Reactive جداگانه‌ای تعریف نشود)، Trait **نباید** خودش `HTMLElement` را به `CoreReactive.App` تبدیل یا wrap کند.

```text
ComponentStructure.create()
        │
        ├── CoreReactive.App
        │       ↓
        │   return structEl        ✅
        │
        └── HTMLElement
                ↓
          ❌ Trait نباید خودش wrap کند
```

این الگو **ممنوع** است:

```ts
const element = ComponentStructure.create(...);   // HTMLElement

return CoreReactive.App.part("section", {          // ❌ همان wrapper قبلی با اسم جدید
    children: [element]
});
```

اگر `create()` خروجی `HTMLElement` بدهد و API Reactive رسمی وجود نداشته باشد، Trait باید متوقف شود و مسئله به پلن بعدی منتقل شود — نه اینکه wrapper با نام جدید اختراع شود.

انسان‌ها در بازسازی معماری استعداد عجیبی برای اختراع دوباره همان مشکل دارند.

## ۷. رفتار Props

حذف wrapper نباید رفتار Props را تغییر دهد.

باید بررسی شود:

```text
classList
    ↓
ComponentStructure root

styles
    ↓
ComponentStructure root

prop_show
    ↓
Structure rendered section

prop_structureClass
    ↓
Structure rendered section

prop_structureStyles
    ↓
Structure rendered section
```

به‌خصوص:

```text
prop_show: false
```

نباید wrapper Trait را مخفی کند و Structure را باقی بگذارد یا برعکس.

## ۸. Lazy Render

این تغییر نباید Lazy Render را تغییر دهد.

تعریف عملی Lazy Render:

```text
new Component(...)
       ↓
constructor
       ↓
NO render
       ↓
getElement()/render request
       ↓
render()
       ↓
renderContentComponent()
       ↓
Trait.renderContent()
       ↓
ComponentStructure.create()
```

ممنوع:

```ts
constructor(...) {
    super(...);

    ComponentStructure.create(...); // ❌
}
```

هدف این است که حذف wrapper هیچ تغییری در زمان اجرای Render ایجاد نکند.

Error Contract پلن 8.1.2 حفظ می‌شود.


اگر در Pattern ثبت نشده باشند، باید خطای صریح ایجاد کنند.

ممنوع:


## ۱۰. Type Safety

این refactor نباید به بهانه حذف wrapper، Type Safety را کاهش دهد.

مخصوصاً:

```ts
getObservable("prop_show")
```

ممکن است:

```ts
App<any> | null
```

برگرداند.

بنابراین:

- Error Contract حفظ شود.
- Cast غیرضروری اضافه نشود.
- `any` جدید وارد Trait نشود.
- اگر API رسمی Type-safe وجود دارد، همان API استفاده شود.

این پلن مسئول حل کامل Type Safety `getObservable()` نیست.

اما نباید وضعیت فعلی را بدتر کند.

## ۱۱. Event Contract

حذف wrapper می‌تواند مسیر event delegation، `data-part-name` یا parent relationship را تغییر دهد.

فقط «Event نشکنند» کافی نیست — باید مشخص شود event روی کدام node باید باقی بماند.

### ۱۱.۱ بررسی مورد نیاز

قبل از حذف wrapper:

- [ ] آیا event listener روی wrapper ❶ ثبت شده است؟
- [ ] آیا `data-part-name` روی wrapper ❶ وجود دارد که Event system به آن وابسته است؟
- [ ] آیا event delegation از parent به wrapper ❶ وابسته است؟
- [ ] آیا `ComponentIcon` identity events روی wrapper ❶ یا روی ❷ ثبت می‌شود؟

### ۱۱.۲ قرارداد Event بعد از حذف

بعد از حذف wrapper ❶، eventها باید روی node مورد انتظار قرارداد `ComponentStructure` باقی بمانند.

اگر قبل از حذف، eventها روی wrapper ❶ بودند، این یعنی wrapper حذف‌شدنی نیست و باید حفظ شود.

برای حذف یک DOM wrapper، نباید بدون بررسی قرارداد یک API عمومی را تغییر داد.

ترتیب تصمیم:

```text
Audit
  ↓
Determine Output Contract
  ↓
Check Consumers
  ↓
Choose Safe API
  ↓
Remove Trait Wrapper
  ↓
Compile
  ↓
Runtime Verify
```

هدف نهایی:

```text
Component
    ↓
ComponentStructureTrait
    ↓
ComponentStructure
    ↓
CoreReactive.App
```

بدون:

```text
Trait
    ↓
Legacy internals
    ↓
HTMLElement
    ↓
Artificial wrapper
```

و:

```text
create()
    ↓
ClComponentBase internals
    ↓
getReactiveElement()
```

ممنوع — `create()` باید بر اساس قرارداد Component جدید خروجی بدهد، نه بر اساس implementation داخلی `ClComponentBase`.
