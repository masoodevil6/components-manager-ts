# Challenge 12.2.1 — IconPage Performance Optimization

> **پیش‌نیاز:** Plan 12.2 (Performance & Observability Module)
> **هدف:** بهبود کارایی رندر IconPage — Attribution → Optimization → Verification
> **الگو:** بهینه‌سازی در لایه Icon Creation Pipeline — بدون تغییر API
> **محدوده:** فقط `MtCreateIcon` و لایه Icon. تغییر `ClIconPage` در Challenge جدا (12.2.2)

---

## ۰. اصول این Challenge

### ۰.۱ قبل از Optimization باید Attribution داشته باشیم

الان می‌دانیم:

```
IconPage
  median ≈ 47 ms
  DOM ≈ 1026
  heap ≈ +9.24 MB
```

و می‌دانیم:

```
componentIcon (single)
  median ≈ 0.46 ms
  p95 ≈ 0.87 ms
```

این تضاد کلیدی است:

```
Single Icon benchmark
        ↓
     ~0.5 ms

80+ icons
        ↓
     ~47 ms

پس scale behavior مشکل دارد.
```

اما هنوز نمی‌دانیم ۴۷ms دقیقاً کجا مصرف شده:

```
IconPage
 ├─ component construction
 ├─ icon definition.render()
 ├─ reactive graph creation
 ├─ SVG node creation
 ├─ attribute binding
 ├─ DOM insertion
 ├─ layout/style
 ├─ translation
 └─ GC / memory allocation
```

**قاعده:** قبل از اندازه‌گیری، متهم را دستگیر نکنیم.

### ۰.۲ Scaling Slope — خطی یا غیرخطی

یک معیار حیاتی که فعلاً نداریم:

```
Icons   Render
1       0.5ms
10      5ms
25      12ms
50      24ms
100     47ms
200     94ms
```

اگر تقریباً خطی باشد: `T(n) ≈ base + n × iconCost` → مشکل per-icon cost است.

اما اگر:

```
1   → 0.5
10  → 2
25  → 4
50  → 10
100 → 47
200 → 150
```

آن‌وقت یک **non-linear bottleneck** داریم — مثلاً GC pressure، scope accumulation، یا چیزی که با scale بدتر می‌شود.

این تفاوت برای انتخاب optimization فوق‌العاده مهم است.

### ۰.۳ Memory — Allocation Pressure نه Leak

`+9.24MB` برای ۸۰ آیکون عدد قابل توجهی است.

ولی `heapDelta` به تنهایی نمی‌گوید leak داریم. ممکن است:

```
allocate
   ↓
render
   ↓
GC بعداً
```

بنابراین در این Challenge:

- `heapDelta` را به‌عنوان **allocation pressure** گزارش می‌کنیم، نه memory leak
- اگر بعد از optimization heap delta کاهش یافت، یعنی allocation کمتر شده
- اگر ثابت ماند، یعنی retained memory است و نیاز به بررسی جدا دارد

### ۰.۴ ۹ computed — هزینه قابل حذف، نه لزوماً علت اصلی

این عدد:

```
۹ computed × ۸۰ icon = ۷۲۰ computed
```

از نظر تعداد درست و از نظر معماری نگران‌کننده است. اما صرف تعداد به‌تنهایی معیار نیست.

ممکن است ۷۲۰ computed خیلی ارزان باشند. در مقابل ممکن است `definition.render()` یا ساخت SVGها هزینه بسیار بیشتری داشته باشد.

بنابراین در این Challenge:

- «۷۲۰ computed یکی از هزینه‌های قابل حذف در static icon creation است»
- نه: «۷۲۰ computed علت ۴۷ms است»

## ۱. تشخیص مسئله

### ۱.۱ داده‌های Performance Report

```
IconPage
  median  47.11 ms
  p95     72.15 ms
  max     148.24 ms
  domElementCount  1026
  memoryHeapDelta  +9.24 MB  ← allocation pressure
  rating: bad (2/5)
```

### ۱.۲ ساختار IconPage

`ClIconPage.render()` حدود **۸۰+ آیکون** را در یک درختوی عمیق از `div`‌های تو در تو می‌سازد:

```text
container (div.row)
  └── div.col-12 (Status)
      ├── div.col-3 → div.border → [Icon, Icon]
      ├── div.col-3 → div.border → [Icon, Icon]
      └── ... (۶ گروه)
  └── div.col-12 (Arrows)
      ├── div.col-3 → div.border → [Icon×۴]
      └── ... (۳ گروه)
  └── ... (۱۰ بخش: Status, Arrows, Exclamation, Calc, Inputs, Files, Loadings, Payments, Users, WebCodes)
```

### ۱.۳ Creation Pipeline هر آیکون

هر فراخوانی `UiCategories.Icons.X.Y()` مسیر زیر را طی می‌کند:

```text
MtCreateCategoryIcon(definition)()
  → UiIcons.CreateIcon(definition, options)
      → MtCreateIcon(definition, options)
          1. new CoreObservable.Scope()           ← heap allocation
          2. CoreObservable.App.computed(×۵)       ← reactive graph setup
          3. definition.render(context)            ← تولید ۳-۶ svgPath
          4. CoreReactive.App.svg({...})           ← ساخت SVG element
              ├── attrsBind: ۴ computed دیگر
              └── children: content (computed)
```

**به ازای هر آیکون:**
- ۱ `Scope` جدید
- **۹ `computed` reactive** (۵ در MtCreateIcon + ۴ در attrsBind)
- ۳-۶ `svgPath` / `svgLine` (هر کدام یک `CoreReactive.App`)
- ۱ `svg` wrapper

**برای ۸۰ آیکون (تخمینی):**
- ۸۰ `Scope`
- ~۷۲۰ `computed`
- ~۳۲۰ `svgPath` element
- ۸۰ `svg` wrapper

**توجه:** این اعداد تخمین ساختار هستند، نه attribution. کدام بخش بیشترین هزینه زمانی دارد را Step ۰ مشخص می‌کند.

**هدف:** قبل از هر optimization، دقیقاً بدانیم ۴۷ms کجا مصرف می‌شود.

#### ۰.۱ Scaling Benchmark — Controlled

یک benchmark کنترل‌شده با تعداد متغیر آیکون. **شرایط باید کنترل‌شده باشد** — فقط تعداد iconها تغییر می‌کند، بقیه شرایط ثابت:

```
سناریو B — Repeated Same Icon:
  همه iconها یک definition دارند

```


خروجی:


تحلیل scaling slope:

- اگر خطی: `T(n) ≈ base + n × iconCost` → per-icon cost مسئله است
- اگر غیرخطی: یک bottleneck وابسته به scale وجود دارد (GC، scope accumulation، ...)
- اگر A و B تفاوت قابل توجه دارند → caching ارزش دارد (evidence برای Step 4)

#### ۰.۲ Creation Stage Instrumentation — Two Levels

instrumentation باید قابل جمع شدن باشد. مجموع stageهای اندازه‌گیری‌شده باید با `renderExecutionMs` قابل تطبیق باشد:

```
Total MtCreateIcon measured time
    +
Uninstrumented framework/DOM time
    ≈
renderExecutionMs
```

**Level 1: Coarse Attribution** — ابتدا فقط ۵ دسته کلی:

```text
MtCreateIcon
 ├── scope + reactive setup    → ?ms
 ├── definition.render()        → ?ms
 ├── svgCreation                → ?ms
 ├── attrsBinding               → ?ms
 └── total MtCreateIcon         → ?ms
```

اگر Level 1 bottleneck را مشخص کرد → کافی است.

**Level 2: Detailed Attribution** — فقط اگر Level 1 کافی نبود:

```text
MtCreateIcon
 ├── createScope               → ?ms
 ├── computedSetup (×۹)        → ?ms
 ├── definition.render()       → ?ms
 ├── svgCreation               → ?ms
 ├── attrsBinding              → ?ms
 ├── append/insertion          → ?ms
 └── translation               → ?ms
```

**توجه instrumentation overhead:** `performance.mark()` برای هر computed × صدها instance ممکن است خودش نویز ایجاد کند. Level 1 را اول اجرا کن. اگر Level 2 لازم شد، روی sample کوچک‌تر (مثلاً ۱۰ icon) اجرا کن، نه ۱۰۰.

خروجی مورد انتظار:

```

 ↓

? ms definition rendering (render() + svgPath)
? ms SVG creation (App.svg)
? ms DOM insertion

```

```

اگر definition.render() dominant است
```

### Step ۱ — Static Icon Fast Path

**پیش‌نیاز:** Step ۰ نشان داده که reactive setup هزینه قابل توجهی دارد.

**ایده:** وقتی ورودی‌ها واقعاً static هستند، reactive setup را دور بزن.

#### ۱.۱ تشخیص Static بودن — نه فقط empty options

تشخیص نباید این باشد:

```ts
// ❌ ناکافی
if (Object.keys(options).length === 0) → Static Path
```

چون ممکن است `definition` خودش reactive باشد، یا default value از مسیر reactive context بیاید.

باید:

```text
resolveIconCreationMode(definition, options)

options
   ↓
explicit observable?
   ├── yes → Reactive Path
   └── no
        ↓
definition/defaults observable?
   ├── yes → Reactive Path
   └── no → Static Path
```

این یک API داخلی `MtCreateIcon` است، نه abstraction عمومی. ساختار داخلی:

```text
MtCreateIcon
 ├── resolveIconCreationMode()
 │     ├── static
 │     └── reactive
 ├── createStaticIcon()
 └── createReactiveIcon()
```

این separation debugging را راحت‌تر می‌کند.

**قاعده:** static بودن باید اثبات شود، نه فرض. constraint اصلی این است:

> Reactive behavior باید حفظ شود.

#### ۱.۲ Static Path Implementation و Invariantها

```text
MtCreateIcon(definition, options)
  ├── resolveIconCreationMode()? → Static Path
  │     ├── استفاده از مقادیر default مستقیم (بدون computed)
  │     ├── render(context) با مقادیر static
  │     └── svg با attrs ثابت (بدون attrsBind computed)
  └── Reactive Path (فعلی، بدون تغییر)
```

**Invariantهای Static Path (قابل بررسی در تست):**

```
Static Path:
  NO Scope
  NO reactive computed
  NO reactive attrs binding

Reactive Path:
  existing behavior preserved
  observable change → icon update همچنان کار می‌کند
```

این invariantها باید در تست‌های regression قابل بررسی باشند.

#### ۱.۳ Benchmark بعد از Fast Path

```
IconPage median:
  قبل: 47ms
  بعد: ?ms

اگر 47 → 8ms  → Fast Path موفق، ولی هنوز برای <5ms نیاز به optimization دیگر
اگر 47 → 2.8ms → Fast Path کافی است. دست به چیزی نزن.
اگر 47 → 45ms  → reactive setup هزینه اصلی نبوده. به Step ۰ برگرد.
```

#### ۱.۴ Behavioral Equivalence Verification

Performance به تنهایی کافی نیست. Static Path باید اثبات کند که خروجی‌اش با Reactive Path معادل است.

```
Static Path output
       ≡
Reactive Path output
```

از نظر:

```
SVG structure (tag hierarchy)
attributes (viewBox, width, height, fill, stroke, ...)
dimensions
icon variants
title / aria-label
class / style
lifecycle
```

و برای Reactive Path:

```
observable change
       ↓
icon update

همچنان باید کار کند.
```

**این regression از خود benchmark مهم‌تر است.** چون قرار است بخشی از reactive machinery را عمداً حذف کنیم، باید اثبات کنیم که خروجی تغییر نکرده است.

### Step ۲ — Static Accessibility Resolution (مشروط)

**پیش‌نیاز:** Step ۰ نشان داده که translation هزینه قابل توجهی دارد، یا بعد از Step ۱ هنوز bottleneck باقی است.

**ایده:** `aria-label` نباید منتظر hover یا focus بماند. Screen reader ممکن است قبل از interaction به element برسد.

پس:

- اگر `definition.title` یک translation key static است → translation را یک‌بار resolve کن و static attribute قرار بده
- اگر translation نیاز به reactive context دارد → Reactive Path (فعلی) حفظ شود

```text
Static Path:
  "aria-label": resolveTranslationOnce(definition.title)  ← static string

Reactive Path:
  "aria-label": computed(...)  ← فعلی، بدون تغییر
```

**اثر (فقط در Static Path):** حذف computed translation در زمان creation

**توجه:** این مرحله الزاماً برای همه اجرا نمی‌شود. اگر بعد از Step ۱ به target رسیدیم (مثلاً 47ms → 3.2ms)، اصلاً نباید به translation دست بزنیم.

### Step 4 — Icon Template Cache (مشروط)

**پیش‌نیاز:** Step ۳ نشان داده که `definition.render()` هنوز bottleneck است.

**اصل مهم:** Cache باید **immutable template/data** باشد، نه reactive node.

#### ۴.۱ چرا cache کردن reactive node خطرناک است

اگر `CoreReactive.App` node را cache کنیم، آن node ممکن است دارای:

```
reactive state
scope
listeners
bindings
parent references
lifecycle
```

باشد. در این صورت `clone(cachedNode)` یک clone ساده نیست. ممکن است cache کردن خود reactive node باعث شود چند icon به یک state مشترک متصل شوند.

#### ۴.۲ راه‌حل: Template Cache

```text
definition.render()
       ↓
immutable SVG description (data)
       ↓
cache

cache hit
       ↓
create fresh DOM/reactive node از template
```

مفهوم:

```ts
type IconTemplate = {
    paths: readonly SvgPathDefinition[];
    lines: readonly SvgLineDefinition[];
    // ... immutable data، نه reactive instance
};
```

Cache فقط description داده‌ها را نگه می‌دارد. هر بار یک reactive/DOM node تازه از روی template ساخته می‌شود.

#### ۴.۳ آیا Cache اصلاً لازم است؟

اگر `definition.render()` برای هر icon فقط چند object کوچک می‌سازد و مثلاً ۰.۰۵ms هزینه دارد، cache کردنش ارزش architectural complexity ندارد.

پس ترتیب درست:

```
Measure (Step 0)
  ↓
Static Fast Path (Step 1)
  ↓
Benchmark (Step 3)
  ↓
اگر render هنوز bottleneck است
  ↓
Template Cache (Step 4)
```

نه:

```
Static Fast Path
  ↓
Cache (از الان committed)
```

Cache را از الان committed design نکن.
