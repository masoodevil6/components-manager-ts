# Plan 8.2.9 — CoreEvent Console Inspector & Flow Monitor

> **پیش‌نیاز:** Plan 8.2.8 (Per-Message Event Scope)
> **هدف:** Observability Layer برای CoreEvent — مشاهده درخت، جریان، سلامت و live stream از Console

---

## ۱. انگیزه

بعد از Plan 8.2.7 و 8.2.8، CoreEvent یک درخت سلسله‌مراتبی از Stepها دارد با routing پیچیده و lifecycle پویا. ولی هیچ راهی برای **مشاهده** این سیستم از Console وجود ندارد.

### ۱.۱ پنج سؤالی که Inspector باید جواب بدهد

| سؤال | API | خروجی |
|:---|:---|:---|
| الان چه Eventهایی وجود دارند؟ | `inspect()` | Tree Snapshot |
| چه اتفاقی افتاد؟ | `trace()` / `trace(id)` | Event Flow |
| این Event دقیقاً کجاست؟ | `find(query)` | Identity Search |
| Event Engine سالم است؟ | `stats()` | Health State |
| همین الان چه اتفاقی دارد می‌افتد؟ | `monitor()` / `monitor(false)` | Live Stream |

### ۱.۲ این صرفاً Debug نیست

این **Observability Layer** است — بدون اینکه Event Engine با ابزارهای debugging قاتی شود. قبل از ادامه جدی SubEvent و ComponentMessages، اگر routing یا disposal خراب شود، به‌جای حدس‌زدن از روی `console.log`های پراکنده، درخت و جریان واقعی Event قابل مشاهده است.

## ۲. قرارداد معماری (Contract)

### ۲.۱ اصول

- **Inspector یک Projection است** — نه بخشی از Event Model.
- **Inspector فقط خواندنی است** — هیچ mutation روی Event Tree انجام نمی‌دهد.
- **Inspector از API عمومی استفاده می‌کند** — به internals دسترسی ندارد.
- **Inspector در production هم موجود است** — ولی سبک (lightweight).
- **Inspector روی `window.Framework.Core.Event` expose می‌شود** — نه یک شیء global جدا.
- **خروجی از `console.group` استفاده می‌کند** — نه plain string — تا Chrome DevTools بتواند objectها را expand کند.

### ۲.۲ جداسازی Model از Inspector

```
CoreEvent
   │
   ├── Event Model (ClStep, ClEventDispatcher, ClRequest, ClResponse)
   │       ← بدون تغییر — نمی‌داند Inspector وجود دارد
   │
   └── Event Inspector (موجود در index.ts)
           ├── inspect()    → Tree Snapshot
           ├── trace()      → Event Flow
           ├── find()       → Identity Search
           ├── stats()      → Health State
           └── monitor()    → Live Stream
```

**`ClStep` تغییر نمی‌کند.** `toInspectTree()` روی ClStep قرار نمی‌گیرد — Inspector مسئول projection است.

## ۳. API طراحی

### ۳.۱ `inspect()` — Tree Snapshot

```javascript
Framework.Core.Event.inspect()
```

خروجی در Console (با `console.group` — قابل expand):

```text
CoreEvent Tree (12 steps, 5 emits)
│
├── ▸ ComponentMessages
│   └── ▸ messages
│       ├── ▸ message_abc123
│       │   ├── ▸ body [emit: ✓]
│       │   └── ▸ icon
│       │       └── ▸ close [emit: ✓]
│       └── ▸ message_def456
│           ├── ▸ body [emit: ✓]
│           └── ▸ icon
│               └── ▸ close [emit: ✓]
│
└── ▸ OtherStep
    └── ▸ child
```

هر `▸` یک `console.group` است — کاربر می‌تواند باز کند و Step object واقعی را ببیند.

### ۳.۲ `trace()` — Event Flow (گذشته)

```javascript
// آخرین Eventها
Framework.Core.Event.trace()

// یک Event خاص با dispatchId
Framework.Core.Event.trace("lxyz123.0")
```

خروجی برای یک Event (با `console.group`):

```text
▼ Event lxyz123.0 — SUCCESS
  │
  ├─ SOURCE
  │    ▸ { identity: Symbol(...), unique: "messages.message_abc.icon.close" }
  │
  ├─ TARGET
  │    ▸ { identity: Symbol(...), unique: "messages.message_abc.body" }
  │
  ├─ REQUEST
  │    ▸ { action: "close", id: "abc" }
  │
  ├─ DISPATCH
  │    source resolved      ✓
  │    target resolved      ✓
  │    emit found           ✓
  │    handler executed     ✓
  │
  ├─ RESPONSE
  │    ▸ { closed: true, id: "abc" }
  │
  └─ STATUS: SUCCESS
```

هر بخش یک `console.group` است — objectها قابل expand در DevTools.

### ۳.۳ `find(query)` — Identity Search


خروجی:

```javascript
Framework.Core.Event.stats()
```

خروجی:

```text
▼ CoreEvent Stats
  │
  ├─ Steps
  │    total:       12
  │    roots:        2
  │    children:    10
  │
  ├─ Handlers
  │    emits:        5
  │
  ├─ Trace
  │    recorded:    23
  │    capacity:   100
  │
  ├─ Dispatch

  │    errors:       2
```

### ۳.۵ `monitor()` — Live Stream

```javascript
// فعال‌کردن live logging
Framework.Core.Event.monitor()

// خاموش‌کردن
Framework.Core.Event.monitor(false)
```

بعد از فعال‌شدن، هر dispatch در Console زنده نمایش داده می‌شود:

```text
[CoreEvent] REQUEST
  source: messages.message_abc.icon.close
  target: messages.message_abc.body
  ▸ payload: { action: "close", id: "abc" }

[CoreEvent] RESPONSE
  status: success
  ▸ value: { closed: true, id: "abc" }
```

و disposal:

```text
[CoreEvent] DISPOSE
  step: messages.message_abc
```

`monitor(false)` خاموشش می‌کند.

**تفاوت با `trace()`:**
- `trace()` — گذشته را می‌بینی
- `monitor()` — از این لحظه به بعد جریان را می‌بینی

## ۴. Root vs Orphan — تفکیک مهم

### ۴.۱ Root

```text
Root Step
  parent === null        ← طبیعی — این ریشه درخت است
  registered === true    ← در registry موجود
```

Rootها **طبیعی** هستند. هر درخت یک یا چند root دارد.

### ۴.۲ Orphan

```text
Orphan Step
  parent reference invalid   ← parent دارد ولی parent آن را نمی‌شناسد
  یا
  parent-child relationship خراب
  یا
  registry/tree inconsistency
```

Orphan **مشکل** است — یعنی `dispose` یا `removeChild` درست کار نکرده.

### ۴.۳ تشخیص

```typescript
// Root: parent === null و registered
// Orphan: parent !== null ولی parent.getChild(parentKey) !== thisStep
```

`stats()` باید هر دو را جدا بشمارد:

```text
Integrity
  roots:     2  ← طبیعی
  orphans:   0  ← مشکل اگر > 0
```

## ۵. Implementation — قرارداد

### ۵.۱ `ClEventDispatcher` — accessorهای خواندنی

```typescript
/** کلیدهای رجیستری — برای inspect و find (Plan 8.2.9) */
getRegistry(): readonly TStepRef[] {
    return Array.from(this.registry.values());
}

/** تعداد emit handlerهای ثبت‌شده — برای stats */
getEmitCount(): number {
    return this.emits.size;
}

/** بررسی وجود emit handler برای یک Step — برای inspect */
hasEmit(step: TStepRef): boolean {
    return this.emits.has(step.identity);
}
```

### ۵.۲ `CoreEvent/index.ts` — Inspector functions

Inspector به‌صورت **توابع مستقل** در `index.ts` پیاده‌سازی می‌شود — نه روی ClStep یا ClEventDispatcher.

```typescript
/* ─────────────────────────────────────────────
   Plan 8.2.9 — Event Inspector (Projection)
   ───────────────────────────────────────────── */

/** درخت Event را در Console نمایش می‌دهد (Snapshot) */
export const inspect = (): void => { ... }

/** جریان اخیر Event را در Console نمایش می‌دهد (Flow) */
export const trace = (dispatchId?: string): void => { ... }

/** جستجوی Step بر اساس unique (substring match) */
export const find = (query: string): void => { ... }

/** آمار سلامت CoreEvent */
export const stats = (): void => { ... }

/** فعال/غیرفعال‌کردن live logging */
export const monitor = (enabled: boolean = true): void => { ... }
```

### ۵.۳ `console.group` به‌جای plain string

Inspector از `console.group` / `console.groupEnd` استفاده می‌کند — نه `console.log` با string. این اجازه می‌دهد Chrome DevTools objectها را expand کند.

### ۵.۴ `monitor()` — استفاده از `ClEventDispatcher.monitor(cb)` موجود

`ClEventDispatcher` از قبل یک `monitor(callback)` دارد که در هر `_pushTrace` صدا زده می‌شود. Inspector از این استفاده می‌کند:

```typescript
let _monitorActive = false;

export const monitor = (enabled: boolean = true): void => {
    _monitorActive = enabled;
    if (enabled) {
        App.monitor((record) => {
            if (_monitorActive) {
                console.group(`[CoreEvent] ${record.status.toUpperCase()} — ${record.dispatchId}`);
                console.log("source:", record.source);
                console.log("target:", record.target);
                console.groupEnd();
            }
        });
        console.log("[CoreEvent] monitor ON");
    } else {
        App.monitor(() => {});  // detach
        console.log("[CoreEvent] monitor OFF");
    }
};
```

### ۵.۵ `app.ts` — بدون تغییر

`window.Framework` از قبل `Core.Event` را expose می‌کند. چون `inspect`, `trace`, `find`, `stats`, `monitor` از `index.ts` export می‌شوند، خود‌کار روی `Framework.Core.Event` موجود خواهند بود.

## ۸. نکات مهم

### ۸.۱ چرا `console.group` و نه plain string؟

`console.log(tree)` تبدیل می‌کند Console را به یک تکه متن مرده. `console.group` اجازه می‌دهد Chrome DevTools object را باز کنی و expand کنی. برای یک Event Framework این حیاتی است — کاربر باید بتواند `request.payload` را expand کند و فیلدهای داخلش را ببیند.

### ۸.۲ چرا Inspector جدا از ClStep؟

`step.toInspectTree()` از نظر فنی شدنی است، ولی Inspector دارد وارد مدل اصلی Event می‌شود. ترجیح: Inspector یک **projection** مستقل است. این separation بعداً به درد می‌خورد — ممکن است بخواهیم `inspect()` یک object ساختاریافته برگرداند و Console formatter فقط یکی از مصرف‌کننده‌هایش باشد.

### ۸.۳ Lifecycle counters

`stats()` باید `created` و `disposed` را بشمارد. این نیاز به counterهای استاتیک در `ClEventDispatcher` یا `ClStep` دارد:

```typescript
// ClEventDispatcher
private static _createdCount = 0;
private static _disposedCount = 0;
```

این counters در `register` و `dispose` آپدیت می‌شوند.

### ۸.۴ Orphan detection

```typescript
// Root: parent === null و در registry
// Orphan: parent !== null ولی parent.getChild(parentKey) !== step
```

این می‌تواند memory leak را تشخیص دهد — اگر بعد از disposal یک Component، orphanها زیاد شوند، یعنی `dispose` درست کار نکرده.

### ۸.۵ `monitor()` و disposal

`monitor()` فعلاً فقط `_pushTrace` را نشان می‌دهد (Request/Response). ولی disposal هم مهم است. نیاز به hook در `CoreEvent.dispose`:

```typescript
// در CoreEvent.dispose — اگر monitor فعال است
if (_monitorActive) {
    console.log("[CoreEvent] DISPOSE —", step.unique);
}
```

### ۸.۶ backward compatibility

این Plan فقط **اضافه‌کردن** است — هیچ API موجود تغییر نمی‌کند. `getTrace()` و `monitor(cb)` قبلی دست‌نخورده باقی می‌مانند (Inspector از آن‌ها استفاده می‌کند).
