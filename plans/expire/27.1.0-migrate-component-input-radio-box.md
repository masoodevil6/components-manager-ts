# پلن 27.1.0 — انتقال `ComponentInputRadioBox` به ساختار جدید

> **وضعیت:** پیشنهادی؛ پیاده‌سازی‌نشده  
> **نسخه پلن:** 27.1.0  
> **منبع Legacy:** `last/tools/components/ComponentInputRadioBox.ts`  
> **راهنما:** `documents/guides/component-create.md`  
> **مقصد:** `src/framework/module_ui/module_components/lists/componentInputRadioBox/`  
> **API موردنظر:** `UiCategory.UI.Inputs.InputRadioBox(config, methods, identity)`

## 1. هدف و محدوده

انتقال `ComponentInputRadioBox` از `ComponentBase` و `ReactiveElement` قدیمی به معماری declarative/runtime جدید، با حفظ انتخاب گزینه، حالت‌های عمودی و افقی، محتوای وابسته به گزینه، disabled، label، callback انتخاب و validation.

پیش از اجرا تأیید شده است که پوشه‌ی `componentInputRadioBox` در `module_components/lists` و کلید ترجمه‌ی اختصاصی آن در `Keys.ts` فعلاً وجود ندارند. پلن شامل ساخت کامپوننت، ثبت در ComponentManager و Category ورودی‌ها، و افزودن ترجمه‌هاست.

مهاجرت مصرف‌کنندگان Legacy، تغییر API آن‌ها و حذف فایل قدیمی خارج از محدوده است. پیش از تصمیم درباره‌ی حفظ یا حذف هر prop، مصرف‌های آن در repository با `rg` بررسی و نتیجه مستند شود.

## 2. رفتار Legacy و قرارداد مهاجرت

Legacy از props پایه‌ی Component/Structure/FormInput/Value/Label و props اختصاصی استفاده می‌کند. مجموعه‌ی گزینه‌ها از `prop_options` می‌آید؛ هر گزینه `{id, name, body?}` دارد. `prop_itemSelected` مقدار انتخاب‌شده را نگه می‌دارد و می‌تواند Observable باشد. کلیک روی گزینه، مقدار و callback شامل شناسه و index گزینه را به‌روز می‌کند. در disabled انتخاب انجام نمی‌شود.

در حالت `vertical`، body هر گزینه زیر عنوان خودش و فقط برای گزینه‌ی انتخاب‌شده دیده می‌شود. در حالت `horizontal`، گزینه‌ها افقی‌اند و فقط یک ناحیه‌ی shared body برای محتوای گزینه‌ی انتخاب‌شده نمایش داده می‌شود. body می‌تواند رشته یا محتوای ReactiveElement/کامپوننت باشد و نباید به `[object Object]` تبدیل شود.

`prop_firstCallback` در صورت فعال‌بودن، callback را برای مقدار انتخاب‌شده‌ی اولیه اجرا می‌کند. این callback باید پس از در دسترس‌بودن selection و options حداکثر یک بار برای هر انتخاب اولیه اجرا شود؛ تغییر props یا rerender نباید باعث اجرای تکراری شود.

## 3. درخت composition و رندر مورد انتظار

```text
ComponentInputRadioBox
├── 1. ComponentLabelTrait (شرطی)
├── 2. part-input-radio-box-form
│   ├── 2.1. ComponentRecyclerView (گزینه‌ها؛ افقی یا عمودی)
│   │   └── part-input-radio-box-option
│   │       ├── part-input-radio-box-option-control
│   │       │   └── ComponentBorder
│   │       │       └── ComponentElementPosition (مرکزکردن نشان انتخاب)
│   │       │           └── ComponentIcon (شرطی بر اساس انتخاب)
│   │       ├── part-input-radio-box-option-title
│   │       └── part-input-radio-box-option-body (عمودی و شرطی)
│     └── part-input-radio-box-shared-body (افقی و شرطی)
└── 3. ComponentValidate (شرطی)
```

`ComponentElementPosition` فقط برای جای‌گذاری نشان انتخاب در مرکز ComponentBorder استفاده شود. والد موقعیت‌دهی باید مبنای `position: relative` داشته باشد. ComponentRecyclerView مسئول جهت چیدمان گزینه‌هاست؛ منطق انتخاب و state در خود `ComponentInputRadioBox` بماند. `ComponentLabelTrait` برای label و tooltip به‌کار رود و props آن دوباره تعریف نشوند.

## 4. Props و نگاشت

تمام props اختصاصی با `Define_ComponentProp<T>`, کلیدهای `Keys`, `satisfies CoreComponents.ComponentProps`, `ExtractPropsType` و `ExtractPropsConfigType` تعریف شوند. props پایه از `ComponentStructureTrait` و `ComponentLabelTrait` به ارث برسند.

| Legacy prop | تصمیم برای ساختار جدید |
|---|---|
| `prop_title` | حفظ برای عنوان ComponentValidate؛ با عنوان label یکی فرض نشود. |
| `prop_name` | مصرف آن در repository بررسی شود. در پیاده‌سازی Legacy مقدار در rendering گزینه‌ها استفاده نمی‌شود؛ تا تعیین تکلیف مصرف‌کنندگان حذف نشود. |
| `prop_options` | حفظ به‌عنوان آرایه‌ی گزینه‌های `{id, name, body?}`؛ نوع body باید رشته و محتوای کامپوننتی را پوشش دهد. |
| `prop_itemSelected` | حفظ به‌عنوان مقدار کنترل‌شده‌ی `string | number | null` و پشتیبانی از Observable سیستم جدید. |
| `prop_direction` | حفظ با enum عمومی جدید `RadioBoxDirection.VERTICAL/HORIZONTAL`؛ پیش‌فرض vertical. |
| `prop_size` | به API جدید منتقل نشود؛ اندازه‌ی عنوان، کنترل و فاصله‌ها از `CoreConfig.Settings.SizeName` و `UtilStyle` بیاید. |
| `prop_labelClass` | مصرف واقعی بررسی شود؛ در صورت حفظ، به کلاس‌های `ComponentLabelTrait` نگاشت شود و label دوباره‌سازی نشود. |
| `prop_firstCallback` | حفظ؛ callback اولیه طبق قرارداد بخش 2 فقط یک بار اجرا شود. |
| `prop_borderIconClass`, `prop_borderIconStyles` | حفظ برای استایل نشان/قاب گزینه؛ استایل reactive بدون mutate کردن Observable ورودی merge شود. |
| `prop_borderIconColor_selected/unSelected/disable` | حفظ و به رنگ Border انتخاب‌شده/نشده/disabled نگاشت شود. |
| `prop_borderIconWidth`, `prop_borderIconRadius`, `prop_borderIconOpacity` | حفظ؛ مقادیر اندازه‌ای بر اساس `sizeName` جاری و `UtilStyle` محاسبه شوند؛ radius عددی نیز پشتیبانی شود. |
| `prop_borderIconBackground_selected/unSelected/disable` | حفظ و به پس‌زمینه‌ی ComponentBorder نگاشت شود. |
| `prop_icon`, `prop_iconClass`, `prop_iconStyles` | حفظ برای نشان انتخاب؛ نبود آیکون نباید محتوای خالی یا `[object Object]` ایجاد کند. |
| `prop_titleShow`, `prop_titleClass`, `prop_titleStyles` | حفظ برای نمایش و استایل عنوان هر گزینه. |
| `prop_titleColor_selected/unSelected/disable` | حفظ؛ رنگ عنوان با انتخاب و disabled واکنش‌گرا باشد. |
| `prop_isAbsoluteRule`, `prop_listRules`, `prop_msgRules` | حفظ و به `ComponentValidate` نگاشت شود؛ validator فقط در حالت فعال و دارای rules رندر شود. |
| props پایه‌ی `prop_isDisable`, `prop_value` و label | از قراردادهای پایه/Trait استفاده شوند؛ از تعریف دوباره پرهیز شود. اگر Legacy مقدار انتخاب را فقط در `prop_itemSelected` نگه می‌دارد، `prop_value` نباید به منبع دوم و ناسازگار state تبدیل شود. |

پیش‌فرض رنگ‌ها و ظاهر از رفتار واقعی Legacy استخراج شود؛ رنگ‌های ثابت یا اندازه‌های پیکسلی صرفاً به دلیل ساده‌ترشدن پیاده‌سازی جایگزین نشوند. کلیدهای ترجمه‌ی کامپوننت، props، schemas، method و examples در `Keys.ts`, `En.ts`, `Fa.ts` اضافه شوند.

## 5. Methods و انتخاب گزینه

یک method عمومی `SELECT_ITEM` با نام runtime سازگار `fn_onSelectItem` تعریف شود. `dataArgs` شامل `ITEM_ID: string | number` و `ITEM_INDEX: number` باشد؛ `componentArgs` مقدار انتخاب‌شده و وضعیت disabled را طبق قرارداد type helperها ارائه کند.

رفتار انتخاب:

1. در حالت disabled، state و callback تغییر نکنند.
2. کلیک روی control یا عنوان همان گزینه دقیقاً یک مسیر انتخاب را اجرا کند؛ bubbling نباید callback را دوبار فراخوانی کند.
3. `prop_itemSelected` و `_CURRENT_SELECTION` همگام شوند؛ Observable بیرونی در صورت ارائه، منبع کنترل‌شده باقی بماند.
4. در حالت vertical، فقط body گزینه‌ی انتخاب‌شده باز باشد. در horizontal، shared body با محتوای همان گزینه به‌روزرسانی شود.
5. کلیک روی ComponentElementPosition داخلی آیکون selection نباید انتخاب را دوبار فعال کند؛ رویداد Border/option یک مالک مشخص برای انتخاب داشته باشد.

## 6. Schemas، Step و ساختار فایل‌ها

`COMPONENT` و `STRUCTURE` از `ComponentStructureTrait.schemas` و `LABEL` از `ComponentLabelTrait.schemas` گرفته شوند. Schemaها صرفاً metadata و prop binding داشته باشند؛ rendering و منطق در runtime بماند.

Schemaهای اختصاصی پیشنهادی:

| Schema | Part پیشنهادی | نقش |
|---|---|---|
| `FORM` | `part-input-radio-box-form` | محفظه‌ی گزینه‌ها، shared body و validate. |
| `OPTIONS` | `part-input-radio-box-options` | فهرست reactive گزینه‌ها و layout. |
| `OPTION` | `part-input-radio-box-option` | یک گزینه، انتخاب و disabled. |
| `OPTION_CONTROL` | `part-input-radio-box-option-control` | ComponentBorder و ComponentElementPosition نشان انتخاب. |
| `OPTION_ICON` | `part-input-radio-box-option-icon` | ComponentIcon انتخاب‌شده. |
| `OPTION_TITLE` | `part-input-radio-box-option-title` | عنوان و رنگ انتخاب/disabled. |
| `OPTION_BODY` | `part-input-radio-box-option-body` | body اختصاصی حالت vertical. |
| `SHARED_BODY` | `part-input-radio-box-shared-body` | body گزینه‌ی فعال در حالت horizontal. |
| `VALIDATE` | `part-input-radio-box-validate` | ComponentValidate شرطی. |

`Step.ts` یک factory مستقل برای instance می‌سازد. Base از `CoreComponents.App` ارث‌بری کند و props/schemaهای Trait را ترکیب کند. مسیر فایل‌ها:

```text
componentInputRadioBox/
├── Definition.ts
├── Props.ts
├── Schemas.ts
├── Methods.ts
├── Step.ts
├── ComponentInputRadioBoxBase.ts
├── ComponentInputRadioBox.ts
├── index.ts
└── examples/
    ├── Default.ts
    ├── Horizontal.ts
    ├── Validation.ts
    └── index.ts
```

`Definition.ts` شناسه‌ی یکتای `component_input_radio_box`, نام `componentInputRadioBox` و نسخه‌ی `v1.0.0` داشته باشد. Constructor از قرارداد `(config?, methods?, identity?)` پیروی کند. `dispose()` باید idempotent باشد و childها، subscriptionها و scopeهای متعلق به کامپوننت را آزاد کند.

## 7. Rendering و وابستگی‌های مجاز

- برای گزینه‌ها از `ComponentRecyclerView`, برای قاب از `ComponentBorder`, برای آیکون از `ComponentIcon`, برای جای‌گذاری نشان از `ComponentElementPosition`, و برای خطاها از `ComponentValidate` استفاده شود.
- ساخت DOM مستقیم برای جایگزینی کامپوننت‌های موجود، `innerHTML` برای body کامپوننتی، یا `document.querySelector` سراسری ممنوع است.
- فهرست گزینه‌ها باید با تغییر Observable `prop_options` و `prop_itemSelected` به‌روز شود؛ گرفتن snapshot با `.get()` در زمان render به‌تنهایی کافی نیست.
- در تغییر فهرست، شناسه‌ی گزینه‌ها یکتا فرض نشود مگر Legacy آن را enforce کرده باشد؛ index و fallback شناسه طبق قرارداد قدیمی حفظ و موارد مبهم مستند شوند.
- رنگ، اندازه، border و فاصله‌ها با tokenهای سیستم و `UtilStyle` محاسبه شوند. اندازه‌ی `prop_size` به‌عنوان ورودی تازه بازسازی نشود.
- هیچ import یا runtime از `last/`, `ComponentBase`, `ReactiveElement`, `Observable` Legacy, `GOG_*`, `TOOLS` یا `ToolsComponents` در مقصد مجاز نیست.

## 8. ثبت ComponentManager و Category

- کامپوننت در `module_components/lists/index.ts` import، در `ComponentManager` ثبت و از barrel export شود.
- Category جدید در `module_categories/lists/ui/inputs/inputRadioBox/` با `Definition.ts` و `index.ts` ساخته شود.
- `inputRadioBox` از `ui/inputs/index.ts` و مسیر عمومی UI export شود تا `UiCategory.UI.Inputs.InputRadioBox(...)` کار کند.
- metadata ترجمه‌ای جدید در `Keys.ts`, `En.ts`, `Fa.ts` اضافه شود؛ چون فضای کلید آن در وضعیت فعلی پیدا نشد، کلیدها باید به‌صورت کامل تعریف شوند.

## 9. Examples

- `Default`: انتخاب Observable اولیه، label، سه گزینه و body عمودی؛ `prop_firstCallback` روشن برای نشان‌دادن callback آغازین.
- `Horizontal`: گزینه‌های افقی و shared body که با انتخاب جابه‌جا شود.
- `Validation`: rules، پیام‌های سفارشی، title مستقل از label و حالت absolute/inline.
- Exampleها از Category عمومی جدید و typeهای جدید استفاده کنند؛ `prop_size` و هر import Legacy در آن‌ها ممنوع است.

## 10. معیارهای پذیرش و بررسی

1. Category عمومی و ComponentManager هر دو `InputRadioBox` را در دسترس قرار دهند.
2. مقدار اولیه و تغییرات بعدی Observable selection در UI منعکس شود؛ انتخاب کاربر نیز طبق قرارداد به مقدار بیرونی برگردد.
3. در حالت vertical، body فقط برای گزینه‌ی منتخب نمایش داده شود؛ در horizontal فقط shared body نمایش داده و با selection همگام شود.
4. body متنی و body کامپوننتی درست نمایش داده شوند؛ `[object Object]` یا استفاده‌ی ناامن از `innerHTML` رخ ندهد.
5. `SELECT_ITEM` با id و index درست، یک بار برای هر انتخاب اجرا شود؛ disabled انتخاب را متوقف کند.
6. `prop_firstCallback` برای انتخاب اولیه در صورت فعال‌بودن فقط یک بار اجرا شود و در rerender تکرار نشود.
7. رنگ/پس‌زمینه‌ی انتخاب‌شده، انتخاب‌نشده و disabled برای قاب، نشان و عنوان درست به‌روزرسانی شود؛ نبود آیکون خطا یا فضای نامناسب نسازد.
8. در تغییر runtime گزینه‌ها، selection نامعتبر به‌صورت مستند مدیریت شود؛ indexها با فهرست فعلی هماهنگ بمانند.
9. validator در نبود rules/در حالت disabled نمایش داده نشود و در حالت فعال مقدار، title و messages صحیح بگیرد.
10. تغییر config `sizeName` روی اندازه‌های وابسته اثر بگذارد؛ API جدید `prop_size` نداشته باشد.
11. dispose، Observable subscriptionها و child componentها را آزاد کند؛ dispose تکراری خطا ندهد.
12. تست رفتاری هدفمند برای selection، first callback، هر دو layout، disabled، reactive options و body کامپوننتی اضافه و اجرا شود.
13. `npx tsc --noEmit`, build موجود و `git diff --check` اجرا شوند؛ خطاهای قبلی repository از خطاهای ناشی از migration جدا گزارش شوند.

## 11. خارج از محدوده

- تغییر مصرف‌کنندگان Legacy یا حذف/انتقال `last/tools/components/ComponentInputRadioBox.ts`.
- بازطراحی عمومی `ComponentRecyclerView`, `ComponentBorder`, `ComponentElementPosition` یا `ComponentValidate`؛ هر ناسازگاری ضروری باید با کمترین تغییر backward-compatible و با شواهد ثبت شود.
- افزودن `prop_size` به API جدید یا ایجاد state دوم ناسازگار با `prop_itemSelected`.
- تغییر قرارداد callback بدون بررسی consumerهای فعلی.
