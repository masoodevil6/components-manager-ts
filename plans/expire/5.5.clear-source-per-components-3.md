# Plan: تفکیک Schema Definition از Schema Behavior و طراحی Runtime Contract

## 1. هدف

ساختار Component باید به چهار مسئولیت مستقل تقسیم شود:

```text
Definition
    │
    │ شناسنامه و Metadata
    ▼
Schema
    │
    │ تعریف ساختاری Part
    ▼
SchemaHandler
    │
    │ رفتار و Rendering
    ▼
Component Runtime
```

هدف این phase:

* `Schemas.ts` فقط مسئول تعریف Schema باشد.
* `SchemaHandlers.ts` مسئول رفتار و Rendering باشد.
* `ComponentStructure` فقط Runtime پایه باشد.
* `ClComponentBase` همچنان fallback مربوط به `renderManagerComponent` را نگه دارد.
* ارتباط Schema و Handler از طریق Contract مشخص انجام شود.
* Handler مستقیماً به `Schemas.ts` وابسته نباشد.
* ساختار برای توسعه ComponentManager و GUI Builder در آینده آماده باشد.
* `Definition.ts` حفظ شود و به‌عنوان شناسنامه و Metadata سطح Component باقی بماند.

# 5. Schemas.ts

`Schemas.ts` باید کاملاً Declarative باشد.

یعنی Schema فقط مشخص کند:

```text
این Part چیست؟
چه Propهایی دارد؟
نام آن چیست؟
توضیح آن چیست؟
```

نباید `method` مربوط به Rendering داخل Schema قرار بگیرد.

ساختار مورد انتظار:

```ts
export const Schemas = {

    COMPONENT: {

        part: "part-component",

            Keys.category.components.basic.schemas.component.name,
```

```ts
export interface ComponentSchemaHandler {

    render(
```

# 7. طراحی ComponentSchemaContext

`ComponentSchemaHandler` نباید مستقیماً به `Schemas` دسترسی داشته باشد.

Context باید اطلاعات مورد نیاز Handler را فراهم کند.

حداقل Contract پیشنهادی:

```ts
export interface ComponentSchemaContext {

    component: ComponentSchemaContextComponent;

    attrsDefault: CoreComponents.PartAttrDefault;

    data: Record<string, CoreObservable.App<any>>;

    extra: Record<string, any>;

    executeSchema(
        schema: string
    ): CoreReactive.App;

}
```

هدف:

```text
Handler
   │
   └── Context
          │
          ├── Component
          ├── Data
          ├── Attributes
          ├── Extra
          └── Schema execution
```

Handler نباید برای اجرای Schema دیگر مجبور باشد:

```ts
import {Schemas} from "./Schemas";
```

انجام دهد.

# 8. ComponentSchemaContextComponent

برای جلوگیری از وابستگی مستقیم Handler به کلاس Concrete، Context فقط API مورد نیاز Runtime را expose کند.

نمونه:

```ts
export interface ComponentSchemaContextComponent {

    _COMPONENT_NAME: string;

    executeSchemaPart(
        part: string
    ): CoreReactive.App;

    renderContentComponent(): CoreReactive.App;

}
```

در صورت نیاز می‌توان APIهای بیشتری اضافه کرد.

### قانون

Context نباید کل Component را به شکل `any` در اختیار Handler قرار دهد، مگر در مواردی که واقعاً نیاز باشد.

هدف این است:

```text
Handler
    ↓
Context Contract
    ↓
Runtime Component
```

نه:

```text
Handler
    ↓
Concrete Component implementation
```

# 9. SchemaHandlers.ts

تمام Rendering مربوط به ComponentStructure به این فایل منتقل شود.

ساختار:

```ts
export const SchemaHandlers = {

    COMPONENT: {

        render(
            context: UiComponents.Basic.Types.ComponentSchemaContext
        ): CoreReactive.App {

            const rtl =
                CoreConfigs.Settings.DirectionRtl.observable();

            const classList =
                context.data?.classList ??
                new CoreObservable.App([]);

            const styles =
                context.data?.styles ??
                new CoreObservable.App({});

            return CoreReactive.App.component(
                context.component._COMPONENT_NAME,
                {
                    attrs: {
                        ...context.attrsDefault,
                    },

                    classBind: [
                        classList,
                    ],

                    stylesBind: {
                        direction:
                            rtl.mapBoolean("rtl", "ltr"),

                        styles: styles,
                    },

                    children: [
                        context.executeSchema("STRUCTURE"),
                    ],
                }
            );
        },
    },


    STRUCTURE: {

        render(
            context: UiComponents.Basic.Types.ComponentSchemaContext
        ): CoreReactive.App {

            const prop_show =
                context.data?.prop_show ??
                new CoreObservable.App(true);

            const prop_structureClass =
                context.data?.prop_structureClass ??
                new CoreObservable.App([]);

            const prop_structureStyles =
                context.data?.prop_structureStyles ??
                new CoreObservable.App({});

            return CoreReactive.App.part(
                "section",
                {

                    classBind: [
                        prop_structureClass,
                        prop_show.mapBoolean(
                            "show",
                            "d-none"
                        ),
                    ],

                    attrs: {
                        ...context.attrsDefault,
                    },

                    stylesBind: {
                        prop_structureStyles,
                    },

                    children: [
                        context.component
                            .renderContentComponent(),
                    ],
                }
            );
        },
    },

} satisfies UiComponents.Basic.Types.ComponentSchemaHandlers;
```

### نکته مهم

این بخش:

```ts
Schemas.STRUCTURE.part
```

نباید در Handler استفاده شود.

Handler باید از Runtime/Context بخواهد Schema را اجرا کند:

```ts
context.executeSchema("STRUCTURE")
```

# 10. Mapping بین Schema و Handler

باید یک Contract مشخص برای ارتباط این دو ایجاد شود.

مطلوب:

```text
Schemas
   │
   ├── COMPONENT
   └── STRUCTURE

SchemaHandlers
   │
   ├── COMPONENT
   └── STRUCTURE
```

TypeScript باید تا حد امکان عدم تطابق را تشخیص دهد.

هدف نهایی:

```ts
type ComponentSchemaHandlers = {
    [K in keyof typeof Schemas]:
        UiComponents.Basic.Types.ComponentSchemaHandler;
};
```

اما Implementation این Type باید با ساختار واقعی Typeهای پروژه هماهنگ شود.

از `any` فقط برای حل temporary type circularity استفاده شود، نه به‌عنوان راه‌حل معماری.

# 11. ComponentStructure.ts

`ComponentStructure` فقط Runtime Base Component باشد.

ساختار:

```ts
export class ComponentStructure<
    TProp extends Record<string, any> = PropsType,
    TSchemas = SchemasType,
    TMethods extends Record<string, any> = MethodsType
> extends CoreComponents.App<
    TProp,
    TSchemas,
    any,
    TMethods
> {

    constructor(
        componentName: string = "structure",
        elId: string | null = null,
    ) {
        super(componentName, elId);
    }

    _COMPONENT_PATTERN =
        CoreComponents.DefineProp<TProp>({
            ...Props,
        } as any);

    _COMPONENT_SCHEMA =
        CoreComponents.DefineSchema<TSchemas, TProp>({

            COMPONENT: {
                part: Schemas.COMPONENT.part,
                props: (Schemas.COMPONENT.props ?? []) as any,
                handler: SchemaHandlers.COMPONENT,
            },

            STRUCTURE: {
                part: Schemas.STRUCTURE.part,
                props: (Schemas.STRUCTURE.props ?? []) as any,
                handler: SchemaHandlers.STRUCTURE,
            },

        } as any);

    _COMPONENT_METHODS =
        CoreComponents.DefineMethod<TMethods, TProp>({
            ...Methods,
        } as any);

}
```

**توجه:** نام `handler` فقط در صورتی استفاده شود که `DefineSchema` و Typeهای فعلی پروژه برای آن طراحی شده باشند. اگر قرارداد فعلی Schema هنوز `handler` ندارد، ابتدا Type و DefineSchema اصلاح شوند.

# 12. تغییر در DefineSchema

قبل از تغییر `ComponentStructure`، بررسی شود که:

```ts
DefineSchema
```

و Typeهای مرتبط چگونه Schema را ذخیره می‌کنند.

هدف این است که Schema بتواند چیزی مشابه این داشته باشد:

```ts
{
    part: "...",
    props: [...],
    handler: ...
}
```

ولی `handler` باید از `Schema Definition` از نظر مفهومی جدا بماند.

### اصل معماری

```text
Schema Definition
        +
Schema Behavior
        ↓
Runtime Schema Registration
```

# 13. تغییر در executeSchemaPart

`executeSchemaPart` در `ClComponentBase` باید منطق Resolution را انجام دهد.

منطق هدف:

```text
executeSchemaPart(part)
        │
        ▼
Schema را پیدا کن
        │
        ├── Handler دارد؟
        │       │
        │       └── Handler.render(context)
        │
        └── Handler ندارد؟
                │
                └── renderManagerComponent(...)
```

Pseudo-code:

```ts
if (schema.handler) {

    return schema.handler.render(
        this.createSchemaContext(...)
    );

}

return this.renderManagerComponent(
    partName,
    attrsDefault,
    data,
    extra
);
```

# 14. renderManagerComponent

در این phase:

### حذف نشود.

این متد در:

```text
ClComponentBase
```

به‌عنوان fallback باقی بماند.

اما:

```text
ComponentStructure.renderManagerComponent
```

حذف شود.

بنابراین:

```text
ClComponentBase
    renderManagerComponent()
          ↑
          fallback

ComponentStructure
    ❌ renderManagerComponent
```

این تصمیم برای Migration تدریجی ضروری است.

```text

    ↓
```



# 18. مثال مورد انتظار برای ComponentButton

ساختار فرزند باید همچنان قابل توسعه باشد:

```ts
export class ComponentButtonBase
    extends ComponentStructure<
        ButtonPropsType,
        ButtonSchemasType,
        ButtonMethodsType
    > {

    override _COMPONENT_PATTERN =
        CoreComponents.DefineProp({
            ...Props,
            ...ButtonProps,
        });

    override _COMPONENT_SCHEMA =
        CoreComponents.DefineSchema({
            ...,
            ...ButtonSchemas,
        });

    override _COMPONENT_METHODS =
        CoreComponents.DefineMethod({
            ...Methods,
            ...ButtonMethods,
        });

}
```

و:

```ts
export class ComponentButton
    extends ComponentButtonBase {

    constructor(
        config,
        methods,
        events?,
        unique?,
        emit?
    ) {

        super("button", null);

        this.renderComponent(
            config,
            methods,
            events,
            unique,
            emit
        );
    }

    override renderContentComponent() {

        return this.executeSchemaPart(
            "part-button-content"
        );

    }

}
```

ComponentButton نباید برای Schemaهای پایه دوباره Renderer بنویسد.

# 21. معیار موفقیت این Phase

Phase زمانی موفق است که:

### Architecture

* [ ] `Schemas.ts` کاملاً Declarative باشد.
* [ ] `SchemaHandlers.ts` مسئول Rendering باشد.
* [ ] `Definition.ts` باقی بماند.
* [ ] `ComponentStructureBase.ts` وجود نداشته باشد.
* [ ] `ComponentStructure.ts` تنها Runtime Base باشد.
* [ ] `ComponentStructure` فاقد `renderManagerComponent` باشد.
* [ ] `renderManagerComponent` در `ClComponentBase` باقی بماند.

### Runtime

* [ ] `executeSchemaPart()` بتواند Handler را Resolve کند.
* [ ] Handler بتواند Schema دیگر را از طریق Context اجرا کند.
* [ ] Handler به `Schemas.ts` وابستگی مستقیم نداشته باشد.
* [ ] Rendering پایه بدون `switch/if` در ComponentStructure انجام شود.

### TypeScript

* [ ] `ComponentSchemaContext` مشخص باشد.
* [ ] `ComponentSchemaHandler` مشخص باشد.
* [ ] Mapping بین Schema و Handler type-safe باشد.
* [ ] وابستگی circular ایجاد نشود.
* [ ] `any` فقط در نقاط واقعاً ضروری باقی بماند.

### Compatibility

* [ ] کامپوننت‌های قدیمی که هنوز `renderManagerComponent` دارند کار کنند.
* [ ] fallback قدیمی حذف نشود.
* [ ] ComponentStructure از مسیر جدید استفاده کند.

# 23. قانون معماری نهایی

از این phase به بعد:

```text
Definition
    = "این Component چیست؟"

Props
    = "چه ورودی‌هایی دارد؟"

Schemas
    = "چه Parts و ساختاری دارد؟"

SchemaHandlers
    = "هر Part چگونه رفتار/Render می‌شود؟"

Methods
    = "چه عملیات‌هایی توسط Component ارائه می‌شود؟"

ComponentStructure
    = "Runtime مشترک Component چیست؟"

ClComponentBase
    = "Runtime Engine و fallback چیست؟"
```

و مهم‌تر از همه:

```text
Schema ≠ Behavior
```

Schema باید بتواند بدون دانستن Renderer توسط ComponentManager، GUI Builder یا ابزار تحلیل ساختار خوانده شود.

همچنین:

```text
Handler ≠ Schema Definition
```

Handler فقط Behavior را پیاده می‌کند.

این تفکیک پایه‌ای است که در مراحل بعد می‌تواند امکان ساخت ComponentManager گرافیکی، ثبت Componentها، انتخاب Schemaها و حتی اجرای Workflow بر اساس Componentها را فراهم کند.
