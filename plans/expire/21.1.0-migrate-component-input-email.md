# پلن 21.1.0 — انتقال `ComponentInputEmail` به ساختار جدید

> **وضعیت:** پیاده‌سازی شد؛ اجرای Vitest در محیط فعلی با `spawn EPERM` متوقف می‌شود.  
> **منبع Legacy:** `last/tools/components/ComponentInputEmail.ts`  
> **راهنمای معماری:** `documents/guides/component-create.md`  
> **الگوی composition:** `componentInput` و `componentInputPassword`  
> **مقصد:** `src/framework/module_ui/module_components/lists/componentInputEmail/`  
> **API موردنظر:** `UiCategory.UI.Inputs.InputEmail(config, methods, identity)`

## 1. هدف و محدوده

انتقال ورودی ایمیل از پیاده‌سازی Legacy به معماری declarative/runtime جدید، با حفظ مقدار کنترل‌شده، نام، disabled، placeholder، آیکون ایمیل، focus/blur/input callbacks و اعتبارسنجی ایمیل.

ساختار composition باید دقیقاً چنین باشد:

```text
ComponentInputEmail
├── 1. ComponentLabelTrait
├── 2. part-input-email-form
│   ├── 2.1 ComponentIcon (آیکون ایمیل، اختیاری/قابل‌جایگزینی)
│   └── 2.2 ComponentInputSimple (type=email؛ شامل clear داخلی)
└── 3. ComponentValidate (شرطی)
```

`ComponentInputEmail` نباید input خام، آیکون clear مستقل، `ComponentElementPosition` یا border موازی بسازد. `ComponentInputSimple` مالک input، clear، مقدار و رخدادهای focus/blur باشد. `ComponentLabelTrait` از طریق سازوکار Trait پروژه استفاده شود، مطابق `ComponentInputPassword`.

## 2. رفتار Legacy و قواعد سازگاری

- مقدار اولیه‌ی Legacy خالی (`""`) است و `prop_value` می‌تواند مقدار مستقیم یا observable باشد.
- نوع ورودی همیشه email است.
- آیکون ابتدای فرم از `prop_icon` استفاده می‌کند، و در نبود آن به `prop_iconEmail` برمی‌گردد. `prop_iconEmail` مقدار پیش‌فرض آیکون ایمیل دارد؛ اگر هر دو null باشند آیکون و فضای آن حذف شوند.
- کلیک آیکون ابتدایی و کلیک label باید input را focus کنند.
- ورودی، focus و blur هر کدام callback عمومی متناظر را با مقدار جاری اجرا کنند.
- پاک‌کردن توسط clear داخلی `ComponentInputSimple` انجام شود و مقدار عمومی را به رشته‌ی خالی تبدیل کند. clear نباید آیکون یا handler دوم در کامپوننت Email داشته باشد.
- اعتبارسنجی وقتی `prop_isDisable` روشن، `prop_hasRules` خاموش، یا rules خالی/نامعتبر است نمایش داده نشود. با rules معتبر، قاعده‌ی ایمیل به rules افزوده شود.
- `prop_title` عنوان `ComponentValidate` است و با عنوان Label یکی نیست.
- از selector سراسری `document.querySelector` و idهای Legacy برای یافتن input استفاده نشود؛ focus باید از reference نمونه‌ی child یا API معتبر همان child انجام شود.

## 3. Props و مهاجرت API

Props مشترک component، structure، value و label از Traitها/ساختار استاندارد به ارث برسند و دوباره تعریف نشوند. Props اختصاصی با `Define_ComponentProp<T>`، متادیتای `Keys` و `satisfies CoreComponents.ComponentProps` تعریف شوند. نوع‌ها با `ExtractPropsType` و `ExtractPropsConfigType` استخراج شوند.

| Prop Legacy | تصمیم برای API جدید |
|---|---|
| `prop_name`, `prop_value`, `prop_isDisable` | از props پایه‌ی ورودی استفاده و به `ComponentInputSimple` forward شوند. رشته‌ی خالی Legacy حفظ شود؛ مقدار `null` در مرز child به `""` تبدیل شود. |
| `prop_labelTitle` و سایر props لیبل | از `ComponentLabelTrait` بیایند؛ در Props محلی تکرار نشوند. |
| `prop_title` | حفظ شود و صرفاً عنوان Validator باشد؛ مقدار پیش‌فرض null/خالی مطابق Legacy و قرارداد ComponentValidate تعیین شود. |
| `prop_backgroundColorForm` | حفظ شود، پیش‌فرض `var(--secondaryColor1)`؛ فقط برای فرم به‌کار رود. |
| `prop_formBorderRadius` | بررسی مصرف واقعی؛ اگر API نگه داشته شود با `UtilStyle` و `CoreConfig.Settings.SizeName` اعمال شود، بدون border تکراری. |
| `prop_colorIcon` | حفظ شود؛ رنگ به `ComponentIcon` منتقل شود و مقدار خالی به رنگ استاندارد سیستم واگذار شود. |
| `prop_size` | حذف شود؛ از `CoreConfig.Settings.SizeName.observable()` و `UtilStyle` استفاده شود. |
| `prop_inputClass`, `prop_inputStyles` | حفظ و به `ComponentInputSimple` منتقل شوند؛ استایل‌های پایه و سفارشی با ترتیب روشن merge شوند. |
| `prop_inputBorderColor`, `prop_inputBorderColorFocus` | در صورت حفظ سازگاری Legacy، به قابلیت‌های رنگی اختیاری `ComponentInputSimple` متصل شوند؛ رنگ عادی پیش‌فرض Primary/GRADE_1 و focus پیش‌فرض Secondary/GRADE_1 باشد. روی input بدون border، استایل موازی نسازید. |
| `prop_inputBorderWidth`, `prop_inputBorderRadius` | مقادیر سایز Legacy به‌عنوان API جدید منتقل نشوند؛ ضخامت و radius استاندارد از config سیستم و util بیایند. |
| `prop_placeholder` | حفظ و به `prop_inputPlaceholder` نگاشت شود. |
| `prop_icon` | حفظ به‌عنوان override اختیاری آیکون ابتدای input. |
| `prop_iconEmail` | حفظ با مقدار پیش‌فرض آیکون ایمیل جدید از UiIcons؛ `prop_icon` بر آن اولویت دارد. |
| `prop_hasRules`, `prop_isAbsoluteRule`, `prop_listRules`, `prop_msgRules` | حفظ و به `ComponentValidate` نگاشت شوند. قواعد با نوع واقعی Validatorهای جدید تعریف شوند، نه `any[]`. |

هر prop قدیمی دیگری پیش از حذف با جست‌وجوی مصرف‌های repo بررسی شود. Props محذوف در مثال‌های جدید استفاده نشوند. متادیتای name/description از کلیدهای ترجمه‌ی موجود برای inputهای مشترک استفاده کند؛ اگر کلید ایمیل اختصاصی لازم شد، آن را طبق راهنمای زبان‌ها اضافه کند.

## 4. Methods و رویدادها

Methods با الگوی `Methods.ts` جدید، metadata ترجمه‌شده، typeهای استخراج‌شده و callbackهای typed تعریف شوند.

| Method جدید | قرارداد |
|---|---|
| `INPUT_CHANGE` | جایگزین `fn_onInput`؛ پس از تغییر یا clear، مقدار نهایی رشته‌ای (clear برابر `""`) را یک بار منتشر کند. |
| `INPUT_FOCUS` | جایگزین `fn_onFocus`؛ فقط در focus واقعی input، مقدار جاری را ارسال کند. |
| `INPUT_BLUR` | جایگزین `fn_onBlur`؛ در blur واقعی، مقدار جاری را ارسال کند. |

adapter مقدار `null` یا مقدار خالی child را به قرارداد Legacy یعنی `""` تبدیل کند. از اجرای دستی callback focus در کنار رخداد focus واقعی پرهیز شود تا هر رویداد دوبار منتشر نشود. کلیک آیکون یا label فقط focus انجام دهد و خودش callback اضافی تولید نکند.

## 5. Schemas و ترتیب فرزندان

`COMPONENT` و `STRUCTURE` از `ComponentStructureTrait.schemas` و schemaهای Label از `ComponentLabelTrait.schemas` گرفته شوند. schema فقط metadata و props را تعریف کند؛ منطق render در runtime بماند.

| Schema | Part پیشنهادی | مسئولیت |
|---|---|---|
| `FORM` | `part-input-email-form` | wrapper فرم و ترتیب فرزندان؛ پس‌زمینه و تنظیمات مجاز فرم. |
| `ICON` | `part-input-email-icon` | `ComponentIcon` ابتدای فرم، با fallback از `prop_iconEmail`؛ حذف کامل در نبود آیکون. |
| `INPUT` | `part-input-email-input` | ساخت `ComponentInputSimple` با `type=email`؛ بدون input خام. |
| `VALIDATE` | `part-input-email-validate` | ساخت شرطی `ComponentValidate`. |

فرزندان `ICON` و `INPUT` باید مستقیم و دقیقاً به همین ترتیب زیر `FORM` باشند؛ `VALIDATE` خواهر فرم و فرزند سطح اصلی باشد. آیکون clear داخلی InputSimple فرزند جداگانه‌ی schema در Email نیست.

## 6. آیکون، input و چیدمان

- default icon از مجموعه‌ی آیکون‌های جدید (برای نمونه تعریف UserEmail مناسب در `UiIcons`) بیاید؛ Legacy `ToolsIcons` import نشود.
- اگر `prop_icon` مقدار دارد همان نمایش داده شود؛ در غیر این صورت `prop_iconEmail` استفاده شود. این انتخاب باید برای مقدارهای observable نیز واکنش‌گرا باشد.
- نمونه‌ی `ComponentIcon` از callback کلیک برای focus کردن `ComponentInputSimple` استفاده کند.
- `ComponentInputSimple` با `prop_inputType=email`، name، value، disabled، placeholder، class و styles متناظر ساخته شود. input واقعی و clear فقط در child باشند.
- شعاع گوشه‌های سمت آیکون، در حضور آیکون و متناسب با `DirectionRtl` سیستم، با props استاندارد چهارگانه‌ی `ComponentInputSimple` تنظیم شود. در نبود آیکون هر چهار گوشه از `UtilStyle.Css_BorderRadius` با `SizeName` جاری استفاده کنند.
- عرض آیکون و input، ارتفاع، padding، border، focus و radius از الگوی `ComponentInput`/`ComponentInputPassword` و محاسبات util پیروی کنند؛ اندازه‌ی ثابت Legacy مثل 30px/35px/20pt وارد نشود.
- در تغییر runtimeی آیکون، disabled، value و config، UI بدون ساخت duplicate child یا listener به‌روز شود.

## 7. اعتبارسنجی ایمیل

- `ComponentValidate` تنها وقتی ساخته شود که کامپوننت enabled باشد، `prop_hasRules === true` و فهرست rules ورودی معتبر و غیرخالی باشد؛ این شرط رفتار Legacy را حفظ می‌کند.
- rule ایمیل با validator رسمی جدید `UtilValidators.validates.IsEmail` ایجاد شود. پیش از استفاده، امضای سازنده و نوع rule با `ComponentValidate/examples/Default.ts` و API واقعی validator تطبیق داده شود.
- قاعده‌ی ایمیل دقیقاً یک بار افزوده شود؛ آرایه‌ی ورودی کاربر mutate نشود و اگر همان validator از قبل وجود دارد، rule تکراری ساخته نشود.
- پیام قابل ترجمه‌ی پیش‌فرض برای ایمیل معتبر/نامعتبر از الگوی IsEmail در Example پیروی کند؛ `prop_msgRules` کاربر در صورت ارائه اولویت داشته باشد. ruleهای سفارشی کاربر دست‌نخورده بمانند.
- `prop_value` کنترل‌شده به Validator منتقل شود و تغییر آن validation را به‌روز کند. `prop_title`، `prop_isAbsoluteRule` و اندازه‌ی سیستم مطابق props ComponentValidate تنظیم شوند.

## 8. فایل‌ها و چرخه‌ی حیات

ساختار پوشه مطابق راهنما و ComponentInputPassword باشد:

```text
componentInputEmail/
├── Definition.ts
├── Props.ts
├── Schemas.ts
├── Methods.ts
├── Step.ts
├── ComponentInputEmailBase.ts
├── ComponentInputEmail.ts
├── index.ts
└── examples/
    ├── Default.ts
    ├── Validation.ts
    └── index.ts
```

- Definition: `id: "component_input_email"`، نام `componentInputEmail` و نسخه‌ی `v1.0.0`؛ بدون وابستگی runtime.
- Base: ارث‌بری از `CoreComponents.App` و ترکیب `ComponentStructureTrait`، `ComponentLabelTrait`، Props/Schemas/Methods جدید؛ Step و identity مطابق الگوی Password.
- Runtime: constructor استاندارد، نگهداری reference فرزندان، render بر اساس schemaها، پل value و callbacks، `dispose()` امن و idempotent.
- `dispose()` باید scope/listener/Step و هر سه child (Label، InputSimple، Icon در صورت وجود، Validate در صورت وجود) را آزاد کند؛ dispose شرطی و بدون duplicate call مدیریت شود.
- `Step.ts` درخت قابل مشاهده را مطابق ترتیب Label → Form(Icon, Input) → Validate تعریف کند.
- `index.ts` export عمومی Component، Props، Schemas، Methods، Definition، مثال‌ها و typeهای عمومی را ارائه کند.
- هیچ import/runtime وابسته به `last/`، `ComponentBase`، `ReactiveElement`، `Observable` قدیمی، `TOOLS`، `GOG_*` یا `ToolsIcons` وارد مقصد نشود.

- در `module_components/lists/index.ts`، کامپوننت import، در ComponentManager ثبت و از barrel عمومی export شود؛ ترتیب ثبت از `componentInput` و `componentInputPassword` پیروی کند.
- Category جدید در `module_categories/lists/ui/inputs/inputEmail/` شامل `Definition.ts` و `index.ts` ساخته شود.
- `InputEmail` در barrel مربوط به `ui/inputs` و `ui` ثبت شود تا مسیر `UiCategory.UI.Inputs.InputEmail(...)` در دسترس باشد.
- callable و `.info`، تعریف version و نمونه‌ها مطابق Categoryهای موجود باشند؛ import چرخه‌ای بین component و category ایجاد نشود.

## 10. مثال‌ها

- `Default`: label، آیکون ایمیل پیش‌فرض، placeholder، مقدار کنترل‌شده و callbackهای input/focus/blur؛ بدون `prop_size`.
- `Validation`: rule الزامی نمونه به‌علاوه‌ی rule ایمیل خودکار، پیام‌های جدا برای الزامی و ایمیل نامعتبر، و تنظیم عنوان Validator.
- مثال‌ها از API جدید Category و `UtilValidators.validates.IsEmail` استفاده کنند؛ هیچ reference از Legacy و هیچ rule تایپی `any` استفاده نشود.

## 11. معیارهای پذیرش

1. API عمومی `UiCategory.UI.Inputs.InputEmail` ثبت و قابل استفاده باشد.
2. DOM درخت مورد انتظار را داشته باشد: Label؛ سپس فرم با دو فرزند مستقیم Icon و InputSimple؛ سپس Validate در سطح اصلی. Validate داخل فرم قرار نگیرد.
3. یک input واقعی با `type=email` وجود داشته باشد و آیکون clear فقط از InputSimple بیاید.
4. مقدار اولیه، تایپ، مقدار observable و disabled به‌درستی forward شوند؛ clear مقدار عمومی را `""` کند و `INPUT_CHANGE` را فقط یک بار اجرا کند.
5. `INPUT_FOCUS` و `INPUT_BLUR` فقط در رویداد واقعی input یک بار اجرا شوند و مقدار جاری را بدهند.
6. کلیک روی label یا آیکون ایمیل input را focus کند؛ نبود آیکون فضای بی‌مصرف نسازد.
7. `prop_icon` بر آیکون پیش‌فرض اولویت داشته باشد و تغییر observable آن UI را به‌روز کند.
8. آیکون و input در RTL/LTR گوشه‌های درست داشته باشند؛ نبود آیکون باعث radius استاندارد چهارگوشه شود.
9. ابعاد با تغییر `CoreConfig.Settings.SizeName` به‌روز شوند و `prop_size` جدیدی وجود نداشته باشد.
10. validation با شرط‌های فعال‌سازی درست ساخته شود؛ rule ایمیل تکراری نباشد، rules کاربر mutate نشوند، پیام‌های سفارشی بر پیام پیش‌فرض اولویت داشته باشند.
11. custom props پشتیبانی‌شده‌ی input و تنظیمات Label/Validate درست به فرزندان برسند؛ border یا input تکراری ساخته نشود.
12. `dispose()` منابع و فرزندان را آزاد کند و اجرای دوباره‌ی آن خطا ندهد.
13. TypeScript/build هدفمند، تست‌های رفتاری جدید و `git diff --check` موفق باشند.
