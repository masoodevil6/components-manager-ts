# Plan 8.1.2 — ComponentTrait

## اشتراک‌گذاری رفتار مشترک بین Componentها بدون ارث‌بری

---

## 0. هدف

در معماری فعلی چند Component مانند:

* `ComponentIcon`
* `ComponentMessages`
* `ComponentButton`
* `ComponentInput`
* `ComponentSelect`

برای استفاده از قابلیت‌های مشترک، بخشی از منطق Rendering و Props را تکرار می‌کنند.

نمونه مشخص، استفاده از `ComponentStructure` است که در Componentهای مختلف باعث تکرار منطق زیر شده است:

1. دریافت Props مربوط به Structure
2. ساخت `ComponentStructure`
3. تزریق `content`
4. ساخت wrapper
5. اتصال Component به Structure

هدف این Plan:

1. حذف کد تکراری
2. اشتراک‌گذاری Props مشترک
3. اشتراک‌گذاری Render Helperهای مشترک
4. حفظ استقلال Componentها
5. جلوگیری از ایجاد Base Classهای جدید
6. جلوگیری از بازگشت معماری Legacy
7. حفظ مرز بین Metadata و Runtime
8. جلوگیری از Silent Failure
9. حفظ Lazy Render
10. ایجاد الگوی قابل توسعه برای Traitهای آینده

---

# 1. اصل بنیادین

> **Trait یک Shared Capability است، نه یک Component و نه یک Base Class.**

Trait نباید:

* کلاس باشد
* از `ComponentBase` ارث ببرد
* Component را به ارث‌بری مجبور کند
* Prototype را تغییر دهد
* State داشته باشد
* Lifecycle داشته باشد
* Event ownership داشته باشد
* Registry داشته باشد
* Business Logic داشته باشد

Trait فقط باید قابلیت مشترک را ارائه کند.

ساختار مفهومی:

```text
Concrete Component
       │
       ├── State
       ├── Methods
       ├── Events
       ├── Lifecycle
       ├── Rendering
       │
       └── uses Trait
              │
              ├── Shared Props
              └── Shared Render Helpers
```

# 2. مسئله فعلی

در `ComponentIcon` منطق مشابه زیر وجود دارد:

```ts
override renderContentComponent(): CoreReactive.App {

    const classList =
        this._COMPONENT_PROPS_BIND["classList"];

    const styles =
        this._COMPONENT_PROPS_BIND["styles"];

    const prop_show =
        this._COMPONENT_PROPS_BIND["prop_show"];

    const prop_structureClass =
        this._COMPONENT_PROPS_BIND["prop_structureClass"];

    const prop_structureStyles =
        this._COMPONENT_PROPS_BIND["prop_structureStyles"];

    const structEl = ComponentStructure.create({

        classList:
            classList?.get() ?? [],

        styles:
            styles?.get() ?? {},

        prop_show:
            prop_show?.get() ?? true,

        prop_structureClass:
            prop_structureClass?.get() ?? [],

        prop_structureStyles:
            prop_structureStyles?.get() ?? {},

        content: () =>
            this.renderIcon(),
    });

    return CoreReactive.App.part("section", {
        children: [structEl],
    });
}
```

این الگو در Componentهای مختلف تکرار می‌شود.

مشکل:

```text
ComponentIcon
ComponentButton
ComponentMessages
ComponentInput
       │
       └──── duplicate Structure integration
```

اگر Props یا Contract مربوط به `ComponentStructure` تغییر کند، تمام مصرف‌کننده‌ها باید به‌صورت دستی اصلاح شوند.

# 5. Trait نباید Base Class باشد

ممنوع:

```ts
class ComponentStructureTrait
    extends ComponentBase {}
```

یا:

```ts
class ComponentStructureBase
    extends ComponentBase {}
```

یا هر Base Class دیگری که صرفاً برای اشتراک این رفتار ایجاد شود.

Component همچنان مستقیماً از Base رسمی خود ارث می‌برد.

```text
ComponentBase
     │
     ├── ComponentIcon
     ├── ComponentButton
     ├── ComponentInput
     └── ComponentCollapse
```

Trait در این hierarchy قرار نمی‌گیرد.

---

# 6. Trait نباید Mixin باشد

Mixin در TypeScript معمولاً Prototype یا inheritance chain را تغییر می‌دهد:

```ts
function ComponentStructureMixin(Base) {
    return class extends Base {
        renderContent() {}
    };
}
```

این معماری مورد نظر نیست.

Trait باید به‌صورت explicit استفاده شود:

```ts
ComponentStructureTrait.renderContent(
    this,
    () => this.renderIcon(),
);
```

بنابراین:

```text
Mixin
    ↓
Prototype modification

Trait
    ↓
Explicit capability
```

بنابراین این دو در یک abstraction قرار می‌گیرند.

Trait همچنان باید کوچک و محدود باقی بماند.

# 8. ComponentStructureTrait

فایل:

```text
src/framework/module_ui/module_components/traits/
    componentStructureTrait/
        Trait.ts
```

پیاده‌سازی اولیه:

```ts
import * as CoreReactive
    from "@/core_reactive";

import * as CoreComponents
    from "@/core_components";

import {
    Props as StructureProps
} from "../../lists/componentStructure/Props";

import {
    ComponentStructure
} from "../../lists/componentStructure/ComponentStructure";


export const ComponentStructureTrait = {

    props: StructureProps,

    renderContent(
        component: CoreComponents.App<any, any, any, any>,
        content: () => CoreReactive.App,
    ): CoreReactive.App {

        const classList =
            component.getObservable("classList");

        const styles =
            component.getObservable("styles");

        const prop_show =
            component.getObservable("prop_show");

        const prop_structureClass =
            component.getObservable(
                "prop_structureClass"
            );

        const prop_structureStyles =
            component.getObservable(
                "prop_structureStyles"
            );

        if (!classList) {
            throw new Error(
                "[ComponentStructureTrait] Missing required prop: classList"
            );
        }

        if (!styles) {
            throw new Error(
                "[ComponentStructureTrait] Missing required prop: styles"
            );
        }

        if (!prop_show) {
            throw new Error(
                "[ComponentStructureTrait] Missing required prop: prop_show"
            );
        }

        if (!prop_structureClass) {
            throw new Error(
                "[ComponentStructureTrait] Missing required prop: prop_structureClass"
            );
        }

        if (!prop_structureStyles) {
            throw new Error(
                "[ComponentStructureTrait] Missing required prop: prop_structureStyles"
            );
        }

        const structEl =
            ComponentStructure.create({

                classList:
                    classList.get(),

                styles:
                    styles.get(),

                prop_show:
                    prop_show.get(),

                prop_structureClass:
                    prop_structureClass.get(),

                prop_structureStyles:
                    prop_structureStyles.get(),

                content,
            });

        return CoreReactive.App.part("section", {
            children: [structEl],
        });
    },
};
```

# 9. اصل مهم: Silent Failure ممنوع

این الگو ممنوع است:

```ts
component.getObservable("prop_show")?.get() ?? true
```

زیرا دو وضعیت مختلف را یکی می‌کند:

```text
prop وجود دارد و مقدار آن true است
```

و:

```text
prop اصلاً ثبت نشده است
```

این دو باید از هم قابل تشخیص باشند.

اگر Trait انتظار دارد:

```text
prop_show
```

وجود داشته باشد ولی Component آن را register نکرده باشد، باید خطای صریح ایجاد شود.

مثال:

```ts
if (!prop_show) {
    throw new Error(
        "[ComponentStructureTrait] Missing required prop: prop_show"
    );
}
```

هدف این است که خطای معماری پنهان نشود.

# 10. دلیل اهمیت Error Contract

در توسعه Componentها، مخصوصاً هنگام استفاده از AI، این وضعیت خطرناک است:

```text
Missing Prop
      ↓
fallback
      ↓
Component renders
      ↓
AI نتیجه می‌گیرد مشکل حل شده
```

در حالی که Component Contract ناقص است.

رفتار مطلوب:

```text
Missing Prop
      ↓
Explicit Error
      ↓
AI / Developer متوجه Contract violation می‌شود
      ↓
Component اصلاح می‌شود
```

بنابراین Trait نباید با fallbackهای بی‌دلیل خطاهای معماری را پنهان کند.

---

# 11. Type Safety

استفاده از:

```ts
component.getObservable(...)
```

مزیت مهمی دارد:

* Public API است
* Trait به Internal Field وابسته نمی‌شود
* وابستگی به `_COMPONENT_PROPS_BIND` کاهش می‌یابد

اما یک Trade-off واقعی وجود دارد.

ممکن است:

```ts
getObservable("prop_show")
```

تایپی مشابه:

```ts
App<any> | null
```

داشته باشد.

در نتیجه نسبت به:

```ts
this._COMPONENT_PROPS_BIND["prop_show"]
```

ممکن است Type Safety کمتری داشته باشد.

این موضوع باید صریحاً پذیرفته شود.

### تصمیم این Plan

در این Plan:

* Public API اولویت دارد.
* Trait نباید برای حفظ Type Safety به Internal Field وابسته شود.
* اصلاح Generic سیستم `getObservable()` خارج از Scope این Plan است.
* `any` فقط در مرز فعلی API مجاز است و نباید به‌عنوان راه‌حل معماری جدید گسترش پیدا کند.

# 19. Lazy Render

Lazy Render یعنی Rendering وابسته به Component نباید قبل از کامل شدن initialization آن اجرا شود.

ممنوع:

```ts
constructor(...) {

    super(...);

    this.renderContentComponent();

}
```

مجاز:

```text
new Component(...)
       ↓
Component initialization
       ↓
getElement()
       ↓
render()
       ↓
renderContentComponent()
       ↓
Trait.renderContent()
```

Trait نباید خودش Rendering را در constructor یا هنگام تعریف object انجام دهد.

# 28. معیار ایجاد Trait جدید

قبل از ساخت Trait جدید این چهار سؤال باید پاسخ مثبت داشته باشند:

1. آیا حداقل دو Component واقعاً قابلیت مشترک دارند؟
2. آیا قابلیت مشترک مستقل از State اختصاصی Component است؟
3. آیا قابلیت به Lifecycle یا Event ownership نیاز ندارد؟
4. آیا Contract Trait را می‌توان کوچک و واضح تعریف کرد؟

اگر پاسخ منفی باشد، احتمالاً Trait abstraction مناسبی نیست.

# 40. دستور اجرای نهایی برای AI

هنگام اجرای این Plan:

1. ابتدا وضعیت فعلی فایل‌ها را بررسی کن.
2. قبل از تغییر هر فایل، Contract مربوط به آن را استخراج کن.
3. Behavior موجود را با Implementation یکی فرض نکن.
4. فقط قابلیت مشترک را به Trait منتقل کن.
5. State، Event، Lifecycle و Business Logic را به Trait منتقل نکن.
6. از Internal API مانند `_COMPONENT_PROPS_BIND` در Trait استفاده نکن.
7. برای Required Props از Silent Fallback استفاده نکن.
8. اگر Contract مشخص نیست، فرض جدید ایجاد نکن.
9. `<section>` wrapper را بدون بررسی Behavior تثبیت نکن.
10. Lazy Render را حفظ کن.
11. Import Cycle را بررسی کن.
12. بعد از هر Phase Compile انجام بده.
13. در پایان Acceptance Criteria را موردبه‌مورد بررسی کن.
14. خارج از Scope هیچ Refactor دیگری انجام نده.

> **هدف این Plan ساخت یک abstraction بزرگ‌تر نیست.**
>
> هدف ساخت یک abstraction کوچک و دقیق برای یک قابلیت مشترک است.
>
> اگر Trait برای حل duplication مجبور شد State، Lifecycle، Event، Registry یا Business Logic دریافت کند، طراحی Trait اشتباه است و باید متوقف و بازطراحی شود.
