# پلن 49.1.0 — ساخت `ComponentCustomForm`

> **وضعیت:** آمادهٔ اجرا<br>
> **دستهٔ ثبت:** دستهٔ موجود `fetch → form` با شناسهٔ `form`؛ دستهٔ جدید ساخته نشود<br>
> **API عمومی پیشنهادی:** `UiCategory.UI.Fetch.CustomForm(config, methods, identity)`<br>
> **کامپوننت‌های ترکیبی:** `ComponentForm`، `ComponentLayout` و `ComponentCollapseLine`<br>
> **راهنمای مبنا:** `documents/guides/component-create.md`

## ۱. هدف و محدوده

کامپوننتی برای تعریف و نمایش فرم‌های سفارشی و گروه‌بندی‌شده ساخته شود. هر گروه به‌صورت یک `ComponentCollapseLine` رندر شود. کامپوننت دو حالت داشته باشد:

- `EDIT`: ویرایش تعریف فرم، گروه‌ها و فیلدهای هر گروه.
- `RUN`: نمایش فرم ساخته‌شده برای ورود داده و ارسال آن.

`ComponentForm` در RUN پوستهٔ فرم بومی، اعتبارسنجی و مسیر ارسال را فراهم کند. `ComponentLayout` محتوای فعال هر دو حالت را در لایهٔ layout قرار دهد. هر دو حالت از یک تعریف گروه و فیلد استفاده کنند تا خروجی EDIT در RUN همان فرم را بسازد.

در نسخهٔ نخست، فیلدها از کنترل‌های موجود پروژه ساخته شوند؛ افزودن Component ورودی جدید و ذخیره‌سازی دائمی تعریف فرم خارج از محدوده است. مقدار پیش‌فرض پیشنهادی `EDIT` است، چون این کامپوننت ابزار ساخت و ویرایش فرم است؛ مصرف‌کننده می‌تواند با `prop_customFormMode: RUN` فرم نهایی را نمایش دهد.

## ۲. قرارداد گروه و فیلد

تعریف فرم به‌شکل آرایه‌ای از گروه‌ها باشد. هر گروه شناسهٔ پایدار، عنوان، وضعیت بازبودن و فهرست فیلدها داشته باشد. هر فیلد شناسه، نام بومی فرم، برچسب، نوع کنترل و تنظیمات مختص همان کنترل را داشته باشد.

```typescript
enum CustomFormFieldType {
    INPUT = "INPUT",
    TEXTAREA = "TEXTAREA",
    CHECKBOX = "CHECKBOX",
    RADIO = "RADIO",
    SELECT = "SELECT",
}

type CustomFormField = {
    id: string;
    name: string;
    label: string;
    type: CustomFormFieldType;
    value?: unknown;
    placeholder?: string | null;
    required?: boolean;
    options?: Array<{label: string; value: string | number}>;
    props?: Record<string, unknown>;
};

type CustomFormGroup = {
    id: string;
    title: string;
    bodyIsOpen?: boolean;
    fields: CustomFormField[];
};
```

`INPUT` از انواع موجود `ComponentInput`، `TEXTAREA` از `ComponentInputDescription`، `CHECKBOX` از `ComponentInputCheckBox`، `RADIO` از `ComponentInputRadioBox` و `SELECT` از `ComponentInputListSelector` استفاده کند. نگاشت هر نوع به Component در Runtime باشد؛ دادهٔ تعریف فرم مستقیماً وارد DOM نشود. اعتبارسنجی فیلدها به API کنترل‌های ورودی موجود متصل شود.

## ۳. تصمیم‌های رفتاری

- `prop_customFormMode` تعیین کند کدام نمای EDIT یا RUN رندر شود. تغییر Observable این prop پس از render باید نما را عوض کند.
- در EDIT، هر گروه داخل `ComponentCollapseLine` باشد و بدنهٔ آن ابزار ویرایش عنوان گروه و تعریف فیلدهایش را نشان دهد. امکان افزودن/حذف گروه و فیلد و ویرایش مشخصات پایهٔ فیلد فراهم شود.
- در RUN، هر گروه همچنان داخل `ComponentCollapseLine` باشد؛ بدنهٔ آن کنترل‌های واقعی فرم را با `name`, `value`, `required`, `placeholder` و تنظیمات نوعی رندر کند.
- در RUN، `ComponentForm` محتوای گروه‌ها را از طریق `prop_forms` دریافت کند و اعتبارسنجی و submit را انجام دهد. در EDIT، editor مستقیماً در `ComponentLayout` رندر شود؛ تغییرهای تعریف فرم به Method مربوطه گزارش شوند و UI ویرایش دکمهٔ submit فرم نهایی را نشان ندهد.
- `prop_customFormFormOptions` فقط برای RUN اعمال شود و مقدار پیش‌فرضش ارسال خودکار را خاموش کند (`prop_runFetch: false`). ارسال شبکه فقط با تنظیم صریح مصرف‌کننده فعال شود.
- برای گروه‌ها `prop_collapseLineCanCollapse` فعال باشد و `prop_collapseLineBodyIsOpen` از تعریف گروه یا مقدار پیش‌فرض باز استفاده کند تا فیلدها هنگام نمایش در دسترس باشند.
- گروه‌ها و فیلدها در پاسخ به ویرایش به‌صورت immutable به‌روزرسانی شوند؛ آرایه و آبجکت ورودی مصرف‌کننده مستقیماً mutate نشوند.
- مقدار هر فیلد از `prop_customFormValues[name]` در صورت وجود، سپس از `field.value` خوانده شود. تغییر مقدار در RUN از Method `VALUE_CHANGE` با شناسه، نام و مقدار تازهٔ فیلد گزارش شود.
- `ComponentLayout` محتوای `ComponentForm` را نگه دارد. `prop_structureClass` و `prop_structureStyles` از Trait پایه بیایند؛ styleهای داخلی layout از propهای سفارشی محدود و مشخص پشتیبانی کنند.
- Methodهای `SUBMIT`، `GET_RESPONSE` و `RESPONSE` رفتار متناظر `ComponentForm` را در RUN به مصرف‌کننده منتقل کنند. Method `TEMPLATE_CHANGE` تعریف جدید گروه‌ها و فیلدها را در EDIT با payload مشخص تحویل دهد.
- دسترس‌پذیری نام فیلدها، برچسب‌ها، وضعیت بازبودن گروه‌ها و دسترسی صفحه‌کلید حفظ شود.

## ۴. معماری و رندر

```text
COMPONENT                              از ComponentStructureTrait
└── STRUCTURE                          از ComponentStructureTrait
    └── ROOT: part-root
        └── ComponentLayout
            ├── EDIT: کنترل‌های ویرایش گروه/فیلد
            │   └── گروه‌ها: تکرار روی prop_customFormGroups
            │       └── ComponentCollapseLine
            └── RUN: ComponentForm
                └── گروه‌ها: تکرار روی prop_customFormGroups
                    └── ComponentCollapseLine
                        └── کنترل‌های واقعی فرم
```

- `COMPONENT` و `STRUCTURE` از `ComponentStructureTrait.schemas` بیایند و در ابتدای `Schemas` قرار گیرند.
- Schemaهای اختصاصی `ROOT` و بخش‌های لازم برای محتوای حالت EDIT/RUN فقط `part`، `props` و metadata ترجمه را تعریف کنند؛ markup، Componentسازی و شرط mode داخل `Schemas.ts` قرار نگیرد.
- `renderManagerComponent` دو Schema پایه را به Trait و Partهای اختصاصی را به متدهای renderer کلاس هدایت کند.
- یک تابع Runtime مسئول تبدیل `CustomFormField` به Component ورودی متناظر باشد. رندر هر گروه با ساخت `ComponentCollapseLine` انجام شود؛ گروه‌ها و فیلدها با selector سراسری پیدا یا دست‌کاری نشوند.
- خروجی گروه‌ها به `ComponentForm` داده شود و خود ComponentForm از طریق `ComponentLayout` درخت اصلی را تشکیل دهد. وابستگی Runtime از Component به Category وارد نشود؛ نمونه‌ها از API Category استفاده کنند.
- Observableهای mode و تعریف فرم در computedهای متصل به Scope کامپوننت مصرف شوند. تغییر mode یا تعریف فرم باید UI را به‌روز کند، بدون آن‌که در هر اجرای computed، child Component تازه و بدون dispose ساخته شود.

## ۵. قرارداد Props پیشنهادی

Props اختصاصی با `Define_ComponentProp<T>` تعریف شوند. `PropsType` و `PropsConfigType` با helperهای `TypeHelpers` استخراج شوند. propهای پایهٔ `ComponentStructureTrait` دوباره تعریف نشوند.

| Prop | نوع و مقدار پیش‌فرض | کاربرد |
|---|---|---|
| `prop_customFormMode` | `CustomFormMode` / `EDIT` | تعیین نمای ویرایش یا اجرای فرم |
| `prop_customFormGroups` | `CustomFormGroup[]` / `[]` | تعریف گروه‌ها و فیلدهای فرم |
| `prop_customFormValues` | `Record<string, unknown>` / `{}` | مقادیر اولیه یا کنترل‌شدهٔ فیلدها |
| `prop_customFormFormOptions` | تنظیمات ارسال و دکمهٔ `ComponentForm` / `{prop_runFetch: false}` | انتقال تنظیمات مجاز URL، controller، fetch و دکمهٔ submit به ComponentForm در RUN |
| `prop_customFormLayoutClass` | `string[]` / `[]` | کلاس‌های wrapper ساخته‌شده با `ComponentLayout` |
| `prop_customFormLayoutStyles` | `Record<string, string>` / `{}` | styleهای wrapper ساخته‌شده با `ComponentLayout` |

Enum `CustomFormMode` با مقدارهای `EDIT` و `RUN` در `Props.ts` تعریف شود. نوع‌های `CustomFormFieldType`، `CustomFormField`، `CustomFormGroup` و configهای لازم نیز در همان لایهٔ declarative تعریف و از `index.ts` export شوند. ساختار تنظیمات داخلی ComponentForm محدود و مستند باشد؛ کل Props آن بدون بررسی و بدون namespace به API سفارشی کپی نشوند.

## ۶. Methods، Step و چرخهٔ عمر

- `TEMPLATE_CHANGE` در حالت EDIT پس از هر تغییر تعریف، آرایهٔ immutable جدید گروه‌ها را ارائه کند.
- `VALUE_CHANGE` در حالت RUN تغییر مقدار را با `FIELD_ID`، `NAME` و `VALUE` گزارش کند.
- `SUBMIT`, `GET_RESPONSE` و `RESPONSE` در حالت RUN قرارداد هم‌نام `ComponentForm` را حفظ کنند؛ callbackهای داخلی به API بیرونی متصل شوند. این Methodها در EDIT فعال نیستند.
- `Methods.ts` برای هر Method نام runtime، ترجمه، `args` و `dataArgs` را مشخص و typeهای Method را از `TypeHelpers` استخراج کند.
- Step به‌صورت factory مستقل هر instance ساخته شود. اگر تغییرهای EDIT از Step عبور می‌کنند، endpointهای آن در `Step.ts` تعریف شوند؛ Step یا Schema محل نگه‌داری state گروه‌ها و فیلدها نباشد.
- `ComponentCustomFormBase` از `CoreComponents.App` ارث ببرد و Definition، Props، Schemas، Methods و قرارداد Trait را فراهم کند.
- کلاس نهایی constructor استاندارد `(config, methods, identity?)`، `renderContentComponent`، مسیر‌دهی Partها، `getElement()` و `dispose()` داشته باشد.
- کلاس مالک childهای `ComponentLayout`، `ComponentForm` و `ComponentCollapseLine` ساخته‌شده در هر گروه باشد. هنگام تغییر mode/تعریف، childهای جایگزین‌شده dispose شوند؛ هنگام dispose کامپوننت والد، همهٔ childها، Scope و Step آزاد شوند.

ثبت‌ها و ترجمه‌ها:

1. `Definition.ts` با `id: "component_custom_form"`، `name: "componentCustomForm"` و `version: "v1.0.0"` ساخته شود.
2. Component و همهٔ declarative exports از `module_components/lists/index.ts` ثبت شوند؛ `CoreComponents.ComponentManager.register` شامل Definition، Props، Schemas، Methods، Examples و constructor باشد.
3. callable عمومی با `CreateCategoryComponent` در `ui/fetch/form/customForm/Definition.ts` ساخته و به `components` در `ui/fetch/form/Definition.ts` افزوده شود. از ساخت Category جدید یا تغییر شناسهٔ `fetch` و `form` پرهیز شود. مسیر دسترسی مصرف‌کننده `UiCategory.UI.Fetch.CustomForm(...)` باشد.
4. `CustomForm` از `ui/fetch/form/index.ts` و `ui/fetch/index.ts` export شود؛ `ui/index.ts` از قبل `Fetch` را export می‌کند.
5. کلیدهای اختصاصی زیر `Keys.category.components.fetch.form.customForm` در `Keys.ts` تعریف و متن فارسی/انگلیسی آن‌ها در `Fa.ts` و `En.ts` ثبت شوند؛ شامل Component، Props، Schemaها، Methodها و Exampleها.

## ۸. مثال‌ها

- **EditMode:** دو گروه نمونه با چند فیلد که در EDIT امکان تغییر عنوان گروه، label، نوع و تنظیمات پایهٔ فیلدها و افزودن/حذف آن‌ها را نشان دهد؛ `TEMPLATE_CHANGE` مقدار جدید را نمایش دهد.
- **RunMode:** همان تعریف گروه/فیلد در RUN، با کنترل‌های واقعی، اعتبارسنجی و callback ارسال فرم.
- هر دو مثال با `UiCategory.UI.Fetch.CustomForm(...)` ساخته شوند، `ComponentExample` و `render(): HTMLElement` را رعایت کنند و نام/توضیح را از `Keys` بگیرند.
- Exampleها در Registry کامپوننت و صفحهٔ Tests قابل‌کشف باشند.

## ۹. معیارهای پذیرش و بررسی

- `UiCategory.UI.Fetch.CustomForm` resolve شود و کامپوننت داخل دستهٔ موجود `fetch → form` نمایش داده شود.
- `EDIT` ابزار ویرایش گروه‌ها/فیلدها را نشان دهد؛ تغییر mode به `RUN` همان تعریف را به فیلدهای قابل‌ورود تبدیل کند.
- هر گروه در هر دو حالت یک `ComponentCollapseLine` باشد و عنوان، وضعیت بازشدن و محتوای گروه درست نمایش داده شوند.
- `ComponentLayout` wrapper بیرونی و `ComponentForm` ظرف فرم نهایی باشند؛ ارسال و اعتبارسنجی RUN از قرارداد ComponentForm عبور کند.
- `TEMPLATE_CHANGE` دادهٔ جدید را بدون mutate کردن config ورودی ارائه کند؛ `SUBMIT`/`GET_RESPONSE`/`RESPONSE` در RUN قابل‌دسترسی باشند.
- تغییرهای Observable پس از render به UI منعکس شوند و ساخت/تعویض child Componentها منابع قبلی را dispose کند.
- تمام گروه‌ها و فیلدهای ساخته‌شده هنگام dispose والد پاک‌سازی شوند؛ در DOM مقدار `[object Object]` یا markup خام از دادهٔ تعریف فرم ظاهر نشود.
- `npm run build:app` و `git diff --check` اجرا شوند. خطاهای type-check موجود پروژه از خطاهای جدید تفکیک و گزارش شوند.

## ۱۰. خارج از محدوده

- ساخت یا تغییر API عمومی `ComponentForm`، `ComponentLayout` یا `ComponentCollapseLine`.
- ایجاد Category جدید زیر `UI.Fetch` یا تغییر دسته‌بندی موجود `fetch → form`.
- ذخیرهٔ دائمی قالب فرم روی سرور/مرورگر، import/export فایل و نسخه‌بندی فرم‌ها.
- drag-and-drop، ساخت input Componentهای جدید، اجرای کد سفارشی، HTML خام یا selector سراسری.
- ارسال شبکهٔ اجباری بدون تنظیم صریح مصرف‌کننده؛ تنظیمات موجود `ComponentForm` باید قابل‌عبور باشند.
