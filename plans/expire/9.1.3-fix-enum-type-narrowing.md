# Plan 9.1.3 — Fix Prop Type Extraction Contract (Enum & Literal Narrowing)

## Problem

`TS2322: Type 'ButtonSemantic.BACK' is not assignable to type 'ButtonSemantic.SUBMIT'`

### Root Cause — تحلیل دقیق

مشکل در **نحوه استخراج نوع Prop** از تعریف Props است، نه در مقدار `default`.

#### زنجیره استنتاج نوع

```ts
// 1. تعریف prop entry
prop_btnSemantic: {
    prop:         "prop_btnSemantic",
    default:      ButtonSemantic.SUBMIT,
    name:         ...,
    description:  ...,
} satisfies TComponentPropEntry<ButtonSemantic>

// 2. استخراج نوع
export type PropsType = ExtractPropsType<typeof Props>;

// 3. نتیجه فعلی (نادرست)
type PropsType = { prop_btnSemantic: ButtonSemantic.SUBMIT, ... }
//                                    ^^^^^^^^^^^^^^^^^^^^^ literal narrowed!

// 4. نتیجه مطلوب
type PropsType = { prop_btnSemantic: ButtonSemantic, ... }
//                                    ^^^^^^^^^^^^^^^ از قرارداد TComponentPropEntry<T>
```

#### چرا `satisfies` کافی نیست

`satisfies TComponentPropEntry<ButtonSemantic>` فقط **اعتبارسنجی** می‌کند که آبجکت
با `Interface_ComponentProp<ButtonSemantic>` سازگار است. اما نوع استنباط‌شده‌ی
`typeof Props` همچنان **نوع literal مقدار `default`** را حفظ می‌کند، نه نوع generic `T`.

`ExtractPropsType` فعلی از `TProps[K]["default"]` استفاده می‌کند — یعنی نوع **مقدار**
را استخراج می‌کند، نه نوع **قرارداد**.

#### مشکل ساختاری

```ts
// Interface_ComponentProp فعلی
export interface Interface_ComponentProp<TPropTypes> {
    prop:              string;
    default:           TPropTypes;  // ← T فقط برای validation، در typeof حفظ نمی‌شود
    value?:            null;
    hasMultiTemplate?: boolean;
    name?:             UtilBrands.TranslationKey;
    description?:      UtilBrands.TranslationKey;
}

// ExtractPropsType فعلی
export type ExtractPropsType<
    TProps extends Record<string, { default: any }>
> = {
    [K in keyof TProps]: TProps[K]["default"]  // ← نوع inferred از مقدار، نه از generic T
};
```

**مسئله اصلی:** `satisfies` resulting expression type را به target type تبدیل نمی‌کند.
بنابراین generic argument استفاده‌شده در target به‌صورت یک metadata قابل بازیابی در
`typeof` ذخیره نمی‌شود. نوع نهایی property همچنان از inference/contextual typing خود
expression حاصل می‌شود و باید با compiler نسخه پروژه verify شود. در نتیجه `T` در
`Interface_ComponentProp<T>` در `typeof Props` قابل بازیابی نیست.

### Scope — All Affected Props

این مشکل مختص enum نیست. **هر مقدار literal** که `satisfies` آن را preserve می‌کند
می‌تواند دچار همین مشکل باشد.

> **نکته:** نوع‌های دقیق inferred باید با TypeScript version و compiler
> configuration پروژه verify شوند. این رفتار به contextual typing و widening بستگی دارد
> و ممکن است بین نسخه‌های TypeScript متفاوت باشد.

| Literal Value | Explicit Generic Contract | Expected Type |
|---------------|---------------------------|---------------|
| `ButtonSemantic.SUBMIT` | `Define_ComponentProp<ButtonSemantic>` | `ButtonSemantic` |
| `null` | `Define_ComponentProp<string \| null>` | `string \| null` |
| `[]` | `Define_ComponentProp<string[]>` | `string[]` |
| `{}` | `Define_ComponentProp<Record<string, string>>` | `Record<string, string>` |

**مشاهدات auto-widen (نیاز به verification با compiler پروژه):**
- `""` → احتمالاً `string` (string literals در mutable context گسترش می‌یابند)
- `false` → احتمالاً `boolean` (boolean literals معمولاً گسترش می‌یابند)

> **اصل مهم:** `satisfies` نوع concrete expression را به‌اندازه‌ای حفظ می‌کند که
> generic contract `T` نمی‌تواند به‌طور قابل اعتماد از `typeof Props` بازیابی شود.
> helper این contract را صریحاً در return type encode می‌کند.
>
> **نکته:** این‌ها automatic widening transformations نیستند. این‌ها explicit prop
> contract‌هایی هستند که توسط `Define_ComponentProp<T>` تامین می‌شوند، در حالی که
> runtime default value بدون تغییر باقی می‌ماند.

### تاثیر روی Methods

`Methods.ts` ها مستقیماً به Props entries ارجاع می‌دهند:
```ts
args: {
    SEMANTIC: ButtonProps.prop_btnSemantic,  // ← نوع narrowed به Methods هم منتقل می‌شود
}
```

`ExtractMethodsComponentArgs` فعلی از `TMethods[K]["args"][ArgKey]` و سپس
`{ default: infer T }` استخراج می‌کند. اگر prop entry بعد از migration از نوع
`Interface_ComponentProp<ButtonSemantic>` باشد، extraction فعلی ممکن است همچنان
از `default` field استخراج کند و `ButtonSemantic.SUBMIT` را برگرداند.

این chain باید در Phase 6 verify شود قبل از تغییر `ExtractMethodsComponentArgs`.

## Investigation — آیا extraction از generic T ممکن است؟

### محدودیت TypeScript

TypeScript در `typeof` یک object literal، **نوع concrete** هر property را حفظ می‌کند،
نه پارامتر generic ای که در `satisfies` استفاده شده. این یک محدودیت ذاتی TypeScript است.

```ts
const x = { a: 5 } satisfies MyInterface<number>;
// typeof x.a === 5 (literal)
// نه number (generic T)
```

هیچ مکانیزمی در TypeScript وجود ندارد که بگوید: «نوع `x.a` را از `MyInterface<number>`
استخراج کن، نه از مقدار `5`».

### نتیجه

**استخراج نوع Prop از generic `T` در `TComponentPropEntry<T>` از طریق `typeof Props`
با `satisfies` ممکن نیست.** این یک محدودیت ذاتی TypeScript است.

اما می‌توان **ساختار تعریف Props** را طوری تغییر داد که generic `T` در نوع استنباط‌شده
حفظ شود: استفاده از یک helper function با return type صریح `Interface_ComponentProp<T>`.

## Alternatives

### Alternative A — Helper Function `Define_ComponentProp<T>(entry)` (Recommended)

**ایده:** به جای `satisfies TComponentPropEntry<T>` روی هر entry، از helper function
موجود `Define_ComponentProp` با overload جدید استفاده می‌کنیم که generic `T` را در
نوع بازگشتی حفظ می‌کند.

```ts
// overload جدید (per-entry)
function Define_ComponentProp<T>(
    entry: Interface_ComponentProp<T>
): Interface_ComponentProp<T>;
```

وقتی `T` **صریحاً** مشخص شود:
```ts
Define_ComponentProp<ButtonSemantic>({ default: ButtonSemantic.SUBMIT, ... })
// T = ButtonSemantic (صریح، نه inferred)
// return type: Interface_ComponentProp<ButtonSemantic>
// typeof x.default === ButtonSemantic (نه ButtonSemantic.SUBMIT)
```

**Syntax مصرف‌کننده:**
```ts
prop_btnSemantic: Define_ComponentProp<ButtonSemantic>({
    prop:         "prop_btnSemantic",
    default:      ButtonSemantic.SUBMIT,
    name:         ...,
    description:  ...,
}),
```

**مزایا:**
- Generic `T` صریحاً مشخص می‌شود — نه نیاز به `as`
- `ExtractPropsType` می‌تواند از generic `T` استخراج کند (به‌جای `default`)
- Validation توسط function parameter type check انجام می‌شود
- برای componentهای آینده، الگوی طبیعی و safe
- از همان نام موجود `Define_ComponentProp` استفاده می‌کند — API موازی ساخته نمی‌شود

**معایب:**
- Syntax هر entry تغییر می‌کند
- نیاز به migration Props.ts های affected
- `Define_ComponentProp<T>` صریح بودن نوع را الزامی می‌کند (که در واقع مزیت است)

### Alternative B — `as` Widening (per-prop)

**ایده:** برای هر prop که `default` آن literal-narrowed است، از `as ExpectedType` استفاده کنیم.

```ts
prop_btnSemantic: {
    default: ButtonSemantic.SUBMIT as ButtonSemantic,
    ...
} satisfies TComponentPropEntry<ButtonSemantic>
```

**معایب:**
- **Workaround، نه اصلاح ریشه** — مشکل برای هر prop جدید تکرار می‌شود
- **فراموشی** — developer ممکن است `as` را فراموش کند
- **تکرار** — نوع هم در `satisfies T` و هم در `as T` نوشته می‌شود

### Alternative C — Type Annotation روی کل Props Object

**رد شده:** چون هر prop نوع متفاوتی دارد، یک annotation کلی نمی‌تواند همه را پوشش دهد.

### Alternative D — Modify `ExtractPropsType` به‌تنهایی

**رد شده:** وقتی entry با `satisfies` تعریف شده، `typeof Props` نوع concrete استخراج می‌کند.
`TProps[K] extends Interface_ComponentProp<infer T>` در اینجا `T` را به‌عنوان
نوع literal استخراج می‌کند (چون `default: ButtonSemantic.SUBMIT` با
`Interface_ComponentProp<ButtonSemantic.SUBMIT>` سازگار است).

### Comparison Matrix

| Criterion | A: `Define_ComponentProp<T>` | B: `as` widening | C: Annotation | D: Modify Extract |
|-----------|:-:|:-:|:-:|:-:|
| اصلاح ریشه | ✅ | ❌ | ❌ | ❌ |
| بدون `as` در default | ✅ | ❌ | ✅ | ✅ |
| حفظ validation | ✅ | ✅ | ✅ | ✅ |
| Safe برای propهای آینده | ✅ | ❌ | ❌ | ❌ |
| استفاده از API موجود | ✅ | ✅ | ❌ | ✅ |
| نام یکپارچه | ✅ | ✅ | ❌ | ✅ |

## Recommended Solution — Alternative A: `Define_ComponentProp<T>`

### Naming — استفاده از API موجود

`Define_ComponentProp` از قبل در پروژه وجود دارد و به‌عنوان `CoreComponents.DefineProp`
در 4 Base class استفاده می‌شود:

- `ComponentStructureBase.ts`
- `ComponentButtonBase.ts`
- `ComponentIconBase.ts`
- `ComponentMessagesBase.ts`

Signature فعلی (برای کل Props object):
```ts
export function Define_ComponentProp<TPropTypes>(
    patterns: { [K in PropType<TPropTypes>]: PropInterface<TPropTypes[K]> }
): { [K in PropType<TPropTypes>]: PropInterface<TPropTypes[K]> }
```

ما یک **overload** اضافه می‌کنیم (per-entry):
```ts
export function Define_ComponentProp<T>(
    entry: Interface_ComponentProp<T>
): Interface_ComponentProp<T>;
```

این دو overload مکمل‌اند: یکی برای کل Props object، یکی برای per-entry.
هیچ API موازی ساخته نمی‌شود.

### Design Principles

1. **Return type صریح:** `Define_ComponentProp<T>` باید **عمداً** `Interface_ComponentProp<T>`
   را به‌عنوان return type داشته باشد. این invariant کلیدی است — extraction فقط از همین
   خروجی استفاده می‌کند.

2. **`satisfies` روی کل Props object حفظ می‌شود:**
   ```ts
   export const Props = {
       prop_btnSemantic: Define_ComponentProp<ButtonSemantic>({...}),
       ...
   } satisfies CoreComponents.ComponentProps;
   ```
   `Define_ComponentProp<T>` validation نوع هر entry را انجام می‌دهد و
   `satisfies CoreComponents.ComponentProps` validation ساختاری سطح بالاتر را انجام می‌دهد.
   این دو validation مکمل‌اند.

3. **`ExtractPropsType` فقط در صورت نیاز تغییر می‌کند:** اگر بعد از استفاده از
   `Define_ComponentProp<T>`، نوع entry به `Interface_ComponentProp<T>` تبدیل شود،
   آنگاه `TProps[K]["default"]` در `ExtractPropsType` فعلی برابر `T` خواهد بود
   (چون `Interface_ComponentProp<ButtonSemantic>["default"]` === `ButtonSemantic`).
   یعنی ممکن است اصلاً لازم نباشد `ExtractPropsType` را تغییر دهیم.
   این باید در Phase 2 با compiler ثابت شود — قبل از هر تغییر.

4. **`ExtractMethodsComponentArgs` فعلاً تغییر نمی‌کند:** تا زمانی که chain
   `Define_ComponentProp<T>` → Props entry → Methods args → extraction
   verify شود.

5. **Bug fix های nullable مستقل از type-extraction fix:** اصلاح `prop_btnIcon` و
   بررسی `prop_icon` به‌عنوان semantic bug fix مستقل در همان Plan نگه داشته می‌شوند،
   اما باید مستقل از extraction regression تست و verify شوند.

## Phases

### Phase 1 — Proof: Overload Resolution + `Define_ComponentProp<T>` Behavior

**هدف:**
1. بررسی تمام استفاده‌های فعلی `Define_ComponentProp` و اثبات اینکه overload جدید
   با آن‌ها تداخل نمی‌کند.
2. ثابت کن که `Define_ComponentProp<T>` با return type صریح، generic `T` را در
   `typeof` حفظ می‌کند — قبل از هر migration.

#### 1A. Grep existing usages + circular import check

قبل از اضافه‌کردن overload، تمام usageهای فعلی `Define_ComponentProp` (aka
`CoreComponents.DefineProp`) باید بررسی شوند:

```
grep -r "DefineProp\|Define_ComponentProp" src/
```

همچنین بررسی کن که `Define_ComponentProp` (در `module_core`) توسط Propsها (در
`module_ui`) import می‌شود. جهت import باید verify شود که circular dependency
جدیدی ایجاد نمی‌کند:
```
grep -r "from.*module_core.*Define_ComponentProp\|from.*core_components.*DefineProp" src/framework/module_ui/module_components/lists/
```
اگر circular dependency وجود دارد، باید قبل از Phase 1B حل شود.

استفاده‌های فعلی (از بررسی قبلی):
- `ComponentStructureBase.ts`: `CoreComponents.DefineProp<TProp>({...Props} as any)`
- `ComponentButtonBase.ts`: `CoreComponents.DefineProp<PropsType & Record<string, any>>({...} as any)`
- `ComponentIconBase.ts`: `CoreComponents.DefineProp<PropsType & Record<string, any>>({...} as any)`
- `ComponentMessagesBase.ts`: `CoreComponents.DefineProp<PropsType & Record<string, any>>({...} as any)`

همگی با signature فعلی (whole patterns object) و `as any` استفاده می‌شوند.
باید verify شود که بعد از اضافه‌شدن overload جدید، TypeScript برای این callها همچنان
overload موجود را انتخاب کند.

> **نکته مهم درباره ترتیب overload:** چون callهای فعلی از `as any` استفاده می‌کنند،
> هر دو overload ممکن است applicable باشند. **overload موجود باید اول declare شود**
> و return type واقعی انتخاب‌شده با `Assert<IsEqual<...>>` verify شود.
> ترتیب overload بخشی از compatibility contract است، نه صرفاً implementation preference.

#### 1B. Add overload to `Define_ComponentProp`

**فایل:** `src/framework/module_core/module_components/tools/prop/Define_ComponentProp.ts`

```ts
import {Interface_ComponentProp as PropInterface} from "./Interface_ComponentProp";
import {Type_ComponentProp as PropType} from "./Type_ComponentProp";

// Overload 1: existing whole-object API (MUST be first for `as any` compatibility)
export function Define_ComponentProp<TPropTypes>(
    patterns: { [K in PropType<TPropTypes>]: PropInterface<TPropTypes[K]> }
): { [K in PropType<TPropTypes>]: PropInterface<TPropTypes[K]> };
// Overload 2: new per-entry API (second, for explicit single-entry calls)
export function Define_ComponentProp<T>(
    entry: PropInterface<T>
): PropInterface<T>;
// Implementation
export function Define_ComponentProp(entry: any): any {
    return entry;
}
```

> **چرا ترتیب مهم است:**
> - callهای فعلی: `Define_ComponentProp<Record<string, any>>({...} as any)` —
>   چون argument `any` است، هر دو overload می‌توانند match شوند. با overload موجود
>   اول، TypeScript آن را انتخاب می‌کند و return contract قبلی حفظ می‌شود.
> - callهای جدید: `Define_ComponentProp<ButtonSemantic>({ prop: ..., default: ... })` —
>   argument یک `Interface_ComponentProp<T>` است که با whole-object overload سازگار نیست
>   (چون `prop` و `default` فیلدهای مستقیم هستند، نه یک map از prop entries).
>   پس TypeScript به overload دوم می‌رود.
>
> **اگر ترتیب برعکس باشد:** overload per-entry اول می‌آید، `as any` با آن match می‌شود،
> و return type به `Interface_ComponentProp<Record<string, any>>` تبدیل می‌شود —
> که با رفتار فعلی ناسازگار است.

#### 1C. Write proof file

**فایل:** `src/framework/module_ui/module_components/tools/type/__verify__/DefinePropProof.ts`

```ts
import {Define_ComponentProp} from "@/core_components";
import type {Interface_ComponentProp} from "@/core_components";

type IsEqual<A, B> =
    (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Assert<T extends true> = T;

// --- Test enum ---
enum TestEnum {
    A = "a",
    B = "b",
}

const enumEntry = Define_ComponentProp<TestEnum>({
    prop: "test",
    default: TestEnum.A,
});

type EnumEntryType = typeof enumEntry;
// Must be Interface_ComponentProp<TestEnum>, NOT concrete with default: TestEnum.A

type _EnumIsInterface = Assert<
    IsEqual<EnumEntryType, Interface_ComponentProp<TestEnum>>
>;

type EnumExtracted = EnumEntryType extends Interface_ComponentProp<infer T> ? T : never;
type _EnumExtracted = Assert<IsEqual<EnumExtracted, TestEnum>>;

// --- Test string | null ---
const nullEntry = Define_ComponentProp<string | null>({
    prop: "test",
    default: null,
});

type NullEntryType = typeof nullEntry;
type _NullIsInterface = Assert<IsEqual<NullEntryType, Interface_ComponentProp<string | null>>>;
type NullExtracted = NullEntryType extends Interface_ComponentProp<infer T> ? T : never;
type _NullExtracted = Assert<IsEqual<NullExtracted, string | null>>;

// --- Test string[] ---
const arrayEntry = Define_ComponentProp<string[]>({
    prop: "test",
    default: [],
});

type ArrayEntryType = typeof arrayEntry;
type _ArrayIsInterface = Assert<IsEqual<ArrayEntryType, Interface_ComponentProp<string[]>>>;
type ArrayExtracted = ArrayEntryType extends Interface_ComponentProp<infer T> ? T : never;
type _ArrayExtracted = Assert<IsEqual<ArrayExtracted, string[]>>;

// --- Test Record<string, string> ---
const objectEntry = Define_ComponentProp<Record<string, string>>({
    prop: "test",
    default: {},
});

type ObjectEntryType = typeof objectEntry;
type _ObjectIsInterface = Assert<IsEqual<ObjectEntryType, Interface_ComponentProp<Record<string, string>>>>;
type ObjectExtracted = ObjectEntryType extends Interface_ComponentProp<infer T> ? T : never;
type _ObjectExtracted = Assert<IsEqual<ObjectExtracted, Record<string, string>>>;

// --- Test boolean ---
const boolEntry = Define_ComponentProp<boolean>({
    prop: "test",
    default: false,
});

type BoolEntryType = typeof boolEntry;
type _BoolIsInterface = Assert<IsEqual<BoolEntryType, Interface_ComponentProp<boolean>>>;
type BoolExtracted = BoolEntryType extends Interface_ComponentProp<infer T> ? T : never;
type _BoolExtracted = Assert<IsEqual<BoolExtracted, boolean>>;

// --- Test: compile-time type widening (regression assertion) ---
// NOTE: This is a regression assertion, NOT an independent proof.
// It is logically implied by _EnumIsInterface above:
//   typeof enumEntry === Interface_ComponentProp<TestEnum>
//   → typeof enumEntry.default === TestEnum (from the interface definition)
// Keep it as a regression guard — if it fails, the return type contract broke.
type _DefaultIsWide = Assert<IsEqual<typeof enumEntry.default, TestEnum>>;

// --- Test: negative type test (validation enforcement) ---
// The explicit generic <T> must enforce validation, not just be decoration.
// @ts-expect-error — default "invalid" is not assignable to TestEnum
Define_ComponentProp<TestEnum>({
    prop: "test",
    default: "invalid",
});

// --- Test: nullable type acceptance ---
// Define_ComponentProp<string | null> with default: null must compile
const nullableEntry = Define_ComponentProp<string | null>({
    prop: "test",
    default: null,
});
type _NullableAccepts = Assert<IsEqual<typeof nullableEntry.default, string | null>>;
```

> **Invariant های compile-time در Phase 1C:**
> 1. `typeof entry === Interface_ComponentProp<T>` — return type صریح (برای enum, nullable, array, object, boolean)
> 2. `typeof entry.default === T` — type widening
> 3. `@ts-expect-error` — validation enforced
>
> **الزام generic صریح:** Consumer usage باید `<T>` را صراحتاً مشخص کند.
> Type inference به‌تنهایی برای حفظ semantic contract کافی نیست. اگر developer
> بنویسد `Define_ComponentProp({ default: ButtonSemantic.SUBMIT })` بدون `<T>`،
> TypeScript ممکن است `T = ButtonSemantic.SUBMIT` را infer کند و همان مشکل
> narrowing دوباره برگردد. API design باید این را enforce کند یا حداقل Plan صریحاً
> بگوید:
> **Consumer usage must provide `<T>` explicitly. Type inference alone is not
> considered sufficient for preserving the intended semantic contract.**
>
> Runtime value preservation در Phase 1E (فایل جدا) انجام می‌شود.

#### 1D. Existing whole-object compatibility proof

**هدف:** ثابت کن که callهای فعلی (با `as any`) همچنان همان return contract قبلی را
dریافت می‌کنند — نه return contract per-entry overload.

```ts
// Simulate existing usage pattern with `as any`
const existingCall = Define_ComponentProp<Record<string, any>>({
    prop_test: { prop: "test", default: "value" },
} as any);

type ExistingCallType = typeof existingCall;

// The return type must match the whole-object contract, NOT Interface_ComponentProp<...>.
// If per-entry overload were selected, return type would be
// Interface_ComponentProp<Record<string, any>> — which is wrong.

// IMPORTANT: Do NOT reconstruct ExpectedExistingCallType independently.
// If the project already has a type alias for the whole-object return contract, use it.
// If not, you may proceed WITHOUT a shared alias — the inline reconstruction below
// is acceptable as a first pass. Only if `_ExistingCallPreserved` FAILS should you
// consider introducing a shared `WholeObjectReturn<TPropTypes>` alias used by BOTH
// the overload AND this test, to ensure comparison against the SAME contract.
//
//   export type WholeObjectReturn<TPropTypes> = {
//       [K in PropType<TPropTypes>]: PropInterface<TPropTypes[K]>
//   };
//
// Then the overload becomes: `): WholeObjectReturn<TPropTypes>;`
// And the test becomes:
//   type ExpectedExistingCallType = WholeObjectReturn<Record<string, any>>;

type ExpectedExistingCallType = {
    [K in PropType<Record<string, any>>]: PropInterface<Record<string, any>[K]>
};

type _ExistingCallPreserved = Assert<
    IsEqual<ExistingCallType, ExpectedExistingCallType>
>;
```

> **اگر `_ExistingCallPreserved` fail شد**، یعنی per-entry overload به‌جای
> whole-object overload انتخاب شده است. این یک مشکل طراحی overload است.
> در آن حالت باید طراحی اصلاح شود (مثلاً rename یکی، یا استفاده از شرط‌های
> سازگارتر) قبل از ادامه migration.

همچنین per-entry call را تست کن تا ثابت شود overload دوم انتخاب می‌شود:

```ts
const singleEntry = Define_ComponentProp<TestEnum>({
    prop: "test",
    default: TestEnum.A,
});

type _SingleEntryIsInterface = Assert<
    IsEqual<typeof singleEntry, Interface_ComponentProp<TestEnum>>
>;
```

> **هر دو `_ExistingCallPreserved` و `_SingleEntryIsInterface` باید همزمان pass شوند.**
> این ثابت می‌کند هر دو overload درست کار می‌کنند و به یکدیگر تداخل ندارند.

#### 1E. Runtime identity proof

**فایل:** `src/framework/module_ui/module_components/tools/type/__verify__/DefinePropRuntimeProof.ts`

> **توجه:** این فایل باید جدا از proof type-level باشد. `tsc --noEmit` کد را

#### 1F. Gate criteria

- تمام Assert های 1C compile شوند → return type === `Interface_ComponentProp<T>` برای همه types
- `_DefaultIsWide` compile شود → نوع `default` widened است (compile-time).
- `_NullableAccepts` compile شود → nullable types قابل پذیرش هستند.
- `@ts-expect-error` negative test compile error مورد انتظار را consume کند → validation enforced.
- `_ExistingCallPreserved` compile شود → callهای فعلی break نمی‌شوند (overload موجود اول انتخاب می‌شود).
- `_SingleEntryIsInterface` compile شود → per-entry call overload دوم را انتخاب می‌کند.
- Runtime identity proof (1E) اجرا و pass شود → helper مقدار runtime را تغییر نمی‌دهد.

اگر همگی pass شدند → ادامه به Phase 2.
اگر هر یک fail شد → طراحی helper را اصلاح کن قبل از هر migration.

### Phase 2 — Proof: Does `ExtractPropsType` Current Need Changing?

**هدف:** ثابت کن که آیا `ExtractPropsType` فعلی (بدون تغییر) بعد از استفاده از
`Define_ComponentProp<T>` همچنان narrowing دارد یا خیر. فقط اگر مشکل persists بود،
تغییر انجام می‌دهیم.

#### 2A. Key Insight

بعد از `Define_ComponentProp<ButtonSemantic>(...)`، نوع entry می‌شود:
`Interface_ComponentProp<ButtonSemantic>`

پس در `ExtractPropsType` فعلی:
```ts
type ExtractPropsType<TProps extends Record<string, { default: any }>> = {
    [K in keyof TProps]: TProps[K]["default"]
};
```

`TProps[K]["default"]` برابر است با `Interface_ComponentProp<ButtonSemantic>["default"]`
که برابر است با `ButtonSemantic` (نه `ButtonSemantic.SUBMIT`).

یعنی **ممکن است `ExtractPropsType` فعلی بدون تغییر درست کار کند.**

#### 2B. Compile proof: Current `ExtractPropsType` with helper output

**فایل:** `src/framework/module_ui/module_components/tools/type/__verify__/DefinePropProof.ts`
(append to Phase 1 file)

```ts
import type {ExtractPropsType} from "../TypeHelpers";

// Use the entries from Phase 1
const testProps = {
    enumProp: Define_ComponentProp<TestEnum>({
        prop: "enumProp", default: TestEnum.A,
    }),
    nullableProp: Define_ComponentProp<string | null>({
        prop: "nullableProp", default: null,
    }),
    arrayProp: Define_ComponentProp<string[]>({
        prop: "arrayProp", default: [],
    }),
    objectProp: Define_ComponentProp<Record<string, string>>({
        prop: "objectProp", default: {},
    }),
    boolProp: Define_ComponentProp<boolean>({
        prop: "boolProp", default: false,
    }),
} satisfies Record<string, Interface_ComponentProp<any>>;

// Test with CURRENT ExtractPropsType (no changes yet)

type _2 = Assert<IsEqual<TestPropsType["nullableProp"], string | null>>;

// --- Negative proof: enum must NOT narrow to literal ---

    IsEqual<IsEqual<TestPropsType["enumProp"], TestEnum.A>, false>
```

#### 2C. Compile proof: Legacy entry behavior

همچنین باید ثابت شود که برای entries قدیمی (با `satisfies`، بدون helper)،
`ExtractPropsType` فعلی چه نتیجه‌ای می‌دهد:

```ts
// Legacy entry (satisfies, no helper)
const legacyEntry = {
    prop: "legacy",
    default: TestEnum.A,
} satisfies Interface_ComponentProp<TestEnum>;

type LegacyDefault = typeof legacyEntry.default;
// Do NOT assume the exact inferred type. Record the compiler result.
// Possible outcomes:
//   a) LegacyDefault === TestEnum.A (literal narrowed) — current bug persists
//   b) LegacyDefault === TestEnum (widened) — unexpected, would mean no bug
//   c) Something else entirely

type LegacyExtracted = ExtractPropsType<{ legacy: typeof legacyEntry }>;
// Record LegacyExtracted["legacy"] from compiler output.
// Do NOT write an Assert with an assumed expected type.
```

> **نتیجه inference مربوط به legacy satisfies entries را فرض نکن.**
> نتیجه دقیق compiler را ثبت کن و compatibility را بر اساس آن تعیین کن.
> TypeScript structural typing ممکن است `infer T` را متفاوت از انتظار تولید کند.
> این یک تست empirical است، نه design assumption.

#### 2D. Decision

- **اگر تمام Assert های 2B pass شدند** → `ExtractPropsType` فعلی **بدون تغییر**
  درست کار می‌کند. ادامه به Phase 3 بدون تغییر `ExtractPropsType`.
  > این نتیجه مطلوب‌تر است — تغییر معماری اضافی ندارد.

- **اگر هر یک از 2B fail شد** → `ExtractPropsType` فعلی مشکل دارد.
  در این صورت:
  1. علت fail را تعیین کن.
  2. بررسی کن که conditional infer (`TProps[K] extends Interface_ComponentProp<infer T> ? T : never`)
     آیا مشکل را حل می‌کند.
  3. **compatibility proof برای تمام consumerهای فعلی `ExtractPropsType` اجرا کن.**
     تغییر constraint از `Record<string, { default: any }>` به
     `Record<string, Interface_ComponentProp<any>>` ممکن است compatibility surface را تغییر دهد.
  4. فقط بعد از تأیید compatibility، update را انجام بده:
  ```ts
  export type ExtractPropsType<
      TProps extends Record<string, Interface_ComponentProp<any>>
  > = {
      [K in keyof TProps]:
          TProps[K] extends Interface_ComponentProp<infer T>
              ? T
              : never;
  };
  ```
  > **بدون fallback.** اگر entry معتبر نیست، `never` نشان‌دهنده failure واضح است.
  > **هر تغییر به `ExtractPropsType` باید input shape فعلی را حفظ کند** مگر اینکه
  > یک migration جداگانه صراحتاً تأیید شده باشد. این یک bug fix است، نه بازطراحی
  > contract عمومی helper.

- **اگر 2C نشان داد entries قدیمی break می‌شوند** → قبل از تغییر `ExtractPropsType`،
  باید یا constraint را loosen کنیم یا migration کامل‌تر انجام دهیم.

#### 2E. `ExtractPropsConfigType` — independent proof

`ExtractPropsConfigType` باید مستقل تست شود. implementation فعلی آن ممکن است
مشابه `ExtractPropsType` باشد، ولی این یک design assumption است — نه fact.

#### 2F. DO NOT change `ExtractMethodsComponentArgs` yet

## Rollback Strategy

اگر migration نیمه‌تمام break شد (مثلاً ۱۵ از ۲۵ entry):

- `git revert` migration commit. Proof files و overload تغییرات مستقل هستند و
  می‌توانند باقی بمانند.
- Overload اضافه‌شده بدون migration هیچ side-effectی ندارد (per-entry overload فقط
  با explicit `<T>` call فعال می‌شود).
- اگر `ExtractPropsType` تغییر کرده بود، آن هم revert شود. Proof files نیازی به
  revert ندارند — آن‌ها فقط type-level tests هستند.
