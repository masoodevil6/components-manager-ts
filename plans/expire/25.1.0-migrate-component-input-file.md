# پلن 25.1.0 — انتقال ComponentInputFile به ساختار جدید

> **وضعیت:** پیشنهادی؛ هنوز پیاده‌سازی نشده است  
> **نسخه پلن:** 25.1.0  
> **منبع Legacy:** `last/tools/components/ComponentInputFile.ts`  
> **راهنما:** `documents/guides/component-create.md`  
> **مقصد:** `src/framework/module_ui/module_components/lists/componentInputFile/`  
> **API مورد انتظار:** `UiCategory.UI.Inputs.InputFile(config, methods, identity)`

## 1. هدف و محدوده

انتقال آپلود فایل از ساختار `ComponentBase` قدیمی به معماری جدید declarative/runtime، با حفظ رفتارها و قرارداد عمومی قابل استفاده: انتخاب فایل با کلیک یا drag-and-drop، محدودیت نوع/تعداد/حجم، تفکیک فایل‌های پذیرفته و ردشده، نمایش فهرست، حذف تأییدشده، اعتبارسنجی، و callbackهای تغییر و حذف.

مبنای انتقال، رفتار موجود در Legacy است. این پلن API تازه‌ای برای آپلود شبکه‌ای یا نگه‌داری فایل روی سرور تعریف نمی‌کند؛ کامپوننت فقط `File`های انتخاب‌شده را مدیریت و به مصرف‌کننده اعلام می‌کند.

## 2. درخت رندر مورد انتظار

```text
ComponentInputFile
├── 1. ComponentLabelTrait (شرطی)
├── 2. part-input-file-form
│   ├── 2.1. part-input-file-value
│   │   └── input[type=file] مخفی
│   ├── 2.2. part-input-file-drop-zone
│   │   └── متن راهنما و وضعیت hover/drag
│   └── 2.3. part-input-file-list (شرطی با prop_showListFiles)
│       ├── فایل پذیرفته‌شده: نام، اندازه، آیکون حذف
│       └── فایل ردشده: نام، اندازه، شرح خطا
├── 3. پنجره تأیید حذف (شرطی)
└── 4. ComponentValidate (شرطی)
```

ساختار از `ComponentStructureTrait` برای `COMPONENT` و `STRUCTURE` استفاده کند. Label از `ComponentLabelTrait` بیاید. برای جزءهای فرمی از کامپوننت‌های موجود نظیر `ComponentIcon`، `ComponentRecyclerView`، `ComponentWindowConfirm` و `ComponentValidate` استفاده شود؛ اگر `ComponentWindowConfirm` در معماری جدید API قابل استفاده ندارد، پیش از ساخت جایگزین، قابلیت موجودش بررسی و دلیل انتخاب مستند شود.

## 3. قرارداد props و نگاشت Legacy

Props پایهٔ component/structure و label دوباره تعریف نشوند؛ از traitها و props پایهٔ مناسب استفاده شود. props اختصاصی با `Define_ComponentProp<T>`, کلیدهای `Keys`, `satisfies CoreComponents.ComponentProps`, و `ExtractPropsType`/`ExtractPropsConfigType` تعریف شوند.

| Legacy | تصمیم در ساختار جدید |
|---|---|
| `prop_name` | حفظ؛ نام فایل input. |
| `prop_accept` | حفظ؛ رشتهٔ accept استاندارد input فایل، پیش‌فرض `*`. |
| `prop_maxCount` | حفظ؛ `null` یعنی محدودیت تعداد اعمال نشود. `multiple` وقتی مجاز باشد فعال شود. |
| `prop_maxSize` | حفظ با واحد و رفتار سازگار Legacy؛ Legacy مقدار را هنگام بررسی در 1000 ضرب می‌کند. واحد نمایشی و مستندات باید با رفتار واقعی پروژه روشن و یکسان شود. |
| `prop_textValidateSize`, `prop_textValidateAccept` | حفظ؛ جای‌گذاری `{{fileMaxSize}}` و `{{fileAccept}}` در توضیح راهنما/خطا انجام شود. متن‌های پیش‌فرض از سیستم ترجمه بیایند، نه متن hard-code محلی. |
| `prop_title` | حفظ به‌عنوان عنوان Validator؛ عنوان label از `ComponentLabelTrait.prop_labelTitle` باشد. |
| `prop_borderColor`, `prop_borderColorHover`, `prop_borderHeight` | حفظ برای استایل drop-zone. رنگ hover باید در رویدادهای ورود/خروج drag اعمال و بازگردانی شود؛ ارتفاع‌های سیستمی تا حد امکان با `CoreConfig.Settings.SizeName` و `UtilStyle` تعیین شوند. |
| `prop_textColor`, `prop_text` | حفظ برای متن راهنما؛ مقدار پیش‌فرض متن از ترجمه بیاید. |
| `prop_showListFiles` | حفظ؛ فهرست فایل‌ها را نمایش/مخفی کند، بدون آنکه دادهٔ انتخاب‌شده را پاک کند. |
| `var_fileIsValid`, `var_fileIsNotValid` | state داخلی باشند؛ به‌عنوان props عمومی قابل تنظیم تعریف نشوند مگر شواهد مصرف‌کنندهٔ واقعی در repository وجود داشته باشد. اگر مصرف‌کننده‌ای به آن‌ها وابسته است، پیش از حذف، مسیر سازگاری و نام جدید مستند شود. |
| `prop_deleteBody`, `prop_deleteBtnCancel`, `prop_deleteBtnAccept` | حفظ؛ متن پنجره تأیید حذف با ترجمه‌های سیستم پیش‌فرض شود. |
| `prop_backgroundColor_itemFile`, `prop_backgroundColor_itemFile_invalid`, `prop_color_itemFile`, `prop_color_itemFile_icons` | حفظ؛ استایل ردیف فایل پذیرفته/ردشده و آیکون حذف. رنگ‌های پیش‌فرض از `UtilStyle.Css_Color` و `UtilConst.ColorMain/ColorGrad` ساخته شوند. |
| `prop_isAbsoluteRule`, `prop_listRules`, `prop_msgRules` | حفظ و به `ComponentValidate` نگاشت شوند. قواعد و پیام‌ها در نبودن/غیرفعال‌بودن validator، validator نامرئی/ساخته‌نشده داشته باشند. |
| `prop_isDisable` و props label/value مشترک | از قرارداد پایه و `ComponentLabelTrait` به‌ارث برسند؛ در حالت disabled انتخاب/حذف فایل و drag/drop انجام نشود. |
| `prop_size` | به API جدید منتقل نشود؛ اندازه از تنظیمات سیستم گرفته شود. |

پیش از تثبیت حذف/تغییر هر نام Legacy، کل repository با `rg` برای مصرف‌کنندگان و نمونه‌های آن جست‌وجو شود. قرارداد `prop_maxSize` و دسترسی بیرونی به `var_fileIsValid`/`var_fileIsNotValid` موارد نیازمند تأیید از روی شواهد مصرف‌اند؛ بی‌دلیل تغییر ناسازگار داده نشود.

## 4. Schemas پیشنهادی

`COMPONENT` و `STRUCTURE` از `ComponentStructureTrait` و `LABEL` از `ComponentLabelTrait` گرفته شوند. Schemaها declarative و محدود به metadata/prop binding باشند؛ رندر و منطق در کلاس کامپوننت بمانند.

| Schema | Part پیشنهادی | مسئولیت |
|---|---|---|
| `FORM` | `part-input-file-form` | نگه‌دارندهٔ ترتیب value، drop-zone و فهرست. |
| `VALUE` | `part-input-file-value` | input[type=file] مخفی، accept/name/multiple، و رویداد change. |
| `DROP_ZONE` | `part-input-file-drop-zone` | کلیک برای باز کردن picker و مدیریت dragenter/dragover/dragleave/drop. |
| `DROP_ZONE_TEXT` | `part-input-file-drop-zone-text` | متن قابل ترجمه و توضیح محدودیت‌ها. |
| `FILES` | `part-input-file-files` | فهرست reactive فایل‌های معتبر و نامعتبر، در صورت فعال بودن نمایش. |
| `FILE_ITEM` | `part-input-file-file-item` | شماره، نام، اندازه و کنترل حذف برای فایل معتبر. |
| `FILE_ITEM_INVALID` | `part-input-file-file-item-invalid` | شماره، نام، اندازه و شرح خطا برای فایل ردشده. |
| `DELETE_CONFIRM` | `part-input-file-delete-confirm` | پنجرهٔ تأیید حذف فایل انتخاب‌شده. |
| `VALIDATE` | `part-input-file-validate` | ComponentValidate مرتبط با فایل‌های معتبر و props قواعد. |

Schema قدیمی `FOOTER_FILES_TOOLTIPS` فقط در صورت نیاز واقعی حفظ شود. در Legacy این schema محتوای tooltipها را می‌سازد، اما استفاده/جایگاهش در رندر اصلی روشن نیست؛ هنگام implementation با جست‌وجوی مصرف و مشاهدهٔ UI تعیین شود که بخشی از رندر لازم است یا قابل حذف مستند.

## 5. رفتار و state زمان اجرا

- component از Base هم‌الگوی کامپوننت‌های جدید و `createInputFileStep()` استفاده کند؛ constructor شکل `config, methods, identity` داشته باشد.
- فایل‌های معتبر و نامعتبر در state observable داخلی نگه‌داری شوند و رندر فهرست با تغییر آن‌ها واکنشی باشد.
- کلیک روی drop-zone، input مخفی را از reference خود component فعال کند؛ از `document.querySelector` و شناسه‌های سراسری برای پیدا کردن input/zone استفاده نشود.
- drag/drop از `DataTransfer.files` استفاده کند؛ رویدادهای drag در زمان disabled از انتخاب/تغییر state جلوگیری کنند. رنگ hover در پایان drag یا drop حتماً به حالت پایه برگردد.
- اعتبارسنجی هر فایل شامل اندازه و accept باشد. accept هم پسوند (`.pdf`)، MIME دقیق (`image/png`) و wildcard (`image/*`) را مانند Legacy پشتیبانی کند.
- محدودیت maxCount فقط تعداد فایل‌های معتبر را محدود کند و ورودی چندفایلی تنها وقتی بیش از یک فایل مجاز است فعال باشد. رفتار دقیق انتخاب چندباره با مقدار قبلی با رفتار Legacy/مصرف‌کنندگان تطبیق داده شود.
- callback تغییر پس از هر بار پردازش انتخاب/drop دقیقاً یک‌بار اجرا شود و آرایه‌های نهایی `FILES`, `VALID_FILES`, `INVALID_FILES` را بدهد. ترتیب فایل‌های معتبر و سپس نامعتبر مطابق Legacy حفظ شود، مگر تست مصرف‌کننده خلاف آن را نشان دهد.
- حذف فایل با پنجرهٔ تأیید انجام شود؛ لغو پنجره داده را تغییر ندهد، تأیید فقط فایل هدف را حذف کند و callback حذف و callback تغییر مطابق قرارداد مستند، بدون دوباره‌کاری یا emit مضاعف اجرا شوند.
- Legacy حذف را با `file.name` انجام می‌دهد؛ بنابراین فایل‌های هم‌نام ممکن است مبهم باشند. در ساختار جدید از شناسهٔ پایدار همان ردیف/File reference برای حذف دقیق استفاده شود، اما payload عمومی `FILE_NAME` حفظ شود. این بهبود نباید فایل هم‌نام دیگری را حذف کند.
- اندازهٔ نمایشی فایل‌ها در ردیف‌ها با واحد خوانا و محاسبهٔ درست بایت به KB باشد؛ فرمول‌های تقسیم Legacy بر 10000 عیناً کپی نشوند، مگر آزمون/قرارداد موجود ثابت کند این خروجی مورد انتظار است.
- ComponentValidate فقط با rules موجود و در حالت فعال ساخته شود؛ مقدار آن با فهرست فایل‌های معتبر همگام بماند.
- فرزندان ساخته‌شده، event stepها، subscriptionها و listenerهای drag در `dispose()` پاک شوند. رندر چندباره نباید listener یا child تکراری بسازد.
- رفتار LTR/RTL، disabled، فایل صفر بایتی، ورودی خالی، accept نامعتبر، maxCount صفر/یک/بیشتر، و drop بدون فایل بدون exception باشد.

## 6. Methods و قرارداد callbackها

نام‌های API عمومی موجود تا حد امکان حفظ شوند. Metadata و آرگومان‌ها در `Methods.ts` به‌شکل typed و بر اساس convention فعلی تعریف شوند.

| Method | Data args | قرارداد |
|---|---|---|
| `CHANGE_FILES` | `FILES: File[]`, `VALID_FILES: File[]`, `INVALID_FILES: FileItemError[]` | پس از پردازش یک batch انتخاب/drop یک‌بار اجرا شود. `FILES` با معنای Legacy (فایل‌های پذیرفته‌شده) حفظ شود؛ دو آرایهٔ مشخص نیز برای وضوح/سازگاری باقی بمانند. |
| `DELETE_FILE` | `FILE_NAME: string` | پس از تأیید و حذف هدف اجرا شود؛ callback تغییر نیز طبق قرارداد قدیمی و فقط یک‌بار وضعیت نهایی را گزارش کند. ترتیب و تعداد emitها هنگام پیاده‌سازی با مصرف‌کنندگان Legacy بررسی و در صورت تفاوت صریحاً ثبت شود. |

Method جدید برای رویدادهای داخلی drag اضافه نشود مگر API عمومی موردنیاز با شواهد مصرف‌کننده مشخص شود.


- Definition دارای `id: "component_input_file"`, `name: "componentInputFile"` و version داخلی `v1.0.0` باشد.
- factory نام `createInputFileStep` داشته باشد و stepهای لازم برای انتخاب فایل/تغییر/حذف را ثبت کند.
- API عمومی در `index.ts` شامل Component، Base، Definition، Props/types، Schemas، Methods/types و Examples متناسب با الگوی اجزای جدید باشد.
- کامپوننت در `module_components/lists/index.ts` و `ComponentManager` مطابق registration فعلی ثبت شود.
- category ورودی در `module_categories/lists/ui/inputs/` به الگوی `Input`, `InputSize` و `InputPhone` اضافه شود تا `Inputs.InputFile(config, methods, identity)` در دسترس باشد.
- برای نام component، props، schemas، methods و exampleها کلیدهای `Keys.ts` و ترجمه‌های `En.ts` و `Fa.ts` اضافه شوند. متن خطاهای قابل مشاهده و متن‌های پیش‌فرض از ترجمه سیستم استفاده کنند.
- مثال‌ها فقط از API جدید استفاده کنند و حداقل آپلود تک‌فایل، چندفایل با limit/accept، و نمایش خطای فایل ردشده را قابل مشاهده کنند.

## 8. معیارهای پذیرش و بررسی

1. کامپوننت از ComponentManager و category ورودی ساخته شود و metadata و examples آن نمایش داده شوند.
2. Label با trait ساخته شود و کلیک آن picker فایل را باز کند؛ label به input همان instance متصل باشد.
3. انتخاب با کلیک و drag/drop کار کند و فایل‌های معتبر/نامعتبر بر اساس accept، maxSize و maxCount درست دسته‌بندی شوند.
4. input مخفی تنها یک‌بار رندر شود؛ `multiple` و `accept` هنگام تغییر props کنترل‌شده همگام شوند.
5. فهرست در حالت نمایش روشن به‌صورت reactive به‌روزرسانی و در حالت خاموش فقط مخفی شود؛ حذف با cancel بدون تغییر و با confirm فقط فایل هدف را حذف کند.
6. `CHANGE_FILES` و `DELETE_FILE` با payload و تعداد فراخوانی مستند اجرا شوند؛ انتخاب بدون تغییر یا رندر مجدد callback مضاعف نسازد.
7. disabled، قواعد اعتبارسنجی، اندازهٔ نام فایل، رنگ‌های وضعیت، LTR/RTL و edge caseهای فایل مدیریت شوند.
8. dispose همهٔ childها و listenerها را پاک کند.
9. `git diff --check`, typecheck هدفمند، build/testهای موجود و تست دستی انتخاب/drag/drop/حذف/disabled انجام شود. خطاهای پایهٔ ازقبل‌موجود از خطاهای افزوده‌شده تفکیک و گزارش شوند.

## 9. خارج از محدوده

- ارسال یا ذخیرهٔ فایل روی سرور و تغییر API شبکه.
- بازنویسی مصرف‌کنندگان Legacy یا Laravel.
- تغییر رفتار عمومی `ComponentRecyclerView`, `ComponentValidate` یا `ComponentWindowConfirm` مگر مانع مستقیم و مستند همین مهاجرت باشد.
- تغییر قرارداد callbackها یا واحد `prop_maxSize` بدون بررسی مصرف‌کنندگان و شواهد.
