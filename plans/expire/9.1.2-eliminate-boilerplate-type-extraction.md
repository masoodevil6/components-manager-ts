# Plan 9.1.2 — متمرکزسازی Type Extraction از Component Definitions

> **نوع:** Refactor معماری — Centralized Type Extraction Contract
>
> **هدف:** متمرکزسازی Type Extraction از Component Definitions و حذف پیاده‌سازی‌های تکراری در Component Modules — جایگزینی ۲۴ type دستی با ۷ Helper Generic متمرکز در `module_components/tools/type`
>
> **انگیزه:**
> در معماری قدیمی (`last/`) یک آبجکت `Configs` متمرکز + helperهای `GOG_ExtractName` / `GOG_ExtractNameValue` وجود داشت که typeها را به‌صورت خودکار از `Configs` استخراج می‌کردند. در معماری جدید (`src/`) این typeها در هر کامپوننت **دستانه نوشته می‌شوند** — دقیقاً همان کد تکراری در `Props.ts`, `Schemas.ts`, `Methods.ts` هر کامپوننت.
>
> **اصل معماری:**
> ```
> Definition → Type Extraction → Component API
> ```
> این Refactor فقط DRY نیست — یک مفهوم مهم معماری ایجاد می‌کند:
> یک Definition Contract، یک Type Extraction Policy.
> این در آینده برای Component Definition / Compiler / CustomComponent / AI بسیار مهم می‌شود.
>
> **مرزبندی Type Helpers:**
> Type Helpers مسئول استخراج یا تبدیل Type از Definition هستند، نه تعریف Contract جدید.
>
> **اصل طلایی:**
> Definition، منبع حقیقت است؛ Type Helpers فقط Policy استاندارد استخراج Type از آن Definition هستند و حق ندارند Contract جدیدی به سیستم تحمیل کنند.
>
> **تفکیک مسئولیت‌ها:**
> ```
> Definition Contract
>       │
>       │ validates
>       ▼
> satisfies Interface_ComponentProp
>       │
>       │ accepted definition
>       ▼
> Type Extraction Policy
>       │
>       ▼
> ExtractPropsType
> ```
> Definition Contract ≠ Extraction Policy. Helper نباید Contract validator شود.

## ۱. وضعیت فعلی — مشکل

### ۱.۱. تکرار در هر کامپوننت

هر کامپوننت (Button, Icon, Messages, Structure, ...) این الگو را دستی تکرار می‌کند:

**Props.ts (هر کامپوننت):**
```typescript
export type PropsType = {
    [K in keyof typeof Props]: typeof Props[K]["default"]
};

export type PropsConfigType = {
    [K in keyof PropsType]: TObservableValue<PropsType[K]>
};
```

**Schemas.ts (هر کامپوننت):**
```typescript
export type SchemasType = {
    [K in keyof typeof Schemas]: typeof Schemas[K]["part"]
};
```

**Methods.ts (هر کامپوننت):**
```typescript
export type MethodsType = {
    [K in keyof typeof Methods]: (event: Event, dataArgs: any, componentArgs: any) => void
};

export type MethodsComponentArgs = {
    [K in keyof typeof Methods]: {
        [ArgKey in keyof typeof Methods[K]["args"]]:
            typeof Methods[K]["args"][ArgKey] extends { default: infer T } ? T : any;
    };
};

export type MethodsDataArgs = {
    [K in keyof typeof Methods]: typeof Methods[K]["dataArgs"];
};

export type MethodsConfigType<TThis = any> = {
    [K in keyof typeof Methods]?: (
        this: TThis,
        event: Event,
        dataArgs: MethodsDataArgs[K] | null,
        componentArgs: MethodsComponentArgs[K] | null,
    ) => void;
};
```

### ۱.۲. مقایسه با معماری قدیمی

**قدیمی (`last/`):**
```typescript
const Configs = {
    keys: { prop_x: { name: "prop_x", value: GOG_SetValue<T>(default) } },
    schemas: { X: { name: "part-x" } },
    methods: { CLICK: { name: "fn_onClick", dataArgs: {...}, componentArgs: {...} } },
} as const;

export type PropsType    = GOG_ExtractNameValue<typeof Configs.keys>;
export type SchemaType   = GOG_ExtractName<typeof Configs.schemas>;
export type MethodsType  = { [K in keyof ...]: ComponentCallBackType<...> };
```

**جدید (`src/`):**
```typescript
export const Props = { prop_x: { prop: "prop_x", default: T, ... } } satisfies ...;
export const Schemas = { X: { part: "part-x", ... } } satisfies ...;
export const Methods = { CLICK: { name: "fn_onClick", args: {...}, dataArgs: {...} } } as const;

// ❌ تکرار دستی:
export type PropsType = { [K in keyof typeof Props]: typeof Props[K]["default"] };
export type SchemasType = { [K in keyof typeof Schemas]: typeof Schemas[K]["part"] };
// ... ۵ type تکراری دیگر
```

## ۲. راه‌حل — Helper Genericهای متمرکز

### ۲.۱. فایل جدید: `tools/type/TypeHelpers.ts`

یک ماژول جدید در `module_components/tools/type/` با helperهای generic.

**اصل Constraint:** هر Helper فقط به حداقل Contract موردنیاز برای استخراج وابسته است — نه کل `Interface_ComponentProp` یا `Interface_ComponentSchema`.

```typescript
// tools/type/TypeHelpers.ts

import type {TObservableValue} from "@/core_observable";

// ──────────────────────────────────────
// Props
// ──────────────────────────────────────

/** استخراج نوع مقدار default از یک Record<Props>
 *
 *  Contract موردنیاز: فقط فیلد `default` */
export type ExtractPropsType<
    TProps extends Record<string, { default: any }>
> = {
    [K in keyof TProps]: TProps[K]["default"]
};

/** استخراج نوع config قابل‌قبول constructor
 *
 *  Behavior فعلی حفظ می‌شود: هر prop فقط TObservableValue<T> می‌گیرد.
 *  مستقیماً به TObservableValue متصل است — نه پارامتر Generic.
 *  TypeScript از Higher-Kinded Type پشتیبانی نمی‌کند،
 *  بنابراین TObservableValue<T> مستقیماً در Helper استفاده می‌شود.
 *
 *  Contract موردنیاز: فقط فیلد `default` */
export type ExtractPropsConfigType<
    TProps extends Record<string, { default: any }>
> = {
    [K in keyof TProps]: TObservableValue<TProps[K]["default"]>
};

// ──────────────────────────────────────
// Schemas
// ──────────────────────────────────────

/** استخراج نام partها از یک Record<Schemas>
 *
 *  Contract موردنیاز: فقط فیلد `part` */
export type ExtractSchemasType<
    TSchemas extends Record<string, { part: any }>
> = {
    [K in keyof TSchemas]: TSchemas[K]["part"]
};

// ──────────────────────────────────────
// Methods
// ──────────────────────────────────────

/** نوع داخلی methodها برای TMethods در ComponentBase
 *
 *  Contract موردنیاز: فقط `name` (برای شناسایی method) */
export type ExtractMethodsType<
    TMethods extends Record<string, { name: string }>
> = {
    [K in keyof TMethods]: (
        event: Event,
        dataArgs: any,
        componentArgs: any,
    ) => void
};

/** استخراج Component Args برای هر method
 *
 *  اگر method فیلد `args` داشته باشد → استخراج type از default
 *  اگر method فیلد `args` نداشته باشد → {} (آبجکت خالی)
 *
 *  Contract موردنیاز: `args` optional — مدیریت شرطی */
export type ExtractMethodsComponentArgs<
    TMethods extends Record<string, any>
> = {
    [K in keyof TMethods]:
        TMethods[K]["args"] extends Record<string, any>
            ? {
                [ArgKey in keyof TMethods[K]["args"]]:
                    TMethods[K]["args"][ArgKey] extends { default: infer T }
                        ? T
                        : any;
            }
            : {};
};

/** استخراج Data Args برای هر method
 *
 *  Contract موردنیاز: `dataArgs` اجباری است.
 *
 *  اگر method فیلد `dataArgs` نداشته باشد،
 *  TMethods constraint را satisfy نمی‌کند و compile error رخ می‌دهد. */
export type ExtractMethodsDataArgs<
    TMethods extends Record<string, { dataArgs: any }>
> = {
    [K in keyof TMethods]: TMethods[K]["dataArgs"];
};

/** نوع config methods برای مصرف‌کننده (Category callable)
 *
 *  Constraint با ExtractMethodsDataArgs هماهنگ است:
 *  هر دو `dataArgs` را اجباری می‌دانند. */
export type ExtractMethodsConfigType<
    TMethods extends Record<string, {
        name: string;
        dataArgs: any;
    }>,
    TThis = any,
> = {
    [K in keyof TMethods]?: (
        this: TThis,
        event: Event,
        dataArgs: ExtractMethodsDataArgs<TMethods>[K] | null,
        componentArgs: ExtractMethodsComponentArgs<TMethods>[K] | null,
    ) => void;
};
```

### ۲.۱.۱. توضیح تصمیم‌های طراحی

| Helper | نوع | Constraint | دلیل |
|:---|:---|:---|:---|
| `ExtractPropsType` | Extraction | `Record<string, { default: any }>` | فقط `default` لازم است — نه کل `Interface_ComponentProp` |
| `ExtractPropsConfigType` | Transformation | `Record<string, { default: any }>` | فقط `default` لازم است — مستقیماً `TObservableValue<T>` (نه پارامتر Generic) |
| `ExtractSchemasType` | Extraction | `Record<string, { part: any }>` | فقط `part` لازم است — نه کل `Interface_ComponentSchema` |
| `ExtractMethodsType` | Extraction | `Record<string, { name: string }>` | فقط `name` برای شناسایی |
| `ExtractMethodsComponentArgs` | Extraction | `Record<string, any>` | `args` optional — **Accepted Technical Debt** (جدول زیر) |
| `ExtractMethodsDataArgs` | Extraction | `Record<string, { dataArgs: any }>` | `dataArgs` همیشه وجود دارد در Contract فعلی |
| `ExtractMethodsConfigType` | Transformation | `Record<string, { name: string; dataArgs: any }>` | constraint با `ExtractMethodsDataArgs` هماهنگ است |

> **تفکیک Extraction vs Transformation:**
> - **Extraction** — نوع را مستقیماً از Definition استخراج می‌کند (`ExtractPropsType`, `ExtractSchemasType`, ...)
> - **Transformation** — نوع استخراج‌شده را به نوع دیگری تبدیل می‌کند (`ExtractPropsConfigType`: `default → TObservableValue<T>`, `ExtractMethodsConfigType`: callback signature)
>
> این تفاوت در Guide روشن شود. برای آینده Compiler و Definition System مهم است.

> **سیاست `any` fallback در `ExtractMethodsComponentArgs`:**
> اگر `args` وجود داشته باشد ولی یک arg `default` نداشته باشد، نتیجه `any` است.
> این رفتار آگاهانه است — Helper مسئول validation ساختار args نیست.
> در صورت نبود `default` طبق extraction policy فعلی نتیجه `any` است.
> اگر در آینده Policy سخت‌گیرانه‌تر (`never`) خواسته شد، آن یک تغییر Policy جداگانه است.

### ۲.۱.۲. Technical Debt ثبت‌شده

| Decision | وضعیت |
|:---|:---|
| `ExtractMethodsComponentArgs` از `Record<string, any>` استفاده می‌کند | **Accepted Technical Debt** |
| **دلیل** | حفظ behavior فعلی و عدم تغییر Definition Contract در این Refactor |
| **ریسک** | کاهش type safety در ورودی generic — Definition ناقص ممکن است silently عبور کند |
| **اصلاح** | Refactor مستقل Type Safety در Plan جداگانه |

> هر `any` خوب نیست، ولی `any` مستندسازی‌شده حداقل جنایت برنامه‌ریزی‌شده است.

## ۷. فاز ۰A — Contract Inspection

قبل از ساخت Helperها، باید Contractهای واقعی سیستم بررسی شوند.
این فاز فقط **inspection** است — هیچ فایلی ایجاد نمی‌شود.

### ۷.۱. موارد بررسی

| مورد | هدف |
|:---|:---|
| `Interface_ComponentProp` | فیلد `default` موجود است؟ نوع آن چیست؟ |
| `Interface_ComponentSchema` | فیلد `part` موجود است؟ |
| Methods Contract | `args` و `dataArgs` در همه کامپوننت‌ها وجود دارند؟ |
| `TObservableValue` | از کجا import شود؟ آیا generic constraint دارد؟ |
| `componentButton/Props.ts` | `typeof Props` با `satisfies` چه شکلی است؟ literal types یا widened؟ |

> **نکته مهم درباره `satisfies` و Literal Inference:**
> `satisfies` معمولاً نوع inferred expression را حفظ می‌کند و الزاماً آن را به نوع annotation تبدیل نمی‌کند.
> بنابراین literal types ممکن است در `typeof Props` حفظ شوند.
> با constraintهای حداقلی (`Record<string, { default: any }>`)، `typeof Props` به‌سادگی سازگار است.
> ولی **همان‌جا که فکر می‌کنیم بدیهی است**، TypeScript ممکن است `""` به‌جای `string` برگرداند.
> Gate ۱ در Phase 0B این رفتار را روی Definition واقعی بررسی می‌کند.

## ۹. فاز ۰B — Compile Gate

بعد از ساخت Helperها، compiler باید feasibility و equivalence را روی یک Definition واقعی ثابت کند.

### ۹.۱. فایل Verification

```typescript
// tools/type/__verify__/Phase0CompileGate.ts
//
// DEVELOPMENT ONLY — feasibility test روی Definition واقعی ComponentButton

import {ComponentButton} from "@/ui_components/lists";
import type {TObservableValue} from "@/core_observable";
import type {
    ExtractPropsType,
    ExtractPropsConfigType,
} from "../TypeHelpers";

// ─── IsEqual + Assert utilities ───
type IsEqual<A, B> =
    (<T>() => T extends A ? 1 : 2) extends
    (<T>() => T extends B ? 1 : 2)
        ? true
        : false;

type Assert<T extends true> = T;

// ─── Legacy Implementation (مرجع) ───
type LegacyPropsType<TProps> = {
    [K in keyof TProps]: TProps[K]["default"]
};

type LegacyPropsConfigType<TProps> = {
    [K in keyof TProps]: TObservableValue<TProps[K]["default"]>
};

// ═══════════════════════════════════════════
// Gate 1: satisfies + literal inference
// ═══════════════════════════════════════════
// آیا ExtractPropsType<typeof Props> همان type فعلی را می‌دهد؟

type _ButtonPropsEquivalence = Assert<
    IsEqual<
        LegacyPropsType<typeof ComponentButton.Props>,
        ExtractPropsType<typeof ComponentButton.Props>
    >
>;

// ═══════════════════════════════════════════
// Gate 2 + 3: PropsConfig compile + TObservableValue compatibility
// ═══════════════════════════════════════════
// آیا ExtractPropsConfigType<typeof Props> compile می‌شود؟
// آیا تمام defaultهای واقعی ComponentButton قابل قبول‌اند؟
// اگر TObservableValue<T extends SomeConstraint> باشد،
// همین‌جا failure می‌گیریم.
// همزمان equivalence با Legacy را هم چک می‌کنیم.

type _ButtonPropsConfigEquivalence = Assert<
    IsEqual<
        LegacyPropsConfigType<typeof ComponentButton.Props>,
        ExtractPropsConfigType<typeof ComponentButton.Props>
    >
>;

// ═══════════════════════════════════════════
// Gate 4: Definition constraint (diagnostic clarity)
// ═══════════════════════════════════════════
// آیا typeof Props واقعاً constraint helper را satisfy می‌کند؟
// اگر Gate 1 compile شده باشد، این خود‌به‌خود برقرار است،
// ولی این خط diagnostic clarity دارد — وقتی compile error رخ دهد،
// تشخیص مشکل سریع‌تر می‌شود.

type _ButtonPropsConstraintCheck =
    typeof ComponentButton.Props extends Record<string, { default: any }> ? true : false;

type _ButtonPropsConstraintAssert = Assert<_ButtonPropsConstraintCheck>;
```

### ۹.۲. چهار تستی که Phase 0B باید قطعی کند

| Gate | تست | ریسک اگر fail شود |
|:---|:---|:---|
| ۱. satisfies + literal inference | `LegacyPropsType<typeof ComponentButton.Props> ≡ ExtractPropsType<typeof ComponentButton.Props>` | Helper type قبلی را تولید نمی‌کند |
| ۲+۳. PropsConfig compile + TObservableValue | `LegacyPropsConfigType<typeof ComponentButton.Props> ≡ ExtractPropsConfigType<typeof ComponentButton.Props>` | `TObservableValue<T>` با بعضی default typeها سازگار نیست |
| ۴. Definition constraint | `typeof ComponentButton.Props extends Record<string, { default: any }>`؟ | `satisfies` نوع را بیش از حد narrow کرده |

> **نکته:** Gate 4 عملاً redundant است — اگر Gate 1 compile شده باشد، constraint خود‌به‌خود برقرار است.
> ولی نگه داشته می‌شود چون diagnostic clarity دارد.

## ۱۰. فاز ۰.۵ — Type Extraction Verification

پیش از مهاجرت کامپوننت‌ها، باید ثابت شود که Helperها دقیقاً همان type قبلی را تولید می‌کنند.

**روش:** Type-level assertions (بدون Runtime):

```typescript
// tools/type/__verify__/TypeExtractionVerify.ts
//
// DEVELOPMENT ONLY — نباید از type/index.ts export شود
//
// ساختار واحد Verification:
// ├── A. Generic extraction equivalence (مثال‌های مصنوعی)
// ├── B. Optional args behavior
// ├── C. ComponentStructure (Props, Schemas, Methods)
// ├── D. ComponentButton (Props, PropsConfig, Schemas, Methods)
// ├── E. ComponentIcon (Props, PropsConfig, Schemas, Methods)
// └── F. ComponentMessages (Props, PropsConfig, Schemas, Methods)
//
// لاحم نیست همه را از روز اول پر کنی، ولی محل Verification واحد باشد.

// ─── IsEqual + Assert utilities ───
type IsEqual<A, B> =
    (<T>() => T extends A ? 1 : 2) extends
    (<T>() => T extends B ? 1 : 2)
        ? true
        : false;

type Assert<T extends true> = T;

// ─── Legacy Implementations (مرجع) ───
type LegacyPropsType<TProps> = {
    [K in keyof TProps]: TProps[K]["default"]
};

type LegacySchemasType<TSchemas> = {
    [K in keyof TSchemas]: TSchemas[K]["part"]
};

type LegacyMethodsType<TMethods> = {
    [K in keyof TMethods]: (event: Event, dataArgs: any, componentArgs: any) => void
};

type LegacyMethodsComponentArgs<TMethods> = {
    [K in keyof TMethods]: {
        [ArgKey in keyof TMethods[K]["args"]]:
            TMethods[K]["args"][ArgKey] extends { default: infer T }
                ? T
                : any;
    };
};

// ═══════════════════════════════════════════
// A. Generic extraction equivalence
// ═══════════════════════════════════════════

type _PropsEquivalence<TProps extends Record<string, { default: any }>> =
    Assert<IsEqual<
        LegacyPropsType<TProps>,
        ExtractPropsType<TProps>
    >>;

type _MethodsArgsEquivalence<TMethods extends Record<string, any>> =
    Assert<IsEqual<
        LegacyMethodsComponentArgs<TMethods>,
        ExtractMethodsComponentArgs<TMethods>
    >>;

// ═══════════════════════════════════════════
// B. Optional args behavior
// ═══════════════════════════════════════════

type _MethodsNoArgsCheck = Assert<
    IsEqual<
        ExtractMethodsComponentArgs<{ CLICK: { name: "fn", dataArgs: {} } }>,
        { CLICK: {} }
    >
>;

// ═══════════════════════════════════════════
// C. ComponentStructure — Real Definition Verification
// ═══════════════════════════════════════════

import {ComponentStructure} from "@/ui_components/lists";

type _StructurePropsCheck = Assert<
    IsEqual<
        LegacyPropsType<typeof ComponentStructure.Props>,
        ExtractPropsType<typeof ComponentStructure.Props>
    >
>;

type _StructureSchemasCheck = Assert<
    IsEqual<
        LegacySchemasType<typeof ComponentStructure.Schemas>,
        ExtractSchemasType<typeof ComponentStructure.Schemas>
    >
>;

type _StructureMethodsCheck = Assert<
    IsEqual<
        LegacyMethodsType<typeof ComponentStructure.Methods>,
        ExtractMethodsType<typeof ComponentStructure.Methods>
    >
>;

// ═══════════════════════════════════════════
// D. ComponentButton — Real Definition Verification
// ═══════════════════════════════════════════
// (بعد از migration componentButton اضافه شود)

// ═══════════════════════════════════════════
// E. ComponentIcon — Real Definition Verification
// ═══════════════════════════════════════════
// (بعد از migration componentIcon اضافه شود)

// ═══════════════════════════════════════════
// F. ComponentMessages — Real Definition Verification
// ═══════════════════════════════════════════
// (بعد از migration componentMessages اضافه شود)
```

> **روش Verification:**
> - **Legacy Equivalence:** Helper را با implementation دستی قبلی مقایسه می‌کند — فقط در زمان Migration.
> - **Real Definition Verification:** روی Definitionهای واقعی کامپوننت‌ها انجام می‌شود — اطمینان از کار کردن Helper با `satisfies`, `as const`, literal types.
> - Expected type دستی دوباره نوشته نمی‌شود — Legacy type به‌عنوان مرجع استفاده می‌شود.
> - تمام Verificationها در یک فایل واحد `TypeExtractionVerify.ts` تجمیع می‌شوند.
>
> این فایل فقط در زمان کامپایل چک می‌شود — اگر Helper اشتباه باشد، TypeScript خطا می‌دهد.

> **بعد از اتمام migration:** Legacy verification را می‌توان حذف کرد، چون نقش migration guard را انجام داده است.

> **نکته مهم:** `ExtractMethodsDataArgs` عمداً Contract فعلی `dataArgs` اجباری را enforce می‌کند.
> نباید برای پذیرش Definition ناقص، constraint آن شل شود.
> اگر حتی یک Method واقعی `dataArgs` نداشته باشد، Helper compile نمی‌شود — و این رفتار صحیح است.
> Freedom ≠ Weak Contract — آزادی یعنی روش composition را تحمیل نکن، نه اینکه هر Definition ناقصی را معتبر بدان.
