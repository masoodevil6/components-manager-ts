# CoreEvent Refinement Plan

## هدف

Implementation فعلی CoreEvent را که اکنون به صورت عملی کار می‌کند، بدون refactor غیرضروری تکمیل و تثبیت کن.

نمونه فعلی:

```ts
const responses = event!.request(
    CoreEvent.requestMap([
        [StepRegister.info.name,   { action: "validate" }],
        [StepRegister.info.family, { action: "validate" }]
    ])
);
```

در حال حاضر Request به چند Step dispatch می‌شود و هر Step از طریق `emit` یک Response تولید می‌کند.

این رفتار باید حفظ شود.

هدف این Phase:

1. تثبیت Contractهای `Step / Request / Response`
2. تفکیک Request منطقی از Dispatch داخلی
3. بهبود Response API
4. آماده‌سازی Runtime برای Monitoring آینده
5. حفظ استقلال CoreEvent از Observable
6. عدم ورود به CoreWorkflow در این مرحله

---

# 1. وضعیت فعلی که نباید خراب شود

این جریان اکنون معتبر است:

```text
Submit
   │
   │ event.request(...)
   ▼
CoreEvent
   │
   ├──────────────┐
   ▼              ▼
Name Step      Family Step
   │              │
 emit           emit
   │              │
   ▼              ▼
Response       Response
   └──────┬───────┘
          ▼
       responses
```

این behavior باید با تست regression حفظ شود.

---

# 2. اصل مهم: Step Identity

Request نباید با string event name کار کند.

این مدل مطلوب نیست:

```ts
"user.info.name"
```

مدل صحیح:

```ts
StepRegister.info.name
```

هر Step باید identity مستقل داشته باشد.

مثلاً:

```ts
class ClStep {

    readonly identity: symbol;

}
```

یا هر implementation مناسب دیگر.

`identity` نباید با مسیر متنی Step یکی باشد.

---

# 3. Path فقط Metadata است

در صورت وجود:

```text
info.name
```

این path صرفاً برای:

* debugging
* logging
* monitoring
* visualization

است.

نباید identity اصلی Step باشد.

مثلاً:

```text
Step
├── identity: Symbol(...)
└── path: "Register.info.name"
```

Identity واقعی همان object/identity داخلی Step است.

---

# 4. Request منطقی و Dispatch داخلی را جدا کن

در implementation فعلی برای هر Target یک `requestId` جدا تولید می‌شود.

مثلاً:

```text
name   → mtfvab4f-3
family → mtfvab4f-4
```

این برای dispatch داخلی قابل قبول است، اما از دید API یک Request واحد وجود دارد.

مدل مطلوب:

```text
Request #100
source: Register.info.submit
   │
   ├── Dispatch #101 → Register.info.name
   │
   └── Dispatch #102 → Register.info.family
```

بنابراین حداقل دو مفهوم باید از هم قابل تشخیص باشند:

```ts
requestId
dispatchId
```

یا نام‌گذاری معادل.

---

# 5. Request ID

هر `event.request(...)` یک Runtime Request اصلی ایجاد کند.

مثلاً:

```ts
const request = event.request(...);
```

این Request دارای:

```ts
request.requestId
```

باشد.

تمام Dispatchهای ایجادشده از آن Request باید بتوانند به Request اصلی اشاره کنند:

```ts
dispatch.requestId
dispatch.dispatchId
```

هدف:

```text
Request #100
   │
   ├── Dispatch #101
   └── Dispatch #102
```

---

# 6. Response باید Request را بشناسد

Response باید حداقل بتواند مشخص کند به کدام Request مربوط است.

مثلاً:

```ts
response.requestId
```

و در صورت نیاز:

```ts
response.dispatchId
response.source
response.target
```

در نظر گرفته شود.

مدل مفهومی:

```text
Response
├── requestId
├── dispatchId
├── source
├── target
├── value
└── metadata
```

لازم نیست تمام این موارد الزاماً در public API باشند، اما architecture باید امکان اضافه شدن آن‌ها را داشته باشد.

---

# 7. Response API

در implementation فعلی نتیجه:

```ts
Map<Step, ClResponse>
```

است.

این Map می‌تواند implementation داخلی باقی بماند.

اما API عمومی نباید به ساختار داخلی Map وابسته شود.

هدف:

```ts
const responses = event.request(...);
```

و امکان:

```ts
responses.get(StepRegister.info.name)
```

وجود داشته باشد.

در صورت نیاز APIهای کمکی نیز قابل اضافه شدن هستند:

```ts
responses.has(step)
responses.entries()
responses.values()
```

اما از expose کردن implementation داخلی غیرضروری خودداری شود.

---

# 8. Response باید Target را حفظ کند

اگر:

```ts
event.request({

    [StepRegister.info.name]: {
        action: "validate"
    },

    [StepRegister.info.family]: {
        action: "validate"
    }

});
```

ارسال شود، Responseها باید به Target خود قابل نسبت دادن باشند.

مثلاً:

```text
Response
├── target: User.info.name
├── requestId: #100
└── value: { value: "Mehdi", valid: true }
```

و:

```text
Response
├── target: User.info.family
├── requestId: #100
└── value: { value: "...", valid: true }
```

---

# 9. `emit` Contract

این بخش بسیار مهم است.

در ReactiveElement:

```ts
emit: request => {
    ...
    return response;
}
```

`emit` یک EventEmitter نیست.

`emit` یک **Request Handler** برای Step متصل به Element است.

یعنی:

```text
CoreEvent
   │
   │ Request
   ▼
Step
   │
   │ unique
   ▼
ReactiveElement
   │
   │ emit(request)
   ▼
Response
```

---

# 10. تفاوت `on` و `emit`

این Contract حفظ شود:

```text
on
│
└── DOM Event Handler
```

مثلاً:

```ts
on: {
    click: (e, event) => {
        ...
    }
}
```

اما:

```text
emit
│
└── CoreEvent Request Handler
```

مثلاً:

```ts
emit: request => {

    return {
        value: "...",
        valid: true
    };

}
```

بنابراین این دو abstraction نباید با هم ادغام شوند.

---

# 11. `emit` فقط زمانی اجرا شود که Target معتبر باشد

CoreEvent باید ابتدا Target Step را resolve کند.

سپس اگر Step به یک ReactiveElement متصل شده و Handler مربوط به آن موجود است:

```ts
element.emit(request)
```

اجرا شود.

CoreEvent نباید مستقیماً DOM را دستکاری کند.

---

# 12. Step بدون ReactiveElement

یک Step می‌تواند فقط یک node منطقی باشد:

```ts
const info = CoreEvent.Step({
    children: {
        name: ...
    }
});
```

و هیچ ReactiveElementای به آن متصل نباشد.

پس CoreEvent نباید فرض کند:

```text
Every Step = ReactiveElement
```

بلکه:

```text
Step
 │
 ├── logical node
 │
 └── optional UI binding
```

باشد.

---

# 13. `unique` در ReactiveElement

Property:

```ts
unique?: CoreEvent.Step;
```

باقی بماند.

نمونه:

```ts
const nameInput = CoreReactive.App.input({

    unique: StepRegister.info.name,

    emit: request => {

        const value =
            (nameInput.getElement() as HTMLInputElement).value;

        return {
            value,
            valid: value.trim().length > 0
        };

    }

});
```

این یعنی:

```text
StepRegister.info.name
          │
          ▼
ReactiveElement
```

و CoreEvent از طریق همین رابطه Handler را پیدا می‌کند.

---

# 14. از string identity استفاده نکن

این:

```ts
unique: "user.info.name"
```

نباید Contract معتبر باشد.

این:

```ts
unique: StepRegister.info.name
```

باید Contract صحیح باشد.

TypeScript باید تا حد امکان این موضوع را enforce کند.

---

# 15. `emit` باید synchronous یا asynchronous بودن را پشتیبانی کند

Implementation را فقط به:

```ts
emit: request => Response
```

محدود نکن.

در آینده ممکن است:

```ts
emit: async request => {

    const result = await something();

    return result;

}
```

نیاز باشد.

بنابراین Contract باید امکان:

```ts
Response | Promise<Response>
```

را داشته باشد.

اما اگر implementation فعلی synchronous است، بدون نیاز آن را پیچیده نکن.

---

# 16. چند Target

این قابلیت حفظ شود:

```ts
event.request(
    CoreEvent.requestMap([

        [StepRegister.info.name, {
            action: "validate"
        }],

        [StepRegister.info.family, {
            action: "validate"
        }]

    ])
);
```

CoreEvent باید بتواند:

```text
1 Request
   │
   ├── Target A
   ├── Target B
   └── Target C
```

را dispatch کند.

---

# 17. Ordering

ترتیب Responseها باید deterministic باشد.

اگر Request به:

```text
A
B
C
```

ارسال شده، implementation نباید به صورت تصادفی رفتار کند.

اگر asynchronous dispatch اضافه شد، همچنان باید رابطه‌ی هر Response با:

```text
requestId
dispatchId
target
```

کاملاً مشخص باشد.

---

# 18. Error Handling

اگر یک `emit` خطا ایجاد کرد:

```ts
emit: request => {
    throw new Error(...);
}
```

کل Runtime نباید بدون اطلاعات کافی crash کند.

Response یا Dispatch باید امکان ثبت:

```text
status: "error"
error: ...
```

را داشته باشد.

مدل:

```text
Request
   │
   ▼
Step
   │
 emit
   │
 ├── success → Response
 │
 └── error   → Error Response
```

این بخش باید با طراحی فعلی هماهنگ شود و over-engineering نشود.

---

# 19. Monitoring Preparation

در این Phase هنوز Monitor UI ساخته نشود.

اما Runtime باید metadata کافی داشته باشد تا بعداً بتوان Event Trace ساخت.

حداقل مفاهیم قابل trace:

```text
Request
requestId
source
target
dispatchId
response
timestamp
status
```

هدف آینده:

```text
Request #100
    │
    ├── name
    │    └── Response
    │
    └── family
         └── Response
```

---

# 20. Logging نباید داخل CoreEvent اجباری باشد

CoreEvent نباید:

```ts
console.log(...)
```

را به عنوان رفتار اصلی Runtime داشته باشد.

Logging باید قابل فعال/غیرفعال شدن یا قابل اتصال به Monitor آینده باشد.

مثلاً architecture باید بعداً امکان چنین چیزی را بدهد:

```ts
CoreEvent.monitor(...)
```

اما فعلاً implementation Monitor لازم نیست.

---

# 21. Observable وارد CoreEvent نشود

CoreEvent نباید برای این معماری به Observable تبدیل شود.

مدل:

```text
CoreObservable
    ↓
State / Reactive Value


CoreEvent
    ↓
Request / Response
```

این دو مستقل باقی بمانند.

---

# 22. ReactiveElement فقط Integration Layer است

CoreEvent نباید به:

```ts
ClReactiveElement
```

وابسته شود.

بهتر است dependency جهت زیر را حفظ کنیم:

```text
CoreEvent
   ↑
ReactiveElement
```

نه:

```text
CoreEvent
   ↓
ReactiveElement
```

یعنی CoreEvent Contract را تعریف می‌کند و ReactiveElement آن را consume/implement می‌کند.

# 27. قانون اصلی این Phase

**Implementation فعلی که در مثال `ClHomePage` کار می‌کند را حفظ کن.**

هدف این Phase:

```text
NOT:
بازنویسی CoreEvent

YES:
تثبیت Contract
بهبود identity
تفکیک request/dispatch
بهبود response
آماده‌سازی monitoring
تثبیت emit
```

قبل از اضافه کردن abstraction جدید، ابتدا بررسی کن آیا primitiveهای فعلی:

```text
Step
Request
Response
emit
unique
```

می‌توانند این قرارداد را به صورت ساده و type-safe پوشش دهند.

از اضافه کردن کلاس‌ها و لایه‌های جدید بدون نیاز واقعی خودداری کن.
