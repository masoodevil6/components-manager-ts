# پلن 30.1.0 — انتقال ComponentBreadcrumb به ساختار جدید

> **وضعیت:** پیاده‌سازی‌شده؛ build و تست مثلث موفق  
> **نسخه پلن:** 30.1.0  
> **کتابخانه قدیمی:** `last/Older/components.js`  
> **منبع Legacy:** تعریف `ComponentBreadcrumbBase` و `ComponentBreadcrumb` در بخش [30–39]، حدود خطوط 26853 تا 27255  
> **نمونه Legacy:** `last/Older/index.html`، بخش نمونه‌های Breadcrumb  
> **راهنما:** `documents/guides/component-create.md`  
> **مقصد پیشنهادی:** `src/framework/module_ui/module_components/lists/componentBreadcrumb/`  
> **دسته‌بندی:** Breadcrumb  
> **API پیشنهادی:** `UiCategory.UI.Breadcrumb.Breadcrumb(config, methods, identity)`؛ گروه مستقل Breadcrumb در UI Category و callable آن باید مطابق الگوی `CreateCategoryComponent` ثبت شوند.

## 1. هدف و محدوده

انتقال Breadcrumb از کلاس‌های سراسری Legacy و تولید HTML/CSS رشته‌ای به قرارداد ComponentManager. رفتار اصلی شامل نمایش مسیر به‌شکل نوار افقی قابل اسکرول، مشخص‌کردن گام فعال، انتخاب یک گام با callback و دکمهٔ بازگشت اختیاری است.

این انتقال `ComponentBreadcrumb` را پوشش می‌دهد و علاوه بر کامپوننت، یک ابزار عمومی شکل در Util اضافه می‌کند تا مثلث‌های CSS به‌صورت پارامتری ساخته شوند. `ComponentBreadcrumbWithArrow` کامپوننت جداگانه‌ای است و در این پلن منتقل نمی‌شود. رفتار و API مصرف‌کنندگان Legacy نیز تغییر نمی‌کند؛ سازگاری مهاجرتی جداگانه، در صورت نیاز، بررسی خواهد شد.

## 1.1. افزودن ابزار عمومی Triangle در Util

مثلث‌های breadcrumb قدیمی با pseudo-elementهای `::before` و `::after`، مرزهای CSS و اندازه/رنگ/جهت وابسته به هر آیتم ساخته می‌شوند. این منطق نباید داخل ComponentBreadcrumb تکرار شود. یک زیرماژول مستقل هم‌سطح `module_styles` به نام `module_shapes` در `module_util` ساخته شود و از همان اصول ماژول‌های Util.Style پیروی کند: تابع خالص و typed، ورودی‌های صریح، خروجی قابل ترکیب در style/CSS و export از barrelهای مربوطه.

API پیشنهادی:

```ts
UtilShape.Css_Triangle({
    direction: "right",
    width: "30px",
    height: "30px",
    color: "var(--primaryColor1)",
    position: {top: "0", insetInlineEnd: "-30px"},
});
```

قرارداد نهایی هنگام پیاده‌سازی با الگوی type/export واقعی Util هم‌راستا شود. تابع باید دست‌کم این قابلیت‌ها را به‌صورت داینامیک داشته باشد:

- جهت نوک مثلث: بالا، پایین، چپ یا راست؛ در Breadcrumb جهت بر اساس RTL/LTR محاسبه شود.
- عرض و ارتفاع مستقل و مقدار رنگ مثلث، بدون ثابت‌های 30px در helper.
- جای‌گذاری pseudo-element و جابه‌جایی آن نسبت به والد، به‌شکل پارامتر ورودی.
- امکان ساخت لایهٔ پشت/حاشیه با فراخوانی جداگانه برای `::before` و مثلث رویی با `::after`؛ رنگ و اندازهٔ هر لایه مستقل باشد تا مرز سفید Legacy قابل بازسازی باشد.
- خروجی فقط مقادیر/اعلان‌های لازم CSS را بسازد؛ DOM، selector مربوط به Component، یا دستکاری state داخل Util قرار نگیرد.

API باید برای جهت‌ها، اندازه‌ها، رنگ‌ها، حاشیه‌ها و offsetهای مختلف قابل استفاده باشد و از نظر پارامتری بودن، تجربهٔ ساخت شکل مثلثی مشابه ابزار مرجع `https://triangle.designyourcode.io/triangle` را پوشش دهد. این مرجع الهامِ قابلیت تنظیم است؛ وابستگی شبکه‌ای یا runtime به سایت ایجاد نشود.

### ساختار پوشهٔ پیشنهادی

ساختار `module_shapes`، هم‌سطح `module_styles` و با همان جداسازی type، method و barrel باشد:

```text
src/framework/module_util/module_shapes/
├── types/
│   ├── const/
│   │   ├── TCTriangleDirection.ts   # بالا، پایین، چپ، راست
│   │   └── index.ts
│   ├── TShapeTriangle.ts            # ورودی‌های جهت، عرض/ارتفاع، رنگ، موقعیت و خروجی CSS
│   └── index.ts
├── methods/
│   ├── MTCssTriangle.ts             # ساخت مقادیر CSS مثلث از روی options
│   └── index.ts
└── index.ts                         # export عمومی نوع‌ها و متدها
```

Barrelهای بالادستی نیز به‌روزرسانی شوند:

```text
src/framework/module_util/index.ts   # export Shapes از module_shapes
src/framework/index.ts               # export عمومی Shapes، هم‌ردیف Styles
```

`TShapeTriangle` قرارداد typed ورودی متد را تعریف می‌کند؛ جهت به‌صورت union type باشد و عرض، ارتفاع، رنگ، رنگ/اندازهٔ لایهٔ پشت و anchor/offsetهای مکانی را با مقادیر CSS بپذیرد. `MTCssTriangle` خروجی CSS را به‌صورت typed بسازد تا Component بتواند آن را در قاعدهٔ pseudo-element خود قرار دهد. اگر هنگام implementation روشن شد خروجی باید بین style object و declaration string تفکیک شود، انتخاب با الگوی دقیق typeهای `module_styles` هماهنگ و در API عمومی یکدست شود.

نام نهایی namespace و alias import با barrelهای فعلی قطعی شود؛ در نمونه‌های این پلن `UtilShape.Css_Triangle` به‌عنوان نام پیشنهادی API استفاده شده است.

ComponentBreadcrumb باید برای مثلث اصلی و لایهٔ پشت آن همین helper را مصرف کند. منطق محاسبهٔ جهت RTL/LTR و تعیین رنگ آیتم فعال/غیرفعال در Component باقی بماند؛ محاسبهٔ borderهای مثلثی در Util.Shape باشد. هر pseudo-element باید از همان helper استفاده کند و CSS رشته‌ای اختصاصیِ محاسبه‌کنندهٔ مثلث در Component حذف شود.

## 2. شواهد و رفتار Legacy

در `last/Older/components.js`:

- `prop_breadcrumbs` فهرستی از موارد دارای `id` و `title` است؛ مقدار پیش‌فرض آرایهٔ خالی است.
- `prop_stepSelected` شناسهٔ گام فعال را تعیین می‌کند و پیش‌فرض آن `1` است.
- چهار prop رنگ برای حالت فعال/غیرفعال وجود دارد. پیش‌فرض‌های Legacy از `tools_const.styles.breadcrumb` می‌آیند:
  - پس‌زمینهٔ غیرفعال: `primaryColor1`
  - متن غیرفعال: `shanColor1`
  - پس‌زمینهٔ فعال: `secondaryColor1`
  - متن فعال: `darkColor1`
- `prop_showBtn` دکمهٔ بازگشت را کنترل می‌کند و پیش‌فرض آن `true` است.
- انتخاب هر مورد، `fn_callback(event, itemData)` را با شیء کامل همان مورد فراخوانی می‌کند.
- دکمهٔ بازگشت، `fn_onBackClick(event, prop_stepSelected)` را فراخوانی می‌کند.
- جهت نوار و دکمه بر اساس `directionRtl` در config Legacy تعیین می‌شود.
- نوار breadcrumb افقی است، فضای سفید متن را نگه می‌دارد و در صورت نیاز اسکرول افقی می‌گیرد.
- اولین/آخرین مورد گوشه‌های متفاوت دارند و مورد فعال از روی برابری `item.id` با `prop_stepSelected` تشخیص داده می‌شود.
- کد Legacy برای هر مورد handler inline و CSS اختصاصی تولید می‌کند. این روش در نسخهٔ جدید استفاده نشود.
- `_TILE_INTERVAL` در کلاس تعریف شده، اما در محدودهٔ پیاده‌سازی بررسی‌شده کاربردی ندارد؛ آن را منتقل نکنید مگر در بازبینی کامل‌تر شاهد مصرفی پیدا شود.

نمونهٔ صفحهٔ Legacy سه مورد با شناسه‌های 1 تا 3، گام فعال 2 و هر دو callback را تنظیم می‌کند.

## 4. API و فایل‌های پیشنهادی

پوشهٔ مقصد مطابق راهنما شامل موارد زیر باشد:

```text
componentBreadcrumb/
├── Definition.ts
├── Props.ts
├── Schemas.ts
├── Methods.ts
├── Step.ts
├── ComponentBreadcrumbBase.ts
├── ComponentBreadcrumb.ts
├── index.ts
└── examples/
    ├── Default.ts
    ├── WithBackButton.ts
        └── index.ts
```

همچنین ساختار پوشهٔ بالا در `src/framework/module_util/module_shapes/` ایجاد شود و barrelهای `module_util` و framework خروجی آن را ارائه کنند. این Utility به ComponentBreadcrumb وابسته نمی‌شود و باید قابل استفادهٔ مجدد برای Componentهای دیگر باشد.

### Props

پیشنهاد اولیه، با حفظ نام‌های قابل‌استفادهٔ Legacy تا زمان بررسی مصرف‌کنندگان:

- `prop_breadcrumbs: Array<{id: string | number; title: string}>`، پیش‌فرض `[]`
- `prop_stepSelected: string | number`، پیش‌فرض `1`
- `prop_showBtn: boolean`، پیش‌فرض `true`
- `prop_unactiveBreadcrumb` و `prop_colorUnactive`
- `prop_activeBreadcrumb` و `prop_colorActive`

نوع واقعی `id) باید در صورت وجود مصرف‌کننده/دادهٔ مستند بررسی شود؛ اگر شناسه‌ها در Legacy از نوع‌های دیگری باشند، نوع prop بر همان شواهد گسترش یابد. برای اسم‌های عمومی‌تر یا تغییر نام propها، ابتدا `rg` روی مصرف‌کنندگان انجام شود و در این پلن rename اجباری نیست.

### Schemas

- `COMPONENT` و `STRUCTURE` از `ComponentStructureTrait`
- `SCROLLER`: ظرف نسبی با عرض کامل و نوار افقی
- `BACK_BUTTON`: دکمهٔ بازگشت اختیاری در ابتدای بصری مسیر، با آیکون جهت‌دار متناسب با RTL/LTR
- `BREADCRUMBS`: ظرف flex با overflow افقی و دادهٔ فهرست
- `BREADCRUMB_ITEM`: عنوان، شناسه، وضعیت فعال و index لازم برای شکل ابتدا/میانه/انتها

اسامی schema و part باید در `Schemas.ts` ثابت و با prefix `part-breadcrumb-` تعریف شوند. دکمه و آیتم‌ها باید keyboard-accessible باشند؛ انتخاب آیتم با کنترل تعاملی مناسب و دکمهٔ بازگشت با ComponentButton/ComponentIcon ساخته شود.

### Methods

- رویداد معنایی `SELECT_BREADCRUMB`: payload شامل event و item انتخاب‌شده.
- رویداد معنایی `BACK`: payload شامل event و شناسهٔ `prop_stepSelected` فعلی.
- قرارداد باید از API عمومی Methods استفاده کند و نام متدهای runtime داخلی افشا نشود.

### Definition و Category

- Definition با id یکتای `component_breadcrumb`، نام `componentBreadcrumb` و نسخهٔ اولیهٔ `v1.0.0` ساخته شود.
- گروه مستقل Breadcrumb در registry مربوط به UI Category اضافه شود و Definition آن با id برابر `breadcrumb`، ترجمه‌های Keys و فهرست شامل ComponentBreadcrumb ساخته شود. namespace گروه از مسیر `UiCategory.UI.Breadcrumb` در دسترس باشد.
- دستهٔ placeholder صفحهٔ Components که پیش‌تر برای Breadcrumb اضافه شده، از دادهٔ دستی به این گروه واقعی متصل شود؛ صفحهٔ فیلتر نباید برای همان دسته منبع دادهٔ موازی نگه دارد.
- metadata، ترجمه‌های فارسی/انگلیسی، نمونه‌ها و ثبت در ComponentManager مطابق راهنما اضافه شوند.

## 5. رفتار و رندر مورد انتظار

1. آیتم‌ها به همان ترتیبی که در `prop_breadcrumbs` هستند نمایش داده شوند.
2. موردی که `id) آن با `prop_stepSelected` برابر است، رنگ فعال داشته باشد؛ بقیه رنگ غیرفعال.
3. کلیک روی آیتم، callback انتخاب را یک‌بار با همان شیء آیتم اجرا کند و خود کامپوننت به‌صورت پنهانی مقدار انتخاب‌شده را تغییر ندهد.
4. دکمهٔ بازگشت تنها در صورت `prop_showBtn === true` رندر شود و callback آن شناسهٔ گام جاری را دریافت کند.
5. ترتیب بصری، جهت پیکان، padding و گوشه‌های ابتدا/انتها در RTL و LTR درست باشد.
6. وقتی تعداد آیتم‌ها از عرض والد بیشتر شد، فقط محور افقی اسکرول‌پذیر باشد؛ عرض والد یا صفحه از نوار بیرون نزند.
7. لیست خالی، یک‌آیتمی و آیتم ناقص/null با رفتار امن رندر شود. برای عنوان خالی، fallback متنی مشخص و امن استفاده شود.
8. برای CSS مثلثی Legacy، از borderهای استاندارد ComponentBorder یا pseudo-element کنترل‌شده در style/classهای Component استفاده شود؛ مقدارهای اندازه از `CoreConfig.Settings.SizeName` و Util بیایند، نه از ابزارهای Legacy یا اعداد پراکنده.
9. متون قابل‌نمایش و tooltipهای جدید از Keys ترجمه شوند؛ عنوان breadcrumbهای ورودی، دادهٔ کاربر است و ترجمه نشود.
10. child componentها، subscriptionها و event stepها در `dispose()` آزاد شوند.
11. `UtilShape.Css_Triangle` برای هر چهار جهت، اندازه‌های نامساوی، رنگ دلخواه، موقعیت و دو لایهٔ `::before`/`::after` خروجی معتبر بسازد؛ helper مستقل از Breadcrumb باشد.
12. ComponentBreadcrumb مثلث‌های ابتدا/میانهٔ مسیر و لایهٔ پشت آن‌ها را با helper عمومی بسازد؛ در RTL/LTR نوک‌ها، رنگ فعال/غیرفعال و هم‌پوشانی مطابق طراحی Legacy قرار بگیرند.

## 6. ثبت و مثال‌ها

- در `module_components/lists/index.ts`، ComponentManager registration اضافه شود.
- UI Category callable برای ایجاد نمونه اضافه شود؛ API نهایی پس از بررسی الگوی فعلی `CreateCategoryComponent` تثبیت شود.
- مثال `Default`: سه آیتم ساده و گام فعال میانی.
- مثال `WithBackButton`: دکمهٔ بازگشت فعال و callbackهای عمومی.
- مثال اختیاری RTL/LTR، بدون hardcode کردن direction در خود مثال؛ از config سیستم استفاده کند.
- هر Example باید `render(): HTMLElement` داشته باشد و نمونه‌ها در صفحهٔ Component details قابل‌استفاده باشند.

## 7. معیارهای پذیرش

1. Component از طریق ComponentManager، UI Category، نمونه‌ها و صفحهٔ جزئیات قابل‌کشف باشد.
2. هیچ تگ custom سراسری روی `window` یا inline event handlerی باقی نماند.
3. فعال/غیرفعال بودن بر اساس `prop_stepSelected` و چهار رنگ سفارشی درست کار کند.
4. callback انتخاب، شیء کامل آیتم را دریافت کند؛ callback بازگشت event و شناسهٔ گام جاری را دریافت کند.
5. نمایش دکمه با `prop_showBtn` کنترل شود.
6. جهت و ترتیب ظاهری در RTL/LTR، همراه با حالت‌های 0، 1 و چند آیتم، درست باشد.
7. overflow افقی در viewport محدود کار کند و بقیهٔ صفحه را جابه‌جا نکند.
8. Props/Schemas/Methods از type helperهای راهنما استفاده کنند و name/descriptionها از Keys بیایند.
9. ابزار Triangle از مسیر export عمومی Util قابل import باشد و تست/نمونهٔ کوچک برای هر چهار جهت و دو pseudo-layer داشته باشد.
10. `npm run build:app`، typecheck مرتبط و `git diff --check` اجرا شوند؛ خطاهای از قبل موجود جداگانه گزارش شوند.
