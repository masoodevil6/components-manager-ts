# پلن 28.0.1 — انتقال `ComponentInputPrice` به ساختار جدید

> **وضعیت:** پیشنهادی؛ پیاده‌سازی‌نشده  
> **نسخه پلن:** 28.0.1  
> **منبع Legacy:** `last/tools/components/ComponentInputPrice.ts`  
> **راهنما:** `documents/guides/component-create.md`  
> **مقصد:** `src/framework/module_ui/module_components/lists/componentInputPrice/`  
> **API هدف:** `UiCategory.UI.Inputs.InputPrice(config, methods, identity)`

## 1. هدف و محدوده

انتقال `ComponentInputPrice` از `ComponentBase`، `ReactiveElement` و ابزارهای Legacy به الگوی declarative/runtime فعلی، با حفظ قرارداد ورودی قیمت، نمایش محاسبات و اطلاعات، پاک‌کردن مقدار، دکمهٔ افزودن، validation و callbackها.

مرجع اصلی پیاده‌سازی، `componentInput` در ساختار جدید است. در implementation، درخت رندر، اتصال `ComponentLabelTrait`، `ComponentInputSimple`، `ComponentIcon`، `ComponentButton` و `ComponentValidate`، چرخهٔ عمر، reactive binding و ثبت عمومی از `ComponentInput` الگو گرفته شود. فقط قابلیت‌هایی به آن افزوده یا تغییر داده شوند که وجودشان در `ComponentInputPrice` قدیمی با کد یا مصرف واقعی ثابت است؛ ساختار مشترک دوباره طراحی نشود.

API عمومی و قرارداد callbackهای قیمت تا حد ممکن با Legacy سازگار می‌مانند. مهاجرت مصرف‌کنندگان Legacy، تغییر Laravel و بازطراحی رفتار قیمت خارج از محدوده است.

پیش از implementation، مصرف‌های `ComponentInputPrice` و شکل دقیق دادهٔ `prop_value`، `prop_calculator` و `prop_information` در repository با `rg` بررسی شوند. هر ناسازگاری یا رفتار Legacy که از شواهد موجود قابل تعیین نیست، پیش از تغییر قرارداد ثبت شود؛ حدس زده نشود.

## 2. شواهد رفتار Legacy و قرارداد مورد انتظار

Legacy این props اختصاصی را دارد:

| Prop | رفتار/تصمیم انتقال |
|---|---|
| `prop_title` | عنوان مستقل validator باقی بماند؛ با عنوان label یکی فرض نشود. |
| `prop_backgroundColorForm`, `prop_formBorderRadius` | ظاهر ظرف فرم را حفظ کنند؛ اندازهٔ radius با `UtilStyle` و `CoreConfig.Settings.SizeName` محاسبه شود. |
| `prop_colorIcon` | رنگ آیکون اصلی را حفظ کند. |
| `prop_size` | مانند `ComponentInput` به API جدید منتقل نشود؛ اندازه‌ها از `CoreConfig.Settings.SizeName` گرفته شوند. |
| `prop_inputClass`, `prop_inputStyles` | به props متناظر `ComponentInputSimple` نگاشت شوند، بدون جایگزینی استایل‌های پایهٔ آن. |
| `prop_inputBorderColor`, `prop_inputBorderColorFocus`, `prop_inputBorderWidth`, `prop_inputBorderRadius` | ظاهر عادی/focus ورودی حفظ شود؛ مقدارهای اندازه با utilهای سیستم و `SizeName` محاسبه شوند. |
| `prop_type`, `prop_placeholder`, `prop_name`, `prop_isDisable`, `prop_value` | به `ComponentInputSimple` و قرارداد props پایه نگاشت شوند. نوع ورودی/قالب متن باید با رفتار موجود حفظ شود. |
| `prop_icon` | آیکون اصلی ورودی؛ به `ComponentIcon` و نوع آیکون جدید تبدیل شود. نبود آیکون باید فضای اضافی یا DOM خالی نسازد. |
| `prop_btnAddStatus`, `prop_btnAddIcon`, `prop_btnAddTitle`, `prop_btnAddClass`, `prop_btnColor` | دکمهٔ افزودن را به‌صورت شرطی با `ComponentButton` بسازند. اندازه، عنوان، آیکون، semantic و callback طبق Legacy بمانند. |
| `prop_isAbsoluteRule`, `prop_listRules`, `prop_msgRules` | به `ComponentValidate` نگاشت شوند؛ validator فقط در صورت وجود rule و فعال‌بودن کنترل ساخته شود. |
| `prop_calculator`, `prop_calculatorColor` | ردیف‌های محاسباتی مشتق از مقدار جاری را حفظ کنند. هر مورد شامل `name`, `title?`, `coefficient?`, `extension?` است و ضریب پیش‌فرض 1 دارد. |
| `prop_information` | نمایش اطلاعات را حفظ کند. هر مورد شامل `title`, `value?`, رنگ‌های عنوان/مقدار و backgroundهای جداگانه است. مقدار پیش‌فرض نمایش `---` باقی بماند. |

Legacy چهار callback عمومی دارد: `fn_onInput`, `fn_onFocus`, `fn_onBlur`, `fn_onClickButton`. هرکدام payload با کلید `VALUE` دریافت می‌کند:

```ts
{
  value: number | null;
  calcs: Record<string, number>;
}
```

`calcs[name]` برابر مقدار عددی ورودی پس از تبدیل قیمت، ضرب‌در coefficient همان ردیف است. حفظ نام callbackها و ساختار payload الزامی است. رفتار Enter هنگام فعال‌بودن دکمهٔ افزودن نیز باید همان callback دکمه را با payload جاری اجرا کند.

`ToolsConverter.convertStringToPrice` و `convertPriceToString` در Legacy برای تبدیل/نمایش استفاده شده‌اند. پیش از implementation بررسی شود که معادل مورد تأیید در ساختار جدید کجاست؛ تبدیل عدد، جداکننده‌ها و گردکردن نباید با کپی‌کردن ناقص فرمول Legacy تغییر کند.

## 3. ساختار درختی پیشنهادی بر پایهٔ `ComponentInput`

```text
ComponentInputPrice
├── 1. ComponentLabelTrait                     ← همان الگوی ComponentInput
├── 2. part-input-price-form                   ← همان ساختار/چینش ComponentInput
│   ├── 2.1. ComponentIcon (آیکون اصلی)         ← همان الگوی ComponentInput
│   ├── 2.2. ComponentInputSimple               ← همان الگوی ComponentInput، با تبدیل قیمت
│   └── 2.3. ComponentButton                   ← همان الگوی ComponentInput، با قرارداد افزودن Legacy
├── 3. part-input-price-validate               ← همان الگوی ComponentInput
└── قابلیت‌های افزودهٔ مخصوص Price:
    ├── کنترل پاک‌کردن مقدار (در محل مناسب فرم؛ مطابق رفتار Legacy)
    ├── part-input-price-calculator (شرطی)
    └── part-input-price-information (شرطی)
```

فرم، label، input، دکمه، validation، عرض‌ها، گوشه‌های وابسته به آیکون/دکمه، رخدادهای پایه و dispose از خود `ComponentInput` الگو گرفته شوند؛ در این بخش‌ها قرارداد تازه نسازید. ورودی قیمت با `ComponentInputSimple` رندر شود و منطق فرمت قیمت در لایهٔ `ComponentInputPrice` به adapter/value handling اضافه شود. کنترل clear فقط در صورتی جداگانه ساخته شود که بررسی `ComponentInputSimple` و Legacy نشان دهد قابلیت موجود آن نیاز Price را برآورده نمی‌کند.

تنها تفاوت‌های ساختاری قطعی با `ComponentInput`، calculator و information اختیاری و کنترل clear مشاهده‌شده در Legacy هستند. calculator و information در Legacy پس از ظرف فرم و در همان wrapper render می‌شوند؛ جایگاهشان حفظ شود، مگر مصرف واقعی شواهد دیگری بدهد. رفتار focus/blur اطلاعات با state reactive پیاده شود، اما رفتار مشترک focus/blur ورودی از الگوی `ComponentInput` بماند.

## 4. Props و نگاشت تفاوت‌ها با `ComponentInput`

- props ساختاری، label و ورودی مشترک با `ComponentInput` هم‌راستا باشند. از `ComponentInputBase` یا `ComponentInput.Props` ارث‌بری/استفادهٔ مستقیم فقط اگر معماری فعلی و typeها اجازه می‌دهند؛ در غیر این صورت قراردادهای shared بدون divergence بازتعریف شوند. ساختار Trait و typeهای config نباید دو بار یا متناقض تعریف شوند.
- مواردی که فقط در `ComponentInputPrice` هستند و باید جداگانه تعریف شوند: `prop_title` (عنوان validator مستقل)، `prop_calculator`, `prop_calculatorColor`, `prop_information` و تنظیم‌های ظاهری/رفتاری اختصاصی فرم یا قیمت که مصرف Legacy آنها را تأیید می‌کند.
- Props آیکون، disabled، name، placeholder، input style، button enabled/title/class/semantic و validation از قرارداد و نام‌گذاری `ComponentInput` پیروی کنند. هر تفاوت نام Legacy فقط در adapter نگاشت شود و API جدید موازی نسازد.
- `CalculatorItem` و `InformationItem` به typeهای عمومی و مستند در `Props.ts` تبدیل شوند. nullable بودن آرایه‌ها، `coefficient` پیش‌فرض 1، `extension` و رنگ‌های اختیاری صریح باشد.
- `prop_value` باید مقادیر `string | number | null` و Observable متناظر را مطابق قرارداد سیستم پشتیبانی کند. تبدیل بین مقدار قابل ویرایش و مقدار قیمت فقط در state/adapter اختصاصی Price انجام شود؛ observable مصرف‌کننده بدون قرارداد مستند mutate نشود.
- نوع آیکون Legacy (`IconsType`) فقط در صورت نیاز، در مرز adapter به descriptor پشتیبانی‌شدهٔ `ComponentIcon` تبدیل شود؛ از کپی منطق مشترک رندر آیکون `ComponentInput` پرهیز شود.
- `prop_size` تعریف نشود؛ مانند `ComponentInput` اندازه‌ها از تنظیم سیستم گرفته شوند.
- تغییر Observable در `prop_calculator` و `prop_information` باید در همان الگوی reactive ساختار جدید بازتاب یابد؛ منطق مشترک ورودی از `ComponentInput` کپی/بازنویسی نشود.

## 5. Schemas، Methods و Step

`COMPONENT`, `STRUCTURE` از `ComponentStructureTrait` و `LABEL` از `ComponentLabelTrait` گرفته شوند. schemaها صرفاً metadata و prop binding داشته باشند و منطق رندر در کلاس کامپوننت بماند. Schemaهای مشترک form/input/icon/button/validate از نام‌گذاری و الگوی `ComponentInput` تبعیت کنند؛ فقط schemaهای Price افزوده شوند.

Schemaهای پیشنهادی:

| Schema | Part | مسئولیت |
|---|---|---|
| `FORM` | `part-input-price-form` | چینش کنترل‌ها و استایل پس‌زمینه/radius ظرف فرم. |
| `INPUT` | part ورودی متناظر با `ComponentInput` | اتصال `ComponentInputSimple` به ورودی و رخدادهای آن. |
| `ICON` | part آیکون متناظر با `ComponentInput` | آیکون اصلی ورودی. |
| `BUTTON` | part دکمهٔ متناظر با `ComponentInput` | دکمهٔ افزودن و اجرای callback Legacy. |
| `ICON_CLEAR` (در صورت نیاز) | part کنترل clear موجود در Legacy | فقط تفاوت اختصاصی پاک‌کردن؛ از قابلیت clear خود `ComponentInputSimple` استفاده شود اگر قراردادش معادل باشد. |
| `CALCULATOR` | `part-input-price-calculator` | نمایش مقدارهای مشتق‌شده بر اساس ورودی جاری. |
| `INFORMATION` | `part-input-price-information` | نمایش داده‌های کمکی و وضعیت focus. |
| `VALIDATE` | `part-input-price-validate` | ساخت شرطی `ComponentValidate`. |

تعریف دقیق part nameهای موجود در Legacy و استفادهٔ آنها در مصرف‌کنندگان بررسی شود؛ در صورت امکان نام‌های فعلی حفظ شوند تا selectorهای عمومی نشکنند. اگر نامی اصلاح می‌شود، علت و اثرش در implementation ثبت شود.

`Methods.ts` باید چهار callback Legacy را حفظ کند؛ نام‌گذاری، اتصال callbackهای مشترک ورودی و قرارداد `Step.ts` مانند `ComponentInput` باشد. تفاوت Price فقط در callbackهای `fn_onInput`, `fn_onFocus`, `fn_onBlur`, `fn_onClickButton` و payload قیمت اعمال شود. method عمومی جدید برای پیاده‌سازی داخلی focus، clear یا محاسبه اضافه نشود.

## 6. State، محاسبه و رخدادها

- مقدار خام تایپ‌شده و مقدار قالب‌بندی‌شده از هم تفکیک شوند تا اعمال فرمت در blur باعث cursor jump یا callback تکراری نشود.
- در هر input، مقدار عددی و `calcs` یک‌بار از state جاری محاسبه و در callback منتشر شوند. محاسبات و نمایش calculator باید با Observable به‌روزرسانی شوند و برای refresh از DOM query/class selector استفاده نکنند.
- در focus، اطلاعات نمایشی مطابق رفتار Legacy نشان داده شود؛ در blur، فرمت قیمت اعمال و اطلاعات پنهان شود. بررسی شود `prop_information` واقعاً باید با focus کنترل شود یا تنها از بیرون نمایش‌پذیر باشد؛ اگر مصرف Legacy این تفاوت را روشن نکند، در implementation انتخابی مستند شود.
- پاک‌کردن، مقدار ورودی/state/calculator را همگام کند، `fn_onInput` را با مقدار خالی/صفر مطابق قرارداد Legacy اجرا کند و سپس focus را برگرداند. مقدار `value` در payload باید طبق converter به `null` یا عدد تبدیل شود؛ تفاوت را با آزمون Legacy ثابت کنید.
- Enter فقط وقتی `prop_btnAddStatus` فعال است از submit پیش‌فرض جلوگیری کند و callback افزودن را یک‌بار اجرا کند.
- دکمه در حالت disabled قابل اجرا نباشد. تغییر دستی یا Observable در disabled، ورودی، clear، افزودن، calculator و validation را همگام کند.
- `dispose()` باید idempotent باشد و child componentها، subscriptionها، event stepها و scopeهای متعلق به instance را آزاد کند.

## 8. معیارهای پذیرش و بررسی

1. Component از ComponentManager و Category عمومی جدید ساخته شود؛ Definition، props، schemas، methods و examples در دسترس باشند.
2. label با `ComponentLabelTrait` ساخته شود و در نبود عنوان/tooltip خالی ظاهر نشود.
3. ورودی با `ComponentInputSimple` باشد؛ focus، blur، disabled، placeholder، name، مقدار Observable و استایل‌های border مطابق قرارداد نمایش داده شوند.
4. تبدیل مقدار به/از فرمت قیمت و payload عددی `VALUE.value` با رفتار مورد انتظار Legacy سازگار باشد؛ مقدار نامعتبر/خالی و اعشار نیز بررسی شوند.
5. محاسبات برای coefficientهای پیش‌فرض و سفارشی و چند نام مختلف نمایش داده شوند؛ با تغییر ورودی فوراً به‌روز شوند و بدون DOM query سراسری کار کنند.
6. clear، focus مجدد، رفتار Enter، دکمهٔ افزودن و callbackها هرکدام یک‌بار و با payload معتبر اجرا شوند.
7. information در حالت بدون/با داده، focus/blur، مقدار اختیاری `---` و جهت LTR/RTL قابل استفاده باشد.
8. validation با rules، disabled و observable rules به‌درستی ساخته/حذف شود و title validator مستقل از label بماند.
9. همهٔ اندازه‌ها از `CoreConfig.Settings.SizeName` و utilهای پروژه بیایند؛ API جدید `prop_size` نداشته باشد.
10. مثال‌های Default/Calculator/AddButton اجرا شوند؛ `git diff --check`، typecheck هدفمند، build/testهای موجود و آزمایش دستی input/focus/blur/clear/Enter/disable انجام شود. خطاهای پایهٔ ازقبل‌موجود از خطاهای این انتقال جدا گزارش شوند.
11. ساختار و رفتار مشترک با `ComponentInput` هم‌راستا بماند؛ تنها تفاوت‌های Price از Legacy (فرمت/محاسبهٔ قیمت، calculator، information، قرارداد clear و callbackهای Price) اضافه شوند.

## 9. خارج از محدوده

- تغییر `ComponentInputSimple`, `ComponentButton`, `ComponentIcon`, `ComponentValidate` یا converter عمومی، مگر باگ مانع‌ساز و مستند که مستقیماً برای این انتقال لازم باشد.
- تغییر قرارداد مصرف‌کنندگان Legacy یا پروژه‌های Laravel.
- حذف فایل Legacy یا تغییر رفتار عمومی خارج از قرارداد انتقال.
- افزودن API جدید صرفاً برای دور زدن محدودیت‌های lifecycle یا دسترسی سراسری DOM.
