# 1. هدف

هدف این Phase بازطراحی `ComponentStructure` به‌عنوان **Base Runtime مشترک تمام Componentها** است.

`ComponentStructure` نباید صرفاً یک کلاس برای نگهداری:

* Props
* Schemas
* Methods

باشد.

این کلاس باید زیرساخت مشترک Runtime Componentها را فراهم کند تا در آینده بتوان قابلیت‌هایی مانند:

* State
* Lifecycle
* Unique Identity
* Workflow Integration
* Runtime Component Management

را بدون تغییر اساسی در معماری اضافه کرد.

---

# 2. معماری هدف

ساختار مفهومی Component به شکل زیر باشد:

```text
                    Component Definition
                           │
                           ▼
                    Component Metadata
                           │
                           │
Props ───────────────► ComponentStructure ◄──────────── Methods
                           │
                           │
                        Runtime
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
           State        Lifecycle      Identity
             │
             ▼
           Schema
             │
             ▼
      SchemaHandler
             │
             ▼
          Rendering
```

تفکیک مسئولیت‌ها:

| بخش                  | مسئولیت                        |
| -------------------- | ------------------------------ |
| `Definition`         | شناسنامه و Metadata            |
| `Props`              | ورودی‌های Component            |
| `Schemas`            | تعریف ساختار UI                |
| `SchemaHandlers`     | رفتار و Rendering Schema       |
| `Methods`            | API/Callbacks رفتاری Component |
| `ComponentStructure` | Runtime Base                   |
| `State`              | وضعیت داخلی Component          |
| `Unique`             | هویت Instance                  |
| `Lifecycle`          | چرخه حیات Component            |

# 3. Definition باید باقی بماند

فایل:

```text
Definition.ts
```

حذف نشود.

`Definition` برای ComponentManager آینده اهمیت دارد و باید مستقل از Runtime باشد.

نمونه:

```ts
import * as UiComponents from "@/ui_components";

export const Definition:
    UiComponents.Basic.Types.ComponentDefinition = {

    id: "component_structure",
    name: "componentStructure",
    version: "v1.0.0",

};
```

در آینده ComponentManager می‌تواند بدون ساخت Instance، اطلاعات Component را از `Definition` دریافت کند.

بنابراین:

```text
Definition ≠ Component Runtime
```

# 4. Schema باید Declarative باقی بماند

`Schemas.ts` فقط ساختار Schema را تعریف کند.

Schema نباید شامل Rendering Function باشد.

نمونه مورد انتظار:

```ts
export const Schemas = {

    COMPONENT: {

        part: "part-component",

        props: [
            Props.classList,
            Props.styles,
        ],

        name:
            Keys.category.components.basic.schemas.component.name,

        description:
            Keys.category.components.basic.schemas.component.description,
    },

    STRUCTURE: {

        part: "part-component-structure",

        props: [
            Props.prop_show,
            Props.prop_structureClass,
            Props.prop_structureStyles,
        ],

        name:
            Keys.category.components.basic.schemas.structure.name,

        description:
            Keys.category.components.basic.schemas.structure.description,
    },

} satisfies UiComponents.Basic.Types.ComponentSchemas;
```

هدف:

```text
Schema = What
Handler = How
```

یعنی Schema مشخص می‌کند:

> این Part چیست و چه Propهایی دارد؟

اما مشخص نمی‌کند:

> چگونه Render شود؟

# 6. Handler باید Context دریافت کند

Handler نباید مستقیماً به Component خاصی وابسته شود.

Context باید اطلاعات Runtime مورد نیاز را در اختیار Handler قرار دهد.

نمونه:

```ts
export interface ComponentSchemaContext {

    component: ComponentSchemaContextComponent;

    attrsDefault:
        CoreComponents.PartAttrDefault;

    data:
        Record<string, CoreObservable.App<any>>;

    extra:
        Record<string, any>;

}
```

در صورت وجود type مناسب فعلی، از همان استفاده شود و type جدید فقط در صورت نیاز ایجاد شود.

# 7. ارتباط Schema و Handler

Schema و Handler باید توسط یک identifier مشترک به هم متصل شوند.

مدل مفهومی:

```text
Schemas.COMPONENT
       │
       │ identifier
       ▼
SchemaHandlers.COMPONENT
```

نباید Rendering Function مستقیماً داخل `Schemas.ts` قرار گیرد.

این کار باعث می‌شود:

* Schema قابل استفاده توسط ComponentManager باشد.
* Metadata از Rendering مستقل باشد.
* Handler قابل تغییر باشد.
* Componentهای پیچیده بتوانند Behavior بیشتری داشته باشند.

# 8. ComponentStructure

`ComponentStructure.ts` باید به عنوان Base Runtime باقی بماند.

ساختار پایه مورد انتظار:

```ts
export class ComponentStructure<
    TProp extends Record<string, any> = PropsType,
    TSchemas = SchemasType,
    TMethods extends Record<string, any> = MethodsType
> extends CoreComponents.App<
    TProp,
    TSchemas,
    any,
    TMethods
> {

    protected _COMPONENT_DEFINITION =
        Definition;

    protected _COMPONENT_PATTERN =
        CoreComponents.DefineProp<TProp>({
            ...Props,
        } as any);

    protected _COMPONENT_SCHEMA =
        CoreComponents.DefineSchema<TSchemas, TProp>({
            COMPONENT: {
                part: Schemas.COMPONENT.part,
                props: Schemas.COMPONENT.props ?? [],
            },

            STRUCTURE: {
                part: Schemas.STRUCTURE.part,
                props: Schemas.STRUCTURE.props ?? [],
            },

        } as any);

    protected _COMPONENT_METHODS =
        CoreComponents.DefineMethod<TMethods, TProp>({
            ...Methods,
        } as any);


    constructor(
        componentName: string = "structure",
        elId: string | null = null,
    ) {
        super(componentName, elId);
    }

}
```

نکته:

`SchemaHandlers` در `_COMPONENT_SCHEMA` به صورت مستقیم به عنوان `method` قرار نگیرد.

اتصال Schema → Handler باید توسط مکانیزم Core انجام شود.

# 12. Unique Identity

`unique` باید متعلق به **Component Instance** باشد، نه Schema.

مثال مفهومی:

```ts

    props,

    events,
    "submit-user"
```

اما Signature نهایی باید با API واقعی Core هماهنگ شود.

```text

    ↓
```

# 17. ComponentButton به عنوان Migration Test

بعد از تکمیل ComponentStructure، `ComponentButton` به عنوان اولین Component برای تست معماری جدید بررسی شود.

ساختار هدف:

```text
ComponentStructure
        │
        ▼
ComponentButtonBase
        │
        ├── Button Props
        ├── Button Schemas
        └── Button Methods
        │
        ▼
ComponentButton
        │
        ├── constructor
        └── renderContentComponent()
```

نمونه:

```ts
export class ComponentButtonBase
    extends ComponentStructure<
        ButtonPropsType,
        ButtonSchemasType,
        ButtonMethodsType
    > {

    protected _COMPONENT_PATTERN =
        CoreComponents.DefineProp({
            ...Props,
            ...ButtonProps,
        } as any);

    protected _COMPONENT_SCHEMA =
        CoreComponents.DefineSchema({
            ...
        } as any);

}
```

کلاس نهایی:

```ts
export class ComponentButton
    extends ComponentButtonBase {

    constructor(
        props,
        methods,
        events?,
        unique?,
        emit?
    ) {

        super("button", null);

        this.renderComponent(
            props,
            methods,
            events,
            unique,
            emit
        );
    }

    override renderContentComponent() {

        return this.executeSchemaPart(
            "part-form"
        );

    }

}
```

Signature واقعی باید مطابق Core موجود باشد و این مثال صرفاً قرارداد معماری است.
