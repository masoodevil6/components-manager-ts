# Plan 8.2.8 — Per-Message Event Scope

> **پیش‌نیاز:** Plan 8.2.7 — SubEvent: قرارداد سلسله‌مراتبی Events
> **هدف:** ایجاد Event Scope مستقل، پایدار و lifecycle-aware برای هر `MessageItem`

---

## 1. مسئله

### 1.1 وضعیت فعلی

در `ComponentMessages.ts`، ساختار فعلی Event به شکل زیر است:

```text
ComponentMessages
└── _COMPONENT_STEP
    ├── message
    └── icon
        └── close
```

در `renderMessages()` یک Event Identity مشترک برای کل لیست استفاده می‌شود:

```ts
unique: this._COMPONENT_STEP?.message ?? undefined
```

در نتیجه تمام Messageهای موجود در `prop_messages` از یک `message Step` استفاده می‌کنند.

ساختار فعلی:

```text
Messages
├── Message A ─┐
├── Message B ─┼── message Step
└── Message C ─┘
```

بنابراین وقتی `close` کلیک می‌شود، Request به یک handler مرکزی ارسال شده و handler باید با استفاده از `payload.id` تشخیص دهد کدام Message باید حذف شود.

---

## 2. هدف معماری

هر `MessageItem` باید Event Scope مستقل خودش را داشته باشد.

ساختار مطلوب:

```text
ComponentMessages
│
└── messages
    │
    ├── message_abc123
    │   ├── body
    │   └── icon
    │       └── close
    │
    ├── message_def456
    │   ├── body
    │   └── icon
    │       └── close
    │
    └── message_xyz789
        ├── body
        └── icon
            └── close
```

در نتیجه:

```text
Close #1 → Message #1
Close #2 → Message #2
Close #3 → Message #3
```

Routing باید بر اساس Event Identity انجام شود، نه با فیلتر کردن تمام Messageها توسط یک handler مرکزی.

---

# 3. Event Identity Contract

این Plan قراردادهای Plan 8.2.7 را برای Dynamic Collection توسعه می‌دهد.

## 3.1 Component Step

`ComponentMessages` یک Step اصلی دارد که در constructor ساخته می‌شود:

```text
ComponentMessagesStep
└── messages
```

این Step متعلق به lifecycle خود Component Instance است.

---

## 3.2 Message Event Scope

هر `MessageItem` یک Event Scope مستقل خواهد داشت:

```text
messages
└── message_<stable-id>
```

این Scope متعلق به lifecycle همان Message Instance است.

---

## 3.3 Event Scope نباید با Render Cycle یکی باشد

Render Cycle فقط مسئول تولید UI است.

Event Scope مسئول Event Identity و lifecycle است.

بنابراین الگوی صحیح:

```text
Render
    ↓
Resolve Message Identity
    ↓
Find existing Event Scope
    ↓
Create Scope فقط در صورت نیاز
    ↓
Render DOM using Scope
```

و نه:

```text
Render
    ↓
Create new Step
    ↓
Destroy old Step
```

---

# 4. Stable Identity

## 4.1 استفاده نکردن از index

Event Identity نباید بر اساس `index` باشد.

الگوی اشتباه:

```text
message_0
message_1
message_2
```

زیرا بعد از حذف آیتم اول:

```text
قبل:
A → 0
B → 1
C → 2

بعد:
B → 0
C → 1
```

در نتیجه Identity پیام‌ها تغییر می‌کند.

---

## 4.2 استفاده از Message ID

Identity باید بر اساس یک شناسه پایدار باشد:

```ts
message_${messageItem.id}
```

در نتیجه:

```text
A → message_A
B → message_B
C → message_C
```

حتی اگر ترتیب تغییر کند:

```text
C A B
```

Identityها همچنان:

```text
C → message_C
A → message_A
B → message_B
```

باقی می‌مانند.

---

# 5. Message Identity و Event Identity

این سه مفهوم باید از یکدیگر جدا باقی بمانند:

```text
Message Identity
       ≠
DOM Identity
       ≠
Event Identity
```

اما می‌توانند به یکدیگر نگاشت داشته باشند.

مثلاً:

```text
Message
id = "abc123"
       ↓
Event Scope
message_abc123
       ↓
DOM
data-id="abc123"
```

`id` مربوط به Business/Data Model است.

`Event Identity` مربوط به Event Routing است.

`DOM Identity` مربوط به UI/DOM است.

---

# 6. MessageItem بدون ID

قبل از implementation باید مشخص شود که آیا `MessageItem` همیشه `id` دارد یا خیر.

اگر قرارداد این باشد:

```ts
interface MessageItem {
    id: string;
    text: string;
}
```

مشکلی وجود ندارد.

اما اگر این حالت نیز مجاز باشد:

```ts
prop_messages: string[]
```

باید Messageها قبل از Render دارای Identity پایدار شوند.

نباید در Render چنین چیزی انجام شود:

```ts
Math.random()
```

زیرا:

```text
render #1
A → abc

render #2
A → xyz
```

در نتیجه Event Identity از بین می‌رود.

بنابراین:

> Message Identity باید قبل از Render و خارج از Render Cycle تثبیت شود.

# 7. Step Factory

فایل `Step.ts` باید دو سطح Event Structure داشته باشد.

## 7.1 Component Scope

```ts
export const createMessagesStep = () =>
    CoreEvent.Step({
        children: {
            messages: CoreEvent.Step({
                request: CoreEvent.Request(),
                response: CoreEvent.Response({ value: "" }),
            }),
        },
    });
```

ساختار:

```text
ComponentMessagesStep
└── messages
```

---

## 7.2 Message Scope

```ts
export const createMessageItemStep = () =>
    CoreEvent.Step({
        children: {
            body: CoreEvent.Step({
                request: CoreEvent.Request(),
                response: CoreEvent.Response({ value: "" }),
            }),

            icon: CoreEvent.Step({
                children: {
                    close: CoreEvent.Step({
                        request: CoreEvent.Request(),
                        response: CoreEvent.Response({ value: "" }),
                    }),
                },
            }),
        },
    });
```

ساختار:

```text
MessageScope
├── body
└── icon
    └── close
```

Factory فقط ساختار Event Scope را ایجاد می‌کند.

Factory مسئول lifecycle یا caching نیست.

---

# 8. Message Event Scope Registry

`ComponentMessages` باید بتواند Event Scopeهای مربوط به Messageها را نگهداری کند.

مفهوم منطقی:

```text
Message ID
    ↓
Message Event Scope
```

مثلاً:

```text
abc123 → Step#1
def456 → Step#2
xyz789 → Step#3
```

این Registry باید Scope را بین Render Cycleهای مختلف نگه دارد.

---

# 9. Resolve کردن Event Scope

در هنگام Render:

```text
Message abc123
      ↓
Scope وجود دارد؟
      │
      ├── بله
      │    ↓
      │   reuse
      │
      └── خیر
           ↓
       createMessageItemStep()
           ↓
       attach SubEvent
           ↓
       register
```

بنابراین اگر Message هنوز در لیست وجود داشته باشد:

```text
render #1
A → Step A1

render #2
A → Step A1

render #3
A → Step A1
```

و نه:

```text
render #1
A → Step A1

render #2
A → Step A2

render #3
A → Step A3
```

# 10. SubEvent

اتصال Message Scope به `messages` باید از API عمومی Event انجام شود:

```ts
CoreEvent.SubEvent(
    this._COMPONENT_STEP.messages,
    stepKey,
    messageStep,
);
```

اما قبل از implementation باید Contract فعلی `CoreEvent.SubEvent` بررسی شود.

باید مشخص شود که SubEvent دقیقاً مسئول کدام موارد است:

```text
SubEvent
├── attach
├── register
├── detach
└── dispose
```

اگر API فعلی این نیازها را پوشش نمی‌دهد، ابتدا باید Contract CoreEvent اصلاح شود.

نباید `ComponentMessages` مستقیماً به internals `Step` دسترسی پیدا کند.

# 11. ممنوعیت دسترسی مستقیم به Step Internals

موارد زیر مجاز نیستند:

```ts
step.children[key] = ...
```

```ts
(step as any).children
```

```ts
(step as any).register(...)
```

یا هر نوع mutation مستقیم روی ساختار داخلی Step.

Component باید فقط از API عمومی استفاده کند:

```text
CoreEvent.Step
CoreEvent.SubEvent
CoreEvent.App.request
CoreEvent.dispose
```

اگر این APIها کافی نیستند، باید خود CoreEvent توسعه پیدا کند.

# 13. renderMessages

در `renderMessages()` نباید دیگر Event Identity مربوط به کل لیست روی container قرار گیرد.

الگوی فعلی:

```ts
CoreReactive.App.div({
    unique: this._COMPONENT_STEP?.message,
    ...
});
```

باید حذف شود.

Container فقط نقش UI container را دارد.

برای هر Message:

```ts
unique: messageStep.body
```

استفاده خواهد شد.

# 14. Render Algorithm

الگوریتم `renderMessages()` باید به شکل زیر باشد:

```text
renderMessages()
    │
    ├── دریافت MessageItems
    │
    ├── برای هر Message
    │     │
    │     ├── resolve stable identity
    │     │
    │     ├── resolve Event Scope
    │     │
    │     ├── اگر Scope جدید است:
    │     │      create
    │     │      attach
    │     │
    │     └── render DOM
    │
    └── synchronize removed scopes
```

# 15. Event Scope باید از Render مستقل باشد

`CoreObservable.App.for()` یک Render/Derived Observable است.

بنابراین نباید lifecycle Event Scope را مستقیماً به callback آن وابسته کنیم.

الگوی خطرناک:

```ts
CoreObservable.App.for(
    messages,
    () => {
        const step = createMessageItemStep();
        ...
    }
);
```

زیرا `mapper` ممکن است چندین بار اجرا شود.

در عوض:

```text
Observable Rendering
        +
Event Scope Registry
        +
Lifecycle Synchronization
```

باید سه مسئولیت جدا داشته باشند.

# 16. Routing

وقتی Close Icon کلیک می‌شود:

```text
Icon#2
   │
   │ Request
   ↓
Message#2
```

Request باید از Event Identity همان Message استفاده کند.

مثلاً:

```ts
CoreEvent.App.request(
    CoreEvent.requestMap([
        [
            messageStep.body,
            {
                action: "close",
                id: messageItem.id,
            },
        ],
    ]),
    messageStep.icon.close,
);
```

`id` می‌تواند همچنان داخل payload وجود داشته باشد، اما دیگر نباید مسئول Routing باشد.

---

# 17. Business ID و Event Routing

این دو مفهوم باید جدا باقی بمانند:

```text
payload.id
    ↓
Business/Data Identity

messageStep
    ↓
Event Routing Identity
```

وجود `id` در payload اشکالی ندارد.

اما handler نباید برای پیدا کردن مقصد Event مجبور باشد کل collection را بررسی کند.

---

# 18. Message Emit Handler

Handler باید متعلق به همان Message Scope باشد:

```ts
emit: (request) => {

    if (request.payload?.action !== "close") {
        return { value: null };
    }

    // update data model

    return {
        value: {
            closed: true,
            id: messageItem.id,
        },
    };
}
```

Routing قبلاً توسط Event Tree انجام شده است.

Handler فقط باید Business Logic مربوط به همان Message را اجرا کند.

---

# 19. State Ownership

Per-Message Event Scope به معنای داشتن State مستقل برای هر Message نیست.

منبع حقیقت همچنان Component Data Model است:

```text
Event
 ↓
Component
 ↓
prop_messages
 ↓
Reactive Render
```

نه:

```text
Event
 ↓
DOM mutation
```

بنابراین همچنان:

```ts
this.set("prop_messages", newMessages);
```

منبع تغییر State خواهد بود.

---

# 20. Lifecycle

Lifecycle هر Message Scope:

```text
NEW
 ↓
create
 ↓
attach
 ↓
active
 ↓
reuse
 ↓
removed
 ↓
detach
 ↓
dispose
```

Scope باید تا زمانی که Message وجود دارد، قابل reuse باشد.

---

# 21. Add

فرض:

```text
A B
```

و سپس:

```text
A B C
```

باید نتیجه:

```text
A → existing Scope
B → existing Scope
C → new Scope
```

باشد.

---

# 22. Remove

فرض:

```text
A B C
```

و سپس:

```text
A C
```

باید:

```text
A → reuse
C → reuse
B → dispose
```

انجام شود.

---

# 23. Reorder

فرض:

```text
A B C
```

و سپس:

```text
C A B
```

هیچ Event Scope جدیدی نباید ایجاد شود.

```text
A → same Scope
B → same Scope
C → same Scope
```

فقط ترتیب Render تغییر می‌کند.

---

# 24. Disposal و Timing

هنگام حذف Message، نباید لزوماً داخل همان Event Handler بلافاصله:

```ts
CoreEvent.dispose(messageStep);
```

اجرا شود.

زیرا ممکن است Event Dispatcher هنوز در حال پردازش همان Event باشد.

ترتیب ترجیحی:

```text
Click
 ↓
executeMethod
 ↓
Event Request
 ↓
Message Handler
 ↓
update prop_messages
 ↓
Reactive Update
 ↓
detect removed Message
 ↓
dispose Message Scope
```

مگر اینکه Contract رسمی CoreEvent صراحتاً disposal حین dispatch را امن اعلام کرده باشد.

---

# 25. Lifecycle Synchronization

بعد از هر تغییر collection:

```text
previous IDs
+
current IDs
      ↓
diff
      ↓
removed IDs
      ↓
dispose corresponding scopes
```

مثال:

```text
Previous:
A B C D

Current:
A C D E
```

نتیجه:

```text
A → reuse
C → reuse
D → reuse
B → dispose
E → create
```

---

# 26. Multiple ComponentMessages

دو `ComponentMessages` مستقل نباید Event Identity مشترک داشته باشند.

مثال:

```text
ComponentMessages#1
└── messages
    └── A → Step A1


ComponentMessages#2
└── messages
    └── A → Step A2
```

با وجود یکسان بودن Business ID:

```text
A#1 ≠ A#2
```

Event Identity باید حداقل در محدوده Component Instance یکتا باشد.

---

# 27. Component Lifecycle

وقتی کل `ComponentMessages` destroy شود:

```text
ComponentMessages
    ↓
dispose Component Event Scope
    ↓
dispose messages
    ↓
dispose all Message Scopes
```

بنابراین Component نباید Event Scopeهای orphan شده داشته باشد.


```text
ComponentMessages

    ├── A
    │   ├── body
    │   └── icon.close

    ├── B
    │   ├── body

    └── C
        ├── body
        └── icon.close
```

```text
Click B.close
      ↓

      ↓

      ↓
ComponentMessages
      ↓
prop_messages = [A, C]
      ↓
Reactive Render
      ↓
B Scope removed
      ↓
B Scope disposed
```

A و C همان Event Scope قبلی خود را حفظ می‌کنند.

# 38. اصل کلیدی Plan 8.2.8

> **Render یک Message را نمایش می‌دهد، اما Event Scope مالک Event Identity و lifecycle همان Message است.**

بنابراین:

```text
Render
    ≠
Event Lifecycle
```

و:

```text
Dynamic Collection
    ≠
Create New Event Identity on Every Render
```

مدل صحیح:

```text
Message Identity
       ↓
Event Scope
       ↓
Stable across renders
       ↓
Dispose only when Message is removed
```

## 41. اصل نهایی

معماری نهایی باید این تفکیک را حفظ کند:

```text
Component
    │
    ├── Data / State
    │
    ├── Render
    │
    └── Event Scope
          │
          ├── Message A
          ├── Message B
          └── Message N
```

هر Message یک **Event Boundary** مستقل دارد، اما مالک State مستقل نیست.

در نتیجه `SubEvent` به عنوان یک Event Scope در Component Layer عمل می‌کند و `CoreEvent` همچنان مسئول Event Engine باقی می‌ماند.

**اصل کلیدی:**

> `SubEvent` باید مرز Event را مشخص کند، نه اینکه Render Cycle را به Event Lifecycle تبدیل کند.
