# Plan 5.9 — Component Runtime Simplification & Composition

## هدف

بازطراحی Runtime کامپوننت‌ها با این اصل:

> **Component باید خودش مسئول State، Methods و Rendering باشد و Composition بین Componentها از طریق API خود Component انجام شود.**

هدف این Phase حذف پیچیدگی‌های غیرضروری مانند:

* `SchemaHandlers`
* وابستگی Runtime به Schema برای Rendering
* `renderManagerComponent` به‌عنوان Router اصلی
* الگوی Legacy برای Render
* ساخت مستقیم Componentها در لایه‌های نامرتبط

و رسیدن به مدلی که استفاده از یک Component تا حد ممکن ساده باشد:

```typescript
const structure = new ComponentStructure({
    classList: ["p-2", "border"],
    prop_show: true,

    content: () => {
        return ReactiveApp.button({
            children: ["Toggle"]
        });
    }
});
```

---

# 1. اصل معماری جدید

معماری باید بر اساس این تفکیک باشد:

```text
Definition
    ↓
Metadata / Identity

Props
    ↓
External Configuration

Schemas
    ↓
Declarative Structure

Component Class
    ↓
Runtime Behavior
    ├── State
    ├── Methods
    ├── Rendering
    └── Composition

ReactiveElement
    ↓
Actual DOM / Reactive UI
```

### اصل مهم

`Schema` نباید مسئول Rendering باشد.

`Schema` فقط تعریف می‌کند:

> این Component چه Partهایی دارد؟

اما این سؤال:

> این Part چگونه ساخته شود؟

باید توسط خود Component پاسخ داده شود.

---

# 2. حذف کامل SchemaHandlers

فایل زیر باید حذف شود:

```text
SchemaHandlers.ts
```

و این الگو نباید دیگر وجود داشته باشد:

```typescript
Schemas.COMPONENT
    ↓
SchemaHandlers.COMPONENT
    ↓
handler.render(context)
```

همچنین `Schema` نباید شامل:

```typescript
handler
render
renderer
callback
```

برای Runtime Rendering باشد.

---

# 3. حذف Rendering Routing غیرضروری

ساختار قدیمی:

```text
executeSchemaPart()
    ↓
renderManagerComponent()
    ↓
switch(partName)
    ↓
template_render_...
```

نباید معماری اصلی Component باشد.

به‌خصوص نباید یک متد مرکزی ایجاد شود که تمام Partهای Component را با `switch` مدیریت کند:

```typescript
switch (partName) {
    case "...":
    case "...":
    case "...":
}
```

این همان الگوی Legacy است که باید از معماری جدید حذف شود.

# 4. ComponentStructure به‌عنوان یک Component واقعی

`ComponentStructure` نباید Base اجباری تمام Componentها باشد.

هر Component واقعی باید مستقیماً از `ComponentBase` ارث‌بری کند:

```typescript
class ComponentButton extends ComponentBase {
}

class ComponentCollapse extends ComponentBase {
}

class ComponentStructure extends ComponentBase {
}
```

بنابراین:

```text
ComponentBase
│
├── ComponentStructure
├── ComponentButton
├── ComponentCollapse
├── ComponentInput
└── ...
```

`ComponentStructure` فقط یک Component عمومی برای ساخت یک Structure قابل استفاده است.

---

# 5. Composition به جای Inheritance

استفاده از Componentها باید از طریق Composition انجام شود.

مثلاً `ComponentStructure` باید بتواند محتوای خود را دریافت کند:

```typescript
const structure =
    new ComponentStructure({

        classList: [
            "p-2",
            "border"
        ],

        prop_show: true,

        prop_structureClass: [
            "bg-light",
            "rounded"
        ],

        content: () => {
            return ReactiveApp.button({
                children: [
                    "Toggle"
                ]
            });
        }

    });
```

اصل:

```text
Inheritance
    ↓
اشتراک رفتار پایه

Composition
    ↓
استفاده از Component داخل Component
```

نباید برای استفاده از یک Component دیگر مجبور به inheritance شویم.

---

# 6. `content` یک Composition Point است

`content` از نظر مفهومی یک Prop معمولی نیست.

این یک نقطه اتصال Composition است.

مدل پیشنهادی:

```typescript
type ComponentContent =
    () => CoreReactive.App;
```

و ComponentStructure می‌تواند چیزی شبیه این داشته باشد:

```typescript
type ComponentStructureConfig = {
    selector?: string | null;
    append?: boolean;

    classList?: string[];
    styles?: Record<string, string>;

    prop_show?: boolean;

    prop_structureClass?: string[];
    prop_structureStyles?: Record<string, string>;

    content?: ComponentContent;
};
```

نکته:

اگر معماری Type System فعلی نیاز دارد این مورد در Props ثبت شود، باید بررسی شود؛ اما از نظر مفهومی `content` باید به‌عنوان **Composition API** شناخته شود، نه Schema Handler.

---

# 7. State باید داخل Component باشد

Componentهایی که State دارند باید State خودشان را نگهداری کنند.

مثلاً:

```typescript
class ComponentCollapse extends ComponentBase {

    protected readonly state = {
        open: new CoreObservable.App(false)
    };

    protected toggle() {
        const value = this.state.open.get();

        this.state.open.set(!value);
    }

}
```

State نباید در:

```text
Schema
SchemaHandler
Example
ReactiveElement خارج از Component
```

قرار بگیرد.

---

# 8. Methods باید داخل Component باشند

Methods مربوط به رفتار Component باید در خود Component قرار بگیرند.

مثلاً:

```typescript
class ComponentCollapse extends ComponentBase {

    protected readonly state = {
        open: new CoreObservable.App(false)
    };

    protected toggle() {
        this.state.open.set(
            !this.state.open.get()
        );
    }
}
```

این Method بخشی از Runtime Component است.

Schema نباید چیزی شبیه این داشته باشد:

```typescript
{
    handler: ...
}
```

# 9. Rendering باید در Component باشد

Component باید بتواند خودش ReactiveElement خود را بسازد.

مثلاً:

```typescript
class ComponentStructure extends ComponentBase {

    protected render() {

        return ReactiveApp.part("section", {

            classBind: [
                this.get("prop_structureClass"),
                this.get("prop_show")
                    .mapBoolean("show", "d-none")
            ],

            stylesBind: {
                styles:
                    this.get("prop_structureStyles")
            },

            children: [
                this.renderContent()
            ]

        });
    }

    protected renderContent() {

        return this.content
            ? this.content()
            : null;
    }
}
```

نام دقیق متدها باید با Core فعلی هماهنگ شود؛ این کد صرفاً مدل معماری است.

# 14. Component Dependency / Composition API

هدف نهایی این است که Component بتواند Componentهای دیگر را به‌صورت استاندارد مصرف کند.

مثلاً:

```typescript
export const Components = {
    icon: UiComponents.Icon
};
```

و داخل Runtime:

```typescript
return Components.icon({
    ...
});
```

یا در صورت نهایی شدن API:

```typescript
return UiComponents.Icon({
    ...
});
```

هدف این است که:

```text
Component A
    │
    ├── uses → Component B
    ├── uses → Component C
    └── uses → Component D
```

بدون inheritance و بدون SchemaHandler.

# نتیجه مورد انتظار

معماری نهایی باید از این:

```text
Schema
   ↓
SchemaHandler
   ↓
renderManagerComponent
   ↓
Legacy Renderer
   ↓
ReactiveElement
```

به این برسد:

```text
Component
│
├── Props
├── State
├── Methods
├── Rendering
└── Composition
        │
        ▼
   ReactiveElement
```

و Schema صرفاً در لایه Declarative باقی بماند:

```text
Definition → Identity
Props      → Configuration
Schemas    → Structure Metadata
Methods    → Metadata / Contract
Examples   → Showcase Metadata

Component  → Runtime
```

**قانون طلایی این Phase:**

> اگر برای ساخت یا رفتار یک Component مجبور شدیم Rendering را از بیرون Component به SchemaHandler یا Router منتقل کنیم، معماری را اشتباه پیاده کرده‌ایم.
