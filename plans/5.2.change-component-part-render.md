# PLAN: انتقال Rendering از `renderManagerComponent` به `Schema.method`

## هدف

حذف وابستگی `ComponentStructure` به `renderManagerComponent` و انتقال مسئولیت Rendering هر Part به `method` همان Schema.

ساختار هدف:

```text
Schema
  │
  ├── part
  ├── props
  ├── metadata
  └── method
        │
        ▼
   Schema Renderer
```

به‌جای:

```text
Schema
  │
  ▼
executeSchemaPart()
  │
  ▼
renderManagerComponent()
  │
  ├── if COMPONENT
  ├── if STRUCTURE
  └── super
```

ساختار جدید باید به این شکل باشد:

```text
Schema
  │
  ▼
executeSchemaPart()
  │
  ▼
Schema.method()
  │
  ▼
CoreReactive.App
```

# 1. بررسی وضعیت فعلی

قبل از هر تغییر، این بخش‌ها بررسی شوند:

```text
ClComponentBase.executeSchemaPart()

Interface_ComponentSchema

TComponentSchemaEntry

ComponentStructureBase

ComponentStructure

Schemas.ts
```

مخصوصاً بررسی شود که `executeSchemaPart` در حال حاضر چگونه `itemPart.method` را اجرا می‌کند.

اگر `method` از قبل در Interface یا Runtime پشتیبانی می‌شود، از همان mechanism استفاده شود و abstraction موازی ایجاد نشود.

# 2. افزودن Type برای Schema Method

در:

```text
basic/types/TComponentSchemaEntry.ts
```

نوع عمومی برای Schema Renderer تعریف شود.

به‌جای:

```ts
this: any
```

یک Context Interface عمومی تعریف شود.

نمونه:

```ts
export interface IComponentSchemaContext {
    _COMPONENT_NAME: string;

    executeSchemaPart(
        partName: string,
        ...args: any[]
    ): CoreReactive.App;

    renderContentComponent(): CoreReactive.App;
}
```

سپس:

```ts
export type ComponentSchemaMethod = (
    this: IComponentSchemaContext,
    attrsDefault: PartAttrDefault,
    data: Record<string, CoreObservable.App<any>>,
    extra: Record<string, any>
) => CoreReactive.App;
```

### نکته

Interface نباید `ComponentStructure` را import کند.

هدف این Context جلوگیری از Circular Dependency است.

`ComponentStructure` در Runtime می‌تواند این Context را فراهم کند، ولی Type Layer نباید به آن وابسته شود.

# 4. انتقال Renderer مربوط به COMPONENT به `Schemas.ts`

در:

```text
ComponentStructure/Schemas.ts
```

برای `Schemas.COMPONENT` مقدار `method` تعریف شود.

Method باید با `function` معمولی نوشته شود، نه arrow function.

نمونه:

```ts
method: function(attrsDefault, data, extra) {

    const rtl = CoreConfigs.Settings.DirectionRtl.observable();

    const classList =
        data?.classList ??
        new CoreObservable.App([]);

    const styles =
        data?.styles ??
        new CoreObservable.App({});

    return CoreReactive.App.component(
        this._COMPONENT_NAME,
        {
            attrs: {
                ...attrsDefault
            },

            classBind: [
                classList
            ],

            stylesBind: {
                direction: rtl.mapBoolean("rtl", "ltr"),
                styles: styles,
            },

            children: [
                this.executeSchemaPart(
                    Schemas.STRUCTURE.part
                )
            ]
        }
    );
}
```

منطق فعلی `renderComponentLayer` بدون تغییر رفتاری منتقل شود.

# 5. انتقال Renderer مربوط به STRUCTURE

در:

```text
ComponentStructure/Schemas.ts
```

برای `Schemas.STRUCTURE` نیز `method` تعریف شود.

نمونه:

```ts
method: function(attrsDefault, data, extra) {

    const prop_show =
        data?.prop_show ??
        new CoreObservable.App(true);

    const prop_structureClass =
        data?.prop_structureClass ??
        new CoreObservable.App([]);

    const prop_structureStyles =
        data?.prop_structureStyles ??
        new CoreObservable.App({});

    return CoreReactive.App.part(
        "section",
        {
            classBind: [
                prop_structureClass,
                prop_show.mapBoolean("show", "d-none")
            ],

            attrs: {
                ...attrsDefault
            },

            stylesBind: {
                prop_structureStyles
            },

            children: [
                this.renderContentComponent()
            ]
        }
    );
}
```

منطق فعلی `renderStructureLayer` باید بدون تغییر رفتاری منتقل شود.

# 8. رفتار `executeSchemaPart`

`executeSchemaPart` نباید برای Schemaهایی که `method` دارند به `renderManagerComponent` وابسته باشد.

منطق مطلوب:

```text
executeSchemaPart
       │
       ├── Schema.method موجود است؟
       │       │
       │       └── YES → method.call(this, ...)
       │
       └── مسیر fallback موجود
```

## 8.1. حفظ Backward Compatibility

در این Phase **فقط override مربوط به `renderManagerComponent` در `ComponentStructure` حذف شود**.

`ClComponentBase.renderManagerComponent` فعلاً حفظ شود و به‌عنوان **fallback / backward-compatible path** باقی بماند.

ساختار هدف:

```text
ClComponentBase
│
├── executeSchemaPart()
│       │
│       ├── Schema.method موجود است
│       │       └── method.call(this, ...)
│       │
│       └── Schema.method وجود ندارد
│               └── renderManagerComponent(...)
│
└── renderManagerComponent()
        └── fallback برای Componentهای قدیمی
```

### ComponentStructure

حذف شود:

```ts
override renderManagerComponent(...)
```

همچنین Rendererهای مربوط به آن که به `Schemas.method` منتقل شده‌اند حذف شوند:

```ts
renderComponentLayer()
renderStructureLayer()
```

### ClComponentBase

فعلاً هیچ تغییری در:

```ts
renderManagerComponent()
```

داده نشود.

دلیل:

* حفظ backward compatibility
* پشتیبانی از Componentهای قدیمی
* جلوگیری از شکستن Componentهایی که هنوز `Schema.method` ندارند
* امکان Migration تدریجی Componentها به معماری جدید

### قانون Migration

از این Phase به بعد:

```text
Schema.method
    ↓
روش استاندارد و ترجیحی
```

و:

```text
renderManagerComponent
    ↓
fallback / legacy mechanism
```

باشد.

`renderManagerComponent` در یک Phase جداگانه و فقط پس از بررسی تمام استفاده‌های آن در Repository می‌تواند deprecate یا حذف شود.

**در این Phase هیچ تغییری در `ClComponentBase.renderManagerComponent` انجام نشود.**

# 9. Schema Method Context

`Schema.method` باید بتواند به قابلیت‌های عمومی Component instance دسترسی داشته باشد.

حداقل Context فعلی:

```text
IComponentSchemaContext
│
├── _COMPONENT_NAME
├── executeSchemaPart()
└── renderContentComponent()
```

در صورت نیاز به متدهای دیگر، فقط زمانی به Context اضافه شوند که:

1. Schema Renderer واقعاً به آن نیاز داشته باشد.
2. آن API بخشی از Contract عمومی Component باشد.
3. اضافه کردن آن باعث coupling با Implementation نشود.

از قرار دادن `ComponentStructure` یا Componentهای concrete داخل این Context خودداری شود.

# 11. Rule جدید معماری

در Guide مربوط به Component/Schema این قانون ثبت شود:

```text
A Schema MAY define a method responsible for rendering its Part.

When a Schema defines a method, the rendering engine MUST execute that method
using the current Component instance as its context.
```

همچنین:

```text
ComponentStructure MUST NOT contain a Part-name-based rendering switch
when the corresponding Schema provides a rendering method.
```

## اصل معماری نهایی

بعد از این تغییر، مسئولیت‌ها باید به این شکل باشند:

```text
ComponentStructure
        │
        │ owns Component instance
        ▼
ComponentStructureBase
        │
        │ owns Component Schema
        ▼
Schema
        │
        ├── part
        ├── props
        ├── metadata
        └── method
                  │
                  ▼
             Renderer
```

**Schema تعریف می‌کند که یک Part چیست و چگونه Render می‌شود.**

**Component مسئول نگهداری Instance و Context است.**

**Rendering Engine فقط Schema را اجرا می‌کند و نباید برای هر Part یک `if/switch` اختصاصی داشته باشد.**
