# Implementation Plan: CoreEvent Module

> **وضعیت:** به‌روزرسانی‌شده پس از بازبینی مهندسی
>
> **تغییرات این نسخه نسبت به نسخه اولیه:**
>
> 1. نام ماژول از جمع (`module_events`) به مفرد (`module_event`) تغییر کرد — مطابق الگوی ماژول‌های موجود (`module_config` ،`module_reactive` ،`module_observable` و...).
> 2. تکلیف رابطه با `CoreObservable` روشن شد: دو سیستم **کاملاً مستقل** هستند. `CoreEvent` هیچ وابستگی و هیچ ادغامی با `CoreObservable` ندارد و بر پایه Callback خالص پیاده‌سازی می‌شود.
> 3. ساختار پوشه‌ها با الگوی واقعی پروژه هماهنگ شد (پوشه `class/` + `types/` + `index.ts` با الگوی export `App`).
> 4. الگوی کلید آبجکت `[Step]: {...}` که از نظر زبان JavaScript قابل اجرا نبود، با الگوی type-safe `requestMap` جایگزین شد.
> 5. بخش «قراردادهای پروژه» (نام‌گذاری `Cl`/`T`/`Mt`، alias، حداقل Phaseهای اجرا) و «ریسک‌های فنی» افزوده شد.

## 0. هدف اصلی

یک ماژول جدید به نام `module_event` در هسته Framework ایجاد شود که یک سیستم سبک و type-safe برای تعریف **Step، Request و Response** فراهم کند.

این سیستم باید از ابتدا با این فرض طراحی شود که در آینده بتواند به یک `CoreWorkflow` / Workflow Graph متصل شود، اما **در این مرحله نباید Workflow Engine پیاده‌سازی شود.**

معماری فعلی باید تا حد ممکن حفظ شود و CoreEvent نباید مسئول State Management یا Observable State باشد.

# 3. مفهوم اصلی معماری

در این معماری، تمام گره‌های منطقی Workflow از نوع `CoreEvent.Step` هستند.

مثلاً:

```ts
const User = CoreEvent.Step({
    children: {
        info: CoreEvent.Step({
            children: {
                name: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response({
                        value: ""
                    })
                }),

                family: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response({
                        value: ""
                    })
                }),

                submit: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response()
                })
            }
        })
    }
});
```

ساختار منطقی:

```text
User [Step]
└── info [Step]
    ├── name [Step]
    ├── family [Step]
    └── submit [Step]
```

هر گره در این درخت یک `Step` است.

یک Step ممکن است:

1. فقط یک container منطقی باشد.
2. Request/Response داشته باشد.
3. فرزند داشته باشد.
4. هم Request/Response و هم children داشته باشد.

نباید فرض شود که هر Step الزاماً به یک ReactiveElement متصل است.

# 5. ساختار Step

Step باید یک runtime object واقعی باشد، نه صرفاً TypeScript type.

مفهوم کلی:

```ts
CoreEvent.Step({
    request?: CoreEvent.RequestDefinition,
    response?: CoreEvent.ResponseDefinition,
    children?: Record<string, CoreEvent.Step>
});
```

نمونه:

```ts
const User = CoreEvent.Step({

    children: {

        info: CoreEvent.Step({

            children: {

                name: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response({
                        value: ""
                    })
                })

            }

        })

    }

});
```

---

# 6. Step باید شناسه داخلی داشته باشد

هر Step باید یک identity داخلی و پایدار داشته باشد.

این identity نباید بر اساس string path ساخته شود.

از این مدل اجتناب شود:

```ts
"user.info.name"
```

در API داخلی نیز تا حد امکان از string path به عنوان identity اصلی استفاده نشود.

پیشنهاد:

```ts
class Step {
    readonly id: symbol;
}
```

یا یک identity داخلی مناسب دیگر.

هدف:

```text
User.info.name
       │
       ▼
   Step object
       │
       ▼
 internal unique identity
```

# 7. دسترسی به children

ساختار definition باید explicit باشد:

```ts
Step({
    children: {
        name: Step(...),
        family: Step(...)
    }
});
```

نباید properties ناشناخته‌ی Step به صورت implicit به عنوان children تفسیر شوند.

یعنی این مدل استفاده نشود:

```ts
Step({
    name: Step(...),
    family: Step(...)
});
```

بلکه:

```ts
Step({
    children: {
        name: Step(...),
        family: Step(...)
    }
});
```

این باعث می‌شود قرارداد Step کاملاً مشخص باشد.

هدف:

```ts
User.info.name
```

```ts

```

برگرداند.

این قسمت باید type-safe باشد.

# 9. Request Definition

Request Definition مشخص می‌کند یک Step چه نوع Requestی را قبول می‌کند.

مثلاً:

```ts
CoreEvent.Step({

    request: CoreEvent.Request({
        validate: true
    }),

    response: CoreEvent.Response({
        value: ""
    })

});
```

مهم:

```ts
CoreEvent.Request(...)
```

در زمان تعریف Workflow نباید یک Request runtime واقعی ارسال کند.

بلکه باید یک Definition/Contract بسازد.

---

# 10. Response Definition

Response Definition مشخص می‌کند یک Step چه نوع Responseای تولید می‌کند.

مثلاً:

```ts
CoreEvent.Response({
    value: "",
    valid: false
});
```

این نیز Definition است.

Request و Response Definition باید از Runtime Request/Response قابل تشخیص باشند.

# 11. Runtime Request

در زمان اجرای واقعی:

```ts
event.request(...)
```

باید یک Request runtime ایجاد و dispatch شود.

این با:

```ts
CoreEvent.Request(...)
```

که در تعریف Step استفاده می‌شود، یک مفهوم نیست.

اگر برای جلوگیری از ابهام لازم است، Definition و Runtime باید naming داخلی متفاوت داشته باشند.

مثلاً:

```text
RequestDefinition
Request
```

و:

```text
ResponseDefinition
Response
```

اما API عمومی می‌تواند تا حد امکان ساده باقی بماند.

---

# 12. Request باید چند Target داشته باشد

یک Request می‌تواند همزمان به چند Step ارسال شود.

مثال:

```ts
const response = event.request(
    CoreEvent.requestMap([
        [User.info.name,     { validate: true }],
        [User.info.family,   { validate: true }]
    ])
);
```

> **نکته فنی مهم (اصلاح نسبت به طرح اولیه):** الگوی `{ [User.info.name]: {...} }` در JavaScript کار نمی‌کند؛ کلید آبجکت همیشه به string تبدیل می‌شود (`"[object Object]"`) و ارتباط با Step از بین می‌رود. بنابراین targetها با آرایه دوتایی `[Step, payload]` و تایپ `TRequestMap` منتقل می‌شوند که هم در runtime درست است و هم به TypeScript اجازه بررسی type-safe کلیدها را می‌دهد.

بنابراین Request نباید فقط یک target داشته باشد.

ساختار منطقی:

```text
Request
│
├── Target: User.info.name
│
└── Target: User.info.family
```

---

# 13. Response باید ساختار Request را حفظ کند

اگر:

```ts
event.request(
    CoreEvent.requestMap([
        [User.info.name,   { validate: true }],
        [User.info.family, { validate: true }]
    ])
);
```

ارسال شود، Response باید بتواند به همان Targetها نسبت داده شود.

Response نیز همان ساختار آرایه دوتایی را حفظ می‌کند:

```ts
[
    [User.info.name,   { value: "Mehdi",     valid: true }],
    [User.info.family, { value: "Maarefian", valid: true }]
]
```

این ساختار (`TResponseMap`) دقیقاً قرینه `TRequestMap` است؛ بنابراین مصرف‌کننده می‌تواند با همان ترتیب، به نتیجه هر Step دسترسی یابد.

هدف مهم:

> Request topology و Response topology باید قابل تطبیق باشند.

# 14. Request/Response چندگانه

# 18. emit در ReactiveElement

ReactiveElement باید بتواند Request مربوط به Step خود را دریافت کند.

`emit` یک **Request Handler** است نه Event Emitter (بخش ۱۴ Clarification). فرم نهایی callback مستقیم است:

```ts
const nameInput = ClReactiveElement.input({

    unique: User.info.name,

    emit: request => {

        return {
            value: nameInput.getElement().value,
            valid: true
        };

    }

});
```

در اینجا `emit` implementation مربوط به Step در UI است.

CoreEvent فقط Contract و Dispatch را مدیریت می‌کند:

```text
CoreEvent.Step
       │
       │ Contract
       ▼
ReactiveElement
       │
       │ emit
       ▼
Runtime implementation
```

تفکیک مسئولیت‌ها (بخش ۱۰ Clarification):

```text
Step تعریف می‌کند:          چه چیزی وجود دارد؟ چه Requestای قبول می‌کند؟ چه Responseای تولید می‌کند؟
ReactiveElement تعیین می‌کند: این Step در UI چگونه اجرا می‌شود؟
```

ممنوعیت‌های پیاده‌سازی (بخش ۱۴ Clarification):

```ts
emit: EventEmitter     // ❌ ممنوع
emit: Observable       // ❌ ممنوع
emit: (...events) => {} // ❌ ممنوع
```

`emit` فقط و فقط یک Request Handler با امضای `(request) => Response | any` است.

# 19. Event و Observable نباید ادغام شوند

این دو سیستم کاملاً جدا بمانند:

```text
CoreObservable
│
└── State
    ├── get
    ├── set
    └── subscribe


CoreEvent
│
└── Interaction
    ├── Request
    ├── Response
    └── callback
```

نباید برای پیاده‌سازی CoreEvent از Observable به عنوان abstraction اصلی استفاده شود.

اگر implementation داخلی در آینده برای برخی قابلیت‌ها از Observable استفاده کرد، این implementation detail است و نباید API CoreEvent را Observable-based کند.

### تصمیم نهایی (تأییدشده)

ماژول `CoreEvent` با ماژول `CoreObservable` **هیچ ارتباطی ندارد**:

```text
CoreObservable  ──✕──  CoreEvent
        (مستقل کامل)      (مستقل کامل)
```

- `CoreEvent` **هیچ importی** از `@/core_observable` ندارد — نه مستقیم و نه غیرمستقیم.
- پیاده‌سازی کاملاً بر پایه **Callback خالص** است (subscriber set ساده، بدون کلاس `ClObservable`).
- هیچ property یا متدی از `CoreObservable` در API عمومی `CoreEvent` ظاهر نمی‌شود.
- همین استقلال، مزیت معماری است: هر دو ماژول قابل تست، قابل استفاده و قابل توسعه به‌صورت مجزا هستند و تغییر در یکی هرگز دیگری را نمی‌شکند.
- تفاوت مفهومی: `CoreObservable` برای **State** (مقدار + اشتراک تغییرات) است؛ `CoreEvent` برای **Interaction** (پیام + پاسخ). هیچ سناریویی نیازی به ترکیب آن‌ها در این لایه ندارد.

# 23. Type Safety

این بخش بسیار مهم است.

هدف:

```ts
User.info.name
```

از نوع:

```ts
CoreEvent.Step<...>
```

باشد.

و:

```ts
unique: User.info.name
```

کاملاً type-safe باشد.

همچنین Request/Response باید در صورت امکان generic باشند.

مثلاً:

```ts
CoreEvent.Step<
    TRequest,
    TResponse
>
```

نمونه:

```ts
const name = CoreEvent.Step({

    request: CoreEvent.Request<{
        validate: boolean
    }>(),

    response: CoreEvent.Response<{
        value: string,
        valid: boolean
    }>()

});
```

هدف این است که TypeScript بتواند Contract بین Stepها را تا حد امکان بررسی کند.

### امضاهای generic پیشنهادی (سطح پیاده‌سازی)

```ts
// تعریف Step — سه پارامتر generic با default
class ClStep<
    TRequest  = Record<string, any>,
    TResponse = Record<string, any>,
    TChildren extends Record<string, ClStep> = Record<string, ClStep>
> {
    readonly id: symbol;
    readonly children: TChildren;
    // ...
}

// dispatch — استخراج type-safe از requestMap
MtRequest<TTargets extends ReadonlyArray<[ClStep, any]>>(
    map: TTargets
): TResponseMap<TTargets>;

// نگاشت قرینه‌ی Response
type TResponseMap<TTargets extends ReadonlyArray<[ClStep, any]>> = {
    [K in keyof TTargets]: TTargets[K] extends [ClStep<infer TReq, infer TRes>, any]
        ? [TTargets[K][0], TRes]
        : never;
};
```

با این ساختار، TypeScript می‌تواند:
1. نوع payload هر target را با Contract همان Step تطبیق دهد.
2. نوع هر عضو ResponseMap را از همان Step استخراج کند.
3. خطای Contract (مثلاً ارسال payload نامعتبر برای یک Step) در زمان کامپایل گزارش شود.

# 28. اولین سناریوی تست اجباری

سناریوی پایه:

```ts
const User = CoreEvent.Step({

    children: {

        info: CoreEvent.Step({

            children: {

                name: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response({
                        value: ""
                    })
                }),

                family: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response({
                        value: ""
                    })
                }),

                submit: CoreEvent.Step({
                    request: CoreEvent.Request(),
                    response: CoreEvent.Response()
                })

            }

        })

    }

});
```

سپس:

```ts
const nameInput = ClReactiveElement.input({
    unique: User.info.name,
    emit: request => {
        if (request.action === "validate") {
            const value = nameInput.getElement().value;
            return { value, valid: value.trim().length > 0 };
        }
    }
});

const familyInput = ClReactiveElement.input({
    unique: User.info.family,
    emit: request => {
        if (request.action === "validate") {
            const value = familyInput.getElement().value;
            return { value, valid: value.trim().length > 0 };
        }
    }
});

const submitButton = ClReactiveElement.button({
    unique: User.info.submit,
    on: {
        click: (e, event) => {
            return event.request(
                CoreEvent.requestMap([
                    [User.info.name,   { action: "validate" }],
                    [User.info.family, { action: "validate" }]
                ])
            );
        }
    }
});
```

وقتی Submit کلیک شد:

```text
Button (آغازگر — بخش ۶ Clarification)
   │
   │ event.request(requestMap)
   ▼
CoreEvents (Dispatcher)
   │
   ├── target: User.info.name   → nameInput.emit(request)   → Response
   │
   └── target: User.info.family → familyInput.emit(request) → Response
   │
   ▼
TResponseMap به فرستنده (Button) برمی‌گردد (بخش ۹ Clarification)
```

هر دو Step باید Request را دریافت کنند و Response تولید کنند.

Responseها باید قابل نسبت دادن به Targetهای اصلی باشند (با `requestId`).

نکات آزمون:
- `nameInput` و `familyInput` یکدیگر را نمی‌شناسند — ارتباط فقط از طریق Stepهاست (بخش ۶ Clarification).
- Button فقط Stepهای موردنظر را Target می‌کند؛ هیچ ارجاع مستقیمی به inputها ندارد.
- امضای `event.request` در callbackهای `on`: پارامتر دوم handler به‌صورت helper تزریق می‌شود که همان `CoreEvent.App.request` را با context فرستنده صدا می‌زند (پیاده‌سازی در Phase 5).
- Step بدون المان متصل (`submit` در این سناریو می‌تواند بدون emit باشد) نباید خطا بدهد — فقط Response پیش‌فرض برمی‌گرداند (بخش ۱۱ Clarification).

# پیوست ب. ریسک‌های فنی شناسایی‌شده

این موارد در بازبینی مهندسی شناسایی شدند و باید حین پیاده‌سازی در نظر گرفته شوند:

### ۱. محدودیت کلید آبجکت JavaScript (بحرانی — حل‌شده در این طرح)

الگوی اولیه `{ [User.info.name]: {...} }` کار نمی‌کند؛ JavaScript کلید را `String()` می‌کند و نتیجه برای همه Stepها `"[object Object]"` است. راه‌حل: ساختار `requestMap` با آرایه دوتایی `[Step, payload]` (بخش ۱۲ همین سند).

### ۲. Proxy برای `User.info.name` — رفتار با کلیدهای ناموجود

دسترسی `User.info.name` از طریق Proxy باید فقط برای کلیدهای موجود در `children` مجاز باشد و برای کلید ناموجود، **خطای کامپایل** (در نوع) و یک error واضح در runtime بدهد — نه برگرداندن `undefined` خاموش که اشکال‌زدایی Workflow را دشوار می‌کند.

### ۳. چرخه حافظه (Memory Leak) در identity ها

`symbol` داخل `Step` و نگاشت `Step → handler` در Dispatcher باید weak نگه‌داری شوند یا API خروج (`MtDispose` / حذف listener) داشته باشند؛ در غیر این صورت استفاده مکرر (مثلاً در SPA با رندرهای متعدد) حافظه نشت می‌دهد. `ClReactiveElement` فعلی هنگام `remove()` باید بتواند ثبت‌های خود را آزاد کند — این نکته در Phase 7 (emit) باید پوشش داده شود.

### ۴. تعامل Response چند-مصرف‌کننده

وقتی یک Step به‌طور همزمان توسط دو Request مختلف هدف قرار گیرد، Dispatcher باید پاسخ‌ها را بر اساس `requestId` تفکیک کند؛ سناریوی هم‌زمانی ساده (بدون async پیچیده) در Phase 5 تعریف شود تا رفتار مشخص و تست‌پذیر باشد.

### ۵. ترتیب گارنتید callbacks

ترتیب اجرای emit برای چند target باید «ترتیب تعریف در requestMap» باشد (deterministic). موازی‌سازی واقعی به Phaseهای بعدی (Workflow) موکول شود تا رفتار نسخه اول ساده و قابل پیش‌بینی بماند.

### ۲.۸. `class/ClEventDispatcher.ts`

```ts
export class ClEventDispatcher {

    private registry: Map<symbol, ClStep>;          // رجیستری همه Stepهای ساخته‌شده
    private emits: Map<symbol, TEmitHandler>;       // رجیستری emit handlerهای ثبت‌شده (المان‌های متصل)

    // نام‌گذاری متدهای instance بدون پیشوند Mt — مطابق الگوی واقعی App (مثل observable.get/set/subscribe)
    register(step: ClStep): void;                          // ثبت Step در رجیستری
    registerEmit(step: ClStep, handler: TEmitHandler): void; // ثبت emit handler یک المان متصل (Phase 7 — بخش ۳.۱ ب)
    request(map: TRequestMap): TResponseMap;               // اجرای requestMap: برای هر target → emit handler ثبت‌شده → Response
    dispose(step: ClStep): void;                           // آزادسازی Step و emit handler از رجیستری‌ها (پیوست ب-۳)
}
```

رفتار `request` نسبت به emit (قرارداد Clarification — بخش‌های ۷ تا ۹):

```text
request(map)
   │
   ├── [Step, payload] ← payload داخل ClRequest با requestId بسته‌بندی می‌شود
   │
   ├── handler = emits.get(step.identity)
   │      ├── موجود  → handler(request) اجرا → خروجی → ClResponse (با همان requestId)
   │      └── نبود   → ClResponse پیش‌فرض خالی (المان بدون emit — بخش ۱۱ Clarification)
   │
   └── همه Responseها در TResponseMap (Map<ClStep, ClResponse>) جمع و به فرستنده برگردانده می‌شوند
```

| `src/framework/module_core/module_reactive/class/ClReactiveElement.ts` | توضیح کامل در بخش ۳.۱ | Phase 6 و 7 |

فایل‌هایی که **تغییر نمی‌کنند**: `module_observable` (طبق بند ۱۹ هیچ ادغامی ممنوع)، `module_configs` ،`module_languages` ،`module_route` و کل `module_ui`.

### ۳.۱. جزئیات تغییرات `CoreReactive` (`ClReactiveElement.ts`)

این فایل تنها فایل موجود در `module_reactive` است که تغییر می‌کند (ساختار فعلی: `class/ClReactiveElement.ts` + `enums/` بدون پوشه `types/` — بررسی شده). چهار تغییر:

#### الف) Phase 6 — افزودن گزینه `unique` به `Options`

تایپ `Options` در ابتدای فایل (خطوط ۱۲ تا ۲۴) یک فیلد جدید می‌گیرد:

```ts
import * as CoreEvent from "@/core_event";        // ← import جدید

type Options = {
    props?: any;
    propsBind?: any;
    children?: any;
    className?: ClassValue;
    classBind?: any;
    styles?: StyleMap;
    stylesCustom?: string;
    stylesBind?: any;
    attrs?: AttrMap;
    attrsBind?: Record<string, CoreObservable.TObservableValue<any>>;
    on?: EventMap;
    unique?: CoreEvent.Step;                       // ← جدید (Phase 6): اتصال اعلانی المان به Step (رشته ممنوع — بخش ۳۰)
    emit?: CoreEvent.EmitHandler;                  // ← جدید (Phase 7): Request Handler این المان — «دریافت» Request از CoreEvents و «بازگرداندن» Response، نه انتشار Event (نوع عمومی: TEmitHandler — پیوست الف)
};
```

- `unique` از نوع `Step` (آبجکت symbol-دار) است؛ مقدار رشته‌ای در کامپایل خطای تایپ می‌دهد (معیار بخش ۳۰).
- `emit` یک **Request Handler** است، نه Event Emitter (بخش ۱۴ سند Clarification). امضای آن:

```ts
// در types عمومی ماژول core_event (در فایل TStepDefinition.ts یا فایل مجزای TEmitHandler.ts)
export type TEmitHandler = (request: TRuntimeRequest) => any;
```

- تفاوت با `on`: ‏`on` برای Eventهای DOM است؛ `emit` برای Requestهای CoreEvents. هرگاه CoreEvents یک Request برای Stepِ متصل به المان (از طریق `unique`) دریافت کند، این callback اجرا و خروجی آن به‌عنوان Response به فرستنده برگردانده می‌شود.
- این گزینه برای **همه المان‌ها** از طریق `Options` فعال می‌شود، نه فقط input/button — چون `Options` مشترک است و factoryهای `static button(...)`/`static input(...)` بدون تغییر امضا از آن بهره می‌برند.
- یک المان فقط یک `unique` دارد (بخش ۱۲ سند Clarification) و CoreEvents نباید فرض کند هر Step دارای `emit` است (بخش ۱۱ — Step می‌تواند بدون المان وجود داشته باشد).

#### ب) Phase 7 — ثبت `emit` handler در Dispatcher

طبق قرارداد Clarification، `emit` **دریافت‌کننده** Request است نه تولیدکننده آن؛ آغازگر Request فرستنده است (مثلاً دکمه با `event.request(...)`). بنابراین در `_setEvents` هیچ Requestی منتشر نمی‌شود؛ فقط هنگام ساخت المان، اگر `emit` تعریف شده باشد، handler به Dispatcher ثبت می‌شود:

```ts
// در constructor — پس از ساخت element (مطابق الگوی الحاق‌های فعلی constructor)
constructor(element: CoreReactive.TElementTag, options: Options = {}) {

    // ... الحاق‌های فعلی ...

    // ← جدید (Phase 7): ثبت emit handler این المان در CoreEvents
    if (this._options.unique && this._options.emit) {
        CoreEvent.App.registerEmit(this._options.unique, this._options.emit);
    }
}
```

متد جدید `registerEmit(step, handler)` به API کلاس `ClEventDispatcher` اضافه می‌شود (بخش ۲.۸): نگاشت `symbol` مربوط به Step → handler در یک `Map` داخلی. هنگام اجرای `request(map)`، Dispatcher برای هر target ابتدا handler ثبت‌شده را جست‌وجو می‌کند:

```text
request(map)
   │
   ├── target: User.info.name  →  handler ثبت‌شده nameInput.emit  →  Response
   └── target: User.info.family →  handler ثبت‌شده familyInput.emit →  Response
```

- المانی که `unique` دارد ولی `emit` ندارد، مجاز است؛ در این حالت Dispatcher برای آن target، یک Response خالی/پیش‌فرض برمی‌گرداند (یا رفتار قابل تعریف در Phase 5).
- ترتیب فراخوانی handlerها «ترتیب تعریف در requestMap» است (پیوست ب-۵ — deterministic).

> نکته مهم: امضای handler صرفاً `(request) => any` است؛ handler نباید Event منتشر کند (بخش ۱۴ سند Clarification — ممنوعیت `EventEmitter`/`Observable`/`(...events)`).

#### ج) Phase 7 — آزادسازی در `remove()`

متد `remove()` فعلی (خطوط ۵۴۵ تا ۵۴۷) فقط `element.remove()` است. برای جلوگیری از memory leak (پیوست ب-۳)، پس از حذف DOM، هر Step ثبت‌شده توسط این المان آزاد می‌شود:

```ts
remove() {
    this.element?.remove?.();

    // ← جدید (Phase 7): آزادسازی emit handler ثبت‌شده این المان در CoreEvents
    if (this._options.unique && this._options.emit) {
        CoreEvent.App.dispose(this._options.unique);
    }
}
```

> نکته: `_bindings` مربوط به CoreObservable در نسخه فعلی `remove()` آزاد نمی‌شود — خارج از دامنه این پلن است ولی به‌عنوان بدهی فنی جداگانه به team پیشنهاد می‌شود.

#### د) ترتیب اعمال در `_applyOptions` — بدون تغییر

گزینه‌های جدید (`unique` و `emit`) در `_applyOptions` پردازش خاصی نمی‌خواهند؛ `unique` و `emit` فقط در constructor (بند «ب» — ثبت handler) و `remove()` (بند «ج» — آزادسازی) مصرف می‌شوند. بنابراین ریسک رگرسیون روی سایر گزینه‌ها (`props` ،`styles` و...) صفر است.

## ۶. پیاده سازی مثال — فرم نام / نام خانوادگی در صفحه خانه (`ClHomePage`)

هدف این بخش، اجرای سناریوی اجباری بخش ۲۸ روی یک صفحه واقعی است: فرم «نام و نام خانوادگی» با دکمه Submit که نتیجه Request/Response در `console` مرورگر قابل مشاهده باشد. این مثال فقط پس از تکمیل Phase 1 تا Phase 7 قابل اجراست (ماژول `core_event` و تغییرات `ClReactiveElement` باید موجود باشند) — بنابراین کد آن در همین پلن مستند می‌شود و نه مستقیماً در سورس.

### ۶.۱. پیش‌نیاز

- فازهای ۱ تا ۵ تکمیل شده باشند (ماژول `module_event` + aliasهای `@/core_event` در `vite.config.ts` و `tsconfig.json`).
- تغییرات Phase 6 و 7 روی `ClReactiveElement` (بخش ۳.۱) اعمال شده باشند.
- تغییر مکمل `_setEvents` مطابق بخش ۶.۲ اعمال شده باشد.

### ۶.۲. تغییر مکمل `_setEvents` — تزریق helper رویداد (تکمیل بخش ۳.۱)

بخش ۳.۱ فقط ثبت `emit` (constructor) و آزادسازی (`remove`) را مستند کرده؛ اما برای اینکه callbackهای `on` بتوانند `event.request(...)` را صدا بزنند (امضای `(e, event)` در سناریوی بخش ۲۸)، wrapped handler فعلی `_setEvents` (خطوط ۴۴۱ تا ۴۵۸ فایل `ClReactiveElement.ts`) باید پارامتر دوم را تزریق کند:

```ts
// وضعیت فعلی (خط ۴۵۱):
handler(e);

// وضعیت هدف (Phase 7 — این بخش):
handler(e, { request: (map) => CoreEvent.App.request(map) });
```

و تایپ `EventMap` (استفاده‌شده در `Options.on`) باید امضای پارامتر دوم اختیاری را بپذیرد:

```ts
type TEventHelper  = { request: (map: CoreEvent.RequestMap) => CoreEvent.ResponseMap };
type TEventHandler = (e: Event, event?: TEventHelper) => void;
type EventMap      = Record<string, TEventHandler>;
```

> سازگاری معکوس: این تغییر backward-compatible است — handlerهای فعلی که فقط `(e)` می‌گیرند بدون هیچ تغییری کار می‌کنند (پارامتر دوم نادیده گرفته می‌شود). `TEventHelper` باید به `types/` ماژول `module_event` نیز اضافه و در `index.ts` آن export شود (الگوی پیوست الف — پیشوند `T`).

### ۶.۳. تعریف Stepهای فرم — `StepRegister`

Stepها عیناً مطابق سناریوی اجباری بخش ۲۸ تعریف می‌شوند. محل کد: ابتدای متد `render` در `ClHomePage.ts` (یا scope ماژول، خارج از `render` — ترجیح: scope ماژول تا در هر `render` بازسازی نشوند):

```ts
import * as CoreEvent from "@/core_event";

// Stepهای فرم ثبت‌نام — مسیر: Register.info.{name|family|submit}
const StepRegister = CoreEvent.Step({
    children: {
        info: CoreEvent.Step({
            children: {
                name:   CoreEvent.Step({
                    request:  CoreEvent.Request(),
                    response: CoreEvent.Response({ value: "" })
                }),
                family: CoreEvent.Step({
                    request:  CoreEvent.Request(),
                    response: CoreEvent.Response({ value: "" })
                }),
                submit: CoreEvent.Step({
                    request:  CoreEvent.Request(),
                    response: CoreEvent.Response()
                })
            }
        })
    }
});
```

> نام‌گذاری: در پلن از `User` در بخش ۲۸ استفاده شد؛ در مثال واقعی نام `StepRegister` انتخاب شده چون فرم یک فرم ثبت اطلاعات است. الگو کاملاً یکسان است — هر دو معتبرند.

### ۶.۴. ساخت المان‌های فرم — `unique` + `emit`

سه المان input نام، input نام خانوادگی و دکمه Submit، دقیقاً با قرارداد بخش ۲۸ و با الگوی factoryهای واقعی `CoreReactive.App` (`static input`/`static button` — خطوط ۵۹۴ و ۶۰۰ فایل `ClReactiveElement.ts`):

```ts
// input نام — دریافت‌کننده Request (emit = Request Handler، بخش ۱۴ Clarification)
const nameInput = CoreReactive.App.input({
    className: ["form-input"],
    attrs: { placeholder: "نام" },
    unique: StepRegister.info.name,
    emit: (request) => {
        const value = (nameInput.getElement() as HTMLInputElement).value;
        console.log("[CoreEvent] request → Register.info.name", { requestId: request.requestId, request });
        return { value, valid: value.trim().length > 0 };   // ← Response این المان
    }
});

// input نام خانوادگی
const familyInput = CoreReactive.App.input({
    className: ["form-input"],
    attrs: { placeholder: "نام خانوادگی" },
    unique: StepRegister.info.family,
    emit: (request) => {
        const value = (familyInput.getElement() as HTMLInputElement).value;
        console.log("[CoreEvent] request → Register.info.family", { requestId: request.requestId, request });
        return { value, valid: value.trim().length > 0 };
    }
});

// دکمه Submit — آغازگر Request (بخش ۶ Clarification) با helper تزریق‌شده (بخش ۶.۲)
const submitButton = CoreReactive.App.button({
    className: ["form-submit"],
    children: ["ثبت"],
    unique: StepRegister.info.submit,
    on: {
        click: (e, event) => {
            const responses = event.request(
                CoreEvent.requestMap([
                    [StepRegister.info.name,   { action: "validate" }],
                    [StepRegister.info.family, { action: "validate" }]
                ])
            );
            // نتیجه در console قابل مشاهده است — هدف این مثال
            console.log("[CoreEvent] responses ← Register.info.submit", responses);
        }
    }
});
```

نکات کلیدی این کد (مطابق قراردادهای پلن):

- هیچ المانی به المان دیگر ارجاع مستقیم ندارد؛ ارتباط فقط از طریق Stepهاست (بخش ۶ Clarification). تنها استثناء مجاز، خواندن `value` المان **خودش** در `emit` خودش است.
- `emit` فقط Request «دریافت» می‌کند و Response برمی‌گرداند — هیچ Eventی منتشر نمی‌کند (ممنوعیت بخش ۱۴).
- `event.request` همان `CoreEvent.App.request` است که به‌صورت helper به handler تزریق می‌شود (بخش ۶.۲).
- خروجی `request` یک `TResponseMap` است که با `requestId` قابل نسبت دادن به Request است (بخش ۲۷ کلاس `ClResponse`).

### ۶.۵. به‌روزرسانی متد `render` صفحه خانه

الگوی فعلی `ClHomePage.ts` (استفاده از `children` با خروجی مستقیم factoryها — `_setChildren` خط ۴۰۳ نمونه `ClReactiveElement` را مستقیم می‌پذیرد) حفظ می‌شود و فقط فرم به آن اضافه می‌شود:

```ts
render(query?: Record<string, string>, extra?: Record<string, any>): HTMLElement {

    const container = CoreReactive.App.div({
        className: ["page", "home"],
        children: [
            // ... محتوای فعلی (pهای translate) بدون تغییر ...

            // ---- فرم مثال CoreEvent (بخش ۶.۳ و ۶.۴) ----
            CoreReactive.App.div({
                className: ["example-form"],
                children: [
                    nameInput,
                    familyInput,
                    submitButton
                ]
            })
        ]
    }).getElement();

    return container;
}
```

> نکته: `nameInput` و `familyInput` و `submitButton` باید **پیش از** `container` ساخته شده باشند (ترتیب در scope تابع رعایت شود). چون `emit` این inputها فقط هنگام Request خوانده می‌شود (نه هنگام ساخت)، تعریف بعد از دکمه هم مشکلی ایجاد نمی‌کند؛ ولی برای خوانایی، ترتیب فوق توصیه می‌شود.

### ۶.۶. خروجی مورد انتظار در Console

پس از اجرای صفحه (`npm run dev` → صفحه خانه) و پر کردن فیلدها و کلیک Submit، این ترتیب در Console ظاهر می‌شود:

```text
[CoreEvent] request → Register.info.name   {requestId: "…", request: ClRequest}
[CoreEvent] request → Register.info.family {requestId: "…", request: ClRequest}
[CoreEvent] responses ← Register.info.submit [ [ClStep, ClResponse], [ClStep, ClResponse] ]
```

معیار موفقیت مثال (مطابق بخش ۳۰):

- هر دو `emit` اجرا شده و مقدار فیلدها در Response آمده است (`{value: "...", valid: true/false}`).
- `requestId` هر دو Response با Request یکسان است (قابل نسبت دادن).
- فیلد خالی → `valid: false` در Response همان فیلد، بدون خطا.
- کلیک مجدد → `requestId` جدید (تفکیک هم‌زمانی — پیوست ب-۴).
