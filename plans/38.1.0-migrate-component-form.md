# پلن 38.1.0 — انتقال ComponentForm به ساختار جدید

> **وضعیت:** پیاده‌سازی شد؛ قرارداد callback پاسخ با توجه به نبود مصرف‌کنندهٔ بیرونی تثبیت شد  
> **نسخه پلن:** 38.1.0  
> **منبع Legacy:** `last/Older/components.js`، بخش ComponentFormBase و ComponentForm  
> **راهنما:** `documents/guides/component-create.md`  
> **مقصد:** `src/framework/module_ui/module_components/lists/componentForm/`  
> **دسته‌بندی هدف:** `fetch → form`  
> **API هدف:** `UiCategory.UI.Fetch.Form(config, methods, identity)`

## 1. هدف و محدوده

انتقال ComponentForm از معماری قدیمی مبتنی بر `ComponentBase`، رشته‌های HTML، عناصر سفارشی سراسری و callbackهای پراکنده به قرارداد فعلی ComponentManager.

کامپوننت جدید مسئول این رفتارها است:

- نمایش محتوای فرم داخل عنصر native `form`.
- قرارگرفتن کل محتوای Form، از ابتدا، داخل یک ComponentBorder که تنظیماتش از API خود ComponentForm قابل کنترل است.
- نمایش دکمهٔ ارسال و پیام‌های اعتبارسنجی.
- خواندن نتیجهٔ اعتبارسنجی ComponentValidateهای داخل همین فرم.
- ارسال فرم به آدرس تنظیم‌شده با `FormData`، در صورت فعال بودن ارسال خودکار.
- نمایش وضعیت loading، پیام پاسخ، خطای درخواست و امکان تلاش دوباره.
- فراهم‌کردن مسیر callback برای برنامه‌هایی که ارسال درخواست را خودشان انجام می‌دهند.

در این پلن، مصرف‌کننده‌های Legacy یا پروژه‌های دیگر تغییر نمی‌کنند و هیچ endpoint یا قرارداد سرور جدیدی تعریف نمی‌شود. HTML خامی که قبلاً از slot قدیمی خوانده می‌شد نباید با `innerHTML` یا تگ‌سازی رشته‌ای وارد DOM شود؛ محتوای فرم در معماری جدید باید از عناصر reactive یا HTMLElementهای ساخته‌شده توسط Componentها ترکیب شود.

## 2. شواهد و رفتار مشاهده‌شده در Legacy

پیاده‌سازی قدیمی در `last/Older/components.js` حدود خطوط 4396 تا 4825 قرار دارد. نمونهٔ مصرف در `last/Older/index.html` و یک مصرف دیگر در ComponentReportPage همان فایل دیده می‌شود. جست‌وجوی مخزن مصرف‌کنندهٔ دیگری برای callbackهای اختصاصی Form پیدا نکرد.

| رفتار یا قرارداد قدیمی | شواهد و تصمیم انتقال |
|---|---|
| درخت Partها با `part_structure → part_border → part_form / part_404 / part_loading / part_button_submit` ساخته می‌شود | با Schemaهای declarative و renderهای اختصاصی جایگزین شود؛ در Schema فقط Part و propها تعریف شوند. |
| `prop_forms` محتوای فرم است؛ در نبود آن HTML اولین body slot استفاده می‌شود | ورودی جدید محتوای reactive/HTMLElement بپذیرد. تبدیل متن به markup ممنوع باشد؛ مثال‌ها Componentها را به‌صورت child ترکیب کنند. |
| `prop_formClass` و `prop_formStyles` روی div بیرونی فرم، و `prop_formsMinHeight` روی عنصر native form اعمال می‌شوند | این تنظیمات در بخش Form حفظ شوند و با CoreReactive و style/styleBind رندر شوند. |
| `prop_borderClass` به `ComponentBorder.prop_structureClass` و `prop_borderStyles` به `ComponentBorder.prop_borderStyles` ارسال می‌شوند | این نگاشت Legacy حفظ شود. سایر propهای ComponentBorder نیز از طریق propهای مستقل ComponentForm به نمونهٔ فرزند forward شوند. |
| submit یک ComponentButton جدا از عنصر native form است و callback آن `call_onCLickBtnSubmit` را اجرا می‌کند | محل بصری کنترل در چیدمان حفظ شود؛ ارسال از مسیر handler کامپوننت انجام شود و صفحه reload نشود. رفتار Enter فقط در صورت بررسی سازگاری به‌عنوان تغییر جداگانه افزوده شود. |
| اعتبارسنجی با عناصر `.component-validate` داخل فرم انجام می‌شود؛ محتوا به شکل JSON شامل title و validates است | در ساختار جدید، فقط اسکریپت‌های JSON با این قرارداد که داخل فرم قرار دارند خوانده شوند؛ از `textContent` و parse امن JSON استفاده شود، نه `innerHTML`. نتیجهٔ همهٔ Validatorها با AND محاسبه شود. |
| `prop_showErrorStepper` تعیین می‌کند با اولین خطای اعتبارسنجی متوقف شویم یا خطاهای همهٔ Validatorها جمع شوند | رفتار حفظ شود؛ مقدار پیش‌فرض Legacy برابر true است. |
| `prop_runFetch=true` مسیر `tools_submit.fetcth` را اجرا می‌کند؛ متد درخواست POST و بدنه FormData است | در helper قدیمی `last/Older/tools.js` پیاده‌سازی native `fetch` دیده شد. در ComponentForm جدید از fetch و FormData استفاده شود، نه global helper یا Componentهای window. |
| دادهٔ سفارشی `prop_data` با فیلدهای فرم merge می‌شود؛ فایل‌ها به‌صورت ورودی‌های تکرارشونده با نام همان فیلد append می‌شوند | serialization باید داده‌های prop و فرم را حفظ کند، از جمله File/File[]؛ برای FormData هدر Content-Type دستی تعیین نشود. |
| پاسخ موفق به‌طور پیش‌فرض JSON است؛ messages، status و resultExp خوانده می‌شوند | messageها به ComponentMessages داده شوند؛ نوع پیام از status استخراج شود و resultExp در صورت وجود، وگرنه کل response، به callback برسد. |
| خطای 404 و خطای شبکه/پاسخ در مسیر catch صفحهٔ خطا و loading را به‌روزرسانی می‌کنند؛ 404 امکان retry دارد | ComponentLoading و ComponentErrorIsEmpty برای نمایش و retry بررسی و ترکیب شوند؛ خطای شبکه نیز loading را ببندد. |
| `fn_onClickSubmit(event, url, formElement, extraData)` در حالت `prop_runFetch=false` فراخوانی می‌شود | به Method تایپ‌دار SUBMIT نگاشت شود و ترتیب معنایی آرگومان‌ها در مستندات API جدید مشخص بماند. |
| `fn_onGetResponse(event, fetchResponse)` بلافاصله پس از شروع ارسال، Promise درخواست را می‌گیرد | این callback با نام GET_RESPONSE حفظ شود و زمان اجرا و نوع Promise صریحاً در Methods.ts مستند شود. |
| `fn_onClickResponse(resultExp, response)` در helper با آرگومان دوم دادهٔ ورودی helper فراخوانی می‌شود، نه body خام response | این تفاوت Legacy در قرارداد Methods مشخص شود؛ پیش از implementation آرگومان دوم با مصرف‌کنندهٔ واقعی تطبیق داده شود و بی‌صدا به معنای دیگری تغییر نکند. |

## 3. تطبیق معماری Legacy و ساختار فعلی

| Legacy | ساختار جدید |
|---|---|
| `ComponentFormBase extends ComponentBase` و `window.ComponentForm` | فایل‌های Base و Component TypeScript؛ ارث از `CoreComponents.App`، constructor با امضای `(config, methods, identity?)` و بدون ثبت global |
| `_COMPONENT_PATTERN` و property defaults | `Props.ts` با `Define_ComponentProp<T>`، نام/توضیح ترجمه‌شده و typeهای `PropsType` و `PropsConfigType` |
| `_COMPONENT_PROPS` و `_COMPONENT_SCHEMA` | `Schemas.ts`؛ ابتدا Schemaهای `ComponentStructureTrait`، سپس Schemaهای Form |
| `templateFn`، template literal و CSS در `style` tagهای رشته‌ای | `renderContentComponent`، `renderManagerComponent` و `CoreReactive.App` |
| `new window.ComponentBorder/ComponentButton` با شناسه‌های DOM دستی | import مستقیم Componentها، composition با instanceهای جدید و نگهداری آن‌ها برای dispose |
| کنترل ComponentMessages/404/Loading از helper سراسری | instanceهای new UI Component با props reactive و state محلی |
| خواندن و parse کردن HTML خطاهای Validator | قرارداد JSON در `script.component-validate` با خواندن `textContent` و parse امن |
| `tools_submit.fetcth` | `fetch`/FormData در runtime خود ComponentForm، بدون وابستگی به Legacy globals |
| اندازهٔ `prop_size` از CSS utilities قدیمی | اندازه‌های UI از CoreConfig و UtilStyle؛ prop_size فقط پس از اثبات مصرف واقعی حفظ شود |
| callbackهای بی‌ساختار روی config | Methods.ts و Step.ts با کلیدهای معنایی و dataArgs تایپ‌شده |
| پاک‌سازی ضمنی DOM | `dispose()` شامل dispose فرزندان، Step و Observable Scope |

### Props قدیمی که بی‌دلیل به API جدید منتقل نشوند

- `prop_size`: اندازه در ساختار جدید از تنظیم سیستم/کامپوننت‌های فرزند گرفته شود؛ شواهد مصرف قابل‌مشاهده‌ای خارج از Form برای این Prop پیدا نشد.
- `prop_title`، `prop_formBackgroundColor` و `prop_titleBackgroundColor`: در کلاس Legacy تعریف شده‌اند اما در render مؤثر استفاده نمی‌شوند. تا وقتی مصرف یا رفتار فعال برایشان اثبات نشده، Prop عمومی جدید نسازید.
- API دکمه فقط فیلدهایی را بپذیرد که ComponentButton جدید واقعاً پشتیبانی می‌کند؛ کلیدهای Legacy ناشناخته silently به DOM منتقل نشوند.

## 5. Schema و درخت رندر پیشنهادی

از `ComponentStructureTrait` برای COMPONENT و STRUCTURE استفاده شود. محتوای اختصاصی در `renderContentComponent` رندر شود و مسیر هر Schema در `renderManagerComponent` مشخص باشد.

    component-form
    └── component-structure
        └── ROOT: part-form-root
            └── ComponentBorder (prop_content = کل محتوای Form)
                ├── FORM_LAYOUT: part-form-layout
                │   ├── FORM_CONTENT: part-form-content
                │   │   └── form: part-form-element
                │   │       └── prop_forms
                │   ├── MESSAGES: ComponentMessages
                │   ├── SUBMIT: part-form-submit
                │   │   └── ComponentButton
                │   ├── REQUEST_ERROR: ComponentErrorIsEmpty
                │   └── LOADING: ComponentLoading

Schemaهای اختصاصی حداقل شامل ROOT، FORM_LAYOUT، FORM_CONTENT، FORM_ELEMENT، MESSAGES، SUBMIT، REQUEST_ERROR و LOADING باشند. Schemaها فقط Part و props را فهرست کنند؛ handler، fetch، state و Component construction در Schema نوشته نشود.

- ComponentBorder اولین child بصری پس از لایه‌های پایهٔ ComponentForm باشد. محتوای آن با `prop_content` خود ComponentBorder از یک ReactiveElement ساخته شود و کل FORM_LAYOUT را در خود جای دهد؛ فقط خود فرم داخل Border نباشد و پیام، دکمه، خطا و loading نیز در همین محتوا باشند.
- همهٔ propهای نمایشی و ساختاری ComponentBorder در API ComponentForm قابل تنظیم باشند. ComponentForm آن‌ها را به instance فرزند forward کند؛ مقدار محتوای فرزند را خودش بسازد و `prop_content` قابل override از بیرون نباشد.
- برای حفظ معنی Legacy، `prop_borderClass` در ComponentForm به `prop_structureClass` فرزند نگاشت شود و `prop_borderStyles` به `prop_borderStyles` فرزند. prop جدید `prop_componentBorderClass` کلاس خود Part مربوط به Border را تنظیم کند؛ `prop_componentBorderStructureStyles` نیز styleهای Structure فرزند را کنترل کند.
- Form content در native `form` رندر شود؛ wrapper و `min-height` از props مربوطه دریافت شوند.
- submit button به ComponentButton واگذار شود. رویداد آن باید از `executeMethod` یا مسیر event رسمی اجرا شود.
- ComponentMessages، ComponentLoading و ComponentErrorIsEmpty از ماژول‌های جدید import شوند؛ تنظیم نمایش آن‌ها با state/props انجام شود، نه selector سراسری.
- Error component دکمهٔ retry داشته باشد و retry همان payload و FormData ارسال قبلی را دوباره نسازد مگر اینکه کاربر مقادیر فرم را تغییر داده باشد؛ FormData برای هر ارسال از وضعیت جاری فرم ساخته شود.

## 6. Validation، Submit و Network

### اعتبارسنجی

1. پیش از submit، فقط descendants داخل form جاری بررسی شوند.
2. اسکریپت‌های `script.component-validate[type="application/json"]` با `textContent` خوانده شوند.
3. هر entry با ساختار `{title, validates}` parse شود. JSON نامعتبر بدون اجرای محتوا رد شود و به خطای فرم تبدیل گردد.
4. فرم وقتی معتبر است که هیچ entryای پیام خطا نداشته باشد؛ نتیجهٔ چند Validator با AND جمع شود. این کار خطای منطقی Legacy را که مقدار validity را با نتیجهٔ Validator آخر جایگزین می‌کرد، تکرار نمی‌کند.
5. اگر `prop_showErrorStepper` true باشد، اولین Validator دارای خطا کافی است؛ در غیر این صورت همهٔ عنوان‌ها و پیام‌ها به ComponentMessages داده شوند.
6. روی موفقیت، پیام خطای قبلی پاک شود و سپس مسیر fetch یا callback دستی اجرا شود.

### ارسال خودکار

- در هر submit یک FormData تازه از native form ساخته و `prop_data` به آن افزوده شود. برای File/File[] کلیدهای هم‌نام به شکل تکرارشونده append شوند.
- روش درخواست POST و پاسخ موفق JSON باشد؛ این همان default مشاهده‌شده در helper قدیمی است. برای FormData، مرورگر باید Content-Type و boundary را تنظیم کند.
- loading هنگام آغاز درخواست روشن و در تمام مسیرهای success، 404، خطای HTTP و exception خاموش شود.
- در پاسخ 200، messages از `response.messages` گرفته شوند؛ نوع پیام بر اساس `response.status` به success/error تبدیل شود و در نبود status، warning باشد.
- نتیجهٔ callback از `response.resultExp` و در نبود آن از خود response ساخته شود.
- در پاسخ 404 یا خطای شبکه، UI خطا نمایش داده شود و BTN_CLICK آن درخواست را دوباره اجرا کند.
- statusهای غیرقابل‌قبول و JSON نامعتبر به مسیر خطا بروند و loading باقی نماند.

### ارسال دستی و قرارداد callbackها

- با `prop_runFetch=false` درخواست خودکار انجام نشود و SUBMIT با event، URL، عنصر native form و دادهٔ اضافی فراخوانی شود.
- GET_RESPONSE هنگام آغاز fetch، Promise درخواست را دریافت کند تا مفهوم فعلی `fn_onGetResponse` حفظ شود.
- RESPONSE پس از دریافت پاسخ، resultExp را دریافت کند. آرگومان دوم Legacy اکنون request data/helper context است؛ قرارداد نهایی آرگومان دوم باید قبل از implementation با مصرف‌کنندهٔ بیرونی تأیید شود. در صورت نبود مصرف‌کننده، API جدید payload ساختاریافتهٔ صریح داشته باشد و تفاوت با Legacy در مستندات ثبت شود.
- callbackها فقط در حالت معتبر اجرا شوند. خطای validation نباید fetch یا callback submit را اجرا کند.

- Step: workflowهای submit، request-start، response و request-error؛ Step قبل از render در constructor ساخته شود.
- index: export عمومی Component، Base، Definition، Props/typeها، Schemas، Methods، Step و Examples.

### ComponentManager و Category

1. در `src/framework/module_ui/module_components/lists/index.ts` کلاس و مشخصات ComponentForm را مطابق الگوی ثبت Componentهای جدید در ComponentManager اضافه کنید.
2. Category جدید `fetch` زیر `src/framework/module_ui/module_categories/lists/ui/fetch/` ساخته شود؛ Form در مسیر `fetch/form` تعریف و از `ui/index.ts` export شود.
3. callable عمومی در `fetch/form/index.ts` با `CreateCategoryComponent` ساخته شود و مسیر استفاده `UiCategory.UI.Fetch.Form(...)` باشد.
4. کلیدهای category، component، props، schemas، methods و examples در Keys.ts و ترجمه‌های En.ts/Fa.ts اضافه شوند.
5. Examples از `ComponentExample` و تابع `render(): HTMLElement` استفاده کنند؛ برای ساخت child UI از callableهای دسته‌بندی و APIهای getReactiveElement/getElement مطابق راهنما استفاده شود.

## 8. مثال‌ها

- **Default:** فرم ساده با دو input جدید، ComponentValidate، دکمهٔ ارسال و پیام خطا؛ بدون endpoint واقعی.
- **Validation:** چند فیلد نامعتبر؛ نمایش تفاوت `prop_showErrorStepper=true/false` و پاک‌شدن پیام بعد از اعتبارسنجی موفق.
- **ManualSubmit:** `prop_runFetch=false`؛ نمایش داده‌های فرم و prop_data از callback، بدون درخواست شبکه.
- مثال request در صورت اضافه‌شدن فقط از mock قابل‌کنترل در تست استفاده کند؛ endpoint عمومی یا backend فرضی در Example قرار نگیرد.

نام و description همهٔ مثال‌ها از Keys ترجمه شوند.

## 9. آزمون پذیرش

- ComponentManager و مسیر `UI.Fetch.Form` آن را کشف و در صفحهٔ Components نمایش دهند.
- محتوای کامل ComponentForm از ابتدا داخل ComponentBorder باشد؛ تغییر هر prop مربوط به Border از طریق ComponentForm روی همان فرزند اعمال شود، بدون آن‌که `prop_content` داخلی قابل جایگزینی شود.
- مثال‌ها بدون `[object Object]`، template string، HTML تزریق‌شده یا عنصرهای قدیمی global رندر شوند.
- child componentها داخل form قرار گیرند و dispose کامپوننت والد آن‌ها، Stepها و Scope را پاک کند.
- اعتبارسنجی فرم خالی و چند خطای هم‌زمان را درست تشخیص دهد؛ validity نتیجهٔ آخرین Validator نباشد.
- با showErrorStepper فعال فقط اولین گروه خطا، و در حالت غیرفعال همهٔ خطاها نمایش داده شوند.
- invalid form نه callback submit و نه fetch را اجرا کند.
- ManualSubmit دادهٔ درست را به callback بدهد و هیچ fetchای انجام ندهد.
- fetch با FormData فیلدهای متنی، داده‌های اضافی و فایل‌ها را حفظ کند؛ header Content-Type دستی نداشته باشد.
- پاسخ موفق، messages، resultExp و callbackها بررسی شوند؛ همچنین 404، پاسخ ناموفق، JSON خراب و network rejection همگی loading را خاموش و error/retry را درست نمایش دهند.
- retry از payload به‌روز فرم استفاده کند و خطاهای قبلی را در زمان شروع درخواست پاک کند.
- دو نمونهٔ هم‌زمان ComponentForm در انتخاب فرم، loading، error، message یا event به هم تداخل نکنند.
- نمونهٔ درخواست در تست از fetch mock استفاده کند؛ هیچ درخواست شبکهٔ واقعی در build یا TestsPage اجرا نشود.
- `npm run build:app` پس از پیاده‌سازی موفق شود.

## 10. موارد خارج از محدوده و تصمیم‌های نهایی پیاده‌سازی

- تبدیل فراخوانی‌های Legacy در `last/Older/components.js`، `last/Older/index.html` یا اپلیکیشن‌های مصرف‌کننده.
- ایجاد endpoint، تغییر Laravel، تغییر شکل پاسخ سرور یا معرفی روش/نوع محتوای جدید.
- حفظ HTML خام قدیمی با `innerHTML`.
- انتقال propهای بی‌اثر `prop_title`، `prop_formBackgroundColor` و `prop_titleBackgroundColor` بدون شاهد مصرف.
- تغییر رفتار Legacy آرگومان دوم `fn_onClickResponse` در مصرف‌کننده‌های بیرونی؛ جست‌وجوی مخزن مصرف‌کننده‌ای پیدا نکرد.
- افزودن پشتیبانی پاسخ HTML؛ helperی که از ComponentForm فراخوانی می‌شود به‌صورت پیش‌فرض JSON دریافت می‌کند.

قرارداد نهایی: `SUBMIT` هنگام غیرفعال‌بودن fetch، `URL` را در `componentArgs` و `FORM` و `EXTRA_DATA` را در `dataArgs` می‌دهد؛ `GET_RESPONSE` بلافاصله پس از شروع fetch، Promise درخواست را می‌دهد؛ `RESPONSE` بعد از پاسخ موفق، `RESULT_EXP` و بدنهٔ parseشدهٔ پاسخ را می‌دهد. این قرارداد جایگزین آرگومان دوم مبهم Legacy در callback پاسخ است؛ در مخزن مصرف‌کنندهٔ دیگری برای آن پیدا نشد.

## 11. نتیجهٔ اجرای پلن

- کامپوننت در `componentForm/` ساخته و در `ComponentManager` ثبت شد.
- API دسته‌بندی `UiCategory.UI.Fetch.Form` در شاخهٔ `fetch → form` اضافه شد.
- محتوای native form، پیام‌ها، دکمه، خطای 404 و loading از ابتدا در `ComponentBorder` است؛ تنظیمات ComponentBorder از propهای `ComponentForm` عبور می‌کنند.
- نمونه‌های Default، Validation و ManualSubmit اضافه شدند؛ نمونه‌ها درخواست شبکهٔ واقعی نمی‌فرستند.
- ترجمه‌های انگلیسی و فارسی برای category، component، props، schemas، methods و examples افزوده شدند.
