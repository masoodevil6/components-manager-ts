## ۱. شرح مشکل — تداخل سه‌گانه

در وضعیت فعلی، **سه کلاس با نام/نقش مشابه** به‌طور موازی در پروژه وجود دارند:

| # | کلاس | مکان | نقش فعلی | وضعیت |
|---|------|------|----------|-------|
| ۱ | `ClComponentBase` | `module_core/module_components/basic/class/` | Base قدیمی Schema-driven با `renderComponent()` + `executeSchemaPart` + `renderManagerComponent` | **زنده در Core** — مصرف توسط `ExampleRenderer` و مستندات |
| ۲ | `ComponentBase` (نسخه legacy) | `src/ccomponentBasic/components/ComponentBase.ts` | کپی قدیمی همان کلاس با API منسوخ | **Legacy** — فقط کد قدیمی `ccomponentBasic` |
| ۳ | `ComponentBase` (نسخه جدید) | `module_ui/module_components/basic/runtime/` | Base جدید Composition-driven (پلن 5.11) با `render()` abstract + Lazy Render | **زنده در UI** — مصرف توسط Button/Collapse/Structure |

### تداخل‌های مشخص

**۱-۱. تداخل نام (Name Collision):**
سه کلاس، دو نام، سه نقش. توسعه‌دهنده جدید نمی‌داند از کدام ارث ببرد. راهنمای رسمی (`documents/guides/component-create.md` بخش ۸) هنوز الگوی قدیمی را آموزش می‌دهد:
```typescript
super("button", null, identity, ButtonStep);   // ← API قدیمی
this.renderComponent(config, methods);          // ← API قدیمی
```
این در تضاد مستقیم با پلن 5.11 و قرارداد جدید این پلن است.

**۱-۲. تداخل مسئولیت (Responsibility Overlap):**
هر دو کلاس زنده، **prop binding** را پیاده‌سازی کرده‌اند (`_COMPONENT_PROPS_BIND` در برابر `bindProp`) با دو الگوی متفاوت و دو الگوی Lifecycle ناسازگار.

**۱-۳. تداخل وراثت و امضا:**
- `ExampleRenderer` (در Core) انتظار API قدیمی (`renderComponent`) دارد
- `ComponentRegistryEntry.constructor` به API قدیمی گره خورده
- فرزندان جدید (Button/Collapse/Structure) امضای `(config, identity)` دارند — که نه با راهنما و نه با الگوی سه‌جنریکی راهنما (بخش ۱۳) هم‌خوان نیست

### سابقه کرش

```
ComponentStructure.ts:115 Uncaught TypeError:
Cannot read properties of undefined (reading 'show')
```
ریشه: فراخوانی `render()` در constructor کلاس پایه قبل از مقداردهی class fields فرزند — که با Lazy Render در اصلاح بعدی پلن 5.11 حل شد، اما ریشه مشکل (وجود دو Base با دو Lifecycle) پابرجاست.

## ۲. مشخصات قطعی ComponentBase (قرارداد نهایی — ویرایش ۲)

### ۲.۱ مکان قطعی

```
src/framework/module_core/module_components/basic/class/ComponentBase.ts
```

**دلیل:** Core لایه زیرساخت است؛ Base Component یک قرارداد (Contract) است نه یک کلاس UI. قرارگیری آن در Core باعث می‌شود:
- هم `module_ui` و هم آینده `module_other` بدون چرخه وابستگی از آن ارث ببرند
- با `ClComponentBase` (Legacy) و `AbComponentConnector` هم‌مکان و قابل مقایسه باشد
- الگوی راهنمای موجود (`component-create.md` بخش ۱۶ که `ClComponentBase` را در Core فهرست می‌کند) حفظ شود

### ۲.۲ جنریک‌های سه‌گانه

| جنریک | نقش | توضیح |
|-------|-----|-------|
| `TProp` | پارامترهای Component | ورودی‌های declarative — selector، append، classList، propهای اختصاصی |
| `TSchema` | سناریو و Scope هر بخش | Metadata بخش‌های سناریو — طبق پلن 5.11 در Rendering نقش ندارد؛ برای مستندسازی/Scope/مانیتورینگ |
| `TMethod` | کال‌بک‌ها و اکشن‌ها | قرارداد API قابل فراخوانی توسط مصرف‌کننده — ورودی آرگومان دوم |

### ۲.۳ constructor سه‌آرگومانی

| آرگومان | نوع | محتوا |
|---------|-----|-------|
| **۱** | `props: TProp` | آبجکت propهای کامپوننت — ریشه از `TProp` |
| **۲** | `methods: TMethod` | آبجکت متدها و کال‌بک‌های کامپوننت — ریشه از `TMethod` |
| **۳** | `identity?: Partial<ComponentIdentity>` | بخش عمومی اتصال: `unique` + `emit` (اتصال به جریان CoreEvent) و `events` (متدهای خود کامپوننت از سمت والد) |

### ۲.۴ امضای نهایی

```typescript
// src/framework/module_core/module_components/basic/class/ComponentBase.ts

export abstract class ComponentBase<
    TProp   extends ComponentPropConfig   = ComponentPropConfig,
    TSchema extends ComponentSchemaConfig = ComponentSchemaConfig,
    TMethod extends ComponentMethodConfig = ComponentMethodConfig
> {

    protected readonly _props:     TProp;
    protected readonly _methods:   Partial<TMethod>;
    protected readonly _identity:  Partial<ComponentIdentity>;
    protected _content: CoreReactive.App | null = null;
    protected _renderScope: CoreObservable.Scope = new CoreObservable.Scope();

    constructor(
        props:    TProp,
        methods:  TMethod,
        identity?: Partial<ComponentIdentity>   // { unique, emit, events }
    ) {
        this._props    = props   ?? ({} as TProp);
        this._methods  = methods ?? ({} as Partial<TMethod>);
        this._identity = identity ?? {};
    }

    /* حفظ‌شده از پلن 5.11 — Lazy Render */
    protected ensureRender(): void { /* ... */ }
    protected abstract render(): CoreReactive.App;
    public getElement(): HTMLElement { this.ensureRender(); /* ... */ }

    /* حفظ‌شده + تغییر نام از _config به _props */
    protected prop<K extends keyof TProp>(key: K): TProp[K] { /* ... */ }
    protected bindProp<K extends keyof TProp>(key: K): CoreObservable.App<any> { /* ... */ }

    /* جدید — دسترسی type-safe به methods */
    protected method<K extends keyof TMethod>(key: K): TMethod[K] | undefined { /* ... */ }

    protected getIdentity(): Partial<ComponentIdentity> { /* ... */ }
    protected emitEvent(payload?: any): void { /* ... */ }
    public dispose(): void { /* ... */ }
}
```

### ۲.۵ قرارداد Identity (آرگومان سوم)

```typescript
identity = {
    unique:  CoreEvent.TStepRef,        // هویت در درخت Workflow والد (اتصال به Event)
    emit:    CoreEvent.TEmitHandler,    // Request Handler — اتصال به جریان CoreEvent
    events:  Record<string, any>,       // متدهای خود کامپوننت از سمت والد (handlerهای DOM)
}
```

**تفکیک آرگومان ۲ و آرگومان ۳:**

| | آرگومان ۲ (`methods`) | آرگومان ۳ (`identity.events`) |
|---|---|---|
| ماهیت | API Business کامپوننت | handlerهای DOM/Event |
| مالکیت | مصرف‌کننده (صفحه/والد) | والد |
| نمونه | `{ CLICK: (e, data) => ... }` | `{ click: (e) => ... }` |
| فراخوانی توسط | `this.method("CLICK")` داخل فرزند | تزریق مستقیم به `on: {}` در render |

### ۲.۶ حفظ‌شدگی Lazy Render

الگوی Lazy Render (اصلاح کرش اخیر) عیناً حفظ می‌شود — `render()` در constructor فراخوانی نمی‌شود؛ اولین `getElement()` رندر را تضمین می‌کند چون class fields فرزند (مثل `this.state`) بعد از `super()` مقداردهی می‌شوند.

## ۳. تصمیم معماری (Decision — بازنگری‌شده)

### D1 — نام‌گذاری و مکان (ویرایش ۲)

| مفهوم | نام قطعی | مکان قطعی |
|-------|----------|-----------|
| Base قراردادی جدید | **`ComponentBase`** | **`module_core/module_components/basic/class/ComponentBase.ts`** (منتقل از UI) |
| Base قدیمی Schema-driven | **`LegacySchemaComponent`** (تغییر نام از `ClComponentBase`) | `module_core/module_components/basic/abstract/` (منتقل به کنار `AbComponentConnector`) |
| کپی منسوخ ccomponentBasic | `@deprecated` — حذف در فاز پاک‌سازی | — |
| پوشه `basic/runtime/` در UI | **حذف** (خالی می‌شود) | — |

**دلیل:** ComponentBase یک قرارداد سراسری است، نه کلاس UI. قرارگیری در Core ارث‌بری بدون چرخه وابستگی برای هر ماژول را ممکن می‌کند و با الگوی راهنمای موجود هم‌خوان است.

### D2 — تفکیک لایه‌ای (Single Source of Truth)

```text
module_core/module_components:
    ├── basic/class/ComponentBase      ← قرارداد واحد Base (سه‌جنریکی)
    ├── basic/class/LegacySchemaComponent ← نگهداری حداقلی کد قدیمی
    ├── tools/* (Prop/Schema/Template/Method) — بدون تغییر
    └── ExampleRenderer — با سازگاری به API جدید

module_ui/module_components:
    ├── basic/manager/ComponentManager — Registry
    ├── basic/types/* — TComponentIdentity و تایپ‌های UI
    └── lists/* — Componentهای واقعی (Structure/Button/Collapse/...)
```

**اصل:** Core فقط زیرساخت و قرارداد؛ UI فقط کلاس‌های Component. هیچ کلاس Base قابل ارث‌بری در UI تعریف نمی‌شود.

### D3 — تکلیف prop binding

الگوی `prop()`/`bindProp()` از پلن 5.11 مرجع است — فقط نام فیلد از `_config` به `_props` تغییر می‌کند (هم‌راستا با آرگومان اول). الگوی قدیمی `_COMPONENT_PROPS_BIND` فقط در `LegacySchemaComponent` باقی می‌ماند و export نمی‌شود.

### D4 — تکلیف ExampleRenderer

`ExampleRenderer` باید دو امضا را بپذیرد:
- Componentهای Legacy: `renderComponent(config, methods, events)` (API قدیمی)
- Componentهای جدید: `new C(props, methods, identity)` + `getElement()` (قرارداد جدید)

تشخیص: بررسی وجود متد `renderComponent` روی prototype.

### D5 — تکلیف مستندات

مستندات زیر باید هم‌زمان اصلاح شوند:
- **`documents/guides/component-create.md`** — بازنویسی کامل بخش‌های ۷، ۸، ۱۳: الگوی `super("button", ...)` + `renderComponent` حذف و با قرارداد جدید جایگزین شود:
  ```typescript
  constructor(props: ButtonPropsType, methods: ButtonMethodsType, identity?: Partial<ComponentIdentity>) {
      super(props, methods, identity);
  }
  ```
- `AI_GUIDE_RULES.md` → رR-ARCH-01: ارث‌بری از `ComponentBase` (Core) به‌جای `ClComponentBase`
- `AI_GUIDE_ARCHITECTURE.md` → جریان ارث‌بری جدید
- `documents/ui/module_components.md` → حذف ادعای وجود Base در UI + ارجاع به Core

## ۷. نکته Lifecycle — تفاوت دو Base

| جنبه | `LegacySchemaComponent` (Core) | `ComponentBase` جدید (Core) |
|------|-------------------------------|---------------------------|
| شروع رندر | فراخوانی دستی `renderComponent()` | Lazy — اولین `getElement()` |
| State | `_COMPONENT_PROPS_BIND` | فیلدهای کلاس فرزند (`this.state`) + `bindProp` |
| امضا | `(name, parent)` + فراخوانی دستی | `(props, methods, identity)` |
| جنریک | ندارد | `TProp` / `TSchema` / `TMethod` |

این جدول به مستندات معماری (فاز ۶) اضافه می‌شود.
